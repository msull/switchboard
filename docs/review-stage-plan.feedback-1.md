# Review feedback

The separation from the existing plan-review workflow makes sense, but this is still a skeleton rather than an implementable plan. Resolve the `PLANNER:` items before folding it into `docs/dispatch.md`, including the following concrete issues.

1. **Run the stage's checks before accepting a no-findings round.** Lines 77–81 complete the stage immediately when reviewers contribute nothing, while checks only run after an implementer. This bypasses the potentially stronger gate proposed at lines 59–62, including on the first round. Require successful stage-gate evidence at the accepted head on every completion path, including cap acceptance. Previously recorded checks may be reused only at the same clean head under an explicit rule. Add a no-findings/failing-gate acceptance case.

2. **Do not inherit command-gate recovery unchanged.** Lines 69–70 propose runner children “like a command gate,” but `dispatch/src/scheduler.rs::poll_gate` automatically starts checks again when its child handle is lost. That contradicts the no-second-launch acceptance row and the stated failure-is-a-decision invariant. `dispatch/src/recover.rs` recovers Switchboard operations, not arbitrary runner children. Specify a durable identity and launch record for each command reviewer, what happens at every crash boundary, and how surviving children and descendants are found and retired before a replacement is permitted. Extend the process-list requirement to command reviewers and checks, not just agent sessions. Test restart after launch but before recording the result, partial fan-out, and park/rerun while a command is running.

3. **Define a command-result protocol instead of inferring success or findings from output presence.** Lines 92–97 treat every nonzero exit with output as findings. Tool/configuration failures can print output too, while ordinary successful tools can print banners. Specify success, findings, and execution-error exit codes (configurable or normalized by pipeline-owned wrappers), whether successful stdout is diagnostic or feedback, and how stderr is retained. Missing or empty agent feedback must fail rather than silently count as approval; explicitly define empty successful command output. Define the sentinel's whitespace/newline handling and reject a sentinel followed by objections. Cover errors with output, findings without usable output, and successful diagnostic output in tests.

4. **Make completion and reviewer retirement concrete for both agent kinds.** “What for Codex” at line 73 is a prerequisite for the example, not an implementation detail. The existing ordinary-agent path uses Stop/zero-exit plus settled artifacts; the workflow has a separate file-settlement mechanism for Codex. Choose a supported completion mechanism for this new stage, including partial writes, stalls, missing files, nonzero exits, and restart after observing completion. A Claude Stop is a finished turn, not proof that its session has exited. Specify when reviewers are killed and read back as gone before an implementer can modify their shared tree. Also specify implementer completion, committed/clean output, required `response.md`, and failed-check behavior. Do not launch another paid round automatically after a failure.

5. **Specify the immutable review target and intentional head transitions.** Lines 42 and 101–104 do not say how the base is resolved or how all concurrent reviewers are proven to have reviewed the same content. Persist base and head SHAs before fan-out, define the diff operation, and require a clean tree with unchanged head before accepting reviewer evidence. Name the policy for changes during review and while a decision is pending. Distinguish an authorized implementer transition from an unexpected head movement: `docs/dispatch.md` currently says moved heads void prior evidence and park the ticket, including earlier `implement` checks. Explain which earlier evidence becomes historical, which checks must be replaced, and how the final review-stage head feeds downstream gates. Test external mutations separately from intended fix commits and ensure another lane's commit does not invalidate this lane's result.

6. **Define how the read-only reviewer rule is achieved.** A prompt saying “never write” does not establish the invariant at lines 71 and 154–155, especially when several agents share one worktree. Specify launch cwd, permissions, access to the repository and plan, and write access to each reviewer's artifact directory. `OperatorKind::reviews_in_tree` and `write_flags` already distinguish Claude and Codex artifact-writing behavior. State whether write prevention is enforced or whether mutation is detected and fails the round; do not claim prevention if only detection is provided. Account for command tools that create caches or modify files, and test a reviewer that changes the tree without committing.

7. **Resolve round, cap, and decision ordering with explicit transitions.** The current sequence can apply fixes in round `cap` and then ask to accept a head that no reviewer has seen. Define whether `cap` counts review passes or fix passes, when the cap decision occurs, and what “findings left” means at that point. If accepting an unreviewed final fix is allowed, show that distinction and preserve the actual reviewed head. Specify exactly what the per-round `ask` decision authorizes: fixes, the next review pass, or both; whether a converged round asks; and how “another round” extends the cap. Decisions must identify the lane, attempt, round, and head, and stale answers must not launch work or accept a changed branch. Test `cap = 1`, no-op fixes, concurrent lane decisions, and the ask/cap interaction.

8. **Finish schema, validation, persistence, and view design against the actual contracts.** `Stage::kind()` currently recognizes only agent, workflow, and gate-only stages; this example has neither `operator` nor `review` and needs a new discriminator. Choose the reviewer namespace and define validation for unknown or duplicate names, empty reviewer lists, unsupported subjects/contexts, absent branches, invalid caps, incompatible stage fields, missing implementers, and incompatible operator kinds. Choose the attempt/round representation and name the additive fields/types in `pipeline.rs`, `ticket.rs`, the ledger, and both wire crates as applicable. `Attempt` and `AttemptView` currently have only one session/run and one gate; recovery, cancellation, process views, and round artifacts need multiple identities. List necessary `model.rs`, `AppAction`, and `Effect` additions, or explicitly explain why existing capabilities suffice. Include serialization defaults/migrations and the schema bump required if serialized Switchboard model types change. Define stable feedback point identifiers and artifact paths isolated by attempt, lane, round, and reviewer, plus how subsequent fresh reviewers receive the prior response when an implementer disputes a point without changing code.

9. **Complete concurrency, cost, and acceptance coverage.** Settle slot accounting and explain budget checks/accounting for simultaneous reviewers across lanes, slot release while awaiting decisions, and sibling cleanup when one reviewer fails. Complete every existing acceptance row with a named `dispatch/tests/first_slice.rs` test against fake Switchboard and the command-runner fake where needed. Add the failure, gate, stale-head, decision, recovery, and mutation cases above, plus two lanes completing independently. State any required real-agent spike for the chosen Codex completion and permission mechanism; the fake alone cannot verify those behaviors.
