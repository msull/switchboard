# Further review feedback

The response reasonably distinguishes a skeleton from the implementation plan that follows. I am not repeating requests to fill in details already assigned to `PLANNER:` items. These remaining points concern the skeleton's settled rules.

1. **Check reuse must match the gate, not just the head (lines 94–100).** The new rule permits checks from another stage to be reused at the same clean head without requiring that they execute the review stage's checks. For example, passing `implement` tests would satisfy a review gate that also requires lint, even though lint never ran. Require successful evidence for the same resolved gate definition and execution context (including argv, cwd and relevant environment), or restrict reuse to the explicitly referenced gate. Otherwise run the review gate. Add a case with two different gates at the same head and verify the stronger gate runs.

2. **Capture the base SHA at the cut, rather than resolving a moving ref each round (lines 56–62).** “The lane's base ref as cut” and “resolved to a SHA when the round starts” are different targets. `Repo::fetch` updates the shared clone's remote refs before cuts, so another ticket can advance `origin/main` between this ticket's review passes. Resolving it again changes the review diff even if this lane's head did not change; an endpoint diff can then include unrelated upstream changes as apparent reversions. Persist the cut's actual base SHA and reuse it throughout review. If a different base policy is intended, state it explicitly and define how a changed base invalidates review evidence. Add a test in which another ticket fetches a newer base between passes.

3. **Replace the settled PID-adoption rule with a recoverable launch/result protocol (lines 193–212).** An ordinary child PID is unavailable before spawning, leaving a crash window between spawn and persisting the PID. After a runner restart, finding that PID alive neither proves it is the original process (PIDs are reused) nor restores the old `std::process::Child` handle needed by the existing polling implementation to collect its exit code. The current rule therefore does not establish either safe cleanup or the command-result protocol. It is fine to leave the mechanism to the planner, but require durable launch intent before execution, verifiable process identity, a way to obtain an exit result after restart, and a defined ambiguous-launch outcome that cannot launch a duplicate or kill an unrelated process. A supervisor or wrapper with durable launch acknowledgement and exit records is one possible solution. Test the spawn-before-PID-save window and PID reuse, not only restart with a fully recorded live child. Also reconcile “No boundary may launch a second copy of anything” with the explicit permission to rerun lost checks: state the exception and require the previous check and descendants to be gone first.

4. **Release a ticket's slot only when all its lanes have stopped consuming it (lines 242–251).** The ticket owns one slot, but its lanes can run independently. If lane A reaches an `ask` decision while lane B is still reviewing or implementing, the unconditional pending-decision rule releases the ticket's slot while paid work remains active. Another ticket can then start despite the configured limit. Retain the slot while any lane has active work; release it when the whole ticket is waiting without active work, and require reacquisition before an answered decision launches more work. Add a two-lane test with one lane waiting and one running, plus a second queued ticket under `slots = 1`.

5. **Define what “one more round” authorizes at the cap (lines 109–117).** At the cap, no fix pass has run. Merely extending the cap and starting the next review pass reviews the same unchanged head, potentially producing an endless sequence of identical cap decisions. State that this answer authorizes a fresh implementer to address the last pass's findings, then checks, then one additional review pass; say whether this replaces the ordinary per-pass `ask` decision. Alternatively choose another explicit sequence. Add `cap = 1 → another round → fix → checks → review`, verifying that the answer triggers exactly one fix pass and that a failed check stops the sequence.

6. **Keep disputed findings unresolved until the reviewer withdraws them (lines 109–111 and the disputed-point acceptance row).** Handing forward `response.md` is useful, but “the point is not raised again as new” must not mean suppressing a valid objection merely because the implementer disputed it. Require the next reviewer to assess the response and either withdraw the point or carry it forward as unresolved; convergence still requires no outstanding objections. Scope point references by round as well as reviewer/id so a fresh review's `<reviewer>-1` cannot be confused with the prior round's different point. Add a no-code-change case where the reviewer rejects the response and the stage remains unconverged.
