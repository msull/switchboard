# Facts for issue #230 (web control surface)

No spike: what is left needs a device or a person's click.

## Settled

- The wire `SessionView` has no excerpt field. It carries `card`, `waiting` and `waiting_reason`, but no `last_message`. — `control/src/lib.rs:637-688`. `last_message` is parsed from the Stop hook (`src/adapters/hooks.rs:71,196`, `src/ports/events.rs:24`) but never reaches a view. The headset shows `waitingReason` (`client/Sources/SwitchboardUI/BrowserView.swift:745`). So the "one-line excerpt the card shows" needs an additive field, or the page drops it.
- `last-response` for any session that is not a Claude Code session answers `400` with code `no_conversation` ("only a Claude Code session has a conversation"). A Claude Code session with no handle yet gets the same code with "has not started a conversation yet". — `src/app.rs:1869-1886`.
- `screen` on a session that is not running answers `400 failed` "not running". — `src/app.rs:1863-1866`.
- No remote route logs `request.query`: `refuse` logs method and path (`src/app.rs:3762-3766`), `pair` the name and scope (`:3666-3670`), the adapter only connection errors (`src/adapters/remote.rs:714`). `RemoteRequest` derives `Debug` with `query` (`:358-371`), so a future `{request:?}` would leak the code.
- The certificate as made today has no SAN, no EKU and no basicConstraints. It has NotBefore 1975-01-01 and NotAfter 4096-01-01. — `src/adapters/remote.rs:101-110`; `~/.cargo/registry/src/*/rcgen-0.14.10/src/certificate.rs:82-96`.
- Apple: for every TLS server certificate on iOS 13+/macOS 10.15+, the name must be in the SAN, and "DNS names in the CommonName … are no longer trusted". "Connections to TLS servers violating these new requirements will fail." Since iOS 13, the 825-day limit and the `serverAuth` EKU apply only to certificates whose NotBefore is after 2019-07-01. Today's NotBefore of 1975 falls outside both, so the missing SAN is the one Apple rule today's certificate breaks. — https://support.apple.com/103769 (published 2023-11-06). Queries: "Apple requirements for trusted certificates iOS 13 macOS 10.15 subjectAltName 825 days".
- Apple's 398-day limit applies only to certificates from preinstalled roots. It "will not affect certificates issued from user-added or administrator-added Root CAs". — https://support.apple.com/102028 (2023-08-21). Same query.
- Chrome has ignored the commonName since Chrome 58. A certificate with no SAN fails name matching with `NET::ERR_CERT_COMMON_NAME_INVALID`. The enterprise fallback policy was removed in 65/66. — Chromium commit "Disable commonName matching for certificates", https://chromium.googlesource.com/chromium/src/+/b166233e0fb8edd9fd4e67bc4a6bfb8e35b79144. Queries: "Chrome 58 remove support for commonName matching … ERR_CERT_COMMON_NAME_INVALID"; "chromium.org EnableCommonNameFallbackForLocalAnchors policy removed Chrome 65 subjectAltName". Corollary: a certificate reissued over the **same key** with an IP SAN keeps every SPKI pin (the pin is over the key, `src/adapters/remote.rs:111`).
- iOS: a certificate from a manually installed profile is not trusted for TLS until the user turns it on under Settings › General › About › Certificate Trust Settings, "Enable full trust for root certificates". Profiles from MDM or Configurator are trusted automatically. — https://support.apple.com/102390. Query: "iOS Certificate Trust Settings full trust root certificates only manually installed profile Apple support". The page names root certificates only. Whether a leaf with no basicConstraints is listed there is under Unresolved.
- WHATWG WebSockets: a browser that offered `Sec-WebSocket-Protocol` values fails the connection unless the 101 echoes one of them. — https://websockets.spec.whatwg.org/ §2.2 step 11.2. Queries: "RFC 6455 Sec-WebSocket-Protocol server response does not include subprotocol client must fail". Today's `respond_upgrade` echoes none (`src/adapters/remote.rs:519-527`, per the investigation).
- The token is URL-safe base64 with no padding (`src/adapters/remote.rs:337-341`). Every character is a `tchar`, so it is a legal subprotocol value.
- The WebSocket handshake is fetched with credentials mode `include`, so cookies for the origin ride on the upgrade the same way they ride on `fetch`. A URL with a fragment throws. — https://websockets.spec.whatwg.org/ §2.2 step 2.
- CSP `'self'` and `wss:`: the spec issue left `'self'` not matching WebSocket schemes. MDN says "connect-src 'self' does not resolve to websocket schemes in all browsers". WebKit bug 201591 (Safari blocked same-host `wss:` under `'self'`) was closed as a duplicate of 235873, "CSP: Improve compatibility of source matching", which was fixed in r292266 (2022-04-02). — https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/connect-src, https://bugs.webkit.org/show_bug.cgi?id=235873. Query: "CSP connect-src 'self' WebSocket wss Safari WebKit bug 'self' does not match ws". Naming `wss:` explicitly in `connect-src` works on every engine whatever the version. OpenBMC ships that workaround (commit 0824e49e in openbmc/phosphor-webui).
- iOS Camera: scanning a URL shows a link, and the user taps it to open the page in Safari. Nothing opens without the tap. — https://support.apple.com/102680. Query: "Apple support scan a QR code with iPhone camera tap the link that appears".

## Unresolved

- **Is there a click-through on iOS Safari for an IP URL whose certificate has no SAN?** Apple says such connections "will fail" (103769). That text is about trust, not the warning page. One forum post (bensoftware) and ThinLinc's docs ("cannot connect through an IP address" in Safari) are leads only. Queries: "Safari iOS "This Connection Is Not Private" self-signed certificate IP address no subjectAltName "visit this website" not shown". **The plan must build anyway**: reissue the certificate over the same key with an `iPAddress` SAN for each served address, and a `dNSName` for the `.local` name if the page is offered by name. Add EKU `serverAuth`, and keep a pre-2019 NotBefore or a validity of 825 days or less. This is the only form that both Apple and Chrome accept as name-matching. Reissue when `local_address()` changes.- **Does `wss://` work on iOS Safari after a click-through exception?** WebKit bug 41419 is still NEW (last comment 2014, rdar 17898486), and a 2011 webkit-dev thread says Safari did not extend an https exception to wss. Cockpit ships a documented workaround: Safari's WebSocket "does not support the WebSocket Secure sessions" with a self-signed certificate "even when they are manually marked as trusted", and it enables "NSURLSession WebSocket" (https://cockpit-project.org/running/safari, undated). The Apple developer forum (https://developer.apple.com/forums/thread/694113) says NSURLSession WebSocket became the default in iOS 15. No source says whether that fixes the exception case on current iOS. Queries: "Safari iOS self-signed certificate WebSocket wss fails after accepting certificate warning WebKit bug"; "Safari iOS 17 accept self-signed certificate then WebSocket wss connection fails …"; "Safari 15 NSURLSession WebSocket enabled by default release notes WebKit". **The plan must build anyway**: the page falls back to polling the REST reads by revision when the events socket fails to open or closes at once, and says it is polling. If wss works, the fallback stays dormant.
- **Can a self-signed leaf be fully trusted on iOS, or only a root?** Apple's page names only roots (102390). Queries as above. **Build to work in both cases**: if the plan offers a certificate download, the certificate has `basicConstraints CA:TRUE` with the same key, or the host makes a separate local CA. Otherwise the click-through is the trust step. The first is a design choice for the planner.
- **Are `Secure; HttpOnly; SameSite=Strict` cookies stored and sent after a certificate exception (Chrome, Safari), and kept across restarts on an IP host?** No source found. A 2014 Chromium thread (Palmer, public-webappsec 2014Dec/0131) is a lead only. Queries: "Chrome secure cookie certificate error origin not set …"; "Chromium cookies not stored or not persisted on HTTPS page with certificate error interstitial proceed"; "Chrome certificate error bypass page isSecureContext service worker … cookies HttpOnly Secure still set" (extended). **Works in both cases**: carry the token as a `Sec-WebSocket-Protocol` value, with the 101 echoing a fixed protocol name, and as a bearer header on `fetch`. This needs no cookie store. A cookie is an addition the plan may make only if the owner's run shows it is kept.
- **How long does iOS Safari keep a certificate exception?** A 2016 blog (kingant.net) saw "indefinitely"; nothing current. Query: "iOS Safari self-signed certificate exception how long remembered …". **Build anyway**: the dialog says the warning may come back.
- **How many connections does a first page load open?** Older sources say 6 per host for HTTP/1.1 (Steve Souders' 2008 roundup; Diffusion docs). Nothing current covers speculative preconnect. Query: "browser maximum persistent connections per host HTTP/1.1 six Chrome Safari speculative preconnect socket pool". **Build anyway**: a page load must not starve the four unauthenticated slots (`src/adapters/remote.rs:567`). Either static replies close the connection (`Connection: close`), or static paths count against a separate bound. The plan picks which.
- **Does the scanned URL reach Safari history before `replaceState`?** No source found. **Build anyway**: the code is single-use and window-bounded (`src/core/remote.rs:46-71`), and the page strips the query first.
