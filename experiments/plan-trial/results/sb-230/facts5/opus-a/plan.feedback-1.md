1. **The excerpt departure rests on a false premise, and the spec already decided where the excerpt comes from.** The plan drops "the one-line excerpt the card shows" because putting it on the wire "would mean a read model built from `UiState`" (plan lines 24-32). The tree says otherwise on two counts:
   - The spec has already made this decision. `docs/remote-client.md:207` says: "The compact card's one-line excerpt is not part of it: that is `last_message` from the `Stop` hook on the record, a field of the session's metadata, and moves with `changed {session}`." Facts line 7 agrees: the excerpt needs an additive wire field, or the page goes without it.
   - The source is not `UiState`. The core already receives the text in `EventKind::Stopped { last_message }` (`src/ports/events.rs:24`, exercised at `src/core/tests.rs:3354`) and discards it. The agent excerpt the card draws comes from `app.conversations`, and that is a `SwitchboardApp` field (`src/app.rs:167`), not a `UiState` one. `UiState::captions` covers only non-agent rows.

   The issue lists the excerpt in the first cut. Nothing in the issue asks to change the spec's answer, and the answer does not need a new read model. Default: the core keeps each session's last `Stopped.last_message`. It goes on the wire as an additive `SessionView.last_message: Option<String>` (`control/src/lib.rs:637`) through the same redaction cut as the other session fields, it moves with `changed {session}`, and the fixtures are extended (issue, decision 5: "the fixture set extended if a view changes"). If the value is kept on a serialized record, that needs a `SCHEMA_VERSION` 16→17 bump and a `migrate` step. If it is kept in runtime core state, it needs neither. The plan has to say which. Either way, the "Fixtures are unchanged" line (plan line 406) and the excerpt follow-up (line 458) go.

2. **The `RemoteReply` literal count is wrong.** Plan line 253 says "The 30 existing literals (28 in `src/app.rs`, 2 in the adapter)". The worktree has 11. Ten are in `src/app.rs`, at lines 1664, 1679, 2365, 2371, 2376, 2754, 3570, 3723, 3736 and 3767. One is in `src/adapters/remote.rs:829`. `tests/` has none. The figure of 28 counts the `-> RemoteReply {` function signatures as well.

3. **The `IDENTITY_SCHEMA_VERSION` bump does nothing as planned.** Only `make_identity` writes the constant (`src/adapters/remote.rs:118`). `update_identity` clones the stored identity and saves it with its old `schema_version` (`src/core/remote.rs:105-117`). `RemoteFiles::load` does not check the version at all (`src/adapters/remote.rs:54-63`). So the `CertificateReissued` transition as described saves `certificate_addresses` into a file that still says version 1, on every existing installation. The bump is there because of the "schema bump for any serialized change" rule, and it means something only if the transition that writes the new field also sets `schema_version = IDENTITY_SCHEMA_VERSION`. Say so under **The actions and effects**, and put it in the core test of step 1 ("emits one `SaveIdentity` whose `schema_version` is the new constant").

4. **Step 0's stop condition never tests the device the cookie question is about.** Choosing the `HttpOnly` cookie while its mechanics are Unresolved is right, and the plan names the cookie as the first test. But step 0 runs only desktop Safari and Chrome (plan lines 349-353). The facts put that question to the owner's iPhone (For the owner, second item), and the acceptance run is on iOS. As written, a desktop pass lets the whole commit be built, and an iOS failure turns up only at the owner's final run. I tried to settle this and could not. The one lead points the wrong way for WebKit: an Apple developer forum report (https://developer.apple.com/forums/thread/104488, June 2018, no reply) says Safari on macOS and iOS did not send an `HttpOnly; Secure; SameSite=Strict` cookie on a later `wss://` handshake while Chrome and Firefox did, and dropping `HttpOnly` fixed it. In that report the cookie was set on the 101, not by a `fetch`, so it does not settle the plan's case. Query run: "iOS Safari self-signed certificate accepted warning cookies not saved Secure HttpOnly". It also found WebKit bug 232088 (https://bugs.webkit.org/show_bug.cgi?id=232088), about Safari refusing `Secure` cookies on localhost over HTTP, which does not apply here. Default: step 0 includes the owner's iPhone run of For the owner items 1 and 2 against the stub: the cookie from `/pair` is sent on the next `fetch` and on the `wss` upgrade, and survives closing Safari. The stop-and-report applies to that result as well as to the desktop ones.
