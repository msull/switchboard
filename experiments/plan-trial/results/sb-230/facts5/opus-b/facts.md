# Facts for issue #230 (web control surface)

No spike was run. No Chrome or Firefox is installed here, and Safari's certificate interstitial needs a person's tap. Sources were read on 2026-10-22.

## Settled

- No reply tells a paired device its current scope except the `/pair` reply. `/info` has none. A raise or drop is only seen as a 403 `scope` on a command. Evidence: `src/app.rs:3568-3604`, `:3662`, `:3166-3171`.
- Two things parse the QR text: `PairingInvite.parse`, from `switchboard-remote pair` (`client/Sources/switchboard-remote/main.swift:111`), and the headset's paste and `SWITCHBOARD_INVITE` (`client/Sources/SwitchboardUI/BrowserView.swift:106`, `:883`). The README documents `pbpaste` (`README.md:277`). Dispatch does not read it.
- `local_address()` takes the source address of the default route to `192.0.2.1`. With a full-tunnel VPN up, that is the VPN interface's address. The QR prints it even while the port is bound to loopback. Evidence: `src/adapters/remote.rs:962-970`, `src/ui/remote.rs:155-166`.
- `make_identity` issues a certificate with no SAN, no EKU and a `not_after` in year 4096. Evidence: `src/adapters/remote.rs:90-110`.
- Apple's rules for TLS server certificates since iOS 13 and macOS 10.15 require the name in the SAN (the CN is ignored). Certificates issued after 2019-07-01 also need the serverAuth EKU and a validity of 825 days or less. Apple says connections that violate them "will fail". Evidence: https://support.apple.com/103769. Queries: "Apple requirements for trusted certificates iOS 13 macOS 10.15 self-signed certificate Safari subjectAltName 825 days".
- Secure context is decided by scheme: `https` and `wss` are "Potentially Trustworthy", and no certificate check takes part. So `crypto.randomUUID` is available to a page loaded after a click-through. Evidence: https://w3c.github.io/webappsec-secure-contexts/ §3.1 step 3. Queries: "secure context https certificate error click through isSecureContext Chrome Safari W3C secure contexts".
- WebSocket handshake: mode `websocket`, credentials mode `include`, so cookies go with it. Browsers MUST send `Origin` (RFC 6455 §4.1 item 8). Evidence: https://websockets.spec.whatwg.org/, https://datatracker.ietf.org/doc/html/rfc6455. Queries: "WHATWG WebSockets standard Sec-WebSocket-Protocol response must match requested protocol fail connection token"; "SameSite cookies WebSocket handshake cross-site WebSocket hijacking Chrome sends cookies Origin header".
- Subprotocol values are characters U+0021 to U+007E with no separators. Base64url without `=` padding fits; `=` does not. The constructor throws `SyntaxError` on an invalid value. If the client offered protocols and the 101 does not echo one, the browser fails the connection. Evidence: RFC 6455 §4.1 item 10 and §4.2.2; WHATWG WebSockets "establish a WebSocket connection" (same queries).
- A non-101 answer to an upgrade, such as a 401, reaches the page only as `error` followed by `close` with code 1006 and `wasClean` false. "User agents must not convey any failure information to scripts." The page cannot read the status from the socket; it must make a REST call to learn it. Evidence: https://websockets.spec.whatwg.org/ (same queries).
- Cookies are not isolated by port (RFC 6265 §8.5). A site is (scheme, host) with the port ignored, and an IP host has no registrable domain. So `https://<ip>:A` and `https://<ip>:B` are same-site, and a cookie set by one instance is sent to the other. Evidence: https://html.spec.whatwg.org/multipage/browsers.html#obtain-a-site, https://greenbytes.de/tech/specs/draft-ietf-httpbis-rfc6265bis-04.html. Queries: "RFC 6265 cookies do not provide isolation by port same IP address different port cookie shared".
- A URL fragment is never sent in the request line, and it is stripped from `Referer`. Evidence: https://w3c.github.io/webappsec-referrer-policy/ §8.4 step 5 ("Set url's fragment to null"); RFC 3986 §3.5. Queries: "URL fragment not sent to server HTTP request Referer fragment stripped RFC 9110 Fetch referrer policy".
- Chrome remembers a certificate-error bypass for 7 days, per host (the port is ignored and decisions are shared across schemes), keyed by error and certificate SHA-256. A new key is therefore a new certificate, which brings a fresh interstitial before any page script runs. Evidence: https://chromium.googlesource.com/chromium/src/+/HEAD/components/security_interstitials/content/stateful_ssl_host_state_delegate.cc (`kCertErrorBypassExpirationInSeconds = 604800`). Queries: "Chrome SSL certificate error "proceed" decision remembered how long per host chrome_ssl_host_state_delegate one week".
- Firefox keys an override by host:port, certificate fingerprint and origin attributes, so a rotated key brings a new interstitial. Evidence: https://searchfox.org/firefox-main/source/security/manager/ssl/nsICertOverrideService.idl. Query: "Firefox nsCertOverrideService override keyed host port fingerprint".
- Chrome's HTTP/1.1 pool allows 6 connections per host, and WebSockets have a separate cap of 255. Evidence: https://chromium.googlesource.com/chromium/src.git/+/HEAD/net/socket/client_socket_pool_manager.cc. Queries: "Chrome maximum 6 connections per host HTTP/1.1 socket pool limit per group preconnect".
- Safari, `SFSafariViewController` and `WKWebView` traffic does not need iOS Local Network permission, so there is no prompt. Evidence: https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy (revision 2026-10-06). Queries: "iOS Local Network privacy permission Safari prompt connecting to private IP address web page TN3179".
- Chrome's Local Network Access prompt (Chrome 142) gates requests from public to local or loopback addresses. A private-IP page calling itself is not gated. Evidence: https://developer.chrome.com/blog/local-network-access (updated 2025-09-29). Queries: "Chrome Local Network Access permission prompt private IP page same origin requests exempt 2025".
- On iOS, a manually installed certificate profile is not trusted for TLS until the owner turns it on under Settings > General > About > Certificate Trust Settings. Evidence: https://support.apple.com/102390. Queries: "Apple support trust manually installed certificate profiles iOS Certificate Trust Settings enable full trust".

## Unresolved

- **Does Safari on iOS offer a click-through for the current certificate (no SAN, no EKU, validity to 4096)? Does Chrome, whose error is `COMMON_NAME_INVALID`?** Tried: the Apple and Chrome queries above. Apple says only that non-compliant connections "fail". Practitioner posts (https://bugzilla.cendio.com/show_bug.cgi?id=7401) report that a SAN fixed iOS 13. No vendor page says whether the interstitial stays bypassable. If favourable, the plan may keep the certificate as issued. If unfavourable, and as the line to build to either way: reissue the certificate over the same key with a SAN (the LAN IP and `<host>.local`), the serverAuth EKU and a validity of 825 days or less, with renewal before expiry. The SPKI and every native pin are unchanged.
- **Does `wss://` work in Safari after the https warning was accepted?** Queries: "iOS Safari WebSocket wss self-signed certificate fails after accepting certificate warning"; "WebKit bug WebSocket self-signed certificate exception not applied wss Safari"; "Safari 15 NSURLSession WebSocket enabled by default WebKit release notes". The evidence conflicts:
  - WebKit bug 41419 is open and last modified 2026-01-12. There the reporter's wss worked only once the certificate was trusted (https://bugs.webkit.org/show_bug.cgi?id=41419).
  - Cockpit's docs say Safari wss fails with a self-signed certificate "even when manually marked as trusted" (https://cockpit-project.org/running/safari).
  - A developer forums thread reports a failure in iOS 26 beta 3 that was fixed in beta 5, with no Apple reply (https://developer.apple.com/forums/thread/792842).

  If favourable, the page uses the events socket as §4.4 says. If unfavourable, and as the line to build to either way: the page must still work when the socket fails, by polling `waiting` and the open session's read on a timer, with "live updates unavailable" said in the header.
- **How long Safari keeps a click-through, and whether it is keyed by host or by host and port.** Queries: "iOS Safari "visit this website" certificate exception how long remembered host self-signed "This Connection Is Not Private"". Only a 2016 blog was found. Build to: the page cannot assume the exception outlives a key rotation or an address change. "Identity changed" may never be shown by the page, because the browser's own interstitial comes first.
- **Do `history.replaceState`, iCloud history, Chrome history or the camera's scan history keep the original URL?** Queries: "Safari replaceState history entry original URL saved in History browsing history query string token". Only old WebKit bugs were found (59195, 263635). Build to: assume the code may persist in history. Its protection is that it is single-use, expires in five minutes and dies after three failures; it is never `replaceState`. A fragment keeps it out of the request line and logs.
- **Does iPadOS Safari send a Mac User-Agent by default?** Queries: "iPadOS Safari desktop-class browsing user agent macOS by default "Request Desktop Website" iPad user agent string". Only forums and WebKit bug 241322 say yes. Build to: a UA-derived name may say "Safari on Mac" for an iPad, so the name must be editable or chosen on the page.
- **Does Chrome on Android trust a user-installed leaf or CA for websites?** Queries: "Android Chrome trusts user-installed CA certificates websites Android 7 network security config user certificates browser"; "Chrome Root Store FAQ locally installed trust anchors user-added certificates honored Android". The Chrome Root Store FAQ is vague. Build to: a certificate download is an option for iOS only; click-through stays the path that works everywhere.
- **Does Android resolve `.local` in a browser?** Queries: "Android Chrome resolve .local mDNS hostname browser support Android 12". The AOSP resolver has since November 2021 (https://source.android.com/docs/core/ota/modular-system/dns-resolver); browser reports conflict. Build to: the QR URL uses the IP.
- **Do Safari or Chrome preconnect speculatively against the 4 unauthenticated slots?** Not found (same pool query). Build to: static files and `/info` must not starve `/pair`. Either answer static paths without holding an unauthenticated slot past the reply, or raise the cap for them.
- **The cost of reading `last-response` for every Claude Code session on real data.** This needs the owner's data directory. Build to: fetch excerpts lazily or in a bounded batch.

## For the owner

- On your iPhone and iPad, do three things:
  - Scan a URL QR with the Camera.
  - Accept Safari's warning for the current certificate.
  - Check whether a `wss://` to the same address connects. The Web Inspector console shows it.

  Each "no" selects the unfavourable branch above. The reissued certificate and the polling fallback work in both cases.
- Which browsers do you mean to support: iPhone Safari, iPad Safari, Safari or Chrome on another Mac, or Android Chrome? Click-through with polling fallback works for all of them. A certificate download helps only on iOS and macOS.
