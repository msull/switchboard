## Settled

### The tree

- The `/pair` reply and every other reply are wrapped by `envelope`/`envelope_at` as `{epoch, revision, body}`. Errors carry `{epoch, revision, error:{code,message}}`. (src/app.rs:3717-3751)
- `send` takes a JSON body `{op, text}`. `op` is 1 to 64 characters and `text` is 1 byte to 16 KiB, both trimmed. Anything else is 400 `bad_request`. A device without `control` scope gets 403 `scope`. A body that is not JSON gets 400. A failed send starting `interrupted` gets 409 `interrupted`. `resume` and `trust` take only `op`. (src/app.rs:3159-3216)
- Nothing checks `Content-Type` on a POST body. The body is parsed with `serde_json::from_slice` (src/app.rs:3175). A cookie-authenticated `send` therefore has no CSRF defence in the tree today. No `Origin` check exists either (investigation notes).
- The headset's paste path is `BrowserView.swift:849` ("Paste the QR code's text") to `PairingInvite.parse` at line 883. `boot(invite:)` at line 105 also calls `parse`. `parse` is `Wire.decode` of JSON (client/Sources/SwitchboardProtocol/Info.swift:114-116). The consumers of the JSON form are `PairingInvite.parse`, `switchboard-remote pair` (main.swift:107-125, one argument or `<host:port> <code> <spki>`), `ConnectionManager.pair(invite:)` and the Swift tests. Decision 3 can be built on that: one `parse` that accepts a URL first, then JSON, covers all of them. The three-argument CLI form needs no change.
- The Rust UI test asserts the invite is JSON with `code`, `spki_sha256` and an `addresses` array (tests/ui.rs:7485-7492). It does not assert the "only paired devices get past /info" hover text (src/ui/remote.rs:113). Changing the payload to a URL changes this test. The hover text is only a string to amend.
- `Cargo.toml` has only `exclude = ["vendor/egui_term"]` (line 91). There is no `include` list, so a root-level `web/` is not dropped. `include_str!` embeds the files at compile time, so the bundle is unaffected.
- `SessionView` has no excerpt field. The card's excerpt is computed in `src/ui/cards.rs` `agent_excerpt`, from conversations and pane captions that live in `UiState` (investigation notes, grep of `control/src/lib.rs` found none). "Each with the one-line excerpt" is therefore a new read model. The alternatives are `last-response` per session, or showing `card` and `waiting_reason` only. The plan chooses; the gap is a fact.
- `RemoteRequest` keeps no `Cookie`, `User-Agent`, `Origin` or `Sec-WebSocket-Protocol`. `RemoteReply` has no header channel and `respond` hard-codes `application/json`. `respond_upgrade` writes no `Sec-WebSocket-Protocol`. Only the exact paths `/api/v1/pair` and `/api/v1/info` are rate-limited. The unauthenticated pool is 4 connections. All of this is from the investigation notes (adapters/remote.rs:360-570, 631, 843).

### The web

- **HSTS does not apply to an IP-literal host.** A user agent must not note an IP literal as a known HSTS host and must not match one on load. Click-through is blocked only for known HSTS hosts. A page addressed by `https://<ipv4>:<port>/` therefore keeps the ordinary click-through interstitial, and "HTTPS-First" upgrades do not remove it. RFC 6797 §8.1.1, §8.3, §8.4, §12.1: https://www.rfc-editor.org/rfc/rfc6797#section-8.1
  - Queries: `Chrome "Proceed to" unsafe self-signed certificate IP address HSTS no proceed link "thisisunsafe"`.
  - Covers: the RFC as published. The `thisisunsafe` posts are forum leads and are not evidence.
- **An IP host is matched against `iPAddress` entries in subjectAltName.** `commonName` is a deprecated fallback. Chrome has ignored the CN since version 58 and the certificate is rejected as `ERR_CERT_COMMON_NAME_INVALID`. Apple's server-certificate rules say the same for DNS names: the SAN is required and the CN is not trusted. The host's certificate has no SAN at all (`CertificateParams::new(vec![])`, adapters/remote.rs:95), so every browser will report a name mismatch beyond "self-signed". Whether the interstitial still offers a proceed link for that combination is not settled (see Unresolved).
  - Sources: https://cabforum.org/working-groups/server/guidance-ip-addresses-certificates, https://support.apple.com/en-us/103769, the Chromium-58 reports in the first search below.
  - Queries: `Chrome Firefox Safari self-signed certificate IP address no subjectAltName ERR_CERT_COMMON_NAME_INVALID proceed anyway`; `RFC 6125 OR "Baseline Requirements" IP address certificate must be in subjectAltName iPAddress not commonName browsers`.
  - **Consequence:** a certificate that lists the address(es) it is served on, as `iPAddress` entries, is a precondition for any browser path, whichever way Decision 1 goes. Address changes (DHCP) would then mean reissuing, which `identity.json` and the key rotation rule (§5) must account for.
- **A click-through exception does not reliably cover `wss://`.**
  - Firefox: Mozilla bug 1187666 (Firefox 39, WONTFIX) says "we don't create dialogs for failed subresources, which is what wss is". The stored exception is the only route, and the workaround is to visit the host and port over `https://` first. https://bugzilla.mozilla.org/show_bug.cgi?id=1187666
  - Safari: WebKit bug 41419 is NEW and unassigned. Safari fails `wss://` to an untrusted certificate with no console message, and works once the certificate is trusted. https://bugs.webkit.org/show_bug.cgi?id=41419
  - iOS 26 beta 3: a developer on Apple's forums reports `wss://192.168.1.81/…` failing with "The certificate for this server is invalid" after the page's warning was accepted. The poster later wrote "seems to be resolved in Beta 5". No Apple statement. https://developer.apple.com/forums/thread/792842
  - Because the page and the socket are the same origin (same host and port), the Firefox workaround is satisfied by the page load itself. The remaining risk is Safari and iOS, where only the user-trusted-certificate path is known to work.
  - Queries: `iOS Safari self-signed certificate "visit this website" WebSocket wss fails after accepting certificate warning`; `Firefox "Add Exception" self-signed certificate wss WebSocket must accept certificate for websocket port separately`.
  - **Consequence:** the plan must give the page a polling fallback (`GET /api/v1/*` with the revision counter) that works when the socket cannot connect, and must say so on the page. This is the line the plan builds to under Decision 1, whichever way it goes.
- **Browsers cannot set a header on `new WebSocket()`.** The constructor takes a URL and an optional list of subprotocols. Browsers send `Origin`, and `Cookie` for the origin. https://websocket.org/reference/headers/, https://blog.openreplay.com/websocket-authentication/ (leads that agree with RFC 6455 §4.1 item 8). Query: `browser WebSocket constructor cannot set Authorization header Sec-WebSocket-Protocol token cookie Origin check`.
- **Sec-WebSocket-Protocol, from RFC 6455 §4.1 and §4.2.2** (https://www.rfc-editor.org/rfc/rfc6455#section-4.1):
  - Values are `1#token`, characters U+0021 to U+007E excluding separators, and unique. A 43-character base64url token is a legal value.
  - If the client offered subprotocols and the server's reply omits the header, the connection is not established (§1.9).
  - A reply that selects a protocol not offered fails the connection.
  - A subprotocol route therefore needs `respond_upgrade` to echo one offered value, and the token sits in a request header that the tree must keep out of logs.
- **Origin on the upgrade:** browser clients must send `Origin`. Browsers do not apply CORS to WebSockets, so the server decides. If the server does not validate `Origin`, it accepts connections from anywhere. A missing `Origin` should not be read as a browser (RFC 6455 §4.1 item 8, §4.2.1 item 7, §4.2.2). A cookie credential on the socket therefore requires an `Origin` check against the host's own origin, and the same applies to `POST` (CSRF). A header-carried token (subprotocol) does not need one.
- **Cookies are not isolated by port.** "If a cookie is readable by a service running on one port, the cookie is also readable by a service running on another port of the same server." A cookie named for this host is sent to any other service on the same IP regardless of port. `Secure` protects only confidentiality in transit, and `HttpOnly` limits the cookie to HTTP requests. RFC 6265 §8.5, §4.1.2.5, §4.1.2.6: https://www.rfc-editor.org/rfc/rfc6265#section-8.5. The `SameSite=Strict` effect on other ports is not separately sourced here; the port-blindness above is the relevant half. A `__Host-` prefix needs `Path=/`, `Secure` and no `Domain`; it does not add port isolation (not sourced here, a lead from general knowledge). Query: none beyond the RFC fetch.
  - **Consequence:** a token cookie on an IP host is readable by every other service the owner runs on that IP, for example the dev servers Dispatch starts. The subprotocol or storage routes do not have this reach.
- **`history.replaceState` replaces the current history entry's URL in place** (same-origin only). Back navigation then shows the replaced URL. MDN says nothing about `Referer`, so `Referrer-Policy: no-referrer` on the page stays a separate, cheap measure. https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState. Not sourced: the camera app's own link preview or an in-app webview keeping the original URL in its own history.
- **Certificate validity limits:** Apple's 825-day limit is stated for TLS server certificates that chain to a root and issued after 2019-07-01. The page does not say whether it applies to a user-trusted self-signed certificate; it covers neither the year-4096 `notAfter` nor a self-signed leaf. That is not settled; see Unresolved. https://support.apple.com/en-us/103769. Query: the same page fetch only.

## Unresolved

1. **Does each browser offer a proceed link for a self-signed, no-SAN, IP-literal certificate?** Tried: the two searches under the SAN claim and the Firefox and WebKit bug pages. The sources cover the name error but not the proceed link, and one WebKit comment (bug 158345) was a search snippet only. Plan: assume the click-through exists on Chrome and Firefox (HSTS does not apply to IP hosts) and still add the IP to the SAN. If favourable, the plan may state click-through as the trust step. If not, the plan must offer the certificate download (a new public path serving data already in the handshake) and say so. Both branches need the SAN work, so the plan builds it unconditionally.
2. **How long iOS or macOS Safari remembers an exception, and whether Safari/iOS applies it to `wss://` today.** Tried: `Safari iOS "This Connection Is Not Private" "visit this website" self-signed certificate asks again…`. No source states a duration. WebKit 41419 is open and the iOS 26 report is one forum post that later cleared. Plan: write the polling fallback and the "reconnecting / trust the certificate" state regardless. If it works, the socket is the primary path; if not, polling is.
3. **Whether the iPhone or Android camera opens `https://<ip>:<port>/?code=…&key=…&id=…`, and in which browser.** Tried: `iPhone camera QR code opens https URL with IP address and port local network Safari self-signed`. Only generic or low-quality pages returned, and a 2018 bug about `@` in URLs, which this URL does not contain. Plan: the page works when the URL is typed or pasted as well, and the pairing window keeps "Copy invite" with the URL. If the camera opens it, the issue's acceptance test is as written. If it does not, the copy path is the way in.
4. **Does a year-4096 `notAfter` or a missing SAN hit an OS limit if the owner installs the certificate as a trusted profile?** Tried: Apple's certificate-requirements page, silent about user-installed leaves. Plan: if the certificate download is picked, issue the certificate with a SAN and a validity within 825 days, and renew it. That also costs nothing if click-through works.
5. **Does an unauthenticated page load stay inside the 4-connection pool?** This is a tree-runnable behaviour but the question is "does a browser's parallel loading fit", and no browser is available in this session. By the code, every connection is unauthenticated until a reply sets `authenticated: true`, a browser opens up to six per host, the accept loop drops over-pool connections silently, and idle connections hold a slot for 30 s (adapters/remote.rs:567-573, 690-700, 810). Plan: bundle the page into as few files as practical, send `Connection: close` on static replies (or answer them on the connection thread without a slot), and test pool use with the host's own client. This holds whichever way a browser behaves.
