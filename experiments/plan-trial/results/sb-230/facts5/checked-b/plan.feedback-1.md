# Plan feedback, round 1 (premises)

Every tree reference in the plan was checked against the worktree at 7fe8949. All of them match: `SCHEMA_VERSION` 16 and `VIEWS_SCHEMA_VERSION` 7 (`src/core/model.rs:12`, `:612`), `IDENTITY_SCHEMA_VERSION` 1 (`src/ports/remote.rs:17`), 30 `RemoteReply {` sites and 3 `RemoteRequest {` sites, and every cited line in `src/app.rs`, `src/adapters/remote.rs`, `tests/remote.rs`, `tests/ui.rs`, `src/ui/remote.rs`, `Cargo.toml:91`, `CHANGELOG.md:9` and `README.md:276`. Most decisions rest on a settled facts line or on the tree, as the plan cites them. The cookie mechanics are unresolved, and the plan correctly makes them the first test (Build order 3). The two objections below are the exceptions.

1. **The certificate-download path rests on nothing and is contradicted by Apple's documentation. Its fix is wrongly deferred as a spec change.** Plan lines 259-263 say the download "is what makes the iOS Safari `wss://` path work at all". Lines 280-283 and follow-up 3 keep the certificate as it is and say a shorter lifetime "reverses a line of §5".
   - **Apple's requirements for TLS server certificates.** https://support.apple.com/en-us/103769 says certificates "issued after July 1, 2019 (as indicated in the NotBefore field)" "must contain an ExtendedKeyUsage (EKU) extension containing the id-kp-serverAuth OID" and "must have a validity period of 825 days or fewer". It adds that "Connections to servers that violate the requirements will fail." The page does not say whether user-trusted certificates are exempt.
   - **iOS will not trust a self-signed leaf without Basic Constraints.** Apple DTS, https://developer.apple.com/forums/thread/720477: "iOS won't let them trust a self-signed certificate without the Basic Constraints extension". A certificate needs that extension "to be considered a CA cert, which is what that UI [Certificate Trust Settings] is all about".
   - **What the host issues.** It uses rcgen 0.14.10 defaults: no EKU (`extended_key_usages: Vec::new()`, rcgen `src/certificate.rs:96`), `IsCa::NoCa` (`:94`, so no Basic Constraints), and `not_after` in the year 4096 (`src/adapters/remote.rs:91-92`). The plan's `reissue_certificate` keeps all three. So the plan's iOS trust route fails on two documented requirements and on one requirement whose scope is unresolved (Unresolved 4). It is a default that depends on a favourable answer.
   - **The deferral premise is false.** No spec line fixes the year 4096. `docs/remote-client.md:308` already provides for "a certificate reissued from the same key (a new expiry)". The year 4096 lives only in the doc comment on `make_identity`.
   - **A robust default costs nothing to the native clients.** Both native verifiers check only the SPKI hash and ignore EKU and validity: the Rust `Pin` (`src/adapters/remote.rs:188-203`) and Swift `Pinning.swift:77-108`. So `make_identity` and `reissue_certificate` should set EKU `ServerAuth` and a validity of at most 825 days. `refresh_certificate` should also reissue when the certificate is near expiry, not only when the address changes. That makes the `Identity` doc comment's "reissued over the same key" literal.
   - **Basic Constraints.** Whether to add `CA:TRUE` to a leaf that also serves TLS is not settled here, because browsers may refuse a CA certificate used as an end entity. Name it as the implementer's or the owner's device test, next to For the owner 1.
   - **Wording.** Until that test passes, the plan, the dialog line (plan 372-375) and the page must not present the download as the iOS fix. On iOS, polling is the path the plan can promise.
   - Queries run: the Apple page fetch; `iOS install self-signed leaf certificate profile not shown in Certificate Trust Settings basicConstraints CA:TRUE required`; the DTS thread fetch.

2. **The cookie's stated cost misreads the RFC the facts cite, and the dialog text inherits the error.** Plan lines 200-206 and the dialog line at 376-377 say `sb_session` "is sent to every other service the owner runs on the same IP". Facts line 42 names "the dev servers Dispatch starts".
   - **What the RFC says.** The cookie is `Secure`. RFC 6265 §4.1.2.5 says "the user agent will include the cookie in an HTTP request only if the request is transmitted over a secure channel". §5.4 says "If the cookie's secure-only-flag is true, then the request-uri's scheme must denote a 'secure' protocol" (https://www.rfc-editor.org/rfc/rfc6265#section-4.1.2.5).
   - **What changes.** Port-blindness (§8.5) still holds, but only for HTTPS services on that IP. Plain-HTTP dev servers never receive the cookie. The cost statement, the dialog line, the §5 amendment and follow-up 6 should all say "other HTTPS services on this IP". The decision itself does not change.
