## On-disk record and rehydration (before the pane)

Nothing new has to be persisted for the page itself.
- `identity.json` (server id, name, self-signed cert, SPKI hash, listen {lan, port}) and `devices.json` (`PairedDevice` in `src/ports/remote.rs:96`: id, name, scope, `token_sha256`, created, last_seen) already hold everything. A browser is one more `PairedDevice`; the host stores only the token's SHA-256 (`remote::token_sha256`, `src/adapters/remote.rs:345`).
- Rehydration of a paired browser = the token the browser keeps, looked up by hash on each request (`authenticate`, `src/app.rs:3127`, via `core.device_by_token`, `src/core/remote.rs:145`). Revocation removes the record, so the next request is 401 `unauthorized` "the token is not known; pair again" (`src/app.rs:3145`). The page can map that 401 to "revoked". The spec says revoke also closes the device's WebSocket.
- The browser-side record is new and lives on the device, not the host: wherever the token lives (an HttpOnly cookie, or storage), plus the pinned `server_id`/`spki_sha256` the page last saw, to say "identity changed, pair again". That is the only new state. If a cookie carries the token, the host needs no new field. If `Set-Cookie` attributes (Max-Age) matter, that is a host choice, not a record.
- Key rotation already deletes every device record (§5), so a browser's cookie or token goes stale in a way indistinguishable from revoke unless `/info` is compared: `/info` is the only unauthenticated place that can say the key changed.
- No `SCHEMA_VERSION` bump is implied unless `PairedDevice` gains a field (e.g. a `kind` or user agent string). The name from the user agent can go in the existing `name`.
- The pairing window is `never saved` state (`src/core/remote.rs` `pairing_at`, `pairing`), so a page opened with an expired code simply gets `pairing_closed` 403 from `/pair`.

## Code the issue touches

- `src/adapters/remote.rs`
  - `read_request` 444-516: parses request line, headers (lowercased), `authorization: Bearer` into `bearer`, upgrade key, query. It does not keep `cookie`, `user-agent`, `origin`, `host` or `sec-websocket-protocol` headers: `RemoteRequest` (360-372) has no field for them. Cookie/subprotocol auth and a user-agent device name each need a new field there. Header block is capped by `MAX_HEAD`.
  - `respond` 530-553: always `Content-Type: application/json`, no other headers, `Connection: keep-alive`, a fixed status reason table (no 302/304/etc.). Static files need a content type, CSP, `Cache-Control`, `X-Content-Type-Options`, and `Set-Cookie` on the pair reply, so this takes more than a body argument. `respond_upgrade` 519 has no subprotocol echo (needed if `Sec-WebSocket-Protocol` is used; a browser closes the socket if the server does not echo one offered protocol).
  - `connection` 770-875: the rate check `Limits::limited` (633-640) keys on exact paths `PAIR_PATH`/`INFO_PATH` (586-587); every other path is unlimited. A page load of `/`, `/app.js` etc. is therefore not rate-limited and counts only against the 4-slot unauthenticated pool (`MAX_UNAUTHENTICATED` 568; accept loop 696-706) until an authenticated reply moves the connection to the paired pool (843-858). A browser opens several connections at once (page plus assets plus keep-alive); the pool count is per TCP connection, with a 5 s handshake timeout (570) and 30 s idle (573). Moving to the paired pool is decided by `reply.authenticated`.
  - Everything goes over the frame: `requests.try_send` to the frame, replies after the frame's next pass (about one frame interval, per Spike 22). Static assets would take the same trip unless answered on the connection thread; the issue does not say which.
  - Certificate: `make_identity` 95, `tls_config` 144. No SAN list is inspected here; whether the cert covers the LAN IP the QR carries is not checked (see questions).

  - `serve_remote` 3017: line 3023 `strip_prefix("/api/v1/")` else 404 `not_found` via `refuse`. `GET /` and static paths are decided here (or in the adapter). Then `info`/`pair` unauthenticated (3028-3029); everything else `authenticate`s (3127) from `request.bearer` only.

## Things the tree says that bear on the decisions

- Pools/rates (decision 4): static pages count nowhere but the 4-slot pool; there is no window for them. `Limits` is a struct of two windows keyed by exact path, extensible additively.
- The spec's token rule: bearer only "over the pinned connection, never in a URL" (§5). A cookie or subprotocol token changes that sentence; both need `RemoteRequest`/`read_request` changes. Cookie also introduces CSRF exposure on `POST /sessions/{id}/send`: the host checks no `Origin`/`Host` today, and `SameSite=Strict` is the only guard named. WebSocket upgrades from other origins are likewise not checked today (nothing consults `origin`).
- The code is a URL query: `read_request` already splits a query and `param`s are "undecoded: ids and numbers only" (`RemoteRequest::query` doc), which holds for the code (Crockford), hex key and a UUID. The page request carrying `?code=` reaches the host, is logged at most by path (`refuse` logs `request.path` without query), but a TLS-terminated GET with the code does go to the server once. Whether the host should answer `/` with the same page regardless of query is a plan choice.
- Safari/iPhone camera: the QR text must be a URL a camera app offers. The QR is made from `payload` string with `qrcode::QrCode::new`; URL length is about 150 characters, fine for QR size.
- Rate on the existing text path: "Copy invite" and the CLI/headset paste take the JSON today; the headset "has no camera" per the issue, and `BrowserView.swift:106` parses lines from pasted/discovered text.
