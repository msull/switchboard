# Facts for issue #230 (web control surface)

No spike was run: every open question left is a real-browser or real-device question, which cannot run here (no iPhone, no Safari with a LAN bind). Git status is clean.

## Settled

### The tree

- The certificate has **no subjectAltName**: `CertificateParams::new(Vec::<String>::new())` and only a CommonName `Switchboard <server_id>`. `src/adapters/remote.rs:95-120` (`make_identity`). Not for the LAN IP or any hostname.
- `respond` writes only `Content-Type: application/json`, `Content-Length`, `Connection`; the status reason table has no 302/304/405-other. `respond_upgrade` writes the 101 by hand with no `Sec-WebSocket-Protocol`, so a subprotocol echo is a one-line additive change. `src/adapters/remote.rs:519-553`.
- `read_request` drops `cookie`, `user-agent`, `origin`, `host`, `sec-websocket-protocol`; `RemoteRequest` (360-372) and `RemoteReply` (389-393: status, body, authenticated) have no header fields. Cookie auth, a user-agent device name, a `Set-Cookie` on the pair reply, or static-file headers each need additive fields. (Investigation notes 18-19, 26.)
- Rate windows key on exact `PAIR_PATH`/`INFO_PATH` only (`Limits::limited`, 633-640); static paths are unlimited and count only against the 4-slot unauthenticated pool (568, 696-706) until a reply with `authenticated` promotes the connection (843-858).
- `serve_remote` refuses anything without the `/api/v1/` prefix as 404 `not_found` (`src/app.rs:3023`). `tests/remote.rs:682` (`the_allowlist_refuses_everything_else...`) only exercises `/api/v1/...` paths, so a new `GET /` does not break it. No test in `tests/remote.rs` or `src/adapters/remote.rs` uses a bare `/` path or `HEAD`/`OPTIONS` (grep). The plan must define HEAD/OPTIONS/trailing slash for the new routes; today they fall to 404.
- Revocation: a removed device's next request is 401 `unauthorized` "the token is not known; pair again" (`src/app.rs:3145`). Key rotation deletes all device records (`docs/remote-client.md` §5, line 315), so a stale token after rotation gives the same 401. Only `/info` (unauthenticated, carries `spki_sha256`/`server_id`) tells them apart: the page must compare `/info` after a 401 to say "identity changed" versus "revoked". Spec line 315/317: client shows "identity changed, pair again" and sends nothing.
- Events: metadata kinds `project`, `space`, `set`, `session` and collections `projects`, `sessions` (id = project), `waiting`, etc. arrive on `/api/v1/events` with **no `watch` frame**; `watch`/`unwatch` is only for content kinds `conversation`, `screen`, `run_output`, `file`. `docs/remote-client.md:240,256`. So "a session starts waiting and moves to top" needs only `changed {waiting}` / `changed {session}` plus a refetch of `waiting`; the last response needs `watch {conversation}` (it is a projection of that key, line 207), and the screen needs `watch {screen}`. A visible content view also refetches every 30 s (line 256). `scope=all` only adds Dispatch worker records (`src/app.rs:246-272`).
- `last_message` (the card's one-line excerpt) is a field of the session's metadata and moves with `changed {session}`, not with `conversation` (spec line 207).
- Only Claude Code sessions have a conversation; other kinds answer "no conversation" and the client falls back to `screen` (line 206): the issue's "last response or screen" split is the API's own.
- The QR payload is built in `src/ui/remote.rs:160-166` from `remote::local_address()` (`src/adapters/remote.rs:962`); the address may be empty (loopback). `PairingInvite.parse` in Swift is `Wire.decode` of JSON only (`client/Sources/SwitchboardProtocol/Info.swift:94-117`).
- The code is Crockford, the key is hex, the id a UUID: none needs percent-decoding, so `read_request`'s undecoded query holds (`RemoteRequest::query` doc). `refuse` logs the path without the query.

### Outside the tree

**1. A WebSocket handshake to a host reached through a self-signed certificate is not reliable in Safari on iOS/iPadOS/Apple-silicon macOS even after the user clicks through.**
Cockpit's own docs: Safari's default WebSocket framework on iOS, iPadOS and ARM Macs does not support `wss://` with a self-signed or invalid certificate even when marked trusted; the workaround it ships is Settings > Safari > Advanced > Experimental Features > "NSURLSession WebSocket", or a valid certificate. https://cockpit-project.org/running/safari . Corroborated by WebKit bug 41419 (open since 2010: Safari honours the HTTPS click-through but not for `wss://`) https://www2.webkit.org/show_bug.cgi?id=41419 . Two agreeing sources, no contradiction found; the Cockpit page names no iOS version, so the evidence covers "as of the page's current text, checked 2026-10-22". Consequence: the page needs a non-WebSocket fallback on Safari (poll `/api/v1/waiting` etc. on an interval, or `changed` by long poll); the WebSocket cannot be the only live path for the iPhone case in the acceptance text.
Queries: "WebSocket cookie sent on upgrade request SameSite Strict HttpOnly Secure self-signed certificate Safari Chrome"; "Safari iOS self-signed certificate visit this website Secure cookies not stored WebSocket wss fails after accepting certificate".

**2. A browser fails a WebSocket whose 101 does not acknowledge a subprotocol the page offered.**
WHATWG WebSockets standard: if the client offered subprotocols and the response's `Sec-WebSocket-Protocol` is absent/not one offered, fail the connection (stricter than RFC 6455, which lets the server omit it). https://websockets.spec.whatwg.org/ . Chrome reports match (Adobe/Lawouach threads, leads only). So a subprotocol token design must echo exactly one offered value in `respond_upgrade`; the standard's token grammar admits base64url/hex.
Queries: "RFC 6455 Sec-WebSocket-Protocol server must echo subprotocol browser fails connection if missing".

**3. CSP `connect-src 'self'` does not cover same-host `wss:` in all browsers (Safari/WebKit).**
MDN note citing w3c/webappsec-csp#7: "`connect-src 'self'` does not resolve to websocket schemes in all browsers" https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/connect-src ; WebKit bug 201591 (service worker, Safari ≤14 unfixed) https://bugs.webkit.org/show_bug.cgi?id=201591 . Two agreeing sources. Build to `connect-src 'self' wss:` (MDN's own example form); this adds no external host because the page is served by a host that is also the only wss target.
Query: "Content-Security-Policy connect-src 'self' does not match wss WebSocket Safari".

**4. Safari has dropped `SameSite=Strict` cookies on WebSocket upgrades, and one report has `HttpOnly; Secure; SameSite=Strict` cookies not sent on a Safari WebSocket while Chrome/Firefox send them.**
WebKit bug 232666 (Strict cookies not sent on WebSocket in restored tabs, Safari 14/15, believed fixed 15.1) https://bugs.webkit.org/show_bug.cgi?id=232666 ; Apple forum thread 104488 (HttpOnly removal made Safari work; no version, no reply) https://developer.apple.com/forums/thread/104488 . The second is a lead (single forum post) and unresolved; the first is a vendor bug that is reportedly fixed. Together with fact 1 this settles only that **cookie-on-upgrade in Safari is an observed risk with no vendor statement it is safe**; it does not settle the current behaviour (see Unresolved U1).
Query: same as fact 1.

**5. Chrome ≥58 matches the host only against the SAN, never the CommonName.**
Forum agreement (Graylog, NethServer, TrueNAS, Palo Alto) and WebKit bug 158345 (Chrome and Safari would not accept a self-signed cert without a SAN) https://bugs.webkit.org/show_bug.cgi?id=158345 ; Cendio bug 7401 (iOS 13 needs SAN, EKU, validity under 3 years) https://bugzilla.cendio.com/show_bug.cgi?id=7401 . The current cert has no SAN (above) and a year-4096 validity, so a browser reaching it by IP gets a name-mismatch error, and per one Palo Alto article Chrome may not offer "Proceed" for a missing SAN (other users report it does; not settled). iOS 13+ also rejects validity over ~825 days for non-root trust (Cendio). Build to: the identity gains a SAN for the address the URL carries, which means the certificate is re-made on address change or the SAN lists every private interface address plus the Bonjour `.local` name; this changes `identity.json`'s certificate and thus the pinned SPKI only if the key is regenerated (it need not be: the SPKI is of the key).
Queries: "Chrome self-signed certificate without subjectAltName ERR_CERT_COMMON_NAME_INVALID IP address URL proceed anyway allowed".

**6. iOS Camera opens a QR's web link in Safari from a notification banner showing the URL (iOS 11+).** https://www.iclarified.com/60903/ios-11-camera-app-recognizes-qr-codes/amp , https://thehackernews.com/2018/03/ios-qr-code-camera.html (hostname-parsing flaw with crafted `@`/port text; our URL has neither `@` nor userinfo). Nothing found on IP-literal hosts, ports or self-signed hosts being refused before Safari; the Camera hands the URL to Safari, which then shows the certificate page. Queries: "iPhone Camera app QR code https URL IP address port self-signed certificate opens Safari notification". Android is not covered.

## Unresolved

**U1. Does current Safari (iOS 26-class, macOS 26-class) carry a `Secure; HttpOnly; SameSite=Strict` cookie, set by a fetch response on a click-through page, on `fetch` and on `new WebSocket()`?**
Tried: the three searches under facts 1 and 4 plus fetching the Apple thread; found only 2021-era and undated reports. Why not settled: no source states current behaviour. Line to build to: **favourable** (cookie works): the plan may use the cookie for `fetch` and WebSocket. **Unfavourable**: the plan must still keep the bearer header for native clients, send the token for the page's `fetch` in an `Authorization` header from memory/`sessionStorage`, and use the `Sec-WebSocket-Protocol` token (echoing it) or authenticate the first WebSocket frame; it must also carry the polling fallback of fact 1. The plan should build the WebSocket path so one transport (subprotocol or first-frame auth) works without cookies, and treat a cookie as an addition only if the owner confirms it (O1).

**U2. Whether an iOS Safari click-through exception covers `fetch` from the page and persists (how long).** Tried: same queries; Cockpit says the HTTPS page works after trust but WebSocket does not. No source gives the duration. Build to: the page treats a failed `fetch` with no HTTP status as "unreachable or certificate not trusted" and says so; it never assumes the exception outlives a session. Favourable: nothing extra. Unfavourable: the pairing window's text names the warning as repeating.

**U3. Whether Chrome/Android offers "Proceed" for a certificate with no SAN, and whether Android camera/Lens opens an IP:port https URL.** Tried: query under fact 5 and 6; sources disagree or are silent. Build to: add the SAN regardless (fact 5); that makes the Chrome case equal to the ordinary self-signed case.

**U4. Whether a Firefox/Chrome page whose query was removed by `history.replaceState` before any request still has the code in the browser history or the camera app's own history.** The camera app and the first `GET /?code=...` request exist before the script runs, so the code reaches the host once and may sit in the camera app's or the OS's history. Not settleable by search. Build to: the code is single-use and the window closes after the pair (spec §5), so a leaked URL is dead after pairing and after five minutes; the plan says so in the dialog and does not claim more.
