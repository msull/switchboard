### The world outside the tree
- **WebSocket subprotocol.** Client offers `1#token` of non-empty strings in U+0021..U+007E; the server returns exactly one value derived from the offer, or none; the client fails the connection if the server names a subprotocol it did not offer, and (WHATWG) if protocols were offered and the response's header is missing or empty. Today `respond_upgrade` (src/adapters/remote.rs:519) sends no `Sec-WebSocket-Protocol`, so a token-carrying offer needs the host to echo it. Whole-token safety: a 256-bit token must be encoded in token characters (hex or base64url) to be legal. Evidence: https://www.rfc-editor.org/rfc/rfc6455#section-4.1 (4.1 item 10, 4.2.2 step 4, 4.3 ABNF); https://websockets.spec.whatwg.org/ (§2.2 step 11.2). Queries: "WebSocket Sec-WebSocket-Protocol server must echo subprotocol browser fails connection RFC 6455 token characters".
- **Origin on the handshake.** A browser MUST send `Origin` on a WebSocket handshake; the server decides; "If the server does not validate the origin, it will accept connections from anywhere" (RFC 6455 §4.1 item 8, §4.2.1/4.2.2). With a cookie carrier the host must therefore check `Origin` on the upgrade, since `SameSite=Strict` stops cross-site pages but not same-site ones (other ports and hosts on the same IP are same-site). A bearer header or a first-message token needs no Origin check against CSRF. Evidence: RFC 6455 §4.1/4.2; https://christian-schneider.net/CrossSiteWebSocketHijacking.html; https://github.com/Syslifters/sysreptor/security/advisories/GHSA-2vfc-3h43-vghh (a SameSite=Strict deployment hijacked from a same-site origin). Query: "Cross-Site WebSocket Hijacking SameSite Strict cookie Origin header check same-site WebSocket handshake". Cookies also make `POST /pair` and `send` CSRF-reachable from another port on the same IP; an `Origin` check on every non-GET covers it.
- **`history.replaceState`** replaces the current entry in place (no new entry, the earlier URL is not in Back), changes the address bar, and loads nothing. It does not erase what was already sent: the server receives the full request line (`?code=…`) on the first GET, and a camera/scanner preview or an OS-level history may have recorded the URL before the page runs. The plan treats the code as exposed to the host's own request log and the device's launcher, mitigated by single use and the five-minute window. Evidence: https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState. Query: "history.replaceState remove query string from address bar session history entry MDN Referrer-Policy no-referrer".
- **Apple's 398-day certificate limit** applies only to server certificates from roots preinstalled on Apple's platforms; Apple states it "will not affect certificates issued from user-added or administrator-added Root CAs." A self-signed leaf is therefore outside the rule; Apple's page does not say what the click-through does with it. Evidence: https://support.apple.com/en-qa/102028 (as fetched 2026-10-22). Queries: "Apple support TLS server certificates macOS iOS requirements 398 days validity user-added root CA exempt".
- **Connections per page.** Browsers open up to 6 HTTP/1.1 connections per host (Chrome, Firefox; Safari 4-6 by age of source); the pool of 4 unauthenticated connections is smaller than that. A page loading HTML, CSS and JS in parallel can exceed it, so the page's assets must be few (one HTML, one JS, one CSS) or served without counting against the unauthenticated pool. Evidence: https://stevesouders.com/blog/2008/03/20/roundup-on-parallel-connections/ (2008, dated), https://docs.diffusiondata.com/docs/6.12.2/manual/html/designguide/solution/support/connection_limitations.html. Preconnect and retry-on-close behaviour was not found (queries: "browser maximum parallel connections per host HTTP/1.1 six … preconnect"); the plan sets the pool and assets so a closed connection is retried harmlessly (idempotent GETs).
- **Camera app.** The iOS Camera shows a banner for a QR link and opens it in Safari on tap. Evidence: https://www.phonearena.com/news/iOS-11-camera-app-reads-QR-codes-how-to-tips-tricks_id95045 (a news article, a lead, not a vendor source; kept only as the default path). Third-party scanners are not covered; see Unresolved.

## Unresolved

1. **Does `wss://` work on iOS Safari after a "visit this website" click-through on a self-signed certificate at a bare IP?** Sources I found say it does not, but none is Apple's statement for current iOS: code-server's iPad guide ("Safari will prevent WebSocket connections unless the certificate is installed as a profile", needs a domain name, a matching SAN, CA:true) https://github.com/cdr/code-server/blob/v3.7.0/doc/ipad.md; Kurento https://doc-kurento.readthedocs.io/en/latest/knowledge/selfsigned_certs.html; WebKit bug 41419, still NEW (opened 2010, last modified 2026-01-12), where a reporter's `wss://` worked only after "always trust" https://bugs.webkit.org/show_bug.cgi?id=41419; error `-9807` reports (Turris, OpenVidu). Chrome added recovery of overridden SSL errors for WebSocket in 2014 (https://codereview.chromium.org/304093003), so Chrome on Android likely works, which is not shown for today. Queries: "Safari iOS self-signed certificate IP address no subjectAltName visit this website WebSocket wss fetch after accepting"; "WebKit bug Safari WebSocket wss self-signed certificate exception Visit this website connection fails iOS"; "Chrome Android WebSocket wss self-signed certificate after proceeding unsafe works or fails". Why it does not settle: the only bug is about desktop Safari and a missing log line; the iOS evidence is guides and forum posts, not a vendor bug that says the behaviour is current.
   - Favourable (works after click-through): the plan may use the events socket as the live path.
   - Unfavourable: the plan must still ship a page that works without any WebSocket: poll a cheap read at an interval and use the `revision` every reply envelope carries to skip re-render, and show "live updates unavailable, refreshing every N s" instead of failing. Build to that in both cases, with the socket as an upgrade when it opens. The plan does not wait on this line. Whichever way the owner's phone answers (below), decision 1 should also state the profile route (host offers its certificate for download) as the documented fallback for a Safari that refuses the socket; a profile route needs a SAN for the IP or name, which is the certificate change in the Settled list.
2. **Is a `Secure; HttpOnly; SameSite=Strict` cookie stored and sent on a click-through origin, including on the WebSocket upgrade?** Not found. The only related evidence is that Chrome refuses service-worker registration on an origin whose certificate it does not trust, even after click-through (https://codereview.chromium.org/2085923002, https://deanhume.com/testing-service-workers-locally-with-self-signed-certificates/), which shows a click-through origin is not a full peer of a trusted one; cookie storage was not addressed. Queries: "Chrome Secure cookie self-signed certificate invalid cert error proceed unsafe cookies not stored"; "secure context page loaded with certificate error click through proceed anyway Chrome Safari service worker disabled cookies Secure attribute".
   - Favourable: the cookie carrier works and keeps the token from page script.
   - Unfavourable: the plan must still carry the token in a way that works without a cookie: `localStorage` plus `Authorization: Bearer` on `fetch`, and for the socket a `Sec-WebSocket-Protocol` offer of the token (RFC-legal as above; the host echoes the one value). Then no cookie exists and no CSRF/`Origin` check is needed for auth, though an `Origin`-equals-`Host` check on the upgrade costs little. Because this branch works in both cases and the cookie branch adds `Origin` checks, a CSRF surface and a new `/pair` reply header, build the bearer-plus-subprotocol path as the base; add a cookie only if the owner's test shows `localStorage` is not retained (item 4).
