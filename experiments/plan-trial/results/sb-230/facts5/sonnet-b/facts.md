# Facts for issue #230 (web control surface)

No spike was run: the questions the plan turns on (a real Safari/Chrome on a real LAN with this host's certificate) need a device and a person's tap, so they go to the owner. `git status` is clean.

## Settled

### The tree
- `last-response` for a non-Claude session is refused `400 no_conversation` ("only a Claude Code session has a conversation"); a Claude session with no resume handle yet gets `400 no_conversation` ("has not started a conversation yet"). The page falls back to `screen` on that code. Evidence: `src/app.rs:1869-1886`.
- `SessionView` carries `kind`, `liveness`, `card` (the card's word), `waiting`, `waiting_reason`, `name`, `last_activity_ms`, `pending`. It has no one-line excerpt field; the card's excerpt is not on the wire. The page uses `card`/`waiting_reason`, or a `last-response` read. Evidence: `control/src/lib.rs:637-690`.
- `/api/v1/waiting` is its own collection, and `?scope=all` lists Dispatch worker sessions. Ordering waiting-first is the host's rank (`docs/remote-client.md:169, 388`); the page needs `sessions` for kind/name, since `waiting` is a membership list. Evidence: `docs/remote-client.md:169,239,388`.
- Swift tests assert `PairingInvite.parse` only on the JSON form (`testInviteParsesTheQRText`); `parse` is a plain `Decodable` decode, so a URL form needs a branch before the decode and the JSON test stays untouched. Evidence: `client/Tests/SwitchboardProtocolTests/FixturesTests.swift:157-165`, `client/Sources/SwitchboardProtocol/Info.swift:94-117`.
- The certificate has no SAN: `CertificateParams::new(Vec::new())` plus a CN; rcgen 0.14.10 default validity is 1975-01-01 to 4096-01-01. Evidence: `src/adapters/remote.rs:101-107`; `~/.cargo/registry/src/*/rcgen-0.14.10/src/certificate.rs:84-85`.
- The SPKI hash depends on the key alone (`key.subject_public_key_info()`), so a certificate re-issued with an IP SAN over the same key keeps `spki_sha256` and the pins. Evidence: `src/adapters/remote.rs:113`.
- With `local_address()` = `None` there is no address to put in a URL (it returns `None` with no network). Evidence: `src/adapters/remote.rs:958-970`.
- Pool, rate and header facts are as the investigation lists them (every new connection counts in the 4-slot unauthenticated pool until a reply is `authenticated: true`; only `/pair` and `/info` are rate-limited; `respond` hardcodes JSON; no cookie/Origin/User-Agent read). Evidence: investigation notes, `src/adapters/remote.rs:444-552, 567-640`.

### The world
- **Chrome ignores the Common Name; a certificate for an IP needs an IP SAN.** Chrome 58 removed CN matching (opt-out only by enterprise policy `EnableCommonNameFallbackForLocalAnchors`). Searching found many reports of `ERR_CERT_COMMON_NAME_INVALID` for exactly this case, with "Advanced > Proceed (unsafe)" the workaround users report. Evidence: https://developer.chrome.com/blog/chrome-58-deprecations ; forum reports from the search (graylog, nethserver, netgate, truenas) are leads that agree. Queries: "Chrome self-signed certificate IP address no subjectAltName ERR_CERT_COMMON_NAME_INVALID cannot proceed". Covers Chrome 58 onward; whether the click-through is offered on current Chrome/Safari for this error is under Unresolved.
- **RFC 6455 §4.1:** a `Sec-WebSocket-Protocol` in the 101 that the client did not offer fails the connection; omitting it when the client offered some is not a failure (subprotocol = null). A failed TLS verification for `wss` fails the connection, and the RFC says nothing of user overrides. Evidence: https://www.rfc-editor.org/rfc/rfc6455.html#section-4.1 ; https://www.w3.org/Bugs/Public/show_bug.cgi?id=23576. Queries: "RFC 6455 client MUST fail connection Sec-WebSocket-Protocol server response omits subprotocol". So a subprotocol carrying the token needs no echo to connect, but the server must not echo a value the page did not offer; browser behaviour on omission is the spec's, not verified per engine.
- **WebKit does not apply an accepted HTTPS exception to `wss`.** WebKit bug 41419 (filed 2010, status NEW, page modified 2026-01-12): a WebSocket to a self-signed host fails until the certificate is trusted at the system level; maintainers declined to share the exception. An Apple forum report on iOS 26 beta 3 shows the page loaded over an accepted self-signed certificate while `wss://192.168.x.x` failed "certificate for this server is invalid"; the poster said beta 5 appeared to fix it, no Apple reply. Evidence: https://bugs.webkit.org/show_bug.cgi?id=41419 ; https://developer.apple.com/forums/thread/792842 . Queries: "Safari iOS WebSocket wss self-signed certificate accepted exception fails"; "Chromium bypass certificate error proceed unsafe WebSocket wss works after accepting cert warning same host". The behaviour exists, unfixed by the vendor's own bug; the plan treats Safari `wss` over a clicked-through certificate as not working unless the owner shows otherwise (see Owner).
- **Firefox honours an accepted exception for `wss` on the same host:port** (Mozilla bug 1187666, WONTFIX on a dialog for subresources; workaround: visit `https://host:port/` first, which the pairing flow does anyway). Evidence: https://bugzilla.mozilla.org/show_bug.cgi?id=1187666. Chrome: only secondhand (WebKit thread) that it honours it; not Settled.
- **Apple's 398-day validity limit does not apply to user-added or administrator-added roots**; the 4096 expiry is therefore not what a browser rejects on a publicly-trusted-CA rule. Evidence: https://support.apple.com/en-us/102028 . This is about roots, not a clicked-through leaf; that a clicked-through leaf escapes it is inferred, hence Owner.
- **CSP:** MDN notes `connect-src 'self'` does not resolve to websocket schemes in all browsers; Safari fixed it in 16.0 (WebKit r292266, Sept 2022); Chrome 71, Firefox by 2018. Evidence: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/connect-src ; https://github.com/w3c/webappsec-csp/issues/7 . The plan may use `connect-src 'self'` for current browsers, or name `wss://<same host>` is not possible without the host, so a Safari older than 16 loses live updates.
- **Referrer:** the default policy is `strict-origin-when-cross-origin`, which sends the full URL including the query on same-origin sub-requests; `Referrer-Policy: no-referrer` (or a `<meta>`) stops it. `replaceState` before the first sub-resource load is not guaranteed (the script is itself a sub-resource), so the response for `/` should carry `Referrer-Policy: no-referrer`. Evidence: https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/Referrer_policy . Queries: "Referrer-Policy no-referrer same-origin subresource Referer header full URL query string default strict-origin-when-cross-origin".
- **`SameSite=Strict` is withheld on a cross-site top-level navigation** (link or QR from another app) and sent on same-site requests. The code's navigation precedes any cookie, and `fetch`/WebSocket are same-origin, so Strict affects only a later open of the page from another app, and the page itself needs no cookie to load. Evidence: MDN definitions as quoted in https://lists.proxmox.com/pipermail/pve-devel/2024-October/065636.html (a project that hit it and moved to Lax). Query: "SameSite=Strict cookie not sent on navigation from QR code scanner or external app link first navigation".
- **iPadOS Safari sends a Macintosh user agent**; `navigator.maxTouchPoints` (>0) is the community workaround; `navigator.userAgentData` is Chromium-only (unsupported in every Safari and Firefox). So "Safari on iPad" vs "Safari on Mac" is a heuristic; "Safari on iPhone" is readable from the UA. Evidence: https://developer.apple.com/forums/thread/119186 ; https://caniuse.com/mdn-api_navigator_useragentdata . Queries: "Safari iPadOS userAgent Macintosh desktop-class ... maxTouchPoints"; "navigator.userAgentData Safari not supported".

## Unresolved

Each line: the plan builds to the stated branch and never waits.

- **Whether Safari and Chrome offer a click-through (not a hard block) for a leaf with no IP SAN on an IP-literal URL.** Tried: the Chrome 58 deprecation page, the ERR_CERT_COMMON_NAME_INVALID search (forum reports only of click-through). No vendor text says the name-mismatch error is bypassable on current builds. Build to: the host issues the leaf with the current `local_address()` as an IP SAN over the same key (SPKI and pins unchanged), reissued when the address changes; if click-through works without it, this is harmless extra.
- **Whether a clicked-through exception survives reload/tabs in Safari, and covers `fetch` and `wss`.** Tried: "Safari iOS This Connection Is Not Private … exception … reload"; WebKit 41419; iOS 26 thread. Only the `wss` failure is evidenced (Settled); the reload behaviour is not. Build to: if favourable, the page uses `wss` as designed. If not, the page must work without the socket: a poll of `/api/v1/waiting` and the open session on a short interval (the revision counter makes it cheap), with the socket an upgrade that fails quietly; and the owner-visible option to trust the certificate on the device first (decision 1) is the documented path in the dialog.
- **Whether a `Secure` cookie is stored from a clicked-through origin in Safari and Chrome, and rides the WebSocket upgrade.** Tried: "Secure cookie not stored self-signed certificate Safari Chrome certificate error HTTPS IP address" (only a WebKit bug about Secure cookies on plain HTTP, bug 232088). Build to: favourable: cookie carries both `fetch` and the socket. Unfavourable: the page keeps the token in `sessionStorage`/`localStorage` and sends it as a header on `fetch`; the socket authenticates with a first message after the upgrade (the host accepts it) rather than a URL or subprotocol; the host adds an `Origin` check either way.
- **Browser caching of assets from a certificate-error origin, and `no-store` vs `no-cache`.** Tried: "HTTP cache not stored when certificate error user bypassed Chrome" (CVE results only). Build to: serve `Cache-Control: no-store` on every static path (correct whether or not the browser caches); never rely on a conditional request.
- **Parallel and speculative connections against the 4-slot unauthenticated pool, and browser retry after a pool-full close.** Not searched with a source that would settle it (browser-internal behaviour; no vendor statement found). Build to: serve static paths on the connection thread without the frame, count them in a pool/rate window of their own sized above 4 page-load connections (or make the pool count only after a request line is read), and treat a close-without-response as retried.
- **Whether a camera/QR app's in-app view shares the system certificate exceptions, and whether the code lands in history/recents before `replaceState`.** No vendor documentation found. Build to: the code is single-use and expires in five minutes or three failures, so a leaked URL after pairing is dead; say in the dialog that the invite is spent once used.

## For the owner

1. Does Safari on the owner's iPhone/iPad, opened on `https://<LAN ip>:<port>/` against a host certificate **without** an IP SAN, offer "Visit this website", and does it still after the host re-issues the certificate **with** the IP SAN? Branch A (works without SAN): the plan may skip reissue. Branch B (blocked without SAN): the plan adds the SAN. The plan adds the SAN in both cases.
2. After the click-through, does the page's `wss://` to the same host open, and does the exception survive a reload and a second tab? A: the socket is the live path. B: the poll fallback above is the live path. The plan builds the poll fallback in both cases.
3. Does the owner's QR scanner open the URL in the system browser or an in-app viewer, and does that viewer accept the click-through? A: the QR is the pairing path. B: the dialog also offers the text URL to paste into Safari. The plan includes the text/copy URL in both cases.
4. Which browsers must be supported (Safari version below 16 loses `connect-src 'self'` for sockets)? Plan targets Safari 16 or later and current Chrome in both cases.
