1. **The build proceeds on a click-through nobody has seen, and spike 23 only gates on the cookie.** Decision 1 chooses the click-through as the trust step. Its support is facts "Unresolved" line 1 (click-through for IP-literal URLs) and line 2 (exception survival), and the plan marks the Apple 398-day inference as unsettled. A negative on the click-through then changes nothing in the plan. The spike's wording is "The `wss` and exception results are recorded as they are seen and change nothing". The only fallback is "a follow-up", so the whole web surface (page, pool, `/me`, certificate rework) could be built for a browser that cannot reach it.
   - I searched "iOS Safari self-signed certificate IP address 'Visit this website' subjectAltName required click through allowed". It confirmed that "Show details > Visit this website" exists on current iOS (https://discussions.apple.com/thread/256235137). Apple's forum says DNS names must be in the SAN since iOS 13 (https://developer.apple.com/forums/thread/125174; https://developer.apple.com/forums/thread/70139, "HTTPS and IP Addresses"). A vendor doc claims Safari cannot connect by IP at all (Crestron, https://sdkcon78221.crestron.com/sdk/Crestron_HTML5UI/Content/Topics/Platforms/Create-Certs.htm). I found nothing that settles whether an IP-only SAN passes, so this stays unresolved.
   - Fix: make "no click-through offered on a real iPhone/iPad Safari with the IP SAN" a stop condition alongside the cookie, so the implementer reports before building anything else. Name the decision-1 download path as what the owner then picks.

2. **The pairing code travels in the URL query, where a fragment would do.** Decision 3 uses `https://<ip>:<port>/?code=<code>&key=...&id=...`. The query is sent to the host in the request line and appears in `Referer`, in history and in the QR scanner's recents (facts Unresolved line 6). The plan spends three mitigations on this: `Referrer-Policy`, `replaceState`, and "the code is single-use". The plan treats that as the "safer store" for the invite, but a `#code=...&key=...&id=...` fragment is never sent to the server or in `Referer`. It also makes the `replaceState` race moot, because the first request carries no secret.
   - `read_request` already splits the query off the path (`src/adapters/remote.rs:495`), so `GET /?...` would have worked either way. With a fragment, `GET /` is simply plain.
   - The page reads `location.hash`, `invite_url` changes one character, and the Swift `parse` and the shared literal change in the same way. Use the fragment, or say why not.

3. **The cookie transport changes a spec line without citing it.** `docs/remote-client.md:312` says the token "is sent only as a bearer header over the pinned connection, never in a URL". Decision 2 adds a cookie, and the plan's docs list says "the cookie for browsers beside the bearer", but its "Where this departs" section does not name the line it amends. A browser cannot pin, so the "pinned connection" half of that sentence is also being given up (decision 1 says as much). The cookie itself is the right store, since an HttpOnly cookie beats `localStorage`. The objection is only that a spec decision (§5, line 312) is changed with no citation. Cite it, and amend the sentence rather than appending a paragraph.

4. **The certificate reissue premise is only half supported.** The plan says the SAN certificate is "derived at bind ... in memory only" and that `OpenPairing` triggers a rebind when `local_address()` changed. `bind_remote` (`src/app.rs:2936-2990`) sets `self.remote = None` and drops every paired device's socket. Reissue-by-rebind is justified by nothing in the facts; the facts only settle that the SPKI hash is unchanged (line 13). Opening the pairing window is a routine act, and the plan accepts "a rebind drops paired devices' sockets once" without saying how often that happens.
   - The cheaper default is to compute the SAN at first bind (from `local_address()`) and rebind only when the address differs, as the plan says.
   - Also state what happens when the LAN IP changes after pairing. A device paired earlier by a cookie keeps working. A fresh QR needs the new address in the SAN, which only the rebind provides.
   - This is a request for the sentence "rebind only if the address differs", which the plan nearly has. Make the conditional explicit and drop "when the pairing window opens" as the trigger. A rebind should be tied to an address change observed at open time, not to the open itself.
