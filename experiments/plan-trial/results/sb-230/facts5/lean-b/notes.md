## Record and rehydration first, then the page

**A paired browser (device record).** On disk: `devices.json` holds a `PairedDevice` made in `new_device` (`core/remote.rs:166–175`): `id`, `name` (the body's `device_name`, trimmed, at most 64 characters), `scope` (from the pairing window), `token_sha256`, `created`, `last_seen`. The token itself is never stored on the host. Rehydration: `IdentityLoaded` loads the devices (`core/remote.rs:23–31`), and each request finds its device by hash (`app.rs:3137–3140`). The reply to `/pair` carries `token`, `scope`, `server_id`, `device_id` in the JSON body (`app.rs:3660–3672`). Today the browser would keep that token in its own storage, which the host knows nothing about. Pane: the paired-devices row (`ui/remote.rs:241–275`) shows name, scope, paired and seen times, and Revoke. Nothing in the tree gives a device its own scope or name back (no `/me` route; `scope` in `/info` is the listing parameter, not a device property).

**The pairing window.** In memory only, never saved (`core/remote.rs:46–54`, `Effect` absent). A restart closes it. Its code is compared at `app.rs:3646`; a wrong key counts too, at `3636–3645`, so a page that sends the wrong `key` spends one of three attempts. The host ignores any `server_id` in the request: `remote_pair` reads only `spki_sha256`, `code` and `device_name` (`app.rs:3626–3655`). The QR and the text are built from `identity` and `window` at render time (`ui/remote.rs:160–166`), not stored.

**The page's own state.** On disk: nothing on the host. In the browser: whatever the page keeps. The tree has no browser storage, so the server id, pinned key, scope and host name the page needs on a later visit have no source except the page's own storage, or a new endpoint.

**The session list.** Rehydrated per request from the core's views (`app.rs:3044–3059`, `3119–3121` hides Dispatch worker records unless `scope=all`). Each row would show `name`, `kind`, `card` (the card's word), `waiting` and `waiting_reason`. There is no excerpt field on `SessionView` (`control/src/lib.rs:637–689`). The Mac card computes its excerpt in the UI: for an agent, the first line of the last answer from the transcript, or the last activity line, or the prompt (`ui/cards.rs:176–180`, `558–575`); for others, the pane caption or the host title (`ui/cards.rs:180–185`). Pane: the list grouped by project, waiting ones first. The waiting mark and the card word are on the wire. The one-line excerpt is not.

**The last response and the screen.** On disk: the agent's transcript JSONL (its path is `SessionView.transcript`, `control/src/lib.rs:687`), read and parsed on the content path (`app.rs:1967`, `3101`). The pane's text is not on disk; it is a tmux snapshot (`screen` route, `app.rs:3101`). Pane: the last answer, or the screen for a session without a conversation. A change arrives as `changed {conversation|screen, id}` from the poll; the page refetches on it. Event payloads carry no body: `event_json` (`app.rs:2646–2659`) sends only type, resource, revision and time.

**A reply.** Rehydration on the host: the `send` body is `{op, text}` (`app.rs:3180–3205`, `text` trimmed, at most 16 KiB, checked at 3193). The op goes to `operations.log` before the keys are sent (design.md A3 status, "The control port's `serve` logs a non-replayable command's request line before it runs"). A repeat of the op is answered from the log; an op with a request line and no reply is `interrupted` and never run again. Pane: the page shows the send accepted; progress is the session's state moving (`PromptSubmitted`, working, `Stop`, spec §4.5 line 279). The page can't know the reply went through until a `changed` frame arrives. A session at Claude's folder-trust question takes the text nowhere until `trust` answers it (`trust_question`, `control/src/lib.rs:662`).

**Revocation and identity change.** Revoke removes the `PairedDevice` (`core/remote.rs:86–92`) and drops the device's subscribers, which closes their sockets (`app.rs:486–500`, `adapters/remote.rs:890–902`). The next request from that token gets 401 with code `unauthorized` and the message "the token is not known; pair again" (`app.rs:3142–3149`). That is the same code and message an unknown token gets, and a rotated key gets it too. So the tree cannot tell the page "revoked" from "never paired" or "key rotated" today. A changed key shows on `/info` as a different `spki_sha256` (`app.rs:3581`, `identity.spki_sha256`), which the page can compare with the one it stored. A WebSocket handshake refused with 401 is a plain non-101 response (`app.rs:3036–3038`, `adapters/remote.rs:864`).

**The first load from a QR.** Today `GET /?code=…` gets `serve_remote`'s JSON 404 (`app.rs:3023–3025`), not a page. Every request reaches the frame through the bounded channel (`adapters/remote.rs:810–825`); the frame drains 8 per pass (`DRAIN_PER_PASS`, `remote.rs:580`, `app.rs:~1587`). The unauthenticated pool is 4 connections, counted at accept (`remote.rs:701–706`), and a connection stays in it until its first authenticated reply (`remote.rs:835–849`). A keep-alive connection after its first request has a 30 s idle timeout (`remote.rs:573`, `783–787`); before the first request the read timeout is the 5 s handshake timeout (`remote.rs:771`). The rate windows apply only to `/api/v1/pair` (6 a minute) and `/api/v1/info` (60 a minute), keyed by exact path (`remote.rs:583–587`, `631–638`); a page path is in neither.

**The certificate a browser would see.** The certificate has no subject alternative names; it is made with an empty name list and a common name `Switchboard <server id>` (`remote.rs:101–106`). Its validity is rcgen 0.14.10's default, 1975-01-01 to 4096-01-01 (`~/.cargo/registry/src/*/rcgen-0.14.10/src/certificate.rs:83–85`). The LAN address the page would be opened at is the outbound-route address (`remote.rs:962–975`), so no fixed IP can be put in the certificate. The SPKI pin is unaffected (the pin is of the key, `remote.rs:168–245`, and `remote-client.md` §5).

**The listen address.** The listener binds the LAN interface only when `listen.lan` is set (`app.rs:2962–2969`), but the QR's address comes from `local_address()` regardless (`ui/remote.rs:157–164`). With the listen off, the QR names an address the port does not answer on. This is in the tree today, not new.

## Decision facts from the tree

1. **Browser trust.** Facts: no SAN, CN only, 1975–4096 validity (above); the code travels in the URL's query and so in the first `GET` (`src/ui/remote.rs:160–166` puts `code` in the payload the issue would turn into a query); `refuse` logs method, path and code name, not the query (`app.rs:3754–3772`), so the host itself does not log the code. `remote-client.md` §5 line 306 ("Require pairing before anything but `/info` and `/pair`") and line 319 (no non-loopback bind without pairing) are the rules the page would amend. A page served before pairing is a new allowlist entry; `serve_remote` refuses every non-`/api/v1/` path today.
2. **Token transport.** `read_request` takes only `Authorization: Bearer` (`remote.rs:487–490`); no cookie, no `Sec-WebSocket-Protocol` (`remote.rs:491–494` takes `Upgrade` and `Sec-WebSocket-Key` only). `respond_upgrade` writes `Upgrade`, `Connection` and `Sec-WebSocket-Accept` and no protocol (`remote.rs:519–526`). `RemoteReply` has no header field (`remote.rs:388–393`); `respond` writes one fixed header set (`remote.rs:530–552`). The `/pair` reply is `envelope(200, &reply, false)` (`app.rs:3672`), so its token is in JSON and the connection is not marked authenticated. Nothing checks `Origin` or `Host` (grep of `src/adapters/remote.rs` and `src/app.rs`). `remote-client.md` §5 line 312: the token "is sent only as a bearer header over the pinned connection, never in a URL", and §7 line 352 says the client keeps its token in the Keychain, which a browser has no equivalent of.
3. **One QR or two.** Every consumer of the invite parses JSON: the CLI (`main.swift` 111), `PairingInvite.parse` (`Info.swift` 113–116), the headset paste (`BrowserView.swift` 883), the launch variable (`BrowserView.swift` 103–107). The Rust side builds the payload but never parses it. The Swift invite test uses an inline JSON string (`FixturesTests.swift` 157–165), not a file from `client/Fixtures/`.
4. **Static paths.** No route; every path other than `/api/v1/` is refused (`app.rs:3023–3025`). `respond` is JSON-only (`remote.rs:530–552`). Static bytes don't need the frame, but `connection()` sends every request to the frame (`remote.rs:810–826`), so a static route on the connection thread would be a second path; nothing in the tree has one.
5. **Tests.** `tests/remote.rs` `http` reads bodies by `Content-Length` and returns them as text (`245–297`), so an HTML body would read; `call` asserts JSON (`299–325`), so a page test needs its own helper. No test drives a browser. The fixture writer is gated behind an environment variable (`1829–1833`). `tests/ui.rs` 7420–7503 is the dialog test.
6. **Device record.** The name would come from the body's `device_name` (`app.rs:3650–3655`, capped at 64 in `core/remote.rs:169`), so a page can set "Safari on iPhone" from its own user agent with no server change; the host never reads `User-Agent` (`read_request` 444–514). The scope is set by the pairing window's radio (`ui/remote.rs:215–224`) and changed in the dialog (`ui/remote.rs:250–255`); the device cannot read it back.

## Spec and design claims this tree contradicts

- `docs/remote-client.md` line 207 says the card's one-line excerpt is "`last_message` from the `Stop` hook on the record, a field of the session's metadata". The tree does not do this. The `Stopped` event carries `last_message` (`src/ports/events.rs:24`, parsed at `src/adapters/hooks.rs:71, 196`), but `core/events.rs:127–135` stores only `last_stop_at` and `pending_at_stop`. `SessionView` has no excerpt. The Mac card computes its excerpt in the UI from the transcript (`ui/cards.rs:176–180`, `558–575`). Storing the text on the record would change a serialized type in `core/model.rs` and need a `SCHEMA_VERSION` bump (CLAUDE.md); a page-side copy of `agent_excerpt` would put logic under the UI, which CLAUDE.md forbids.
- The issue says "revoked" should be said plainly on the next request. The tree gives revoked, unknown and rotated tokens the same 401 (`app.rs:3137–3149`).
- `remote-client.md` §4.3 line 194 and §5 line 306 give the port's pre-pairing surface as `/info` and `/pair`. The page changes that.
