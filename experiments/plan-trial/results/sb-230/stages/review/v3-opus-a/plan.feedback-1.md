1. **The 825-day validity is not met by setting `not_after` alone.** Decision 1, The record and The actions and effects ("`not_after` = now + 825 days minus a day") rest on the premise that `not_after` sets the validity period. Neither the tree nor the facts support that. `make_identity` builds `rcgen::CertificateParams::new(..)` and never sets `not_before` (`src/adapters/remote.rs:102-110`). rcgen 0.14 (`Cargo.lock:4035`, 0.14.10) defaults to `not_before = date_time_ymd(1975, 1, 1)` and `not_after = date_time_ymd(4096, 1, 1)` (https://docs.rs/rcgen/0.14.5/src/rcgen/certificate.rs.html, `impl Default for CertificateParams`). Apple's page (https://support.apple.com/en-us/103769, `facts.md` line 19) says the validity period of 825 days or fewer "is measured using the NotBefore and NotAfter fields", and that the issuance date, which decides whether the post-1 July 2019 rules apply at all, is taken from NotBefore. A reissue that sets only `not_after` has a validity of about 52 years and a 1975 issuance date. So it fails the 825-day rule, and it is outside the scope where the `serverAuth` rule applies. That undercuts the "helps in every branch" premise of Unresolved 1 and 3. The fix: set `not_before` to now minus a small skew (a day), and `not_after` to `not_before` plus at most 825 days. The unit test in The tests ("`certificate_expires` is at most 825 days out") should assert the span `not_after − not_before` ≤ 825 days in the DER, not the expiry alone.

2. **`load_identity` does not refuse a newer file, and nothing writes the bumped version.** The record says "`RemoteFiles::load_identity` (`src/adapters/remote.rs:74`) already refuses a newer file." The tree says otherwise. `load_identity` is `self.load(IDENTITY_FILE)` (`:74-76`), and `load` is a plain `serde_json::from_slice` with no version check (`:55-64`). The only other use of `IDENTITY_SCHEMA_VERSION` is the literal in `make_identity` (`:118`; `git grep IDENTITY_SCHEMA_VERSION`). `schema_version` is a plain field copied from the file (`src/ports/remote.rs:27`). A version-1 identity that gets reissued keeps `schema_version: 1` in memory and is written back as 1 with the new fields, unless the reissue sets it. CLAUDE.md requires readers to accept older versions and the store to refuse to write a newer one. The plan needs three changes: (a) reissue sets `schema_version = IDENTITY_SCHEMA_VERSION`; (b) the version guard is added in `RemoteFiles::load`/`save` for identity, if the plan wants it; (c) drop the "already refuses" premise. Without (b), an older build reads and rewrites a newer file silently. serde ignores the unknown fields, which drops `certificate_names`, and the next bind of the new build then reissues. That is harmless, but it is not what the plan claims.

3. **The `.local` SAN name has no source.** Rehydration and The signals use "`<LocalHostName>.local`", and The UI's dialog relies on the certificate "already cover[ing] both". The tree has no LocalHostName reader: `git grep` finds no `LocalHostName` or `scutil` under `src/`. The tree's one `.local` name is Bonjour's host, `format!("{}.local.", default_server_name())` (`src/adapters/bonjour.rs:41`), and `default_server_name` is `hostname -s` (`src/adapters/remote.rs:304-313`). `hostname -s` is not the LocalHostName in general. A Home Manager discussion shows that with a DHCP-assigned name `hostname -s` returns that name, while `scutil --get LocalHostName` returns the Bonjour name the user chose (https://github.com/nix-community/home-manager/pull/3458; also https://support.getprimo.com/en/articles/useful-scripts on the three separate scutil keys). Query: `macOS scutil LocalHostName vs HostName "hostname -s" Bonjour .local name difference`. No Apple primary source came up. Pick one source and name it. A robust default is to reuse `default_server_name()`, as Bonjour does, so the SAN and the advertised host agree. The alternative is to read LocalHostName behind `cfg(target_os = "macos")`, falling back to that default. Either way the Linux CI arm must compile and not shell out to `scutil`.
