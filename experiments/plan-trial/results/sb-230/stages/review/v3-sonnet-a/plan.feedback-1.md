1. **"`RemoteFiles::load_identity` (`src/adapters/remote.rs:74`) already refuses a newer file" is false, and the `IDENTITY_SCHEMA_VERSION` bump rests on it.** Premise: the plan's "The record" section. Support: nothing. The tree contradicts it. `load_identity` is `self.load(IDENTITY_FILE)` (`src/adapters/remote.rs:74-76`), and `load` (`:55-63`) is a bare `serde_json::from_slice`. A grep for `schema_version` in `src/adapters/remote.rs`, `src/core/remote.rs` and `src/app.rs` finds one use, which writes the constant at `src/adapters/remote.rs:118`. Nothing reads it back. `Identity` (`src/ports/remote.rs:26-42`) has no `deny_unknown_fields`. So the bump to 2 protects nothing: an older build reads a v2 file, ignores the two new fields, and carries on. CLAUDE.md says "the store refuses to write a newer one", and that is the store's `model.rs` path, not `RemoteFiles`. The plan also says an older file "reads with empty names" and treats that as a decision, but it does not say who checks the version. Fix: either add the check (a new refusal in `load_identity`, which is a behaviour change to name in the contract list), or drop the claim and say the bump is a marker only and that `#[serde(default)]` is what makes old files readable. Don't present the refusal as existing.

2. **`<LocalHostName>.local` has no source.** Premise: "Rehydration" lists `<LocalHostName>.local` among the names the certificate answers to, and "the certificate already covers both". Support: nothing in the facts (Unresolved 9 says no query was run) and nothing in the tree. The only host-name code in the tree is `default_server_name`, which runs `hostname -s` (`src/adapters/remote.rs:303-312`). That is the shell host name, not the Bonjour `LocalHostName`, and the two differ on a Mac whose name was edited in Sharing settings. The advertiser takes `identity.server_name` (`src/app.rs:2999`), which can be user-edited. The plan has to say where `certificate_names()` gets the name: a new `scutil --get LocalHostName` call, or the existing `hostname -s`. It also has to say what happens when the name is empty or contains characters illegal in a DNS SAN (rcgen rejects them), because `bind_remote` would fail on that and the port would not come up at all. A robust default is available: put the `.local` SAN in only if the name passes a DNS-label check, and otherwise leave it out and still bind.

3. **A failed reissue in `bind_remote` is not given a default.** Premise: "`bind_remote` (`src/app.rs:2936`) reissues first". Support: nothing says what happens on error. `bind_remote` is the only way the port comes up, and it already returns `Err` for a missing key (`src/app.rs:2950-2955`). If the reissue fails (a SAN rcgen rejects, a write error on `identity.json`, no `local_address()` at all), then as written the remote port, and with it every paired native client, goes down because of an enhancement the browser page needs. State that a reissue failure is logged and the old certificate is served. The plan treats the reissue as "costs nothing if unneeded", which is true only if it cannot break the bind.

4. **The "click-through is the trust step" decision has no fallback if Safari will not proceed, though the plan's claim of working "on either branch" covers only the socket.** Premise: Decision 1 and the Acceptance paragraph ("None of these steps depends on the socket, the cookie or the `.local` name"). Support: `facts.md` Unresolved 1 asks whether the exception covers `fetch` and `wss`. For `wss` the facts have two sources, WebKit bug 41419 and the code-server iPad doc, that say it does not. For `fetch` and the page load itself there is only the Apple page ("websites [may] not load in Safari", `facts.md` Settled, Apple's TLS rules). That is the same page that says the current certificate meets none of the rules. The plan's polling floor covers a lost socket. It does not cover a page that cannot load, or a same-origin `fetch` that the exception does not carry. Step 1 of the acceptance run is exactly that. The reissue is the plan's only mitigation, and Unresolved 2 and 3 (IP SAN, 825 days) leave it unproven. I did not run new searches. The facts record the queries already tried and the plan adds no new evidence. The fix is small and costs no code: say in Decision 1 that if A is unfavourable for the page load itself, the feature does not ship in this cut and the certificate download/profile issue becomes a blocker. Drop "holds on either branch" from the signals section, since the polling claim holds only on the branch where the page and `fetch` work.

5. **"Static paths ... `Connection: close`, so its slot ... is freed as soon as the reply is written" does not follow from the connection loop.** Premise: the "Pool and rate" bullet. Support: `connection` (`src/adapters/remote.rs:770-870`) is a `while let Some(request) = read_request(...)` loop. It frees the pool slot only when the function returns, and nothing in the plan says `respond_static` ends the loop. `respond` writes `Connection: keep-alive` (`:545`), and the loop would go on to the next `read_request` under `IDLE_TIMEOUT`. A header alone frees nothing. The plan's pool test ("four sequential static loads leave the pool free") would pass only if the loop returns. State that `connection` returns `Ok(())` after a static or non-API reply. Also state that the rate check already runs on every request in the loop, so a browser that keeps the connection open and ignores `close` cannot hold a slot.

6. **The `Origin` rule trusts the `Host` header it is meant to check against.** Premise: "Origin when present must equal `https://<Host header>`". Support: nothing in the facts. `facts.md` Settled says only that browsers send `Origin` and a server may validate it (RFC 6455). A page on `https://attacker.example` that DNS-rebinds to the Mac's address sends `Host: attacker.example:<port>` and `Origin: https://attacker.example:<port>`, which satisfy the comparison. It then rides the `SameSite=Strict` cookie only if the cookie is sent to that host, and a cookie is scoped to the host it was set for. So the cookie transport is not exposed. The bearer-transport socket is exposed to nothing, since a page cannot read the token. The check is therefore redundant for the default transport and weak for the cookie, and the plan should not describe it as a hijack defence. Say it compares against the host's own known addresses (`certificate_names` plus loopback) instead of echoing `Host`. That is a stronger check, and the names are already on the record.
