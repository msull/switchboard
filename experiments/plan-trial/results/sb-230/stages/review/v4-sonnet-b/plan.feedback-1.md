1. **Decision 2 rests on Unresolved 5 coming back favourable, and it has no fallback.**
   - The plan builds one transport, the `Secure; HttpOnly; SameSite=Strict` cookie. It drops the `Authorization` bearer path for the browser, drops the subprotocol token, and drops `localStorage`.
   - It says that if the cookie does not come back on a same-origin `fetch`, "the finding goes to the owner as a follow-up and no ... transport is added." The whole page is then dead on arrival.
   - Facts line 46 says to "plan to either transport behind one server-side reader that accepts the bearer header, the cookie and the subprotocol token, and let the first manual run pick". Facts line 57 (Owner D) says "the server accepts all three transports regardless". The plan contradicts both, and cites no tree line against them.
   - Evidence the cookie half is at risk. WebKit bug 276313 reports Safari not sending a session cookie on a self-signed dev certificate after the user accepted the risk: https://bugs.webkit.org/show_bug.cgi?id=276313. WebKit bug 232088 shows Safari refusing `Secure` cookies from contexts it does not treat as secure: https://bugs.webkit.org/show_bug.cgi?id=232088. I searched "Safari self-signed certificate accepted exception Secure cookie Set-Cookie stored not sent". The reports are unconfirmed, but they are exactly the case this plan targets (click-through certificate, IP host), and nothing in the facts settles it.
   - The cookie is the right primary choice. What is missing is a default beside it. Either keep the server-side reader for a second transport (the WebSocket subprotocol token, or a bearer header held in memory only, never `localStorage`) so a failed cookie test does not end the feature, or say plainly that the issue's acceptance depends on the cookie and name that as the owner's risk. The plan does neither.

2. **The `IDENTITY_SCHEMA_VERSION` bump is described, not stated, and the CLAUDE.md migration rule is only half met.**
   - The tree has `IDENTITY_SCHEMA_VERSION = 1` (`src/ports/remote.rs:17`) and nothing reads it back. `grep schema_version` finds only the write at `src/adapters/remote.rs:118`. The plan's "the value ... at implementation time, plus one" is therefore always 2 and should say so.
   - CLAUDE.md asks for a step in a migrate function for a serialized change. The plan argues that `load_identity` is a plain deserialize, and the tree agrees (`src/adapters/remote.rs:74`). The plan should say outright that this is the deliberate exception and that the version is cosmetic. As written, the "Contract additions" list reads as if a migration were pending.

3. **The plan changes a decision in `docs/remote-client.md` §5 (line 312) that the issue may not have asked it to change, and the evidence for the issue's wording is not cited.**
   - §5 says the token is "sent only as a bearer header over the pinned connection". The plan sends it as a cookie. That is an identity and trust-boundary change.
   - The plan amends §5 itself, and the amendment is reasoned (script cannot read the cookie). But it never says the issue asked for it. The facts file only says the server "accepts all three". Cite the issue text that licenses a non-bearer transport, or flag the change as one that needs the owner's explicit approval before it ships.
   - The same applies to §5 line 309, "a relayed request through a substituted certificate fails". The plan weakens this for browsers. It is honest about it, but it is also a binding statement that the plan overrides.
