# Plan: a web control surface on the remote port (issue #230)

One commit. The app runs at every step; the order below is the order to build in. File and line references are to this worktree at 7fe8949. "Facts" is the facts file; a line under Settled is cited as such, a line under Unresolved or For the owner is named where the decision is made, and the default on that decision is the design that works whichever way the answer goes.

## Where this departs from the issue

- **"The page shows the one-line excerpt the card shows."** There is no such field on the wire. `SessionView` (`control/src/lib.rs:637-688`) has `card`, `waiting_reason`, `last_stop_at_ms` and no excerpt; the Stop hook's `last_message` is built at `src/adapters/hooks.rs:196` and the core reads only `pending` (`src/core/events.rs:132`). The plan adds no read model. The list shows the card word, the waiting reason and the age; for waiting sessions only (at most eight) it fetches `last-response` once, unwatched, and shows its first line. This is the headset's method (`client/Sources/SwitchboardUI/BrowserView.swift:149-163`).
- **"The device's scope in the header."** `docs/remote-client.md` §5 says the host answers each later request with the device's scope. It does not: scope leaves the host only in the `/pair` reply (`src/app.rs:3662`), and nothing says it afterwards. A scope changed in the dialog would never reach the page. The plan adds one authenticated read, `GET /api/v1/device`.
- **"'Revoked' said plainly."** `authenticate` (`src/app.rs:3127-3153`) refuses a revoked token and a never-paired one with the same code, `unauthorized`. The plan does not change the code. The page keeps a non-secret marker (`server_id`, `device_id`) in `localStorage`; a 401 with a marker is "revoked", a 401 without one is "not paired".
- **"Any path outside `/api/v1/` is refused."** True, but only on the frame, after the request took an inbox slot (`src/app.rs:3023`). The static paths are answered on the connection thread instead, so a page load costs the frame nothing.
- **§5: "the host refuses a pairing whose `spki_sha256` is not its own, so a relayed request … fails."** That holds for a client that pins the key it talks to. For a browser the `spki_sha256` in the POST comes from the page, and under a relay the page is the impostor's. The key in the URL catches a genuine page reaching a wrong genuine host (a second installation at the address, a rotated key); it does not catch a relay. §5 gets this said in its own words.
- **Facts, Unresolved 8: "the code is single-use, refused after its first attempt."** The tree does less. The window closes on the first *successful* pairing (`src/core/remote.rs:57-61`); a failed attempt counts and the window closes at the third (`:49-56`, `PAIRING_ATTEMPTS`). So a pairing URL that leaks stays valid until it is used, three attempts fail, or five minutes pass. The plan keeps those rules (they are the spec's, §5) and says so in the spec instead of claiming more. The page compares keys before it posts, so a mismatch never counts against the window.
- **Facts, Unresolved 7: "`KeyPair::from_pem` … unverified."** It exists and the tree uses it (`src/adapters/remote.rs:139`, `:146`). Reissuing a certificate over the stored key needs no new key API. The `time` types rcgen's validity fields take are not a direct dependency (`chrono` is, `Cargo.toml:37`); the plan builds the dates with `rcgen::date_time_ymd` from a `chrono` date.
- **Facts, Settled (subprotocol): "the server echoes the token protocol."** The plan echoes a fixed second protocol, `switchboard.v1`, which the page offers beside the token. WHATWG step 11.2 and RFC 6455 §4.1 are met (a protocol came back, and it is one the client sent), and the token is not repeated in a response header.

## The record

No new record kind, and `SCHEMA_VERSION` (`src/core/model.rs:12`, 16 today) and `VIEWS_SCHEMA_VERSION` (`:612`, 7 today) do not move.

A browser is one more `PairedDevice` in `devices.json` (`src/ports/remote.rs:96-107`), a file with no version, written by `Effect::SaveDevices`. Its name is the page's own `device_name` ("Safari on iPhone"), taken by `remote_pair` (`src/app.rs:3606`) and cut to 64 characters in `AppCore::new_device` (`src/core/remote.rs:166`). No `kind` field: the name is enough to tell a browser in the dialog (issue decision 6). Rehydration is unchanged: `IdentityLoaded` puts the devices back and a token is checked by hash on every request.

`identity.json` changes, because a browser checks names and dates the native clients never looked at. Today the certificate has no subjectAltName at all and rcgen's default validity (`make_identity`, `src/adapters/remote.rs:95-127`).

- `Identity` (`src/ports/remote.rs:26-42`) gains `certificate_names: Vec<String>` and `certificate_not_after: Option<SystemTime>`, both `#[serde(default)]`.
- `IDENTITY_SCHEMA_VERSION` (`src/ports/remote.rs:17`, 1 today) becomes the value in that file at implementation time, plus one, since a ticket landing in parallel may take the next number first. The identity loader has no version branch (`src/adapters/remote.rs:74`) and no `store::migrate` step applies: it is not a `model.rs` type. The defaults are the migration; an older build that loads the file and saves it drops the two fields, and the next launch of this build writes them again.
- A certificate made by `make_identity` and by the new `reissue_certificate(identity, key_pem, names, now)` carries: the SANs (`localhost`, `127.0.0.1`, `::1` and `remote::local_address()` when there is one, as `iPAddress`), `serverAuth` EKU, `not_before` now and `not_after` 825 days out, and `is_ca` set explicitly (`BasicConstraints` path length 0), because the saved-file route below needs CA:true (Facts, Settled: code-server's iPad guide; Apple's 825-day and SAN rules). All set explicitly because the rcgen defaults are unverified (Facts, Unresolved 7). No `.local` name: Facts, Settled says it reaches Safari over mDNS but it was not tested on a device, so it is not a SAN.
- The key is reused, so `spki_sha256` and every pairing survive (§5: "a certificate reissued from the same key still verifies"). The reissue happens in `load_identity` (`src/app.rs:2780`), in the branch where the Keychain key matches `identity.spki_sha256`: when `certificate_names` differs from the wanted names, `certificate_not_after` is `None`, or it is under 30 days away. It saves through `services.remote.save_identity` directly, as `make_identity` does at `src/app.rs:2866-2875`, not through an action. That is deliberate: an action would emit `Effect::SaveIdentity`, whose arm rebinds the port when the listen setting differs from `remote_bound`, and `bind_remote` clears `remote_bound` first, so a reissue from inside a bind would recurse. A read-only instance does not reissue (it does not for `make_identity` either).
- A network change while the app runs leaves the old address out of the certificate until the next launch. The browser's exception is per address and lost anyway (Facts, Unresolved 3: treated as lost at each launch). Written into the design status as a known gap.

## The signals

None of the host's signals change; the page speaks the protocol the headset speaks, and the page's one new read is `GET /api/v1/device`. Two additions on the connection:

- **The token on the WebSocket (issue decision 2).** `new WebSocket(url, ["switchboard.v1", token])`. `read_request` (`src/adapters/remote.rs:444`) reads `Sec-WebSocket-Protocol` on an upgrade: when it lists `switchboard.v1` the request carries `subprotocol: Some("switchboard.v1")`, and any other item is the token, which goes into `bearer` when no `Authorization` header gave one. `respond_upgrade` (`:519`) writes `Sec-WebSocket-Protocol: switchboard.v1` when the request offered it (Facts, Settled: a client that offers protocols fails the handshake if none is echoed). The base64url token is a legal `token` value (Facts, Settled: RFC 7230 `tchar`, RFC 6455 §4.2.2). Native clients keep the bearer header. **No cookie is set or read anywhere.** Reasons, each from Facts: cookies are not isolated by port, so every HTTPS service on the Mac would receive a `Secure` cookie (Settled); a `SameSite=Strict` cookie can be missing from a WebSocket in a restored Safari tab (Settled, WebKit 200345 and 232666); whether Chrome and Firefox send it (Unresolved 4) and whether `Secure` works on an IP host (Unresolved 5) are unanswered. The subprotocol route depends on none of them, so O3 (does it survive a Safari restore) changes nothing.
- **Where the token lives on the device.** `localStorage`, per origin, which is readable by any script on the origin; a cookie would not be. The plan's answer is that the only script is `/app.js` under `script-src 'self'`, and the page writes every host string with `textContent`, never `innerHTML`. That is the residual risk and the dialog text does not hide it. The page also stores the non-secret marker (`server_id`, `spki_sha256`, `device_id`).
- **`Origin` on upgrades (Facts, Settled: RFC 6455 §1.3, §4.2.2).** `read_request` also keeps `Origin` and `Host`. `remote_subscribe` (`src/app.rs:2723`) refuses with 403 `bad_origin` an upgrade whose `Origin` is present and is not `https://` plus the request's own `Host`. That accepts the IP, a hostname or loopback, whichever the page was opened by, and a request with no `Origin` (a native client). It runs after `authenticate`, so a stranger learns nothing. POSTs need no check: they need the `Authorization` header, which a cross-site page cannot send without a CORS preflight the host never answers.

## The actions and effects

One pair, for the saved-file route. Facts, Unresolved 1 (does iOS Safari offer a click-through at all) is conflicted, and Settled says a click-through does not carry `wss://` on iOS (WebKit 41419; code-server's guide). A phone that offers no click-through can reach nothing the host serves, so the certificate cannot be offered by the host's own port; it comes from the Mac.

- `AppAction::SaveHostCertificate` → `Effect::WriteHostCertificate { pem: String }`. `app.rs` writes `<data dir>/host-certificate.crt` (public bytes, temp file then rename) and answers with the existing `Effect::Reveal(path)` path so Finder shows it for AirDrop. No result action.
- The reissue in `load_identity` is not an action (above).

## The UI

### The page (`web/index.html`, `web/app.js`, `web/app.css`)

Embedded with `include_str!` through a new `src/adapters/web.rs`, which is pure: `asset(method, path) -> Asset` with the content type and bytes. No build step, no dependency, no framework. Portable to the Linux CI. `Cargo.toml`'s `exclude` (`:91`) lists only `vendor/egui_term`, so `web/` ships.

**Paths and headers (issue decision 4).** `GET /` (`text/html; charset=utf-8`), `GET /app.js` (`text/javascript; charset=utf-8`), `GET /app.css` (`text/css; charset=utf-8`). Any other method on those is 405. Nothing else: the HTML carries `<link rel="icon" href="data:,">` so the browser asks for no favicon, and every other path outside `/api/v1/` still goes to the frame and answers 404 JSON. Every static reply has `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Connection: close`, and
`Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`.
No inline script, no inline style attribute, no external resource. `connect-src 'self'` may not match `wss:` in every Safari; that is covered by the polling fallback below, not by loosening the policy to `wss:`.

**Where they are answered.** On the connection thread in `connection` (`src/adapters/remote.rs:765`), before the rate check and before the frame (§4.1: the frame does core state only). The reply is written with a new `respond_asset` and the connection then sends `close_notify` and ends, so a page load does not hold an unauthenticated slot for the 30-second idle timeout. Nothing logs the request: `refuse` (`src/app.rs:3754`) never logs a query and this path never reaches it, so `/?code=…` is not written anywhere.

**Pools and windows.** Static paths count against the unauthenticated pool of 4 (`MAX_UNAUTHENTICATED`, `:567`) and get a window of their own: `STATIC_PER_MINUTE = 60` beside `PAIR_PER_MINUTE` and `INFO_PER_MINUTE` (`:583-587`), 429 past it, in `Limits::limited` (`:629`). A load is the HTML alone, then the stylesheet and script together, then `/info` on one kept connection: at most three open at once, because each static connection closes on reply. The pool stays at 4. How many connections iOS Safari really opens (Facts, Unresolved 6; O5) is not known; the pool size is a measurement for the owner, not an input to this commit.

**What the page does**, in `app.js`, in this order:

1. First statement: read `location.search` into locals and call `history.replaceState(null, "", location.pathname)`. Nothing else runs before it. Whether a browser has already recorded the URL, or syncs it, is not knowable here (Facts, Unresolved 8; O4). The mitigation is the window's own rules (above), and the dialog says the QR is as sensitive as the code.
2. `GET /api/v1/info`. If a marker exists and its `server_id` or `spki_sha256` differs from `/info`'s: "identity changed, pair again", clear the token, send nothing with it.
3. With `code`, `key` and `id` in the query: refuse if `key` or `id` differs from `/info`'s; otherwise `POST /api/v1/pair {code, device_name, spki_sha256: key}` (body keys as `remote_pair` reads them, `src/app.rs:3626-3645`). `device_name` is built from `navigator.userAgent` and `maxTouchPoints` ("Safari on iPhone", "Chrome on Mac"; an iPad reports as a Mac). Keep the token and the marker.
4. With a token: `GET /api/v1/device` (name, scope), `GET projects`, `GET projects/{id}/sessions` for each, grouped by project, waiting first and marked, each with kind, card word, waiting reason and age. Hidden worker records stay hidden (no `?scope=all`, `src/app.rs:3116`).
5. With neither token nor query: the page shows "Open Remote devices on the Mac, allow pairing, and scan the QR code", and a code field. The field shows the key `/info` presented in the dialog's short form ("Compare with the Key line on the Mac") and posts that key with the typed code: the headset's typed-code path (design status, "Pairing by the typed code"). It is weaker than the URL, because a relay serves both the key and the page, and the page says the owner must compare.
6. Live: open `/api/v1/events` with the subprotocol token; wait for `hello`; snapshot; reconcile by revision as §4.4 steps 1-4 say (a `changed` whose revision is past a snapshot's refetches that resource, one refetch in flight per resource). `changed` for `session`, `sessions`, `waiting`, `projects` refetches the list, which is how a session that starts waiting moves to the top. Opening a session sends `watch` for its `last-response` (Claude Code) or `screen` (anything else), fetches after `watching`, refetches on `changed` and every 30 seconds, and sends `unwatch` on leaving. Only that one key is watched, so the 128-key cap (`WATCH_CAP`, `src/content.rs:42`) is nowhere near; the eight excerpt reads are plain GETs.
7. **Polling is the default, the socket the enhancement** (Facts, Settled: an iOS click-through does not carry `wss://`). If the socket does not reach `hello` in five seconds or closes, the page polls `GET waiting`, the project lists and the open view every five seconds and says "live updates off" in the header. Nothing in steps 1-5 or in the acceptance depends on the socket.
8. Reply box: shown only when `/device` says `control`; `POST sessions/{id}/send {op, text}` with `op` from `crypto.getRandomValues` (Facts, Settled: `randomUUID` is secure-context only, and Unresolved 2 is unanswered, so the fallback is the only path). On a timeout, `GET ops/{op}` before any resend (§4.5). A 403 from `send` refetches `/device`. Re-read every 30 seconds and on a socket close; a close is how a revoke (`revoke_closes_the_devices_socket`, `tests/remote.rs:2892`) shows up at once.
9. A 401 with a marker: "This device was revoked on the Mac. Pair it again." Without one: step 5's text.

Not in the page, per the issue: tickets, the conversation beyond the last response, drafts, dictation, runs, pinned files, `resume`, `trust` and a `prompt_refusal` explanation. A session with `trust_question` or a `prompt_refusal` shows the reason as text and no reply box.

### The pairing window and the dialog (`src/ui/remote.rs`)

- The QR payload (`:160-166`) becomes the URL `https://<host>:<port>/?code=<code>&key=<spki_sha256>&id=<server_id>`, built by a new pure `invite_url(ip, port, server_id, spki_sha256, code)` in `src/core/remote.rs` (an IPv6 address gets brackets). "Copy invite" copies the URL. The JSON form is dropped from the host: nothing needs it (issue decision 3). `PairingInvite.parse` keeps accepting it, so text copied from an earlier build still pairs. With no network address there is no URL, so no QR; the code, key and "no network address" are shown as text, which is what the headset's typed path needs.
- One line in the pairing block, saying what the click-through is: "A browser warns about this certificate because the Mac made it itself. Compare the key the page shows with the Key line here, then continue." This is issue decision 1: **the click-through on the local network is the trust step, said in the dialog.** Why not the host offering the certificate first: a certificate fetched over the connection the browser does not yet trust adds nothing to the key comparison the page already does, and iOS wants a SAN, an EKU, 825 days and CA:true of it (Facts, Settled), all decisions the click-through route does not need. What the click-through does not buy is said in the dialog too: a page an impostor serves is not a genuine page.
- A secondary button, "Save certificate for a phone", dispatching `SaveHostCertificate`, with hover text: "For a device whose browser offers no way past the certificate warning, or for live updates on an iPhone. Send the file to the device, install it and turn on full trust. Trusting it makes that device trust this Mac's key for any site; do it only on your own devices." Which devices need it (O1, O2) is the owner's to answer on a phone; this commit does not depend on the answer.
- §5's rule is amended, not broken: before pairing a non-loopback bind serves `/info`, `/pair` and the three static paths, nothing else.

## The tests

- **`src/adapters/web.rs`**: the embedded HTML references only `/app.js`, `/app.css` and the `data:` icon; every `/api/v1/...` literal in `app.js` matches an arm of `serve_remote` (`src/app.rs:3017`); no `<script>` without `src`, no `style=`, no `on…=` attribute, no `http://` or `https://` in any of the three; `asset("POST", "/")` is a 405; a path outside the three is `None`.
- **`src/adapters/remote.rs`**: `read_request` keeps `Origin`, `Host`; takes the token from `Sec-WebSocket-Protocol` into `bearer` and sets `subprotocol`; `respond_upgrade` echoes `switchboard.v1` only when offered. `reissue_certificate` keeps `spki_sha256` (`spki_sha256_of_cert` before and after), the DER contains the SAN addresses and the `serverAuth` OID, `not_after` is within 825 days.
- **`src/core/tests.rs`**: `invite_url` for an IPv4 and an IPv6 address, and that the code in it is the window's.
- **`src/app.rs` tests with the fakes**: an identity with no `certificate_names` is reissued at `load_identity` with the same `spki_sha256`, the devices kept and one identity save; an identity whose names and expiry are current is not saved again; the missing-key path still clears the devices.
- **`tests/remote.rs`**: `http` (`:245`) returns the headers as well as the body. New tests: the three paths answer 200 unpaired with the content type, CSP, `no-store` and `nosniff`, and the page references only paths the host serves; `GET /?code=ABCD` answers the page and the reply body does not contain the code; an unknown path outside `/api/v1/` is still 404 JSON; `STATIC_PER_MINUTE` answers 429 and leaves `/pair`'s window untouched; static replies close the connection and release the unauthenticated slot (the existing `stalled_strangers_fill_their_own_pool_and_never_a_paired_clients`, `:3226`, is the model). **The pairing flow end to end with the host's own client, the way the CLI does it** (no UI test drives a browser): open a window, build the URL with `invite_url`, parse it back, `GET /info`, refuse a URL whose key differs without posting, `POST /pair`, `GET /device` shows the scope, read `waiting` with the bearer. Then the socket as the page opens it: an upgrade with `Sec-WebSocket-Protocol: switchboard.v1, <token>` and a same-host `Origin` gets 101 and the echo; a foreign `Origin` gets 403 `bad_origin`; a wrong token in the protocol gets 401; after revoke the next request is 401 and the socket closes. The `GET /device` fixture `client/Fixtures/device.json` is written by `write_fixtures` and read in `the_client_fixtures_decode_on_both_sides` (`:1829`). The allowlist test (`:682`) gains `device`.
- **`tests/ui.rs`** (`remote_devices_dialog_opens_pairing_and_revokes_a_device`, `:7424`, is the neighbour): with a window open, the dialog shows the certificate sentence and "Save certificate for a phone", and clicking it dispatches `SaveHostCertificate`; with no network address no QR is drawn and the text says why.
- **Swift** (`client/Tests`): `PairingInvite.parse` takes the URL (IPv4, bracketed IPv6, missing `id` rejected, a non-`https` scheme rejected) and still takes the JSON. `addresses` becomes the URL's `host:port`; check how `Address` parses a bracketed IPv6 before relying on it. `parse` is the only change to `PairingInvite`'s shape-free API, so the eight test files and three other sources that use it (Facts, Settled: 12 files) are untouched. `main.swift`'s usage line reads `pair '<invite url or json>'`.
- **Not tested by CI:** the page's logic (query parse, `replaceState`, revision reconcile, the polling fallback). No JS runner is added; the issue rules out a dependency. The acceptance run below is the check.

## Acceptance (by hand, on a phone)

Open the pairing window with `Control`, scan the QR, continue past the warning, see the sessions; start a session waiting and watch it rise without a reload (by the socket, or within five seconds by polling if the header says live updates are off); send a reply and see it arrive; revoke the phone in the dialog and see "revoked" on its next request. If the phone offers no way past the warning, use "Save certificate for a phone" and repeat. Each step passes with the socket off.

Dev aids: `SWITCHBOARD_DATA_DIR`, `SWITCHBOARD_TMUX_SOCKET` and the script lines `remote-listen lan <port>` and `pairing <code>` already put an instance on the network with a window open; no new `SWITCHBOARD_` variable.
