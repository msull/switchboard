# Facts for issue #230 (browser page on the remote port)

No spike run; worktree left clean. "W" = WebSearch, "F" = WebFetch. Query text is given per claim.

## Settled

- iOS 13+ TLS server certificates need the DNS name in subjectAltName (CN ignored), `serverAuth` EKU, and validity of 825 days or less. The page makes no exemption for user-trusted certificates. Evidence: https://support.apple.com/103769 (F). Query: W "iOS 13 requirements for TLS server certificates subjectAltName 825 days manually trusted certificate".
- On iOS, a click-through does not carry `wss://`. WebKit bug 41419 is open (NEW, modified 2026-01-12); its 2010 report and a 2011 list thread agree that trusting the certificate made `wss` work and the HTTPS acceptance did not; the maintainer prefers logging to a warning sheet. Evidence: https://bugs.webkit.org/show_bug.cgi?id=41419 (F); https://lists.webkit.org/pipermail/webkit-dev/2011-June/017385.html (W). Query: W "WebKit Safari iOS WebSocket wss self-signed certificate exception not applied bug". Agreeing project doc: code-server's iPad guide says Safari blocks WebSockets unless the certificate is installed as a profile, with a matching SAN and `CA:true`, and asks for a domain name rather than an IP: https://github.com/cdr/code-server/blob/v3.7.0/doc/ipad.md (F). Query: W "iOS Safari self-signed certificate warning proceed IP address no subjectAltName wss WebSocket". Two sources agree, so the plan must not rely on a click-through for the socket on iOS.
- `.local` names over mDNS reach Mobile Safari on the same network; unicast `.local` DNS is unreliable. Evidence: code-server guide (above, which suggests a `.local` name); https://discussions.apple.com/thread/6555023 (W). Query: W "Safari iOS mDNS .local hostname resolve Bonjour name from Safari". Not tested on a device.
- Chrome 58+ ignores CN and needs the SAN for hostname matching. Evidence: https://textslashplain.com/2017/03/10/chrome-deprecates-subject-cn-matching/ (W, one Chromium engineer's post: a lead). Query: W "Chrome 58 deprecate common name certificate hostname matching subjectAltName only announcement". Safari agrees: https://bugs.webkit.org/show_bug.cgi?id=158345 (W). The plan builds the SAN regardless.
- A WebSocket that requests a subprotocol must get one back. WHATWG step 11.2 fails the connection if the client sent protocols and the response has no `Sec-WebSocket-Protocol`; RFC 6455 §4.1 fails it if the server names one the client did not send. Evidence: https://websockets.spec.whatwg.org/ (F); https://www.rfc-editor.org/rfc/rfc6455.html (F). Query: W "WebSocket Sec-WebSocket-Protocol browser token subprotocol authentication cookie vs protocol header Safari Chrome" (search gave only lead posts; the standards settle it). The server echoes the token protocol in the 101.
- A base64url token is a legal subprotocol value: RFC 7230 `tchar` includes `-` and `_`, and RFC 6455 §4.2.2 takes the value as a `token`, which may not be empty. Evidence: https://datatracker.ietf.org/doc/html/rfc7230#section-3.2.6 (F); RFC 6455 §4.2.2 (F). Standards query only.
- The server must validate `Origin` on WebSocket upgrades. RFC 6455 §1.3 says Origin protects against unauthorized cross-origin use; §4.2.2 says a server that does not validate it accepts connections from anywhere. Evidence: https://www.rfc-editor.org/rfc/rfc6455.html (F). The fetch covered the first 100,000 characters only; §10.2 was not read.
- Cookies do not isolate by port (RFC 6265 §8.5), so every HTTPS port on one host receives the same cookies; a `Secure` cookie is sent only on secure schemes (§5.4). Evidence: https://www.rfc-editor.org/rfc/rfc6265.html (F). Standards query only.
- For an https origin, `isSecureContext` depends only on the scheme, not on certificate validity: W3C §3.1 step 3 reads "If origin's scheme is either "https" or "wss", return "Potentially Trustworthy"". Evidence: https://www.w3.org/TR/secure-contexts/ (F). Query: W "W3C secure contexts potentially trustworthy origin https certificate error user bypass". What browsers do after a click-through is Unresolved 2.
- `crypto.randomUUID` is secure-context only; `getRandomValues` is not. Evidence: MDN via mirror, https://ligm.univ-eiffel.fr/~forax/MDN/developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID.html (W). Query: W "MDN crypto.randomUUID secure context only available". Generate op ids with `getRandomValues`.
- A `SameSite=Strict` cookie can be missing from a WebSocket in a restored Safari tab. WebKit 200345 (open, last comment 2021-07-08): a Strict cookie is sent on a normal load but only the Lax cookie after "Reopen Last Closed Window". WebKit 232666 (Safari 14/15, RESOLVED CONFIGURATION CHANGED, 2021-11-03): Strict cookies are omitted on WebSockets in restored and history-loaded tabs; the maintainer declined to change old versions. Evidence: https://bugs.webkit.org/show_bug.cgi?id=200345 (F); https://bugs.webkit.org/show_bug.cgi?id=232666 (F). Query: W "Safari SameSite=Strict cookie WebSocket handshake sent same-site WebKit". The socket must not depend on a Strict cookie alone.
- The Stop hook's `last_message` is not on the record. `src/adapters/hooks.rs:196` builds `EventKind::Stopped { last_message, pending }`, `src/ports/events.rs:24` carries it, and the core reads only `pending` (`src/core/events.rs:132`). `SessionView` (`control/src/lib.rs`) has no excerpt field. Tree.
- `WATCH_CAP` is 128 (`src/content.rs:42`). Tree.
- No test under `tests/` builds `RemoteRequest` or `RemoteReply` as a literal. They are built in `src/adapters/remote.rs:506` and `src/app.rs` (`:1664`, `:1679`, `:2365`, `:2371`, `:2376`). Tree.
- `PairingInvite` is used in 12 Swift files: four under `client/Sources` (`switchboard-remote/main.swift`, `SwitchboardUI/BrowserView.swift`, `SwitchboardClientCore/ConnectionManager.swift`, `SwitchboardProtocol/Info.swift`) and eight under `client/Tests`. Tree.

## Unresolved

1. Does iOS Safari offer a click-through for an untrusted self-signed certificate on a bare IP? Kurento says iOS "will outright reject untrusted self-signed certs, instead of showing a security warning" (https://doc-kurento.readthedocs.io/en/stable/knowledge/selfsigned_certs.html, F). A search result describes a "Show Details / Visit this website" path, from a third-party manual rather than Apple (W "iPhone Safari 'This Connection Is Not Private' visit this website self-signed certificate local network iOS 17 Show Details"). Sources conflict and the iOS version is unknown. Build to: no dependency on the click-through. Owner: O1.
2. Click-through on Chrome and Firefox for a no-SAN certificate on an IP, and whether `isSecureContext` is `true` after one. Query: W "window.isSecureContext after proceeding past certificate error interstitial Chrome secure context". Only a 2017 secondhand W3C-list report says yes. Build to: SAN in the certificate, and a `getRandomValues` fallback. Owner: O2.
3. Does a click-through persist across launches? Query: W "Chrome certificate exception proceed anyway persist across browser restart session only self-signed". Chrome: no source. Firefox: a Mozilla bug shows "Permanently store this exception" checked by default (a lead). Build to: treat the exception as lost at each launch.
4. Do Chrome and Firefox send `SameSite=Strict` cookies on same-origin WebSocket handshakes? Only WebKit sources found (Settled above). Build to: the token travels in `Sec-WebSocket-Protocol`, so the socket does not depend on this.
5. Does `Secure` work on an IP-address host in browsers? RFC 6265 §5.4 allows it for a secure scheme; no browser source found. One unanswered Apple Developer Forums post reports a Safari non-resend of an HttpOnly+Secure+SameSite=Strict cookie set on a 101: https://developer.apple.com/forums/thread/104488 (F). Build to: the cookie name carries `server_id`, and nothing depends on the cookie for the socket.
6. Connections per host from iOS Safari. Query: W "Chrome max connections per host HTTP/1.1 six parallel connections Safari WebKit per-host limit". Chrome's 6 comes from secondary sources. The WebKit Mac scheduler source returned 404 to F (https://opensource.apple.com/source/WebKit2/WebKit2-7537.71/NetworkProcess/mac/NetworkResourceLoadSchedulerMac.mm.auto.html). Build to: a small page connection count, and measure (O5).
7. rcgen 0.14 defaults. Query: W "rcgen CertificateParams default not_after 4096 self_signed KeyPair from_pem rcgen 0.14"; F https://docs.rs/rcgen/0.14.10/rcgen/struct.CertificateParams.html. The docs give no defaults, and the crate source could not be read from this session. The tree's "year 4096" comment (`src/adapters/remote.rs:91`) is unverified. Build to: set `not_before`, `not_after` (≤825 days), SANs, `serverAuth` EKU and `is_ca` explicitly. Whether `KeyPair::from_pem` exists for a reissue over the stored key is also unverified; compile it before relying on it.
8. Does `history.replaceState` remove the query from Safari's history menu, "recently closed", or iCloud tab sync, or does the browser record the URL before the script runs (including Chrome and Firefox)? Query: W "history.replaceState URL query removed from Safari history recently closed tabs iCloud tab sync before script runs". Nothing on these. One WebKit report says `replaceState` may add history-menu entries, and a maintainer replied that Safari decides what the menu shows (https://bugs.webkit.org/show_bug.cgi?id=58072, W). Build to: the code is single-use, refused after its first attempt, and expires with the window (five minutes); a leaked URL then grants nothing.

## For the owner

- O1 (Decision 1): On an iPhone, does Safari offer a click-through for the host's certificate on its IP, and does the page then load and fetch? Does a profile with a SAN certificate (CA:true, serverAuth, ≤825 days, full trust enabled) let `wss://` connect? Either branch works if the plan ships the profile download for the socket and falls back to polling `/api/v1/` when the socket fails, so no branch depends on the click-through.
- O2 (Decision 1): Does `window.isSecureContext` read `true` on the device after the click-through? If yes, use `crypto.randomUUID`; if no, use `getRandomValues`. Both work with the fallback.
- O3 (Decision 2): On the device, does a token in `Sec-WebSocket-Protocol` survive reopening Safari and history navigation? The protocol route does not depend on cookies, so it works either way.
- O4 (Decisions 1 and 3): Does the browser keep the pairing URL in history or tab sync after `replaceState`? Either answer is covered by the single-use code and five-minute expiry in Unresolved 8.
- O5 (Decision 4): How many connections does iOS Safari open to one host on a page load, and how long does it keep them? Measure before the pool size is fixed.
