# Plan: a browser page on the remote port (issue #230)

File and line references are to this worktree at 7fe8949. "Facts" is `facts.md`; "Settled", "Unresolved n" and "O n" are its sections and entries.

## Where this departs from the issue

- **"The one-line excerpt the card shows" is not on the wire.** `SessionView` (`control/src/lib.rs:636`) has no excerpt field. The Stop hook's `last_message` is built (`src/adapters/hooks.rs:196`, `src/ports/events.rs:24`) but the core reads only `pending` (`src/core/events.rs:132`); it is not on the record (Facts, Settled). The plan adds no read model. A list row shows `card`, `waiting_reason` and `liveness`. The last response is shown in the session view, one fetch for the open session. The headset's per-session `last-response` fetch is not copied: N fetches and N watches against a cap of 128 (`src/content.rs:42`) would evict the headset's watches.
- **"The device's scope in the header": no endpoint returns it after pairing.** Scope appears only in the `/pair` reply (`src/app.rs:3662`); `info` is unauthenticated, and spec §5 line 316 ("the host answers with the device's scope") does not hold. Plan: an additive authenticated `GET /api/v1/device`, `{device_id, name, scope}`. It is the device's own record, not a read model.
- **"Revoked" cannot be told from "never paired" by the refusal.** `authenticate` (`src/app.rs:3127`) gives code `unauthorized` for both. Plan: no new code. The page keeps a non-secret marker `{server_id, spki_sha256, device_id}` beside its token. After a 401 it reads `/info`: a different `server_id` or key means "identity changed, pair again", the same ones mean "revoked". Key rotation deletes `devices.json` (spec §5), so a rotated host also gives 401, and the key comparison is what separates the two.
- **"Any path outside `/api/v1/` is refused" is true, but late.** The prefix match (`src/app.rs:3023`) runs on the frame after the request has taken inbox space. The static paths are answered on the connection thread, before the inbox, as §4.1 says ("the frame does core state only").
- **§5's sentence "the host refuses a pairing whose `spki_sha256` is not its own, so a relayed request … fails" does not hold for a browser.** A relay forwards `/info` faithfully, and the page's POST body, which feeds `remote_pair`'s check (`src/app.rs:3639`), comes from the impostor's page. The URL's `key` catches a genuine page on the wrong genuine host (a second installation, a rotated key). The spec text is amended to say so.
- **The single-use code is slightly weaker than Facts, Unresolved 8 states.** The window closes at the first successful pairing or the third wrong code (`src/core/remote.rs:51-66`, `PAIRING_ATTEMPTS`), not after the first attempt. A leaked URL is therefore good until the first pairing or five minutes, which is the QR's exposure today. The plan leaves it and says so in the spec.
- **Facts, Unresolved 7 says `KeyPair::from_pem` is unverified; the tree uses it** (`src/adapters/remote.rs:139,146`). A certificate can be reissued over the stored key without changing `spki_sha256`.
- **Facts, Settled's list of `RemoteRequest`/`RemoteReply` literals is mixed up.** The tree has one `RemoteRequest` literal (`src/adapters/remote.rs:506`) and 30 `RemoteReply {` sites. The plan extends `RemoteRequest` and leaves `RemoteReply` alone, so no reply literal changes.
- **Decision 2 is settled the other way from the issue's lead candidate.** Facts, Unresolved 4 and 5 and WebKit 200345/232666 (Settled) mean the socket cannot depend on a cookie, and the token then has to reach the page's script for the subprotocol anyway, so an `HttpOnly` cookie protects nothing. No cookie is set (RFC 6265 §8.5, Settled: cookies do not isolate by port).

## The record

No new record kind and no `model.rs` change. A browser is one more `PairedDevice` (`src/ports/remote.rs:96`) in `devices.json`, which is a bare `Vec` with no schema version. Its name is the page's `device_name` ("Safari on iPhone", from the user agent), cut to 64 characters by `new_device` (`src/core/remote.rs:166`). Scope is chosen in the pairing window as today. No `kind` field: the name is enough, and the dialog already lists and revokes by name.

Versions as they are today: `SCHEMA_VERSION` 16 (`src/core/model.rs:12`) and `VIEWS_SCHEMA_VERSION` 7 (`:612`) do not change. `IDENTITY_SCHEMA_VERSION` is 1 (`src/ports/remote.rs:17`); it bumps to the value there at implementation time, plus one, because a ticket landing in parallel may take the next number first.

`Identity` gains `#[serde(default)] pub names: Vec<String>`, the subjectAltNames the certificate was issued for. Old files read as empty, so no migration step is needed. This is what makes a certificate reissue decidable without parsing the DER. `Identity` is built literally at `src/adapters/remote.rs:117`, `src/core/tests.rs:11769` and `tests/ui.rs:7436`; those three gain the field.

Rehydration is unchanged (`IdentityLoaded`, `src/core/remote.rs:22`). The certificate is reissued at bind time, not on the wire, so a stale page on a device never matters.

**The certificate (Decision 1's mechanics).** `make_identity` today sets no subjectAltName, no EKU and rcgen's default validity (`src/adapters/remote.rs:102`). iOS requires a SAN, `serverAuth` and 825 days or less, and Chrome and Safari ignore CN (Settled). So:

- `make_identity` and a new `reissue_certificate(identity, key_pem, names)` set, explicitly: SANs `localhost`, `127.0.0.1`, `local_address()` (`src/adapters/remote.rs:962`), `<hostname>.local`; EKU `serverAuth`; `not_before` now minus a day; `not_after` 800 days out; `is_ca` as a CA with no path restriction, because the one project doc that installs a certificate on an iPad asks for it (Settled, code-server guide). Facts, Unresolved 7 says rcgen's defaults are unverified; setting each explicitly means the plan does not depend on them.
- `bind_remote` (`src/app.rs:2936`) compares `names` with the current set and the certificate's age (over 700 days) and reissues over the Keychain key when either differs. The key and `spki_sha256` do not change, so pairings and the native pin survive (spec §5: "a certificate reissued from the same key … still verifies").
- The public certificate is also written as DER to `<data dir>/remote-certificate.cer` at bind (the data directory only, never a project directory). This is the owner's way to AirDrop it to a device if the browser offers no click-through (Facts, Unresolved 1; O1).
- Gap, named: an address that changes mid-session leaves the SAN stale until the next bind. A browser then warns again; native clients are unaffected.

## The signals

- **Trust (Decision 1).** Picked: **the click-through is the trust step** for the page and for REST, said in the pairing window. The page's default does not need the socket (below), so it works wherever the browser lets the owner proceed. The enhancement, behind that default, is the certificate: the page footer links `/switchboard.cer` (DER, `application/x-x509-ca-cert`), and the file in the data directory covers a browser that offers no click-through. Why this order: on iOS a click-through does not carry `wss://` (WebKit 41419 and the code-server guide, Settled), so the socket there needs an installed certificate whichever way the page loads. Making the install the *only* path would put a profile install in front of every first visit. Whether iOS Safari offers the click-through at all on a bare IP is Unresolved 1 (O1); the plan neither assumes it nor routes around it beyond the file above.
- **What the `key` in the URL buys:** a genuine page refuses to send the code to a host whose `/info` key differs. It does not authenticate the host to the page; see the departure above. The dialog says: "Your browser will warn about the certificate. Accept only on your own network; the code works once and for five minutes."
- **Token (Decision 2).** Held by the page in `localStorage` under `switchboard:<server_id>`, with the marker above. Origin-scoped, so unlike a cookie it is not sent to other services on the host's other ports (RFC 6265 §8.5, Settled). `fetch` sends `Authorization: Bearer`. The socket is opened as `new WebSocket(url, ["switchboard.v1", token])`. The host takes the token from the subprotocol value that is not `switchboard.v1` when no `Authorization` header is present, and echoes `Sec-WebSocket-Protocol: switchboard.v1` in the 101, which the browser requires (WHATWG step 11.2, RFC 6455 §4.1, Settled). A base64url token is a legal protocol token (RFC 7230 `tchar`, Settled). The token is never in a URL. Native clients send the header and no subprotocol and are unchanged.
  - Cost, said in the spec: any script on the origin can read the token. The CSP below (no inline script, no external resource) is what bounds that.
  - Whether the token survives a browser restart or history navigation is O3; the page treats a missing token as "pair again" and the socket does not depend on a cookie.
- **Origin (Settled, RFC 6455 §4.2.2).** The host rejects, with 403 `origin`, any `/api/v1/` request whose `Origin` header is present and is not `https://<Host header>`. This works for an IP, a `.local` name or loopback without a list. Native clients send no `Origin`. Not a CSRF defence on its own (there is no ambient credential to ride); it is the check the RFC asks for.
- **Live changes.** Default: the page polls `GET waiting` every 4 s and compares the envelope's `revision`; on a change it refetches the list (§4.4's rule: apply replies by revision), and the open session's `last-response` or `screen`. A read of a content key works without a watch. Enhancement: when `new WebSocket` opens, the page sends `watch` for the open session's key only and `unwatch` on leaving it, and the poll slows to 30 s as a heartbeat; on `changed` it fetches, on `resync_required` or close it falls back to the 4 s poll and retries the socket after 30 s. Nothing in the acceptance steps needs the socket: "a session that starts waiting moves to the top" is met by the poll.
- **Op ids** are made with `crypto.getRandomValues`, formatted as a UUID v4. `randomUUID` is secure-context only and whether a click-through counts is Unresolved 2 (O2); `getRandomValues` works either way. On a timeout the page reads `GET ops/{op}` before retrying (§4.5).
- **Static paths (Decision 4).** Exactly `GET /`, `/app.js`, `/app.css`, `/switchboard.cer`. Everything else falls through to the frame, which answers 404 as today; `/favicon.ico` is avoided by `<link rel="icon" href="data:,">`. Query strings are ignored for matching and never logged, so `/?code=…` is not logged (`refuse` logs method and path only, `src/app.rs:3754`; the static arm logs nothing).
  - Headers on the three page files: the right `Content-Type` with `charset=utf-8`; `Cache-Control: no-store` (the files are small and must not outlive an upgrade); `X-Content-Type-Options: nosniff`; `Referrer-Policy: no-referrer`; `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. No inline script or style; the script styles through classes only.
  - Whether `connect-src 'self'` admits `wss://` on Safari is unchecked (nothing in Facts); if it does not, the socket fails and the poll default carries the page, so it is not a gate. The acceptance run records which it was.
  - Pool and rate: statics are answered with `Connection: close`, so a page load frees its slot of the unauthenticated 4 (`MAX_UNAUTHENTICATED`, `src/adapters/remote.rs:567`) at once instead of holding it for `IDLE_TIMEOUT` 30 s. A static window of 60 a minute per listener is added beside `/pair` 6 and `/info` 60 (`Limits::limited`, `:631`), 429 past it. A TLS handshake that fails behind the warning still holds a slot until `HANDSHAKE_TIMEOUT` (5 s). How many parallel connections iOS Safari opens is Unresolved 6 (O5): the pool of 4 stays, and the acceptance run measures it; the number does not decide the design.
  - The page with neither code nor token: "Open the pairing window on the Mac and scan its QR", and a code field that, when submitted, shows the host's short key (from `/info`) for the owner to compare with the dialog's Key line before the code is sent. That is the headset's path (spec §5) in a browser.
- **Spec amendment.** §5 line 306 becomes "Require pairing before anything but `/info`, `/pair` and the page's own four static files, none of which carries session data". The bind rule is unchanged: a non-loopback bind still serves nothing else before pairing.

## The actions and effects

- `AppAction::CertificateReissued { certificate: String, names: Vec<String> }`, handled in `remote_action` (`src/core/remote.rs`) through `update_identity`, so it emits `Effect::SaveIdentity` and the atomic write is the existing path. It is added to the routing arm at `src/core/action.rs:1248`. `bind_remote` dispatches it, then builds the TLS config from the core's identity, so core and file never disagree. No new `Effect`, no new port: the reissue is `remote::` adapter code like `make_identity`.
- `RemotePort::bind` gains a `certificate: Vec<u8>` argument so the connection thread can serve `/switchboard.cer` without the frame; its one caller is `bind_remote` (`src/app.rs:2969`).
- `RemoteRequest` (`src/adapters/remote.rs:360`) gains `host: Option<String>`, `origin: Option<String>` and `protocol_offered: bool`. `read_request` (`:444`) fills them from `host`, `origin` and `sec-websocket-protocol`, and puts the subprotocol token into `bearer` when no `Authorization` header is present. `authenticate` is unchanged. `respond_upgrade` (`:519`) writes the echo when `protocol_offered`.
- A new `src/adapters/web.rs` holds the four assets (`include_str!("../../web/…")` and the certificate bytes) and a `respond_static` that writes the headers above. `connection` (`:763`) checks it before the rate window and the inbox. A new `respond` variant takes extra headers so `respond` itself does not change.
- `serve_remote` (`src/app.rs:3017`) gains the origin check before the router and one arm, `("GET", ["device"])`, after `authenticate`, answering `{device_id, name, scope}` in the envelope. The `/device` path joins the allowlist test.
- No change to `Effect`, `ports/`, or `SessionView`. CI portability: `include_str!` of `web/*` and `rcgen` are the same on Linux.

## The UI

- **The page** (`web/index.html`, `web/app.css`, `web/app.js`; plain JS, no framework, no build step):
  - header: host name, device name, scope (from `/device`), connection state (live / polling);
  - sessions grouped by project (`GET projects`, then `projects/{id}/sessions` once, again only on a revision change), waiting first and marked, each with kind, `card`, `waiting_reason` and `liveness`; worker records hidden (the host already does, `scope=all` is not requested);
  - session view: `last-response` for a Claude Code session, `screen` otherwise; the reply box posts `send` with `{op, text}` only at `control` scope and is absent at `read`; a 403 `scope` refusal switches the view to read and refetches `/device`;
  - hidden in this cut (Owner decision, default: hidden): a reply to a session at the folder-trust question (`trust_question`), `prompt_refusal`, resume;
  - states said plainly: "revoked", "identity changed, pair again", "pairing is not open", "wrong code", and the certificate footer link when the socket fails.
- **Pairing flow in the page:** read `code`, `key`, `id`; `history.replaceState` to `/` before any other work; `GET /info`; compare `spki_sha256` and `server_id` with the URL's; `POST /pair {code, device_name, spki_sha256}` only on a match; store token and marker; render. Any mismatch stops with the plain message and sends nothing.
- **Pairing window (`src/ui/remote.rs:155-206`):** the QR payload becomes `https://<address>:<port>/?code=<code>&key=<spki_sha256>&id=<server_id>`, with an IPv6 address bracketed. "Copy invite" copies that URL. The meta line gains the trust sentence above and the path of `remote-certificate.cer`. The `addresses` JSON is dropped from the QR (Decision 3): the CLI and the headset's paste field take the URL, and the Swift parser still reads the old JSON so a text copied earlier works.
- **Swift:** `PairingInvite.parse` (`client/Sources/SwitchboardProtocol/Info.swift:93`) tries a URL first (`URLComponents`: `code`, `key`, `id`, the host and port become `addresses`), then JSON. `PairingInvite`'s fields do not change, so its eight test files, `ConnectionManager`, `BrowserView` and `switchboard-remote pair '<invite>'` (`main.swift:12`) keep working. The usage text says "the QR's URL or JSON".
- **Docs:** README Layout rows for `web/`, `src/adapters/web.rs` and the new test; the dev-aid paragraph (README l.270-279) changes "Copy invite" to the URL and adds driving the page with `SWITCHBOARD_SCRIPT` `pairing <code>` against a test data dir (no new environment variable). `docs/remote-client.md`: §4.1 bounds (static paths, the static window, `Connection: close`), §4.3 (`/device`, the static table), §5 (the amended lines: before-pairing rule, relayed-request sentence, token transport, QR as URL, Origin, the certificate). `docs/design.md`: a "Browser page" item in the remote status section of "Remote client (2026-10-12)" (l.3107, before "Versioning and updates" at l.3585) listing the known gaps: the stale SAN mid-session, the untested page script, the unresolved facts (O1-O5). `CHANGELOG.md` Unreleased gets one line.

## The tests

- **`tests/remote.rs`** (extend `http`, `:245`, to return headers as well as the body; it keeps only `Content-Length` today):
  - the four static paths answer 200 with the named `Content-Type`, CSP, `Cache-Control: no-store`, `nosniff` and `Connection: close`, and unpaired;
  - the embedded page references only paths the host serves: parse `index.html`, `app.js` and `app.css` for `/…` references and assert each is a static path or under `/api/v1/`;
  - `/?code=…` answers the page, and the log capture holds no query;
  - the static window answers 429 past 60 a minute; a page load does not hold a slot (open four, read each to completion, a fifth connection still gets in), modelled on `stalled_strangers_fill_their_own_pool_and_never_a_paired_clients` (`:3226`);
  - end-to-end pairing as the CLI does it, with the pinned client and the page's exact sequence (`/info`, key compare, `/pair`), then a read with the bearer;
  - a WebSocket offered `["switchboard.v1", token]` is accepted with the echo in the 101 and no `Authorization` header; a wrong token is refused; a native upgrade with a header and no subprotocol is unchanged;
  - `Origin` equal to the host is accepted, a foreign `Origin` gets 403 `origin` on `/pair`, a POST and the upgrade, and an absent one is accepted;
  - `GET /device` returns the scope, follows a scope change in the next request, and is 401 after `RevokeDevice`; `/device` joins `the_allowlist_refuses_everything_else_with_no_side_effect` (`:682`);
  - the certificate: its SANs include the names, EKU is `serverAuth`, validity is at most 825 days, and a reissue keeps `spki_sha256` (so a client pinned before still connects); `bind` reissues when `names` is stale.
- **`src/core/tests.rs`:** `CertificateReissued` emits one `SaveIdentity` with the new certificate and leaves devices and the pairing window alone; no change when the names are equal.
- **`tests/ui.rs:7474-7492`:** the existing "Copy invite" test asserts a JSON object; it now asserts the URL's scheme, code, `key`, `id`, and a bracketed IPv6 address from an injected address.
- **Swift** (`client/Tests/SwitchboardProtocolTests`): URL parse, old JSON parse, IPv6 URL, a URL without `code` refused. Run locally with `swift test`; Linux CI cannot run it, so the plan does not claim CI covers it.
- **Not covered, said so:** the page's JavaScript (the replaceState order, revision reconcile, the poll fallback) has no runner and the issue rules out a dependency. It is checked by hand with `SWITCHBOARD_SCRIPT` `pairing <code>` in a desktop browser, and on a phone for the acceptance.
- **Acceptance, in order, each step independent of the socket:** open the pairing window; scan with a phone; proceed past the certificate warning (or install `remote-certificate.cer` first if the browser offers no click-through, O1); see the sessions; a session that starts waiting moves to the top within a poll; send a reply and watch it arrive; revoke the phone and the page says "revoked" on its next request. Record, without gating anything on them, whether the socket connected (O1, O2), what `isSecureContext` read (O2), whether the token survived reopening (O3), whether the URL stayed in history after `replaceState` (O4) and the connection count (O5).

## Commit message

Serve a browser page on the remote port, paired from a URL that carries the code

## Contract additions

- `Identity.names: Vec<String>` (`#[serde(default)]`), `IDENTITY_SCHEMA_VERSION` bumped to the value at implementation time plus one.
- `AppAction::CertificateReissued { certificate, names }`.
- `RemoteRequest.host`, `RemoteRequest.origin`, `RemoteRequest.protocol_offered` (in `adapters/remote.rs`, not `ports/`).
- `RemotePort::bind` takes `certificate: Vec<u8>`.
- Endpoint `GET /api/v1/device` → `{device_id, name, scope}`; refusal code `origin` (403).
- Static paths `GET /`, `/app.js`, `/app.css`, `/switchboard.cer`, served before pairing.
- WebSocket subprotocol `switchboard.v1` and token-as-subprotocol on the events upgrade.
- The pairing QR and "Copy invite" text are a URL; `PairingInvite.parse` accepts a URL or the old JSON.
- `remote::reissue_certificate`; the certificate now carries SANs, `serverAuth`, an 800-day validity and `is_ca`.
- New files: `web/index.html`, `web/app.css`, `web/app.js`, `src/adapters/web.rs`, `<data dir>/remote-certificate.cer`.
