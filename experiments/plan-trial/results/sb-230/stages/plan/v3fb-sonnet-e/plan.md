# Plan for #230: a browser page on the remote port

Line numbers are as they are in this worktree at 7fe8949. "Settled", "Unresolved N" and "O1–O5" are the sections and items of the facts file. The page is a third speaker of the protocol; the host changes are small and the page is plain HTML, CSS and JS under `web/`.

## Where this departs from the issue

- **"Any path outside `/api/v1/` is refused."** True, but on the frame, after the request took a slot in the 64-deep inbox (`serve_remote`, `src/app.rs:3023`). A stranger's `GET /anything` should not cost the frame. The connection thread answers the three page paths and 404s every other non-API path itself (see the signals).
- **"The one-line excerpt the card shows."** It is not on the wire. `SessionView` (`control/src/lib.rs:636`) has no excerpt, and the Stop hook's `last_message` never reaches the record (Settled: `src/adapters/hooks.rs:196`, `src/ports/events.rs:24`, read only for `pending` at `src/core/events.rs:132`). Making it a field means a record change for a cosmetic line. The plan adds no read model: a card shows the card word and, for a **waiting** session only, the first line of `last-response`, fetched lazily the way the headset's compact card does (`client/Sources/SwitchboardUI/BrowserView.swift:149-163`). The page watches only the open session's one content key, so the 128-key watch set (`WATCH_CAP`, `src/content.rs:42`) is untouched.
- **"The device's scope in the header."** No endpoint returns a device's current scope; `/pair` answers it once and `info` is unauthenticated (`remote_info`, `src/app.rs:3568`). A scope changed in the dialog would be invisible. The plan adds `GET /api/v1/device` (additive).
- **"'Revoked' said plainly."** `authenticate` (`src/app.rs:3127`) refuses an unknown token and a missing token with the same code, `unauthorized`. The plan keeps the code (the Swift client may key on it) and has the page keep a non-secret marker of what it paired with, so a 401 with a marker is "revoked" and a 401 without one is "pair this device".
- **"A click-through is the trust step", and the acceptance's "accept the certificate warning".** Settled: on iOS a click-through does not carry `wss://` (WebKit 41419 and the code-server guide), and iOS 13+ wants a SAN, `serverAuth` and at most 825 days. `make_identity` (`src/adapters/remote.rs:95`) sets no SAN, no EKU, no validity. Unresolved 1 says iOS may offer no click-through on an IP at all. The plan makes the certificate acceptable to a browser (below), offers it for install, and words the acceptance as "once the browser trusts the certificate, by install or by accepting its warning".
- **Decision 2's cookie.** Settled: a `SameSite=Strict` cookie is missing from WebSockets in restored Safari tabs (WebKit 200345, 232666), and cookies are shared by every port on the host (RFC 6265 §8.5). The socket needs a script-supplied credential anyway, so an HttpOnly cookie would protect nothing the script can already read. The plan has no cookie.
- **`docs/remote-client.md` §5, "the host refuses a pairing whose `spki_sha256` is not its own, so a relayed request … fails".** That holds for a native client that checks the key of the connection it is on. A browser page cannot read the certificate it is talking over; it compares the URL's `key` with what `/info` *claims*, and a relay forwards `/info` faithfully and the page's body. What the check catches is a genuine page on the wrong genuine host (a second installation at that address, a rotated key). §5 must say so.
- **The facts file's "the code is single-use, refused after its first attempt" (Unresolved 8).** The tree says: the code is consumed by the first *successful* `/pair` (`AppAction::Paired` closes the window, `src/core/remote.rs:65-68`), and wrong codes or keys count to three (`PairingFailed`, `PAIRING_ATTEMPTS`) inside five minutes (`PAIRING_WINDOW`, `src/core/action.rs:972`). A URL that leaks into history after the phone has paired grants nothing; one that leaks before, for at most five minutes, can still pair. The plan builds to that, and the dialog says so.
- **`crypto.randomUUID` for the op id.** Secure-context only (Settled), and what a click-through does to `isSecureContext` is Unresolved 2 (O2). The page makes ops with `crypto.getRandomValues`, 16 bytes as hex, which the 64-character `op` limit takes (`OP_CAP`).

## The record

No new record kind, and no change to `model.rs` (`SCHEMA_VERSION` is 16 at `src/core/model.rs:12`, `VIEWS_SCHEMA_VERSION` is 7 at `:612`; neither moves) or to `devices.json`, which is an unversioned bare `Vec<PairedDevice>` (`src/adapters/remote.rs:80-86`). A browser is a `PairedDevice` like any other; its name is the page's own `device_name` (`Safari on iPhone`, made from `navigator.userAgent`), cut to 64 characters by `new_device` (`src/core/remote.rs:166`). No `kind` field (Decision 6): the name says what it is, and the dialog already lists, rescopes and revokes by device.

**The identity's certificate changes; its key does not.** `Identity` (`src/ports/remote.rs:26`) gains two fields, both `#[serde(default)]`:

- `cert_names: Vec<String>`: the DNS and IP names in the certificate's SAN.
- `cert_expires: Option<SystemTime>`: the certificate's `not_after`.

`IDENTITY_SCHEMA_VERSION` (1 at `src/ports/remote.rs:17`, used only when `make_identity` stamps a new identity) goes to the value there at implementation time, plus one. `identity.json` is rewritten through `RemoteFiles::save_identity` as today; nothing reads the version to refuse a file, so older files load with empty names and no expiry, which reads as "stale".

A certificate is **reissued over the stored key** by a new `remote::reissue_certificate(identity, key_pem, names, now) -> Result<Identity, String>`, using `rcgen::KeyPair::from_pem`, which the tree already calls (`src/adapters/remote.rs:139,146`). The SPKI hash, `server_id` and `created` are unchanged, so no pairing is invalidated and the native pin (which ignores names and validity) is unaffected. The params are set explicitly, because rcgen's defaults are unverified (Unresolved 7; the "year 4096" comment at `:91` is a claim, not a fact): the SANs, `serverAuth` EKU, `not_before` a day back, `not_after` 800 days out (under the 825 of Settled), and `is_ca` set because the profile route needs `CA:true` (code-server guide, Settled; O1 says the same). If the crate version has `name_constraints`, permit only the SAN names, so an installed certificate cannot vouch for other sites; check it compiles, and if it does not, the dialog's install text says what installing trusts. `make_identity` calls the same params code.

**When it is reissued.** `cert_names` differs from the wanted names (the machine's `<hostname>.local` from `hostname -s`, as `default_server_name` finds it at `:304`, and `local_address()` at `:962`), or fewer than 60 days remain, or the fields are empty. Checked at `bind_remote` (`src/app.rs:2936`) and when a pairing window opens (a match on `AppAction::OpenPairing` in `dispatch_inner`, `:483`, that rebinds when the address left the SAN). Writing `identity.json` is the only write, through the existing atomic path.

**Exported certificate.** `<data dir>/host-certificate.crt`, the public certificate as PEM, is a derived file written on the owner's click and listed in the README's data directory paragraph. It is the one addition on disk.

**On the device.** The page keeps one `localStorage` entry for its origin: the token and a marker `{server_id, spki_sha256, device_id, name}`. The token is readable by any script on the origin; the only script is the host's own, under a CSP with no inline script and no external resource. That is the cost of Decision 2, and the alternative (a cookie) would not have kept the token from the script. The pairing window is still not durable (`src/core/remote.rs:46-73`).

## The signals

The page is served from the connection thread, not the frame (§4.1: "the frame does core state only"; the page needs none). In `connection` (`src/adapters/remote.rs:770`), after `read_request` and before the rate check, `web::route(method, path)` decides:

- `GET /` → `index.html`, `GET /app.js`, `GET /app.css`. Query ignored; it is never logged (`refuse` already logs method and path only, `src/app.rs:3754`, and the asset path never reaches it). `HEAD` and other methods on those paths → 405.
- Any path that is not `/api/v1/…` and not one of the three (`/favicon.ico` included) → 404 `not_found`, answered here. Paths under `/api/v1/` go to the frame as today.
- Headers, one fixed set: `Content-Type` `text/html`, `text/javascript` or `text/css`, each `; charset=utf-8`; `Cache-Control: no-store` (so a page never outlives its host version; the page is 3 small files); `X-Content-Type-Options: nosniff`; `Referrer-Policy: no-referrer` (the first URL carries the code); `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`; and **`Connection: close`**.
- `respond` (`:530`) takes a small `Headers` argument (a slice of name/value pairs) so JSON replies keep their two headers and assets add theirs; `RemoteReply` (`:389`) is unchanged because the frame never answers an asset.

**Pools and windows (Decision 4).** The 4 unauthenticated slots (`MAX_UNAUTHENTICATED`, `:567`) are what an unpaired page load competes for, and iOS Safari's connection count is Unresolved 6 (O5). The default does not depend on it: an asset reply closes its connection, so the slot returns at once instead of idling for 30 s (`IDLE_TIMEOUT`), and a page of three files needs a slot only while a file is in flight. A load never needs more than the parallelism the browser chooses, and a dropped connection is retried by the browser. Static paths get a rate window of their own beside `/pair` and `/info` (`Limits`, `:623`): 120 a minute per listener, 429 past it, via a third `RateWindow`. A paired page's API fetches move their connection to the paired pool on the first authenticated reply, as for any device.

**The new request fields** (`RemoteRequest`, `:360`; built literally only at `:506` and in `src/app.rs`, never in `tests/`, so additions break nothing; it is in `adapters/`, not `ports/`, but is extended additively anyway): `origin: Option<String>`, `host: Option<String>`, `subprotocol: bool`. `read_request` fills them from `Origin`, `Host` and a `Sec-WebSocket-Protocol` that lists `switchboard.v1`.

**The token reaches the socket as a subprotocol (Decision 2).** The page opens `new WebSocket("wss://host/api/v1/events", ["switchboard.v1", "bearer.<token>"])`. On an upgrade request only, `read_request` takes the `bearer.` item as `bearer` when there is no `Authorization` header, so `authenticate` (`:3127`) is untouched. `respond_upgrade` (`:519`) echoes exactly `Sec-WebSocket-Protocol: switchboard.v1`, never the token; a browser fails the handshake without an echo (Settled, WHATWG), and a base64url token is a legal protocol value (Settled, RFC 7230). The native clients keep the bearer header and send no protocol, so they get no echo. A `Sec-WebSocket-Protocol` on a non-upgrade request is ignored. `fetch` carries `Authorization: Bearer` from the same stored token.

**Origin (RFC 6455 §4.2.2, Settled).** In `remote_subscribe` (`:2723`), if the request has an `Origin`, its authority must equal `Host`; otherwise 403 `bad_origin`. A native client sends none and passes. This works for the IP, the `.local` name and loopback with no configured list, which is the owner question in the notes. Other methods need no check: the credential is a header the browser never adds on its own, so a cross-site request carries none.

**Live updates when the socket fails.** Settled says the socket cannot be relied on over a click-through, and a Strict cookie is not in play. So the page's default is polling and the socket is the enhancement: the page polls `GET waiting` and the sessions of projects it shows every 3 s, and skips rendering when `epoch` and `revision` are the same as the last reply. When `new WebSocket` reaches `hello`, it stops polling and reconciles by §4.4 (subscribe, wait for `hello`, snapshot, refetch whatever has an event past its snapshot's revision); when the socket closes or sees `resync_required` it goes back to polling and retries every 15 s. The open session's content is refetched every 3 s while polling and every 30 s with the socket up, as §4.4 asks of a visible content view. The acceptance step "moves to the top without a reload" holds on either path.

**New endpoint.** `GET /api/v1/device` under any paired device: `{device_id, name, scope, server_name}`, handled after `authenticate` in `serve_remote` (`:3017`). It answers the header and is the page's check that it is still paired. `info` lists `device` among its capabilities (`:3580`). It changes nothing on the Swift side, which ignores unknown capabilities and does not call it.

**Pairing from the URL.** The page, in order: read `code`, `key`, `id` from `location.search`; call `history.replaceState(null, "", "/")` before anything else; `GET /api/v1/info`; refuse to go on (and send nothing) if `info.spki_sha256` differs from `key` or `info.server_id` from `id` ("this is not the host whose code was scanned"); otherwise `POST /api/v1/pair {code, spki_sha256: key, device_name}`; store token and marker; fetch `device`. With a stored marker, `/info` is checked against it on every load first: a different key or `server_id` clears the token and shows "identity changed, pair again", with nothing sent. `remote_pair` (`:3606`) is unchanged: it still compares the key and the code itself. What a browser cannot do, and the page does not claim, is check the key of the certificate it is on.

## The actions and effects

- `AppAction::ExportHostCertificate` → `Effect::ExportCertificate(Identity)`. The arm in `run_remote_effect` (`src/app.rs`, beside `SaveIdentity`) calls a new `RemoteStore::write_certificate(&self, pem: &str) -> Result<PathBuf, String>` (real: `RemoteFiles`, atomic write of `host-certificate.crt`; fake: `FakeRemoteStore` records the text and returns a path) and dispatches the existing `AppAction::RevealDocument` (`src/core/action.rs:248`) with the path, so Finder shows the file for AirDrop. Read-only instances refuse, like `save_devices`.
- `AppCore::invite_url(&self, host: IpAddr, port: u16) -> Option<String>`, pure, in `src/core/remote.rs`: `https://<host>:<port>/?code=<code>&key=<spki_sha256>&id=<server_id>`, an IPv6 host in brackets, the code as the window holds it. `None` without an identity or a window. The URL replaces the JSON in the UI; the UI only draws it (`src/ui/remote.rs:155-173` becomes a call).
- Reissue is a function called from `bind_remote` and the `OpenPairing` match, not an action: it is I/O on the key and the file, like `make_identity` at load (`src/app.rs:2860`).
- Swift: `PairingInvite.parse` (`client/Sources/SwitchboardProtocol/Info.swift:114`) tries a URL first (`URLComponents`, `code`, `key`, `id`, `addresses` from the host and port) and JSON second, so a JSON invite and `pair <host:port> <code> <spki>` still work (`client/Sources/switchboard-remote/main.swift:107-125`). Its other callers (`ConnectionManager.swift:474,482`, `BrowserView.swift:106,883`, eight test files) construct the struct and are untouched.

**One QR (Decision 3).** The QR and "Copy invite" carry the URL only. Nothing needs the JSON: the headset pairs from the Bonjour record and a typed code, and its paste field and the CLI go through `parse`.

**Decision 1, picked.** The trust step is **installing the host's certificate on the device first**, said in the dialog, and a click-through is left to work where the browser offers one. Why: the install route works under both answers to O1 and O2 (the page needs no click-through), the iOS socket needs it (Settled), and the SAN, EKU and validity the certificate now carries are what both routes need. The install route rests on Settled (the 825-day and SAN rule) and on O1 for what an iPhone does after the install; that is the enhancement for the socket, and the default (REST polling) does not wait on it. The URL's host is the LAN IP, since a `.local` name reaching Mobile Safari is Settled only as "not tested on a device"; the dialog also offers "Copy link with the .local name" for owners whose phones resolve it, and the certificate carries both names. An installed certificate stops matching when the IP changes; reissue adds the new IP and the owner saves and installs again. §5's rule becomes: no non-loopback bind serves anything before pairing but `/info`, `/pair` and the three page files (which hold no state and no secret).

## The UI

**Host (`src/ui/remote.rs`).** In the pairing block: the QR is made from `invite_url`; the text beside it shows the URL; "Copy invite" copies it; a secondary "Copy link with the .local name"; a secondary "Save certificate…" (dispatches `ExportHostCertificate`) with one meta line: "To open the page in a browser, install this certificate on the device and enable full trust for it, or accept the browser's warning where it offers one. The page can tell it is the host whose code you scanned; it cannot check the certificate itself." The Paired devices table needs no change. Spacing uses `GAP` and `PAD` as the file does.

**The page (`web/index.html`, `app.js`, `app.css`, no framework, no build step).** Embedded by `src/adapters/web.rs` with `include_str!`.

- Header: host name (from `device`), the device's name and scope, a `live` or `polling` word.
- States, each said plainly: *open the pairing window on the Mac and scan its code* (no code, no token; no code-entry form in this cut, since a typed code leaves the page nothing to compare the key with); *this is not the host whose code was scanned*; *identity changed, pair again*; *revoked on the host, pair again* (a 401 with a marker); *pairing closed or the code is wrong* (the `pairing_closed`, `wrong_code` codes); *the host is not answering*.
- List: `projects`, then each project's sessions; the waiting ones first within a project and also gathered in a "Waiting" band at the top, marked with the card word; each card shows kind, state, and the first line of `last-response` for a waiting session.
- Session view: `last-response` for a Claude session (watch key `conversation`), `screen` otherwise; one `watch` frame for the open key, the fetch after `watching` (§4.4), `unwatch` on leaving.
- Reply box: shown only for `control` scope, posts `sessions/{id}/send {op, text}` with a `getRandomValues` op and, on a timeout, asks `ops/{op}` and follows §4.5 (`done`: use it; `interrupted`: show the state, never resubmit; `unknown`: resubmit with the same op). Disabled with the reason shown when the session has `prompt_refusal` or `trust_question`. Resume and the trust button are not on the page in this cut.
- Dispatch tickets, conversation history, drafts, dictation, runs and pinned files stay out, as the issue says.

## The tests

- **Static paths** (`tests/remote.rs`): `http` (`:245`) grows a sibling that returns the headers. The three paths answer 200 with the exact `Content-Type`, CSP, `no-store`, `nosniff`, `no-referrer` and `Connection: close`, and the connection ends after the reply; the answer comes with **no frame polled**, proving the connection thread served it; `GET /?code=X&key=Y&id=Z` answers the same page; `/favicon.ico` and `/api/v2/x` are 404 without the frame; a non-GET is 405; the 121st load in a minute is 429; three stalled strangers (the shape of `stalled_strangers_fill_their_own_pool_and_never_a_paired_clients`, `:3226`) leave a fourth slot that eight sequential page loads pass through.
- **Embedded page references only what the host serves** (`tests/remote.rs`): scan `index.html` for `src`/`href` and `app.js` for `/api/v1/…` string fragments (a `${…}` segment becomes `x`); every non-API reference is one of the three paths, and every API reference, requested with a paired token, answers something other than the allowlist's "not available on this port" refusal (`src/app.rs:3095`); `index.html` has no inline `<script>` or `style=` and names no `http` URL. This is the only check CI makes of the page's source.
- **Token transport** (`subscribe_at`, `:1960`, extended): a subscription with only `Sec-WebSocket-Protocol: switchboard.v1, bearer.<token>` gets a 101 that echoes `switchboard.v1` and not the token; a wrong token is 401 with no 101; the same header on a plain GET is 401; an `Origin` that differs from `Host` is 403 `bad_origin`, a matching one passes, none passes; a header-bearer subscription gets no echo. The existing `revoke_closes_the_devices_socket` (`:2892`) is rerun for a protocol-token subscriber.
- **Pairing end to end as the CLI does it** (`tests/remote.rs`): open a window; build the URL with `invite_url`; split it as the page does; `GET /`, `GET /api/v1/info`, compare key and id, `POST /pair` with the URL's code and key; `GET /api/v1/device` returns the scope and name; raise the scope in the core and the next `device` shows it; a second `/pair` with the same code is refused (`pairing_closed`); revoke and the next `device` is 401 `unauthorized`. A wrong `key` in the body is refused `wrong_key` and counts toward the three.
- **`GET device`**: unpaired refused, paired answers; add `device.json` to `client/Fixtures` (written with `SWITCHBOARD_WRITE_FIXTURES=1`) and the allowlist test (`:682`) lists it. The existing fixtures do not change.
- **UI** (`tests/ui.rs`, beside the existing pairing-window test): the window shows the URL text and the "Save certificate…" and "Copy link with the .local name" buttons; a click on the first dispatches `ExportHostCertificate`.
- **Swift** (`client/Tests`, run with `(cd client && swift test)`, not in CI): `parse` reads a URL, an IPv6 URL, a URL with extra parameters, and still reads the JSON.
- **Not tested by CI:** the page's own logic (query handling, `replaceState`, revision reconcile, the polling fallback), since the tree has no JS runner and the issue rules out a dependency. It is checked by a recorded run on a phone: the acceptance below, with the browser, iOS version, whether a warning was offered, whether the socket reached `hello` or the page stayed polling (O1, O2, O3, O4, O5), and whether `connect-src 'self'` admitted the `wss://` connection, which is not in the facts file. Those answers go in the design status entry.

**Acceptance (by hand, on a phone, with `SWITCHBOARD_SCRIPT` `remote-listen lan <port>` and `pairing <code>` against a test data dir).** Open the pairing window, scan the QR; once the browser trusts the certificate (installed, or its warning accepted), the page lists the sessions with the waiting ones marked and the address bar shows no code; a session that starts waiting moves up within about three seconds without a reload; with `control` scope, a reply sent from the page arrives in the pane; revoke the phone in the dialog and the page says "revoked" on its next request; the pairing window's second use of the same code is refused.
