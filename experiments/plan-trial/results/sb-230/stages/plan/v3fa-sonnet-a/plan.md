# Plan for #230: a web control surface on the remote port

Line numbers are as they are in this worktree at 7fe8949. "Facts" is `inputs/facts.md`; "Settled", "Unresolved" and "For the owner" are its headings. One commit, README and design status updated, the app runs at every step.

## Where this departs from the issue

- **"The one-line excerpt the card shows."** It is not on the wire. `SessionView` (`control/src/lib.rs:636-688`) has no excerpt, and `last_message` reaches the core only as a hook event (`src/ports/events.rs:24`), never as a field of a record or view (Facts, Settled, tree line on `last_message`). The headset fetches `last-response` per session for its compact card. The plan shows the card's word (`card`) and `waiting_reason` on each row and no excerpt. Fetching `last-response` for every listed session would put one watch per session into a set capped at 128 (`src/app.rs:1789-1795`), which can evict the headset's watches (For the owner 9, unmeasured). Adding an excerpt field to `SessionView` is the owner's call and a later change. The row works whichever way that goes.
- **"The device's scope … in the header."** No endpoint returns a device's scope after pairing (`remote_info` is unauthenticated, `src/app.rs:3568-3600`). The page keeps the scope from the `/pair` reply and corrects itself when a `send` is refused with `403 scope` (`src/app.rs:3166-3172`). It goes stale when the owner raises a device's scope in the dialog, until the device re-pairs. For the owner 8 may add an endpoint later; nothing here depends on one.
- **"Revoked said plainly."** `authenticate` gives `unauthorized` both for no token and for an unknown token (`src/app.rs:3125-3153`), so the code cannot tell them apart. The page tells them apart itself: it keeps a non-secret marker (`server_id`, `device_id`, scope, key) beside its token, and a 401 on a request that carried a token is "revoked or forgotten". No host change (For the owner 7: a new code stays an option and the page would not need it).
- **"The `key` in the URL lets a genuine page refuse to send the code."** True only for a genuine page on the wrong genuine host. A page cannot read the certificate it is talking over, so it compares the URL's key with what `/info` claims, and a relay forwards `/info` faithfully. §5's sentence "the host refuses a pairing whose `spki_sha256` is not its own, so a relayed request … fails" (`docs/remote-client.md:309`, the "Pairing verifies the key" bullet) holds for the native clients, whose pin is checked by the TLS stack, and does not hold for a browser: the `spki_sha256` in the `/pair` body is written by whatever page the browser loaded. The plan amends that sentence (below). Trust in the first visit is the owner's check of the certificate, decision 1.
- **"The browser then trusts that certificate for that address."** Not established. The certificate has no subjectAltName at all (`make_identity`, `src/adapters/remote.rs:95-127`) and a `not_after` in the year 4096. Apple's rules for server certificates are a DNS or IP name in the SAN, validity of 825 days at most, and EKU `serverAuth` (Facts, Settled, HT210176), and Chrome requires a SAN (Facts, Settled). Whether iOS Safari lets the owner click through a no-SAN certificate on a bare IP is Unresolved (Facts, Unresolved 1). The plan reissues the certificate with the SANs and limits the browsers ask for (decision 1), so it does not matter which way that answer falls.
- **"Any path outside `/api/v1/` is refused."** True, but on the frame after the request was queued (`src/app.rs:3023`). The page's paths are answered on the connection thread before the queue, so a page load costs the frame nothing (decision 4).
- **"A name from the user agent."** The host reads no `User-Agent` (`read_request`, `src/adapters/remote.rs:444-513`, keeps only the bearer, the upgrade key, the length). The page builds the name itself and sends it as `/pair`'s existing `device_name` (`src/app.rs:3650-3655`). No host change, no `kind` field (decision 6).
- **"The spec forbids the token in a URL."** It is the project's own spec, `docs/remote-client.md:312` (Facts, Settled, tree line), not an external rule. The plan keeps it: the token never appears in a URL.
- **The pairing code in a URL** is new, not a departure, but note what the issue leaves open: whether the URL with the code is recorded in history before `replaceState` runs (Facts, Unresolved). The code is single-use (Facts, Settled; the window closes on `Paired`, `src/core/remote.rs:65-66`), so a recorded URL is dead after the first pairing, and the page removes it as its first statement.

## The record

- **No new record kind, no `model.rs` change.** `SCHEMA_VERSION` (`src/core/model.rs:12`, 16 today) and `VIEWS_SCHEMA_VERSION` (`:612`, 7 today) do not move. A browser is one more `PairedDevice` (`src/ports/remote.rs:96-107`) in `devices.json`, a bare list with no version (`RemoteFiles::load_devices`, `src/adapters/remote.rs:80-86`). Pairing, scope, revoke, rehydration by `IdentityLoaded` and the dialog's list work unchanged.
- **`identity.json` gains two additive fields**, both `#[serde(default)]`, on `Identity` (`src/ports/remote.rs:26-42`):
  - `certificate_names: Vec<String>`: the names and addresses in the certificate's SAN, sorted.
  - `certificate_expires: Option<SystemTime>`: when the certificate stops being valid.
  `IDENTITY_SCHEMA_VERSION` (`src/ports/remote.rs:17`, 1 today) is bumped to the value in that file at implementation time, plus one. A ticket landing in parallel may take the next number first. Readers accept older files (the new fields default to empty and `None`, which reads as "reissue now"); the writer writes the new number.
- **The certificate is reissued over the stored key.** `make_identity` always makes a new key (`:101`); the reissue is the same `self_signed(&key)` call (`:109`) with the key loaded by `KeyPair::from_pem` from the Keychain item (Facts, Settled, tree line on `make_identity`). The SPKI hash is unchanged (§5: the pin is the key, not the certificate), so no pairing, no token and no native client's pin is affected. The new certificate carries: CN as today; SAN `localhost`, `127.0.0.1`, `::1` and the route-chosen address from `remote::local_address()` (`:962-970`); EKU `serverAuth`; `not_before` a day back; `not_after` 800 days out (inside Apple's 825). Facts, Unresolved says whether the Apple rule binds a user-trusted certificate is unknown, so the certificate is issued inside the limits and the answer does not matter. `.local` names are left out: whether iOS Safari resolves them is Unresolved and optional (Facts), and the URL uses the IP.
- **Rehydration.** The certificate is reissued when it is due: `certificate_names` differs from the wanted set, or `certificate_expires` is within 30 days, or it is `None` (every existing install, once, at its first launch on this build). That check is a pure function in `src/core/remote.rs` (`certificate_due(identity, wanted_names, now)`), so it is a core test; the app calls it at launch after `load_identity` and once a second on `Tick` while a pairing window is open, which is when a moved address matters. A key missing from the Keychain still takes the existing path (`src/app.rs:2782-2858`, a new identity, devices cleared); a reissue never runs without a key whose SPKI matches the identity's.
- **The page is not a record.** It is bytes compiled in. On the device the page keeps `{token, server_id, device_id, scope, spki_sha256, server_name}` in `localStorage` under one key. The browser keeps its own certificate decision per host.
- **Decision 2, where the token lives: `localStorage`.** Any script of the origin can read it (Facts, Settled); the CSP below allows only the page's own script and no inline script, so only that script runs. A cookie would hide it from script but rests on whether Safari sends `SameSite=Strict` cookies on a same-origin WebSocket handshake (Facts, Unresolved), so the cookie is not built. Revisit it after a device check; it would be an addition beside the subprotocol, not a replacement.

## The signals

- **The events socket, token as a subprotocol (decision 2).** A browser's `new WebSocket(url, protocols)` takes no headers (Facts, Settled). The page offers `["switchboard.v1", "bearer.<token>"]`. The token is base64url, 43 characters of `A-Za-z0-9-_`, which are valid subprotocol token characters (RFC 6455 §4.1, Facts, Settled). The host must echo exactly one offered value or the browser fails the connection (RFC 6455 §4.2.2, Facts, Settled), so the 101 echoes `Sec-WebSocket-Protocol: switchboard.v1` and never the token. Native clients send the `Authorization` header and no subprotocol, and are unchanged.
  - `read_request` (`src/adapters/remote.rs:444-513`) reads `Sec-WebSocket-Protocol`. On a request that asks to upgrade and has no `Authorization` bearer, an offered `bearer.<token>` becomes `bearer`. Elsewhere it is ignored, so the token cannot be passed as a subprotocol on a plain request. `RemoteRequest` (`:359-372`) gains `echo_protocol: bool` (true when `switchboard.v1` was offered) and `cross_origin: bool` (below). No test builds `RemoteRequest` literally (Facts, Settled), and `RemoteReply` is not touched.
  - `respond_upgrade` (`:519-527`) takes `echo_protocol` and adds the header. The connection thread already clones `upgrade_key` before moving the request (`:797`); it clones the flag the same way.
  - If the page offered `bearer.<token>` and no `switchboard.v1`, the request is not a page's and is answered as it would be without a token.
- **Origin (For the owner 4, RFC 6455 §10.2 "SHOULD verify").** The owner's allowlist is not needed for a default that holds: `read_request` reads `Origin` and `Host`, and `cross_origin` is true when an `Origin` is present and is not `https://` plus the request's own `Host`. The frame answers `403 bad_origin` to a cross-origin request on `/api/v1/` for the upgrade and for any non-GET, logged by path only. Native clients send no `Origin` and are never refused. A page reached by IP, by `localhost` or by loopback matches its own `Host`, so no list of addresses is kept. The owner can still choose a tighter list later.
- **Watch frames and `changed` events, unchanged.** The page speaks §4.4: it opens the socket, waits for `hello {epoch, revision}`, sends `{"type":"watch","resource":{"kind":"conversation"|"screen","id":<record id>}}` (the shape `src/app.rs:1720` reads) for the open session, waits for `watching`, then fetches. Every snapshot's envelope carries `revision` (`envelope`, `src/app.rs:3730-3741`); an event past a snapshot's revision refetches that resource, and `epoch` changing refetches everything. `resync_required` or a close reconnects and resends watches. A visible content view refetches on its own every 30 seconds (§4.4).
- **The page works without the socket.** Whether a click-through covers `wss://` on every browser is Unresolved (Facts), and a CSP `connect-src 'self'` may not cover `wss:` on an older Safari. So listing and reading are REST: if the socket does not open within 5 seconds the page refetches the list every 10 seconds and the open session every 10 seconds, and says "live updates are off". The socket is the enhancement; the acceptance steps' list, view and reply do not depend on it. Only "moves to the top without a reload" does, and it holds on the polling fallback within 10 seconds.
- **No change** to the revision counter, the diff, the content cache, the watch set or its cap.

## The actions and effects

- **Core: one action.** `AppAction::CertificateReissued { identity }` in `src/core/action.rs`: replaces the identity (names and expiry included), emits `Effect::SaveIdentity` (existing). Core test below. `OpenPairing`, `ClosePairing`, `PairingFailed`, `Paired`, `RevokeDevice` are unchanged.
- **Port and adapter.** `ports::RemoteStore` is unchanged. `adapters::remote` gains `reissue_certificate(identity, key_pem, names, now) -> Result<Identity, String>` beside `make_identity`, and `RemotePort::bind_with(addr, tls, certificate_der, wake)`; `bind` (`:667`) calls it with an empty certificate so its callers in `tests/remote.rs` do not change. `Shared` (`:642`) keeps the DER. `adapters/fakes.rs` needs nothing new: no new port.
- **Static pages on the connection thread (decision 4).** A new `src/adapters/web.rs` holds `include_str!("../../web/index.html")`, `app.css`, `app.js` and the table of paths. In `connection` (`:787-833`), before the frame is asked and after the rate check, a `GET` for a path in the table is answered with `respond_with` (the existing `respond` generalized to take a content type and extra headers; `respond` calls it with JSON). This is the §4.1 rule "the frame does core state only" kept: the pages need none. The connection stays in the unauthenticated pool; the page's first `fetch` with its token comes back `authenticated: true` and moves the connection to the paired pool as `:834-849` already does.
- **The paths, exactly.** Only these four, all `GET`.

  | Path | Content-Type |
  |---|---|
  | `/` | `text/html; charset=utf-8` |
  | `/app.js` | `text/javascript; charset=utf-8` |
  | `/app.css` | `text/css; charset=utf-8` |
  | `/host.cer` | `application/x-x509-ca-cert` (the DER; public, 404 when empty) |

  Every one carries `Cache-Control: no-store` (the page is tied to this binary's version, and `no-store` means no ETag logic), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (the page URL carries a code on first load), and `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. No inline script, no inline style, no external resource. `index.html` has `<link rel="icon" href="data:,">` so the browser never asks for `/favicon.ico`. A query string is ignored and, as `refuse` does (`src/app.rs:3754-3772`), never logged; the static arm logs nothing.
- **Pool and rate (For the owner 6).** A page load competes in the pool of 4 unauthenticated connections (`:567-568`), which a browser's parallel connections and a failed handshake behind the warning may fill (Facts, Unresolved: unmeasured on iOS). The default: static paths get a rate window of their own, 120 per minute per listener beside `PAIR_PATH`/`INFO_PATH` in `Limits` (`:583-640`), answered 429 `rate_limited`; the pool is unchanged; the page reconnects on a dropped socket and retries its first `fetch` once after a second. A phone that finds the pool full sees the page's plain "the host is busy, retrying" and the retry, not a dead page. The pool size stays the owner's, with the measurement on a phone.
- **§5's rule, amended** (`docs/remote-client.md:306`): "Require pairing before anything but `/info`, `/pair` and the page's own four files." The four files are public and carry no state; none is served by the frame; an unpaired non-loopback bind serves nothing else.
- **Router.** `serve_remote` (`src/app.rs:3017-3121`) gets one change: the `bad_origin` refusal on `cross_origin`, before the prefix match's `authenticate`. `authenticate` is unchanged, since the subprotocol token arrives as `request.bearer`.
- **The app's certificate refresh** (`src/app.rs`, near `load_identity` at `:2782`): `refresh_certificate` builds the wanted names, asks `certificate_due`, loads the key, calls `reissue_certificate`, dispatches `CertificateReissued`, and calls `bind_remote()` (`:2936`) if the port is listening so the new certificate is served. A rebind drops open connections, the same as a listen change does; it happens only when the certificate is due, at launch or when the address moved under an open pairing window. Paired devices reconnect with the same pin.
- **The pairing URL.** `pub fn invite_url(address: IpAddr, port: u16, server_id: Uuid, spki_sha256: &str, code: &str) -> String` in `src/core/remote.rs`, pure: `https://<address>:<port>/?code=<code>&key=<spki>&id=<server_id>`, an IPv6 address in brackets. Code, key and id are Crockford, hex and UUID characters, so nothing is percent-encoded.
- **Decision 3, one QR.** The QR and "Copy invite" carry the URL only. The JSON `{server_id, spki_sha256, code, addresses}` is dropped from the dialog. Nothing needs it from the dialog: the headset pairs from the Bonjour record and a typed code (`ConnectionManager.lookup`, `pair(_:code:)`), and `switchboard-remote pair <host:port> <code> <spki>` takes three arguments (`main.swift:12-13, 107-125`). What still takes a single text argument is the headset's paste field and `switchboard-remote pair '<invite>'`, so `PairingInvite.parse` (`client/Sources/SwitchboardProtocol/Info.swift:93-116`) tries a URL first (`URLComponents`: scheme `https`, `code`, `key`, `id`; `addresses` is the one `host:port`, IPv6 re-bracketed) and falls back to the JSON, so an old invite still pastes. `PairingInvite`'s fields do not change, and its other users (`ConnectionManager.swift`, `BrowserView.swift`, the test files under `client/Tests`) are untouched. The CLI usage line (`main.swift:12`) reads `pair '<invite url or json>'`.

## The UI

- **The pairing window** (`src/ui/remote.rs:155-215`): the QR encodes `invite_url`. Beside the code, the Key and Address lines stay. A line under them, decision 1: "A phone's browser will warn that the certificate is not trusted. Tap through it, or install `https://<address>:<port>/host.cer` first, and check the Key line against the key the page shows. The page opens only for the address above." Nothing in the line promises which of the two works on a given phone (Facts, Unresolved). With no route-chosen address there is no URL and no QR: the window shows the code and "No network address found." "Copy invite" copies the URL.
- **Decision 1, the trust step.** The dialog says the tap-through is the trust step, and the page shows its comparison of the URL's key and `/info`'s key, which catches a genuine page on a wrong genuine host and does not catch a relay. The certificate download is built beside it, not in front: it is one public path, and the SAN certificate is what both routes need (Facts, For the owner 1 and 2). If a phone refuses the tap-through, the download is the route; if it refuses both, the plan has no further remedy and says so in the design.md gap.
- **The page** (`web/index.html`, `app.css`, `app.js`, plain, no framework, no build step, no dependency):
  - *First statement of `app.js`:* read `location.search`, then `history.replaceState(null, "", location.pathname)`, before anything is awaited.
  - *Pairing:* if the URL had `code`, `key` and `id`: `GET /api/v1/info`; if `spki_sha256` or `server_id` differs from the URL's, say "This is not the host whose code was scanned" and send nothing; otherwise `POST /api/v1/pair {code, device_name, spki_sha256: key}`, store the marker and token, show the sessions. `pairing_closed`, `wrong_code` and `wrong_key` are said as what they are.
  - *No code, no token:* "Open Remote devices on the Mac, choose Allow pairing, and scan the code." No code-entry form: the key could not be checked.
  - *A stored token:* `GET /info` first. A `server_id` that matches with a different key is "identity changed, pair again", nothing is sent, and a "Forget this host" button clears storage. An unknown `server_id` is the same. A 401 on any request that carried the token is "revoked or forgotten by the host, pair again", the socket closes.
  - *Header:* host name, the scope word.
  - *List:* `GET projects`, then `GET projects/{id}/sessions` per project (what the headset does); waiting sessions first within and across projects, marked; each row the session's name, `kind`, `card`, `waiting_reason`. A `changed sessions` or `waiting` event refetches the affected project. Dispatch's worker records are hidden as the API hides them (`scope=all` is not sent).
  - *Session:* `last-response` for a Claude Code session, `screen` otherwise, refreshed on `changed`. A session whose `trust_question` is true shows "answer the folder-trust question on the Mac"; a non-null `prompt_refusal` disables the reply box and shows its text. Resume is not on the page (For the owner, question on `prompt_refusal`: hidden in this cut).
  - *Reply:* the box shows when the stored scope is `control`. It posts `sessions/{id}/send {op, text}`. The op is 32 hex characters from `crypto.getRandomValues`, not `crypto.randomUUID`, which needs a secure context (Facts, Settled) that a clicked-through page may not have (Facts, Unresolved): uniqueness is all an op needs (`OP_CAP` 64, `src/app.rs:4260`). On a timeout the page asks `GET ops/{op}` and never resends blind (§4.5). A `403 scope` hides the box and stores `read`.
  - *Device name:* a small function maps the user-agent string to "Safari on iPhone"; falling back to "Browser".
- Not in this cut: Dispatch tickets and decisions, the conversation beyond the last response, drafts, dictation, runs, pinned files, resume, any off-LAN route (§9 stands).
