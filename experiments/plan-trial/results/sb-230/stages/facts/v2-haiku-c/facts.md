# Issue #230 facts (stage facts-v2-haiku-c)

No spike was run; nothing was committed. Queries are listed under the claims they produced. WebFetch quotes are as the fetch summary returned them.

## Settled

- The WebSocket constructor takes only `url` and optional `protocols`; a script cannot set headers. Evidence: https://websockets.spec.whatwg.org/ (constructor). Queries: "WebSocket constructor cannot set custom headers browser Authorization header workaround cookie SameSite same-origin websocket cookies sent Safari".
- RFC 6750 §2.3: a token in a URI query "SHOULD NOT be used unless it is impossible" to send in the header or body. The issue's "the spec forbids" is overstated. Evidence: https://www.rfc-editor.org/rfc/rfc6750.txt §2.3.
- Browsers always send `Origin` on a WebSocket upgrade ("if the request is coming from a browser client"), so the host can check it. Evidence: RFC 6455 §4.1 and §4.2.2 at https://www.rfc-editor.org/rfc/rfc6455.txt.
- A client that offered subprotocols MUST fail if the server selects one it did not offer; a server that selects none omits the header. The issue's "the server must echo" is not the RFC's rule. Evidence: RFC 6455 §4.1.
- Subprotocol strings are U+0021–U+007E and not separators, so a base64url token fits. Evidence: RFC 6455 §4.1 (reading, not a test).
- Cookies do not isolate by port (a port's service reads another port's cookies on the same host). Evidence: RFC 6265 §8.5, https://www.rfc-editor.org/rfc/rfc6265.txt. A per-`server_id` cookie name stops clashes between Switchboard instances, not other HTTPS services on the Mac.
- A `Secure` cookie is sent only over a secure channel. Evidence: RFC 6265 §4.1.2.5.
- An https origin is potentially trustworthy by scheme alone; the spec does not consider certificate validity. So secure-context APIs apply to a page reached over https, including after a click-through, per the spec. Evidence: https://w3c.github.io/webappsec-secure-contexts/ §3.1. Browser behaviour after a bypass is Unresolved.
- `crypto.randomUUID` is secure-context only; MDN marks it Baseline since March 2022. Evidence: https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID.
- `history.replaceState` replaces the current entry's URL, requires the same origin, and does not load the URL. Evidence: https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState (quotes the HTML spec; the WHATWG History section was not reached).
- Not in the issue: the page URL is sent as `Referer` on same-origin subresource requests under the default policy, which includes the query. `<script src>` and `<link>` load before the page's script runs `replaceState`, so the code reaches the host in `Referer` unless the page response sets `Referrer-Policy: no-referrer`, which omits the header. Evidence: https://www.w3.org/TR/referrer-policy/ §3.1, §3.2, §8.3 (same-origin case inferred from §8.3). The host logs no headers (`src/app.rs:3754`).
- Apple's TLS server rules: RSA ≥2048; the DNS name in the SAN ("names only in the CommonName are no longer trusted"); `id-kp-serverAuth` EKU for certificates issued after 1 July 2019; validity ≤825 days. Evidence: https://support.apple.com/en-us/103769. The current certificate fails the SAN, EKU and validity rules as written. The rule names DNS names, not IP addresses.
- The current certificate has no SAN, CN `Switchboard <server_id>`, and runs to year 4096. `make_identity` uses `CertificateParams::new(Vec::<String>::new())` at `src/adapters/remote.rs:102` with a fresh key at `:101`. rcgen 0.14.10 (`Cargo.lock:4035`) defaults to `not_before` 1975-01-01, `not_after` 4096-01-01, empty SANs. Evidence: https://docs.rs/rcgen/0.14.10/src/rcgen/certificate.rs.html lines 81–107.
- Chrome matches hostnames only against the SAN since Chrome 58, so a SAN-less certificate fails the name check. Evidence: Chromium security-dev "Intent to Remove: Support for commonName matching in certificates", https://groups.google.com/a/chromium.org/g/security-dev/c/IGT2fLJrAeo/m/rYQ83CSdAgAJ, agreeing with https://www.thesslstore.com/blog/security-changes-in-chrome-58/. Queries: "Chrome 58 removes Common Name fallback certificate hostname matching subjectAltName required".
- Safari does not accept a self-signed certificate without a SAN. Evidence: WebKit bug 158345 (open, NEW), comment 6: "couldn't get Chrome or Safari to accept the self-signed server cert without a SAN", https://bugs.webkit.org/show_bug.cgi?id=158345; agrees with Apple's CN rule above.
- Safari has used 6 connections per host since 2009. Evidence: WebKit changeset 42559, "WebCore should use a maximum of 6 connections per host, not 4", https://trac.webkit.org/changeset/42559/webkit. Current Safari: Unresolved. Query: "WebKit maximum connections per host HTTP/1.1 Safari six parallel connections".

## Unresolved

- **Current Safari connection limit.** Only the 2009 commit is primary; blogs say 6. Build line: size the unauthenticated allowance for at least 6, or answer static paths on the connection thread so a page load does not depend on the pool. This is required either way, since 4 is below the known limit.
- **Does a click-through on iOS Safari, Chrome or Firefox also cover `wss://` and `fetch`?** WebKit 41419 (open, 2014) reports a self-signed `wss://` working only after "always trust", https://bugs.webkit.org/show_bug.cgi?id=41419; WebKit 158345 says WebSocket fails under self-signed certificates. Neither says a page-level exception fails for WebSocket. Query: "WebKit Safari self-signed certificate exception applies to WebSocket wss connection fetch same host bug". Build line: do not rely on `wss` after a click-through; the device run decides.
- **Chrome: does a click-through survive a browser restart?** No source found. Queries: "Chrome NET::ERR_CERT_COMMON_NAME_INVALID proceed anyway self-signed certificate per-host bypass lost after restart"; "chromium bug certificate error bypass 'proceed' not persisted across browser restart session-only SSL interstitial allow exception". Build line: the dialog says the browser may ask again.
- **Firefox: scope and persistence of an exception.** Bugzilla 594502 (open; one comment by Rodney Rehm) says an accepted exception covers "schema, hostname, port" only, https://bugzilla.mozilla.org/show_bug.cgi?id=594502. One comment is a lead, not a settle. A search summary of Mozilla support says permanent exceptions are not offered for most sites; the fetched Mozilla article was not the relevant one. Query: "Firefox 'permanently store this exception' self-signed certificate exception persists across restart; Chrome proceed bypass not remembered after restart". Build line: as above.
- **Does Safari send cookies on the WebSocket handshake?** Apple Developer Forums 104488 (2018, no answer) reports Safari did not send `HttpOnly; Secure; SameSite=Strict` cookies on a `wss` reconnect that Chrome and Firefox sent, https://developer.apple.com/forums/thread/104488. WebKit 255524 is about fetch and asset requests, not WebSocket, https://bugs.webkit.org/show_bug.cgi?id=255524. Query: "Safari iOS WebSocket SameSite Strict cookie not sent same-origin wss handshake cookie". Build line: do not depend on the cookie reaching the socket.
- **Does a browser fail a handshake that offered a subprotocol and got none back?** The RFC allows omission. GitHub reports say Chrome fails (akka-http #2042; http4s #1656), not vendor statements. Query: "browser WebSocket handshake Sec-WebSocket-Protocol server did not echo subprotocol connection fails Chrome Safari Firefox". Build line, correct under both readings: the server selects one fixed name the client offered (for example `switchboard.v1`), and the token travels as a second offered value. The token then sits in the upgrade's `Sec-WebSocket-Protocol` header, so the plan must not log upgrade headers.
- **Does iOS apply the 825-day and SAN rules to a manually trusted self-signed leaf?** Apple's page is silent on manual trust. A blog reports trustd rejecting user-trusted leaves over 825 days; an Apple DTS note recommends CA-signed leaves over self-signed ones, https://discussions.apple.com/thread/254725586 and https://www.certkit.io/blog/apple-doesnt-care-who-signed-your-certificate. Queries: "iOS 13 825 day rule does it apply to manually trusted self-signed leaf certificate installed profile 'certificate trust settings' exempt". Build line, correct in both branches: reissue with a DNS SAN, `serverAuth` EKU, ≤825 days, RSA-2048.
- **Does iOS Safari resolve a `.local` name, and does it accept an IP SAN?** Not searched; Apple's rule names DNS only. Build line: the SAN carries both the DNS name and the IP, and the URL uses whichever the device run shows working.
- **Can the certificate be reissued over the stored Keychain key?** The key is stored as PEM in the Keychain (`src/adapters/remote.rs:136`), so a new certificate can keep the SPKI. The rcgen call was not checked against 0.14.10. Build line: reissue with the same key and test that `spki_sha256` is unchanged.
- **Does `replaceState` keep the code out of Safari's history and iCloud tab sync before it runs?** Not researched past MDN. Build line: `Referrer-Policy: no-referrer` on the page; the code is in no link the page makes.

## For the owner

- **Trust route (decision 1).** Click-through or a profile install? The same reissue (DNS SAN, `serverAuth`, ≤825 days, RSA-2048) serves both. The sources do not say which route Safari honours for a self-signed leaf; the device run decides.
- **Device runs, each with an answer that works either way.** (a) After accepting the warning on an iPhone, do `fetch` and `wss://` work? If `wss` fails, the token goes in the subprotocol path. (b) Does an ordinary page load exhaust the unauthenticated pool? If so, static paths answer on the connection thread. (c) Does a cookie reach the socket on Safari? If not, the subprotocol path carries the token. (d) Does the code survive in history or iCloud tab sync? If so, the spec must say the code can persist there.
- **Token transport (decision 2).** Build the subprotocol path (fixed echoed name, token as a second value), which needs no Safari cookie behaviour; add the cookie only if the device run shows it reaches the socket.
- **Origin policy.** Browsers always send `Origin`. The owner names the accepted origins (IP, `.local`, loopback); the plan compares the upgrade's `Origin` against that list and refuses others.
- **URL host (decision 3).** IP, `.local`, or both: both work if the SAN carries both names.
- **Revoked versus never paired (decision 6).** A new refusal code is additive and needs no source; the owner chooses it or a page-side marker.
- **Scope after pairing.** Owner chooses a new authenticated endpoint or accepting a stale `/pair` value; either works.
- **Page with no code and no token.** Owner's choice; no source question.
- **Watch set.** Whether a page watching `conversation` for every session evicts the headset's watches (cap 128) is a load test, not a source question.
