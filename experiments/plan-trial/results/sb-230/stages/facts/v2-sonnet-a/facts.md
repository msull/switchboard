# Facts for #230 (web control surface on the remote port)

No spike was run: every open question that is not answered by a source or the tree needs a real phone, so it goes to the owner. Git status is clean.

## Settled

**The tree**
- `RemoteRequest` (`src/adapters/remote.rs:360-372`) has `method, path, query, body, bearer, upgrade` only. It lives in `adapters/`, not `ports/`, so the CLAUDE.md additivity rule (model.rs, action.rs, ports/) does not cover it. Adding `cookie`, `origin`, `user_agent` fields is free of contract rules. Evidence: grep `RemoteRequest {` finds only the definition; nothing under `tests/` builds one literally. `RemoteReply { status, body, authenticated }` is built literally ~15 times in `src/app.rs` (`:1664`, `:2365`, `:2754`, `:3570`, `:3723`, `:3736`, `:3767`), so new header fields on it mean touching each, or a constructor, or a second reply type for static answers.
- Neither `Origin` nor `Sec-WebSocket-Protocol` is read or written anywhere in `src/adapters/remote.rs` (grep: no matches), so both token transports and any Origin check are new code.
- The Stop hook's `last_message` is carried on the event (`src/ports/events.rs:24`, `src/adapters/hooks.rs:71,196`) but no field in `src/core/` stores it (grep of `src/core/*.rs` minus tests: none), and `SessionView` has no excerpt. The spec's claim (`docs/remote-client.md:207`) that the excerpt is "on the record" is not borne out. Captions are computed in `refresh_captions` (`src/app.rs:1093`). So an excerpt on the wire is a new additive field plus a store, or the page fetches `last-response` per session as the headset does.
- A certificate can be reissued over the same key without moving the pin: SPKI is the pin, not the certificate bytes (`docs/remote-client.md:308,395`). `make_identity` always generates a new key (`src/adapters/remote.rs:101`), but `rcgen::KeyPair::from_pem` is already used (`:139,146`) to read the Keychain key back, so a reissue path over the existing key is code that composes existing calls.
- Watch set cap is 128, least-recently-read evicted, never refused; a read of an evicted key still answers (`docs/remote-client.md:131,254,543`). A page watching many keys degrades the headset's `changed` events only until its next read.
- `PairingInvite` is used by `ConnectionManager.swift`, `BrowserView.swift`, `switchboard-remote/main.swift`, `Info.swift` and 8 test files under `client/Tests` (grep). `addresses` is `[String]` (`Info.swift:98`); URL parsing must produce a one-element list.

**The world**
- A browser WebSocket handshake with offered subprotocols fails unless the server echoes one of them; the server's value is a single token; client values are tokens from U+0021–U+007E minus separators, unique. RFC 6455 §1.9, §4.1, §4.2.2: https://www.rfc-editor.org/rfc/rfc6455#section-4.1 . (Query: none; fetched directly as the standard.) So a token-as-subprotocol design must write `Sec-WebSocket-Protocol` in the 101 (`respond_upgrade`, `:519-527`, does not today), and the token must be base64url-safe.
- Apple's TLS server certificate rules (iOS 13/macOS 10.15): the DNS name must be in SAN (CommonName not trusted); EKU must include serverAuth and validity must be ≤825 days for certificates with NotBefore after 1 July 2019; connections that violate them fail. https://support.apple.com/103769 . Queries: "Apple support iOS trust certificate requirements TLS server certificates SAN 825 days ExtendedKeyUsage". Consequence: the current certificate (no SAN, `CertificateParams::new(vec![])`, `not_after` year 4096, `src/adapters/remote.rs:91-127`) violates all three. The page does not say what applies to a click-through exception versus a manually trusted certificate; the second sentence below does not settle that.
- Chrome 58+ matches hostnames against SAN only, ignoring CN; a certificate without SAN gives `NET::ERR_CERT_COMMON_NAME_INVALID [missing_subjectAltName]`. Sources are vendor support articles that agree (RSA: https://community.securid.com/s/article/Google-Chrome-reports-NET-ERR-CERT-COMMON-NAME-INVALID-due-to-missing-Subject-Alternative-Names-when-accessing-the-RSA-Identity-Router-Single-Sign-On-Portal ; Haivision https://doc.haivision.com/additional-resources/the-common-name-invalid-error). Queries: "Chrome certificate error self-signed missing subjectAltName ERR_CERT_COMMON_NAME_INVALID proceed anyway IP address"; "Chromium net error ERR_CERT_COMMON_NAME_INVALID overridable...". These settle that the error occurs; they do not settle whether it is click-through (see Unresolved).
- Firefox shows no prompt for a failed `wss://` subresource: Mozilla marked bug 1187666 WONTFIX; the page must be visited over HTTPS first and the exception added there, and this works when the server is addressed by IP. https://bugzilla.mozilla.org/show_bug.cgi?id=1187666 (queries: "Firefox WebSocket wss self-signed certificate exception \"Add Exception\" must visit https first then websocket connects"). The page-then-socket order in the issue matches that workaround, same address and port.
- Safari and WebKit: bug 41419 (open since 2010, last modified 2026-01-12) records that WebSocket TLS failure is a hard failure by spec and that Chrome treats the user's acceptance as covering both; its reporter had wss work only after "always trust". https://bugs.webkit.org/show_bug.cgi?id=41419 . Cockpit's documentation states Safari's default iOS WebSocket framework "does not support the WebSocket Secure sessions" with a self-signed or invalid certificate "even when they are manually marked as trusted", and names the workaround Advanced > Experimental Features > "NSURLSession WebSocket". https://cockpit-project.org/running/safari . Queries: "WebSocket self-signed certificate Safari iOS wss connection fails after accepting certificate exception"; "iOS Safari self-signed certificate no subjectAltName IP address ... WebSocket". Two sources agree (WebKit's own tracker, an open bug, plus a shipping project's documented workaround): **on iOS Safari a `wss://` events socket to a self-signed host should be assumed not to work** by default. The page needs a non-WebSocket fallback (poll the revision, §4.4 periodic refetch) to be usable on the issue's own acceptance device.
- `crypto.randomUUID` is available only in secure contexts (MDN). https://developer.mozilla.org/en-US/docs/Web/API/crypto/randomUUID . Whether a click-through self-signed page is a secure context is not settled (see Unresolved). The plan can avoid the question: build the op id from `crypto.getRandomValues`, which MDN says works outside secure contexts.
- Cookie handling: scheme/host/port semantics for a same-origin `wss://` handshake carrying `SameSite=Strict` cookies are shown only for Electron and a Chromium proposal (https://electronjs.org/docs/latest/api/structures/web-socket-options ; https://groups.google.com/a/chromium.org/g/blink-dev/c/qB7DKqxkiaA/m/w0XzGvEyBAAJ). Treated as Unresolved below, not as settled.
- WebSocket handshakes carry no custom headers, so a cookie-based WebSocket is open to cross-site hijacking unless the server checks `Origin` (Include Security: https://blog.includesecurity.com/2025/04/cross-site-websocket-hijacking-exploitation-in-2025/). This is a lead (one blog) plus the standard: a server that authenticates a socket by cookie must check `Origin` there. If the plan uses a cookie, it must add the check.

## Unresolved

Each: what was tried, why it did not settle, the line the plan must build to.

1. **Does a click-through exception work on iOS Safari for a no-SAN, CN-only certificate on a bare IP, and does it apply to `fetch` and `wss://`?** Queries: "iOS Safari self-signed certificate no subjectAltName IP address \"Visit This Website\" WebSocket wss fetch after accepting"; "Safari iOS \"Visit This Website\" certificate exception ...". Found: a ThinLinc bug (https://bugzilla.cendio.com/show_bug.cgi?id=7401) where adding SAN fixed `wss` on iOS 13 (OSStatus -9807); an Apple Community thread that "Visit this Website" can fail; a WebKit comment that neither Chrome nor Safari accepted the no-SAN certificate. All forum or third-party; none current. Does not settle. *Plan builds to:* reissue the certificate over the same key with a SAN for the address the invite names, EKU serverAuth, and validity ≤825 days (or whatever the owner picks, see below), because that satisfies every rule above and is harmless to the pin. If favourable (it worked without), the plan has still lost nothing. If unfavourable, the plan must do it anyway and also keep the polling fallback in item 2. Do not plan on the current certificate.
2. **iOS Safari `wss://` after click-through.** The two agreeing sources above (WebKit bug 41419, Cockpit) say it fails; both are old or secondary for current iOS, and the Apple developer thread found mentions an iOS 18.3.1 regression for a non-browser client. *Plan builds to:* the page treats the socket as optional: on failure it falls back to refetching the visible view and the session list every few seconds against `revision`. If favourable, the plan may drop the fallback to a slower safety refetch. If unfavourable, "moves to the top without a reload" is met by polling.
3. **Chrome/Firefox click-through for a CN-only certificate.** One source (Palo Alto article) says Chrome offers no proceed link for this error; another (RSA) says Advanced shows more. Contradictory, vendor-secondary, not Chromium's own docs. Does not settle. *Plan builds to:* the SAN reissue in item 1, which removes the error class.
4. **Secure context for a click-through page, `Secure` cookie on an IP host, `SameSite=Strict` on a same-origin WebSocket in Safari/Firefox.** Queries: "secure context crypto.randomUUID self-signed certificate accepted ..."; "SameSite=Strict cookie sent on same-origin WebSocket handshake Safari Chrome Firefox; Secure cookie IP address host". Nothing primary found. *Plan builds to:* no use of `crypto.randomUUID`; if the owner picks a cookie, the page must still work when the socket is refused (falls to item 2) and the cookie name carries `server_id`. If favourable, cookie and socket work together. If unfavourable, the cookie still carries REST and polling.
5. **Is the URL with the code recorded in history/tab sync before `replaceState`; does `replaceState` clear the history entry; does the exception persist across launches/IP changes?** Queries: "Safari WebKit history.replaceState URL query removed from history entry ..."; "Safari iOS \"Visit This Website\" certificate exception how long remembered session IP address changes". Only a 2016 blog ("remembered indefinitely", untested on iOS) and unrelated WebKit bugs. Does not settle. *Plan builds to:* treat the code as exposed to the history once, mitigated by the code being single-use and the window closing after five minutes or the first success; state this in the spec text. If the code is not recorded, nothing changes. If it is, the single-use limit is what protects.
6. **`.local` names from iOS Safari.** Query: "iOS Safari .local mDNS hostname resolve Bonjour https self-signed ...". iOS has native mDNS (secondary source: Kurento docs https://doc-kurento.readthedocs.io/en/latest/knowledge/selfsigned_certs.html) and a certificate's name must match the name typed. Not primary. *Plan builds to:* the IP in the URL and in the SAN; a `.local` SAN may be added if the owner confirms.
7. **Static pages versus the pool of 4 and iOS Safari's connection count/idle time.** No search run (no primary source exists for Safari's internals, and this is a measurement on the device). *Plan builds to:* answer static GETs on the connection thread with `Connection: close` and keep them out of the frame, and size nothing on Safari's count; the existing test `stalled_strangers_fill_their_own_pool...` (`tests/remote.rs:3226`) is the model.

## For the owner

Each has an answer for either branch, and the plan can proceed on the stated line either way.

1. **Trust step (decision 1): click-through only, or a downloadable certificate?** Facts: Apple's page does not say what a manually trusted certificate needs beyond the three rules above; iOS gives a `wss://` failure even for manually trusted ones per Cockpit. Click-through: dialog says "this certificate is yours; accept the warning once". Download: adds a `/ca` path and a profile, and the same SAN/EKU/825-day rules. *Works in both:* reissue with SAN/EKU/≤825 days (item 1) and say in the dialog that the click-through is the trust step. The download is additive later.
2. **Token transport (decision 2): cookie or subprotocol?** Facts: both need new request fields and a response header. Subprotocol requires an echo in the 101; the cookie requires an `Origin` check on the upgrade. *Works in both:* host keeps the bearer header; adds `Origin` check (same host and port as the request's `Host`) on the upgrade; the page works without the socket.
3. **One QR or two (decision 3).** Facts: `PairingInvite.parse` can try the URL first and JSON second, so nothing breaks (`Info.swift:93-116`). *Works in both:* URL becomes the QR; the CLI and headset accept both; JSON stays until the owner removes it.
4. **Reissue certificate with SAN: who reissues when the address moves?** *Works in both:* reissue when the pairing window opens and the address is not in the SAN (the key is unchanged, so pins hold). If the owner declines, the page can only be reached after a manual exception per address.
5. **Revoked versus never paired.** `authenticate` gives `unauthorized` for both (`src/app.rs:3125-3153`). *Works in both:* an additive refusal code for "token not known", and a non-secret marker the page keeps in `localStorage`.
6. **Device scope after pairing.** No endpoint returns it. *Works in both:* the page shows the scope from the `/pair` reply; an additive authenticated read can be added if the owner wants staleness removed.
7. **Excerpt.** *Works in both:* the page fetches `last-response` per listed Claude session at first, with a watch budget under 128; an additive `SessionView` excerpt can replace it later.
8. **Device record `kind`.** *Works in both:* the name from the user agent is enough; `kind` is an additive `#[serde(default)]` field in an unversioned file if wanted.
9. **A phone run to accept the issue.** Acceptance ("scan, accept the warning, see sessions, a waiting session moves to the top, send, revoke") needs a real iPhone; nothing here can run it. *Works in both:* the host-client end-to-end test in `tests/remote.rs`, plus a manual run recorded by the owner on iOS Safari to settle Unresolved 1-2.
