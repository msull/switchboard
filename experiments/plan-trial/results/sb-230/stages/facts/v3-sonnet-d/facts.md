# Facts for issue #230 (web control surface)

No spike was run. Every open browser question that a spike could answer needs a real iPhone or iPad, which this session does not have. Those go to the owner. Evidence is current to July 2026 and earlier, as dated per line.

## Settled

**From the tree**

- The hook event carries `last_message` (`src/ports/events.rs:24`, `src/adapters/hooks.rs:71,196`). No stored record or `SessionView` field carries it: `src/core/model.rs`, `src/ports` and `src/adapters` have no other hit, and `control/` has none. The spec says it is "a field of the session's metadata" (`docs/remote-client.md:207`), and the tree does not do that. A card excerpt on the wire needs a new field plus a store of it.
- `RemoteRequest` is defined at `src/adapters/remote.rs:360` and built by literal only in `read_request` (`:506`). `tests/remote.rs` never names it. Adding fields touches one construction site. `RemoteReply` is built literally at about 30 sites in `src/app.rs` (for example `:1664`, `:3723`, `:3736`, `:3767`) and at `src/adapters/remote.rs:829`. Response headers therefore want a constructor or a `Default`, not 30 edits. Both types live in `adapters/` or `app.rs`, not `ports/`, so CLAUDE.md's additivity rule for the shared contract does not name them.
- `make_identity` always generates a new key (`src/adapters/remote.rs:101`). Reissuing a certificate over the old key is possible, since `KeyPair::from_pem` is already used (`:139,146`), but no function does it today.
- `PairingInvite` is used in 9 files under `client/` (`Info.swift`, `main.swift`, `ConnectionManager.swift`, `BrowserView.swift`, and the tests). `addresses` is a `[String]` (`Info.swift:98`).
- The watch set is capped at 128 keys for the whole port, with silent LRU eviction (`docs/remote-client.md:131,254`). A page watching one key per listed session shares that cap with the headset. An evicted key still reads correctly. It loses `changed` until the next read, and the spec says the client's periodic refetch covers this (`:254`).

**From outside the tree**

1. A WebSocket subprotocol offer needs an echo. RFC 6455 §4.1: a client MUST fail the connection if the response names a subprotocol that was not offered. The response may omit the header, and then the subprotocol in use is null. Offered values are non-empty tokens in U+0021..U+007E excluding separators, so base64url is allowed. Evidence: https://www.rfc-editor.org/rfc/rfc6455.html (fetched). Queries: "WebSocket handshake Sec-WebSocket-Protocol server must echo subprotocol browser fails connection RFC 6455 token characters". The same search turned up secondary reports that browsers close the socket when the server sends no echo for an offered list (W3C bug 23576). Their wording conflicts with the RFC's "may omit". The plan should echo the chosen value, which is correct under both readings.
2. A cookie with `Secure` is sent only on `https:` requests. `HttpOnly` hides the cookie from script but still sends it on `fetch`. `SameSite=Strict` sends it only on same-site requests. A `__Host-` cookie needs `Secure`, `Path=/` and no `Domain`. Evidence: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie (fetched). Queries: "SameSite=Strict cookie sent WebSocket handshake same-origin; Secure cookie IP address host".
3. Cookies are scoped by host, not port. The `__Host-` prefix does not narrow that. It only forbids `Domain`, so a cookie reaches every port of the host. This is the same MDN page as line 2.
4. A WebSocket handshake carries `Origin`, and the server must validate it. The protocol does not check it, so a cookie-authenticated socket without an Origin check is open to cross-site hijacking. Evidence: https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/11-Client-side_Testing/10-Testing_WebSockets (OWASP, via search result). Query: "WebSocket Origin header not enforced server must validate cross-site WebSocket hijacking...". Header-token auth (a `Sec-WebSocket-Protocol` value) is not sent automatically by the browser, so it is not exposed to this attack.
5. A secure context is defined by the URL scheme (`https`, `wss`, `file`, or loopback). MDN does not mention certificate errors. Evidence: https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts (fetched). For `crypto.randomUUID`, the plan may use it on an https page, but behaviour after a click-through is not stated by the standard. Service workers are known to be refused by Chrome on certificate errors (https://bugzilla.mozilla.org/show_bug.cgi?id=1162772), so the plan must not use one. A fallback for the op id (random bytes from `crypto.getRandomValues`, formatted as a UUID) removes the dependency. See Unresolved 3 for the unsettled part.
6. Apple's rule for trusted TLS server certificates (certificates issued after 1 July 2019): the DNS name must be in the subjectAltName (CommonName is ignored), EKU `serverAuth` is required, validity at most 825 days. Evidence: https://support.apple.com/103769 (fetched). The page says nothing about user-added roots. The current certificate has no SAN, no explicit EKU and a year-4096 `not_after` (`src/adapters/remote.rs:102-110`, per the investigation). It meets none of the three. Query: "Apple support TLS server certificates requirements iOS 13 macOS 10.15 825 days subjectAltName user-added root CA not affected".
7. WebKit has an open bug since 2010 (https://bugs.webkit.org/show_bug.cgi?id=41419, status NEW, last modified 2026-01-12) that `wss://` to a self-signed server fails. In that bug, the connection worked only after Safari was set to always trust the certificate, and WebKit declined to add a bypass for WebSocket on the grounds that the spec requires failing when verification fails. A second open bug (https://bugs.webkit.org/show_bug.cgi?id=158345, status NEW, last comment July 2021) records that a normal page load must come first with the certificate accepted, and that a fuller fix would move WebSocket onto `NSURLSession`; an experimental feature for that exists. Both bugs are open with agreeing reports, which settles that the behaviour exists and is unfixed. It does not tell us what current iOS does, see Unresolved 1. Queries: "Safari WebSocket wss self-signed certificate fails even after accepting certificate exception"; "WebKit WebSocket wss does not use certificate exception accepted in Safari self-signed...".
8. Apple's `.local` rule: all Bonjour operations, including resolving a `.local` name, need local network access in native apps (https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy). That is about native APIs. It does not tell us what Safari does with a `.local` URL, see Unresolved 6.

## Unresolved

Each item says what to build to, favourable or not.

1. **Does iOS Safari give the owner a way past this certificate, and does a click-through cover `wss://`?** Tried: the queries under Settled 7, plus "Safari iOS self-signed certificate no subjectAltName IP address 'visit this website' proceed WebSocket wss fetch exception" and "iOS Safari 'This Connection Is Not Private' 'Show Details' 'visit this website'". Findings: forum posts describe "Show Details, visit this website" working on a router certificate, but also failing on iOS 26 (Apple Community thread, January 2026). Kurento's docs say iOS Safari rejects untrusted self-signed certificates with no way to proceed (https://doc-kurento.readthedocs.io/en/stable/knowledge/selfsigned_certs.html). Those are not primary sources and they disagree. The WebKit bugs are old and do not cover iOS 26. No vendor text covers the SAN-less IP case. **Build to:** if the click-through covers `fetch` and `wss`, the plan adds nothing. If it does not (the likelier reading of the two open bugs), the plan must still (a) issue a certificate with a SAN for the address, EKU `serverAuth` and validity of 825 days or less, over the same key so the SPKI pin holds, and (b) make the page work without a WebSocket: poll `/api/v1/` with a revision-based refetch, and treat the socket as an upgrade. The acceptance line "moves to the top without a reload" is then met by polling.
2. **Does Chrome, Firefox or macOS Safari let the user proceed past a SAN-less certificate on an IP?** Tried: "Chrome self-signed certificate IP address without subjectAltName IP ERR_CERT_COMMON_NAME_INVALID proceed unsafe still available". Chrome ignores CommonName (since 58, per several vendor KB articles); the sources disagree on whether "Proceed" is then offered, and none test a current release. **Build to:** the same certificate as line 1(a), with the IP in the SAN, so the name error does not arise. A bypass is not needed on this path.
3. **Does a click-through page count as a secure context, and does it keep `Secure` cookies and `SameSite`?** Tried: "self-signed certificate accepted browser secure context crypto.randomUUID certificate error isSecureContext true", "Chrome certificate error proceed unsafe page isSecureContext service worker...". The standard keys on the scheme; no source tests a bypassed page. **Build to:** feature-detect. Make the op id with `getRandomValues` (no `randomUUID` dependency). If cookies are the token transport, the plan needs the Bearer/subprotocol path as the fallback the page uses when the cookie is not stored, so the plan cannot rest on cookies alone.
4. **Does Safari send a `SameSite=Strict` cookie on a same-origin `new WebSocket()`?** Tried: the Settled 2 query. An Apple forum thread (https://developer.apple.com/forums/thread/104488) reports Safari not resending an HttpOnly/Secure/Strict cookie on a second `wss` connection; WebKit bug 232666 says Strict cookies were missing over WebSocket in restored tabs in Safari 14 and 15, "seems fixed in 15.1". These are reports, not a vendor statement for current iOS. **Build to:** favourable, the cookie works; unfavourable, the page sends the token as a `Sec-WebSocket-Protocol` value (the host echoes it, per Settled 1). Plan for the header form to be accepted in both cases (it is also what the native clients' bearer path maps to).
5. **Does `history.replaceState` remove the query from Safari's stored history, tab list and iCloud tab sync?** Tried: "history.replaceState remove query string from browser history entry URL sensitive token Safari history records initial URL". Found only patterns; one source says replaceState "doesn't prevent the creation of a new entry in the global browser history". The HTML standard says it rewrites the current entry, but no source covers when a browser records the first URL. The code is in the QR URL, so the first navigation records it before any script runs. **Build to:** make the code single-use and short-lived (the pairing window already closes after five minutes or three wrong codes, `src/core/remote.rs:46-73`). A code that stays in history is then harmless once the window closes or the code is spent. The plan must state that in the spec rather than claim the history is clean.
6. **Does a `.local` name resolve from iOS Safari?** Tried: "Safari iOS .local mDNS hostname Bonjour resolves in Safari browser https local network permission". Only native-API sources. **Build to:** the IP as the URL host (what `local_address()` returns today). If the owner later confirms `.local` works, it can be an additional address; nothing in the plan waits on it.
7. **How many parallel connections Safari opens per host, and how long it keeps them.** Tried none beyond the above; not searched for separately. **Build to:** the pool of 4 must not be the page's budget. Serve the page's files with `Connection: close`, or have the page's total unauthenticated requests before pairing be few (one HTML file with inline-free CSS and JS is three requests). The plan can add a test with 6 parallel requests in `tests/remote.rs` following `stalled_strangers_fill_their_own_pool_and_never_a_paired_clients` (`:3226`).
8. **Does an 825-day limit apply to a certificate under a user-trusted root or a directly trusted self-signed certificate on iOS?** Tried: "Apple 825 days limit applies to user-installed trusted root CA certificates iOS exempt". Apple's page is silent (Settled 6). The 398-day page says user-added roots are exempt, and one forum poster reports the 825-day limit enforced anyway. **Build to:** at most 825 days of validity either way, and the plan names the reissue as part of the address-change story.

## For the owner

Each needs a device. The plan cannot wait on them, and the branch given works in both cases.

1. **On an iPhone, with the current certificate: can the owner proceed past the warning, does the page load, do `fetch` and `new WebSocket` both work afterwards?** Favourable: no certificate work is required for iOS, only for Chrome (Unresolved 2). Unfavourable: the SAN certificate and the polling fallback (Unresolved 1). The plan builds the SAN certificate and the polling fallback regardless, so both outcomes work.
2. **Does the same hold after the SAN certificate is installed (same key)?** Favourable: the socket works. Unfavourable: the page polls. Same build as above.
3. **After the owner accepts the warning, does the browser still trust it after closing the tab, after a relaunch, and after the host's IP changes?** I found no source. Favourable: the click-through is a once-per-address step. Unfavourable: the owner sees the warning on each launch; the dialog says so. The plan includes that sentence either way.
4. **Does the QR code, scanned with the iOS camera, appear in Safari history or iCloud tabs after the page loads?** Favourable: nothing extra. Unfavourable: the code in history is spent or expired by then (Unresolved 5). The plan makes the code single-use in both cases.
