# Facts for #230 (browser page on the remote port)

No spike was run: every question the plan turns on is either settled by a source or needs a device (goes to the owner). Searched 2026-10-22. Design choices from the investigation's Open questions marked [owner] are the planner's and are not restated here.

## Settled

### The tree

- `RemoteRequest` is constructed only by the listener (`src/adapters/remote.rs:360-374`, `impl` at `:374`). `tests/` never builds one (grep `RemoteRequest` in `tests/`: no hits), so adding `cookie`/`origin`/`user_agent` fields touches only the adapter. It lives in `adapters/`, outside the CLAUDE.md additivity rule for `model.rs`, `action.rs` and `ports/`.
- `RemoteReply { status, body, authenticated }` is built literally at about 12 sites in `src/app.rs` (`:1664, 1679, 2365, 2371, 2376, 2754, 3570, 3723, 3736, 3767`) and by none in `tests/`. A header field on it needs a `..Default`/constructor or an edit at each site; `envelope`/`envelope_at` (`:3717-3736`) are the funnels.
- The card excerpt exists on the record: the `Stop` hook's `last_message` is parsed at `src/ports/events.rs:24`, carried through `src/adapters/hooks.rs:71,196`, and written by `src/bin/switchboard-hook.rs:37` (from `last_assistant_message`). The spec calls it the card's excerpt (`docs/remote-client.md:207`). It is not in `control/src/lib.rs` `SessionView`, so putting it on the wire is an additive field there plus fixtures on both sides. Fetching `last-response` per session is the alternative.
- A reissued certificate over the same key keeps `spki_sha256`: the key is read from the Keychain PEM with `rcgen::KeyPair::from_pem` (`src/adapters/remote.rs:139,146`), and the hash is of the key's SPKI (`:105`). `make_identity` (`:95-127`) always generates a new key today, so reissue needs a new function that takes the PEM. It writes `identity.json` through the existing atomic save. The certificate has no SAN and no EKU (`:101-107`).
- Swift `PairingInvite` is used in `ConnectionManager.swift`, `BrowserView.swift`, `switchboard-remote/main.swift` and 8 test files (list: `grep -rl PairingInvite client`). `addresses` is a list in `KnownServer.swift:14` and `ConnectionManager.swift:441-483`. `main.swift:120` builds `addresses: [rest[0]]`, so the `host:port code spki` form never needs the list to have more than one entry.
- `authenticate` returns the same code `unauthorized` for no token and for an unknown token (`src/app.rs:3125-3153`), so the page cannot tell revoked from never-paired by code. No endpoint returns the device's current scope (`remote_info`, `:3568-3600`, is unauthenticated). Both are from the investigation's reading; I re-read neither.

### The world

- **A page over `https` is a secure context by scheme.** MDN Secure Contexts: "Documents are secure contexts when their resources are delivered over an HTTPS connection" (https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts). The page says nothing about certificate trust, so whether a click-through exception changes it is not documented. Query: "crypto.randomUUID secure context self-signed certificate https IP address isSecureContext MDN". Plan: do not depend on `crypto.randomUUID`; build the op id from `crypto.getRandomValues` or fall back, and the page can test `isSecureContext` at runtime. (`crypto.randomUUID` is secure-context-only per https://developer.mozilla.org/en-US/docs/Web/API/crypto/randomUUID.)
- **A subprotocol token needs the server to echo it.** WHATWG WebSocket standard: if the client gave protocols and the response carries no valid `Sec-WebSocket-Protocol`, the browser fails the connection (https://websockets.spec.whatwg.org/, handshake response processing). A server echoing one the client did not offer also fails (RFC 6455). `respond_upgrade` (`src/adapters/remote.rs:519-527`) writes none, so that option needs a change there. Allowed characters are the RFC 6455 token set, which includes base64url (`-`, `_`) but not `=` padding or `+`/`/` (token grammar, RFC 6455 §4.1 by reference; I fetched the WHATWG page, not the RFC). Queries: "Sec-WebSocket-Protocol token browser server must echo subprotocol otherwise connection fails RFC 6455 4.1".
- **Apple's rules for a TLS server certificate** (https://support.apple.com/103769, iOS 13 / macOS 10.15 onward): the DNS name must be in the SAN (CommonName is not trusted); certificates issued after 2019-07-01 need EKU `serverAuth` and a validity of at most 825 days. The page says nothing about IP SANs or about user-trusted certificates. A later mailing-list post (not fetched from Apple) cites 398 days for certificates issued on or after 2020-09-01; Apple has said that applies to publicly trusted roots, which I did not confirm. So the current certificate (no SAN, no EKU, `not_after` year 4096, `:90-92`) fails Apple's published rules on all three counts. Plan: any certificate the plan issues for a browser has SAN, `serverAuth` and validity of at most 398 days. Queries: "Apple support requirements for trusted certificates in iOS 13 and macOS 10.15 825 days subjectAltName serverAuth".
- **WebKit's click-through may not cover `wss://`.** WebKit bug 41419, "Unverified cert: Allow wss:// if user has accepted https:// warning?", is open (status NEW, last modified 2026-01-12, no fix recorded): Safari rejects `wss://` to a host whose certificate is untrusted, and the reporter's connection worked only after setting the certificate to always-trust (https://bugs.webkit.org/show_bug.cgi?id=41419). The Apple Developer Forums thread has WKWebView overriding server trust not applying to WebSockets (found through search, not fetched). code-server's iPad doc: "Safari will prevent WebSocket connections unless the certificate is installed as a profile on the device", and reach it by a domain name, not a bare IP, "Otherwise Safari will refuse to allow WebSockets to connect" (https://github.com/cdr/code-server/blob/v3.7.0/doc/ipad.md, v3.7.0, so old). Cendio bug 7401: iOS 13 failed `wss` with OSStatus -9807 until the certificate had a SAN (also EKU and a shorter validity) (https://bugzilla.cendio.com/show_bug.cgi?id=7401, retested 2019-10). Queries: "WebKit Safari WebSocket wss self-signed certificate exception not applied after accepting certificate in browser"; "iOS Safari self-signed certificate no subjectAltName IP address ... WebSocket wss". Two sources agree with an open vendor bug: on Safari, a click-through is not a safe basis for the events socket. Evidence covers Safari up to the dates above; no source tests iOS 18/26. Plan: do not make the live-update path depend on a click-through. Either the plan has the page fall back to polling `/api/v1/` on an interval when the socket fails (REST works under a click-through), or the host offers its certificate for installation (decision 1). Both are needed for the acceptance line to hold on an iPhone in the worst case.
- **`SameSite=Strict`/`HttpOnly` cookie on Safari's WebSocket handshake has an unanswered bug report.** Apple Developer Forums thread 104488 (June 2018, 0 replies): Safari on macOS and iOS did not send an `HttpOnly; Secure; SameSite=Strict` cookie on the next `wss` connection, Chrome and Firefox did; removing `HttpOnly` fixed it (https://developer.apple.com/forums/thread/104488). That is one report from 2018, so it is a lead, not evidence of the current behaviour; no vendor documentation was found. Query: "SameSite=Strict cookie sent on same-origin WebSocket handshake; Secure cookie IP address host". This is under Unresolved below, not here.

## Unresolved

- **Does a click-through on iOS Safari (current release) work for `fetch` and `wss://` against a SAN-less certificate on a bare IP?** Tried: five searches above and the fetches of bug 41419, Cendio 7401, code-server. They agree it is at best unreliable and none tests a current iOS. Build to: a certificate with SAN for the IP actually in the URL plus `serverAuth` and bounded validity; a polling fallback in the page. If favourable, the plan may drop the fallback to a degraded mode; if not, it must offer the certificate for install (decision 1) and say so in the dialog.
- **Cookie vs. subprotocol token on Safari.** Tried: the cookie query above; found only forum thread 104488 (2018). Build to: the `HttpOnly` cookie is the plan's choice only if the end-to-end phone run in "For the owner" passes; otherwise a subprotocol token (host echoes it) with the token in `sessionStorage`. The host keeps the bearer header for native clients either way. The plan must make the page work with either, behind one function.
- **Does `Secure` work on an IP host, and are cookies shared across ports?** Not looked up beyond the search above. Cookie scope by host, not port, is the investigation's reading of RFC 6265 and is not verified here. Build to: a cookie name that carries the `server_id`, and the page treating a missing cookie as "pair again".
- **Does the browser remember a certificate exception across launches, and when the IP changes?** Query: "Safari remembers certificate exception ... how long iOS self-signed session only Chrome Proceed unsafe remembered". Nothing relevant found (results were about certificate lifetimes). Build to: the page must work after a fresh warning every time; do not rely on a remembered exception, and say in the dialog that the warning may recur.
- **Is the URL (with the code) recorded by the browser before `replaceState` runs, and does `replaceState` clear the history entry?** Query: "history.replaceState remove URL query from browser history Safari iOS visited URL recorded before JavaScript runs". Only MDN's description that `replaceState` replaces the current entry; nothing on whether the first navigation is also logged or synced. Build to: the code is single-use and expires in five minutes or on three failures (`src/ui/remote.rs`, spec §5), so a leaked URL is dead once used; the plan states this as the mitigation and does not claim the history is clean.
- **Parallel connections per host and idle keep-alive on iOS Safari.** Not searched to a primary source. Build to: the pool of 4 (`:567`), so the page must be at most three files (HTML, one JS, one CSS), all `Connection: close` or answered quickly, and the plan tests the pool with the existing `stalled_strangers_fill_their_own_pool...` model (`tests/remote.rs:3226`).
- **Does a Bonjour `.local` name resolve from iOS Safari?** Not searched. Build to: the IP in the URL; a `.local` name is optional, and a SAN covering both costs nothing.
- **Watch set capped at 128 and the page's `conversation` watches.** Tree-answerable by the planner from `docs/remote-client.md` §4.4; not looked at here. Build to: watch only the open session's content key, and the list through `changed {session}`.

## For the owner

- **Does the page load, `fetch` and `new WebSocket` end to end on a real iPhone/iPad after the warning, with the current certificate and with a SAN certificate?** (Needs a device.) If yes: the click-through is the trust step and the plan says so in the paired-devices dialog; the cookie or token choice follows the next line. If no: the host offers its certificate for installation on the device, and the plan builds the certificate to Apple's rules above. The plan builds the polling fallback and the SAN certificate in both cases, so it never waits on this.
- **With the cookie option: is the `HttpOnly; Secure; SameSite=Strict` cookie sent on the page's `wss` handshake on that device?** If yes, use the cookie. If no, use the subprotocol token. The plan builds the host to accept the bearer header, the cookie and the subprotocol token in that order, which works either way.
- **Which address does the phone reach the Mac by (the route-chosen IP, a `.local` name)?** If it is the route-chosen IP: the URL uses `local_address()`. If not: the pairing window shows the address list and the owner picks. The plan puts the chosen host in the SAN either way.
