# Facts for #230 (browser page on the remote port)

No spike was run: every question the plan turns on is either settled by a source or needs a device (iPhone), so none was runnable here.

## Settled

### Tree
- `RemoteRequest` is defined only in `src/adapters/remote.rs:360-372` (`adapters/`, not `ports/`); `tests/` never names it (`grep -rn RemoteRequest tests` is empty), so new fields (`cookie`, `origin`, `user_agent`, `Sec-WebSocket-Protocol`) touch only `read_request` and `src/app.rs`. `RemoteReply` is built literally ~12 times in `src/app.rs` (e.g. `:1664`, `:3723`, `:3736`, `:3767`); a header field needs a default or a constructor change there. Neither is in `model.rs`, `action.rs` or `ports/`, so the additivity rule does not bind them.
- `last_message` is not on the session record or on `SessionView`. It exists only on the hook event (`src/ports/events.rs:24`, `src/adapters/hooks.rs:71,196`, the hook binary truncates at 200 chars, `src/bin/switchboard-hook.rs:37,639`); `grep last_message src control` outside tests finds nothing in `core/` or `control/`. The card's excerpt on the wire needs a new field or per-session `last-response` fetches. (Spec l.291 claim is stale.)
- Cert reissue over the same key is possible in code: the private key is a Keychain PEM, `rcgen::KeyPair::from_pem` is already used (`src/adapters/remote.rs:139,146`), and `make_identity` (`:95-127`) is the only place a key is generated and sets no SAN. SPKI hash depends on the key only (`:245`), so a new cert over the same key keeps `spki_sha256`.
- Swift `PairingInvite` is used by `ConnectionManager.swift`, `BrowserView.swift`, `main.swift` and 7 test files (`grep -rln PairingInvite client`); `addresses` is read as a list at `ConnectionManager.swift:483` and built as a one-element list at `main.swift:120`, so a URL parse can fill a one-element list and nothing breaks.
- Watch set cap is 128 keys, LRU eviction, never refused, and a read of an evicted key still answers (`docs/remote-client.md:131,254,543`). A page watching many keys evicts the headset's silently, costing it `changed` until its next read.
- Unauthenticated pool is 4, paired 12, only `/pair` (6/min) and `/info` (60/min) are rate-limited (notes, `src/adapters/remote.rs:567-587`).

### Browsers and platforms
- **Cookies are not isolated by port** (RFC 6265 §8.5). A `Secure` cookie set by one Switchboard instance is sent to every HTTPS service on the same host name, whatever the port. Evidence: https://kb.cert.org/vuls/id/804060 (quotes the RFC); https://bug.dillo-browser.org/507/ ; draft-ietf-httpbis-rfc6265bis-05 carries the same rule. Queries: "cookies not isolated by port RFC 6265 cookie shared across ports same host". `localStorage` is per origin and does not have this property (origin definition; not separately searched).
- **Certificate needs a SAN or Chrome rejects the name.** Chrome 58+ ignores CN (https://textslashplain.com/2017/03/10/chrome-deprecates-subject-cn-matching/); Apple: "DNS names in CommonName are no longer trusted" (https://support.apple.com/103769). WebKit bug 158345 comment 6 says Chrome and Safari do not accept a self-signed server cert without a SAN for wss (https://bugs.webkit.org/show_bug.cgi?id=158345). The current cert has no SAN, so the plan must add SANs (the IP and a `.local` name) for any browser path to be reliable. Queries: "Chrome certificate without subjectAltName commonName ignored ... proceed"; "Apple requirements for trusted certificates iOS 13 ...".
- **Apple's trust rules for a certificate**: RSA >= 2048, SHA-2, name in SAN, and for certs issued after 2019-07-01 an EKU with `id-kp-serverAuth` and validity <= 825 days (https://support.apple.com/103769, fetched). The page does not say whether user-trusted self-signed certs are exempt; a reissue for browsers should satisfy all of it anyway (year-4096 `not_after` violates the 825-day rule). Note `rcgen` default key is ECDSA, so the RSA rule does not apply, but that is not on Apple's page either way.
- **iOS/iPadOS Safari's default WebSocket stack does not carry a click-through or manually trusted self-signed certificate to `wss://`**; the workaround is the experimental flag Settings > Safari > Advanced > Experimental Features > "NSURLSession WebSocket" (https://cockpit-project.org/running/safari, fetched; no iOS version named). Consistent: WebKit 41419 thread (https://lists.webkit.org/pipermail/webkit-dev/2011-June/017385.html: https exception, wss still fails; Chrome applies it to both) and bug 158345 comments 11-16 (NSURLSession work, status NEW, last comment 2021). Queries: "Safari WebSocket wss self-signed certificate accepted exception not applied fetch iOS WebKit". Only old/third-party evidence for current iOS, so the plan must not depend on `wss` working on an unmodified iPhone with a self-signed cert (see Unresolved line for the build).
- **WebSocket subprotocol**: a server must not answer a subprotocol the client did not offer (RFC 6455); if the client offered one and the 101 does not select one, WHATWG says fail the connection; Chrome fails in practice (search result summary of RFC 6455/WHATWG/Chrome reports; queries: "WebSocket Sec-WebSocket-Protocol server must echo subprotocol browser fails connection"). So a subprotocol token needs `respond_upgrade` (`src/adapters/remote.rs:519-527`) to echo exactly one value; today it echoes none.
- **`crypto.randomUUID` is secure-context only** (MDN https://developer.mozilla.org/en-US/docs/Web/API/crypto/randomUUID). Whether a click-through https origin counts as secure is not settled (Unresolved).
- **Chrome refuses service-worker registration on a click-through cert** (https://bugzilla.mozilla.org/show_bug.cgi?id=1162772 and https://deanhume.com/testing-service-workers-locally-with-self-signed-certificates/). The first cut uses no service worker, so no impact; a PWA/offline install is out.
- **`history.replaceState` changes the current session-history entry but does not stop the browser's global history from recording the original URL**; Safari decides what its History list shows (WebKit bug 142151, https://bugs.webkit.org/show_bug.cgi?id=142151; MDN text quoted in the search result). So the code in the URL can remain in Safari's/Chrome's history list. The plan must treat the code as visible in history and rely on its limits (5 minutes, three failures, one use) rather than on `replaceState`. Query: "history.replaceState removes URL query from browser history entry Safari Chrome".

## Unresolved

1. **Does a click-through accepted cert apply to `fetch` and `wss://` in iOS Safari, macOS Safari, Chrome, Firefox?** Tried: the Safari/wss query above and the WebKit mailing list and bugs. Evidence for Chrome (applies) and for iOS Safari (wss fails without the experimental flag) is old and third-party; nothing for Firefox. Needs an iPhone. Build to: the page works with REST polling alone (list, `last-response`/`screen`, `send` via the revision counter and a periodic refetch, which §4.4/watch-set text already assumes); `/events` is an enhancement used when `new WebSocket` opens, falling back to a 2 to 3 s poll of `GET waiting`/the open view. Favourable: the socket gives live moves without a reload. Unfavourable: the acceptance line "moves to the top without a reload" is met by the poll.
2. **Is a click-through https origin a secure context** (`crypto.randomUUID`, `Secure` cookie storage)? Queries: "secure context certificate error self-signed https crypto.randomUUID available after proceeding past warning"; "Chrome self-signed certificate proceed ... isSecureContext". No source found. Build to: make op ids with `crypto.getRandomValues` (a 128-bit hex string), never `randomUUID`; the `Secure` cookie question goes with item 3.
3. **Do `SameSite=Strict; Secure` cookies get set on an IP-address host over a click-through cert and sent on same-origin `new WebSocket()`?** Query: "WebSocket ... cookies SameSite=Strict same-origin". Found only a Safari bug where Strict cookies were not sent on WebSocket in restored tabs, fixed in 15.1 (https://bugs.webkit.org/show_bug.cgi?id=232666). A same-origin request is same-site by definition, so sending is expected, but no source states it for WebSocket. Build to: decision 2 should not rest on the cookie reaching the socket. Take the `Sec-WebSocket-Protocol` token or a short-lived single-use ticket fetched by an authenticated `fetch` (header or cookie) and given to `new WebSocket` as the subprotocol, so only one path has to work. Favourable: the cookie alone is enough. Unfavourable: the ticket path works regardless. Either way the host keeps the bearer header for native clients and, with a cookie, must check `Origin` (cookie auth makes the socket and POSTs cross-site targets).
4. **Does the click-through survive restart or an IP change (Safari, Chrome, Firefox, iOS)?** No query returned a source. Build to: the page shows "reload and accept the certificate again" if its first `/info` fetch fails, and the stored identity marker (server_id, key) is checked against `/info` at each load.
5. **Does the QR URL with the code reach history/tab sync before the page runs?** Partly answered (replaceState item above). Not found: iCloud tab sync behaviour. Build to the same rule: code is single-use and time-limited; consider also invalidating it on first successful `/pair`.
6. **Does iOS Safari open/keep more connections than the pool of 4 allows?** Queries not run; needs a device and a measurement. Build to: serve static files from the connection thread without frame cost, count them in a separate cap (or let them leave the unauthenticated pool after the response with `Connection: close`) so a page load of 3 to 4 files plus a TLS-warning handshake cannot starve `/pair`. Favourable: no change needed; unfavourable: this is already in place.
7. **Does Bonjour `.local` resolve from iOS Safari?** Not searched (no reliable source expected). Build to: the QR carries the route-chosen IP, with the SAN covering the IP and a `.local` name; the Config/dialog shows the URL as text for the other case.

## For the owner

1. **Trust step (decision 1): click-through, or offer the certificate for download?** Given the iOS Safari `wss` finding, click-through is unlikely to give a working socket on iPhone without the experimental flag. Branch A (owner picks click-through): the plan serves a SAN-bearing cert and the page runs on REST polling; works in both cases. Branch B (download/install): needs a cert with SAN, `serverAuth` EKU and <= 825 days, a per-address reissue, and a manual device trust toggle that only the owner can verify on a phone. The plan should build A and list B as later. Works in both: A.
2. **Reissue the identity cert over the same key with SANs and a bounded validity?** Required for any browser path (Unresolved/Settled above). Yes: plan the reissue at startup when the SAN set does not cover the current `local_address()`, keeping `spki_sha256`; No: browsers rely on CN only and Chrome/Safari refuse the name, so the plan must still serve the page and say the warning cannot be cleared. Works in both: build the reissue as a function and let the owner enable it.
3. **Origin check on `/events` upgrade and POSTs.** Yes: accept the `Host` the request arrived on (scheme https + same host:port), refuse others; No: with a cookie this is open to cross-site hijacking, so the plan makes it required when a cookie is used. Works in both: check only when a cookie authenticates.
4. **How the page tells "revoked" from "never paired".** Plan an additive refusal code (for example `revoked`) and a non-secret marker in `localStorage` (server_id, device_id, no token); both cost little. Works in both.
5. **Device scope after pairing.** Add `GET /api/v1/device` (authenticated, returns scope and name) or keep the `/pair` reply: the plan adds the endpoint; if the owner declines, the header shows the scope from `/pair` and says "as of pairing".
6. **Card excerpt.** Add an additive excerpt field to `SessionView` (fixtures change on both sides), or per-session `last-response` fetch. Works in both: the page fetches `last-response` for visible sessions only and uses the field if present.
7. **One QR with the URL, JSON dropped?** Plan: URL form first in `PairingInvite.parse` with the JSON as fallback so old text still pairs; if the owner drops JSON, delete the fallback and the 7 Swift tests' invite literals.
8. **Static path set, cache policy, rate window, empty-state text, `kind` on the device, trust-question/resume on the page.** Defaults the plan may take: `/`, `/app.js`, `/app.css`; `Cache-Control: no-store`; `default-src 'self'` CSP; "open the pairing window and scan" when no code and no token; name only (no `kind`); trust question and resume hidden in the first cut. Owner may override without changing the rest.
9. **A manual phone run.** Cannot run here. Plan the host-side HTTP-client test as the CI gate and record a phone run as the acceptance check by the owner.
