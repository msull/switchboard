# Facts for #230 (web control surface)

No spike was run: every open question left is a browser or device behaviour, which a spike here cannot reach (no iPhone, no Safari on iOS). Nothing was committed.

## Settled

**Tree**
- `make_identity` builds the certificate with `CertificateParams::new(vec![])`, so no subjectAltName, a CN only, rcgen's default validity (comment says year 4096), no EKU set. Evidence: `src/adapters/remote.rs:88-127`.
- `make_identity` always generates a new key; reissuing over the same key needs a new function that takes the Keychain PEM. The SPKI hash is a function of the key alone, so the pin survives a reissue. Evidence: `src/adapters/remote.rs:98-112`, `spki_sha256 = sha256_hex(key.subject_public_key_info())`.
- `respond_upgrade` writes the 101 with no `Sec-WebSocket-Protocol`; `RemoteRequest` is built at one literal (`src/adapters/remote.rs:506`) and `RemoteReply` literals are all in `src/app.rs` (about 20 sites, e.g. `:1664`, `:2365`, `:2754`); none in `tests/remote.rs` by grep of `RemoteRequest {`. Adding fields touches `src/adapters/remote.rs` and every `RemoteReply { .. }` in `app.rs` unless a constructor or `Default` is used. `RemoteRequest` is under `adapters/`, not `ports/`, so CLAUDE.md's additivity rule for the shared contract does not name it; additive anyway is cheap.
- The card excerpt is a record field: `last_message` exists on the session record, fed by the hook's `last_assistant_message` (`src/bin/switchboard-hook.rs:37`; `last_message: None` in `src/core/tests.rs:1717`). It is not on `SessionView` (`control/src/lib.rs:636-688`, per the notes). So the page needs either an additive `SessionView` field or per-session `last-response` fetches.
- `PairingInvite` is used by `ConnectionManager.swift`, `BrowserView.swift`, `switchboard-remote/main.swift`, `Info.swift` and seven test files under `client/Tests` (list: `grep -rl PairingInvite client`). A URL form must be added beside the JSON parse, not instead of it, unless all are changed together.
- §5 of the spec says a relayed request through a substituted certificate fails because the host checks `spki_sha256`; for a browser the body is built by the page, so under an impostor the sentence does not hold. The spec must be amended. Evidence: `docs/remote-client.md:309`; the page cannot read the TLS certificate (no web API exposes it).

**Outside the tree**
- A server must not send `Sec-WebSocket-Protocol` unless the client offered it, and the client fails the connection if the server names a subprotocol not offered. The client's own list is tokens (U+0021..U+007E minus separators), unique; the server's reply is a single token. Evidence: RFC 6455 §4.1 step 6, §4.2.2, §4.3, https://www.rfc-editor.org/rfc/rfc6455.html. Queries: "Sec-WebSocket-Protocol server must echo subprotocol browser closes connection RFC 6455 token characters".
- Chrome fails a handshake when the client offered a subprotocol and the 101 carries none ("Sent non-empty 'Sec-WebSocket-Protocol' header but no response was received"). Evidence: Chromium handshake helper (as copied in Cobalt) https://cobalt.googlesource.com/cobalt.git/+/308ed6b84664d59944cd65f4b4359c28a2443be6/src/cobalt/websocket/web_socket_handshake_helper.cc; reports at https://forum.defold.com/t/websocket-sec-websocket-protocol-no-response-was-received-solved/66716 (a lead, agrees with the source). Consequence: if the token travels as a subprotocol, `respond_upgrade` must echo it, and the token must be base64url (token characters; `=` padding is not a problem for tokens? `=` is in the token grammar, but drop padding to be safe). The protocol's server token is therefore a value the page chose, a secret in the 101 echo. Query: "Sent non-empty 'Sec-WebSocket-Protocol' header but no response was received" Chrome WebSocket.
- Cookies ride the WebSocket opening handshake as ordinary header fields (RFC 6455 §1.3, §4.1, https://www.rfc-editor.org/rfc/rfc6455.html), and `wss://` counts as `https://` for same-site (Chromium Schemeful Same-Site, https://groups.google.com/a/chromium.org/g/blink-dev/c/qB7DKqxkiaA/m/IEqPn3RYDgAJ). Together this supports, but does not run, a same-origin `wss` handshake carrying a `SameSite=Strict` cookie; see Unresolved.
- Cookie scope is host and path, never port: a cookie set by `host:8080` goes to `host:3000`. `HttpOnly` hides it from script; `Secure` is sent only over HTTPS. Evidence: https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies. This confirms the notes' port-sharing concern; a cookie name per `server_id` is the mitigation and does not stop another HTTPS service on the Mac from receiving it.
- Apple requires, for TLS server certificates on iOS 13 / macOS 10.15 and later: the DNS name in SAN (CN is not trusted), EKU `serverAuth` for certificates issued after 1 July 2019, validity of 825 days or fewer, SHA-2 signatures, RSA at least 2048. Violations "will fail". The page does not mention manually trusted or self-signed certificates and does not mention IP addresses. Evidence: https://support.apple.com/103769. Consequence: a year-4096 certificate with no SAN and no EKU violates the validity, SAN and EKU rules; do not expect it to be trustable as an installed certificate on Apple devices. Queries: "iOS trusted TLS server certificates requirements SAN 825 days extendedKeyUsage serverAuth support.apple.com HT210176".
- Chrome stopped matching a hostname against the commonName in 58; a certificate without SAN is `ERR_CERT_COMMON_NAME_INVALID`. Evidence: https://groups.google.com/a/chromium.org/d/msg/security-dev/IGT2fLJrAeo/csf_1Rh1AwAJ and https://textslashplain.com/2017/03/10/chrome-deprecates-subject-cn-matching/. Whether the interstitial still lets the user proceed for that error is under Unresolved.
- Firefox does not show a prompt for a failed `wss://` subresource; the supported route is to visit the same host:port over https first and accept the exception, after which `wss` works (WONTFIX). Evidence: https://bugzilla.mozilla.org/show_bug.cgi?id=1187666. Since the page and the socket share one origin here, the page load itself performs that click-through. Queries: "Firefox Chrome self-signed certificate exception applies to WebSocket wss same host after accepting warning...".
- `crypto.randomUUID` is limited to secure contexts (https or loopback). Evidence: https://developer.mozilla.org/en-US/docs/Web/API/crypto/randomUUID, https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts. MDN does not say whether a click-through exception keeps the context secure (see Unresolved). Plan: do not depend on it, build the op id from `crypto.getRandomValues` or a counter-plus-random fallback.

## Unresolved

1. **Does Safari (iOS and macOS) let the owner proceed past a certificate with no SAN served on a bare IP, and apply that exception to `fetch` and `wss`?** Queries: "Safari iOS self-signed certificate without subjectAltName CN only 'visit this website' ERR_CERT_COMMON_NAME_INVALID IP address"; "WebKit Safari self-signed certificate accepted click-through WebSocket wss fails fetch XHR not trusted bug". Found: WebKit bug 41419 (2010, Safari 5; a `wss` with an untrusted certificate fails until the certificate is trusted in Keychain, developers resisted an easy bypass, https://bugs.webkit.org/show_bug.cgi?id=41419) and a vendor note that Safari on iOS/macOS refuses `wss` to an https page on an IP with a self-signed certificate (https://support.tsplus.net/support/solutions/articles/44000038552-safari-ios-macos-on-https-address-with-secured-websockets-connection-fails). Both are old or vendor posts, not current Safari. The webkit-dev thread returned 403. Not settled; it needs a device.
   - Build to: the plan must not rest on a Safari click-through carrying the socket. Whatever the answer, give the certificate a SAN for the address it is served on (IP SAN) and `serverAuth` EKU, and a validity under 825 days, as an additive reissue over the same key (pin unchanged). If a click-through does carry `fetch` and `wss`, the owner's one tap is the trust step; if not, the page must still work over `fetch` alone (poll on a timer, `GET /api/v1/events` is not required for the first cut) and the plan names the socket as the part that needs the installed certificate.
2. **Does a `SameSite=Strict; Secure; HttpOnly` cookie reach a same-origin `new WebSocket()` handshake in Safari, Chrome and Firefox, and does `Secure` work with an IP host?** Query: "SameSite=Strict cookie sent with same-origin WebSocket handshake browsers Secure cookie IP address host". Only the Schemeful Same-Site note above came back; no browser statement. Not settled.
   - Build to: cookie as the primary transport on `fetch` (that part is plain cookie behaviour on a same-origin request). For the socket, make the host accept the token from the cookie or, equally, from a `Sec-WebSocket-Protocol` value that it echoes, and keep the bearer header for native clients. The page uses the cookie first; if the cookie-bearing handshake fails, it falls back to the subprotocol with the token fetched from a one-time authenticated `fetch`. This costs one extra authenticated endpoint at most. The plan never waits on the browser matrix.
3. **Is a click-through page a secure context (so `crypto.randomUUID` and `Secure` cookies work)?** Queries: "crypto.randomUUID secure context only HTTPS certificate error bypass secure context MDN isSecureContext"; fetched MDN Secure Contexts: silent on certificate exceptions. Not settled.
   - Build to: feature-test `isSecureContext`/`crypto.randomUUID`, fall back to `getRandomValues`; set the cookie `Secure` anyway because the origin is https.
4. **How long a browser keeps the click-through, and whether it survives an IP change.** Query: "Safari iPhone 'Show Details' 'visit this website' self-signed certificate remembered how long; Chrome certificate error bypass remembered 7 days browser restart". Only a forum note that Safari's bypass is not permanent and can be cleared from the Debug menu. Not settled. Build to: assume the warning returns; the page's saved marker (server id, device id, never the token) lets it say "pair again" plainly. A DHCP address change is a new origin with its own cookie, so the plan should prefer a `.local` name if (see owner) it resolves.
5. **Whether the URL with the code reaches history, tab list or iCloud tab sync before `replaceState` runs, and whether `replaceState` rewrites the history entry (not only the address bar).** Not searched to a primary source (no vendor documents it). Build to: the code is single-use and expires in five minutes or three wrong tries (`src/ui/remote.rs`, `docs/remote-client.md:309`), so a copy left in history is dead after the window closes. The plan says that, and the dialog tells the owner the QR is for one device.
6. **Bonjour `.local` from iOS Safari, parallel connection count and keep-alive of iOS Safari, and whether a page load exhausts the pool of four.** Not searched beyond the search above. Build to: serve the static files from the connection thread without the frame, set `Connection: close` on them so unpaired slots free at once, and test pool behaviour in `tests/remote.rs` like `stalled_strangers_fill_their_own_pool_and_never_a_paired_clients` (`tests/remote.rs:3226`). A real-device load stays a manual step.
7. **Does the 128-key watch cap evict the headset when the page watches many keys?** Tree question, not looked at (`remote_subscribe`, `src/app.rs:2723`); the watch set is per socket in the notes' reading. Build to: the page watches only the open session's key plus the list key.

## For the owner

1. **Trust step (decision 1).** Click-through as the trust step, said in the paired-devices dialog, or a downloadable certificate.
   - Favourable (Unresolved 1 shows Safari carries `fetch` and `wss` after a tap): click-through alone, with the SAN reissue.
   - Unfavourable: still ship the page with the click-through and the SAN/EKU/validity reissue, and add the certificate download as a separate later item. Click-through works in both cases.
2. **Reissue the certificate over the same key with an IP SAN and a validity under 825 days?** It changes `identity.json` and needs a rule for the address that moves. Works in both cases; the pin does not change.
3. **Origin check on the upgrade and on POSTs (cross-site WebSocket hijacking, CSRF).** `remote_subscribe` checks neither. RFC 6455 §10.2 leaves the check to the server. Favourable (a cookie works): required, accept an `Origin` whose host equals the request `Host`. Unfavourable (subprotocol token only): still do it; costs one more header read.
4. **Revoked versus never paired (page states).** Add an additive refusal code, or keep a non-secret marker on the device. Works in both cases: the marker, since an HttpOnly cookie hides itself from the page.
5. **Scope in the header.** No endpoint returns the device's scope after pairing (notes, `remote_info` is unauthenticated). Add an authenticated `GET /api/v1/device`; or show the `/pair` reply scope and accept staleness. Works in both cases: the new endpoint.
6. **Card excerpt.** Additive `SessionView` field fed from the record's `last_message` (fixture change on both sides), or per-session `last-response` fetches. Works in both cases: the field.
7. **JSON invite.** Keep it only if the Swift tests and `BrowserView` still need it; `PairingInvite.parse` should read both. Works in both cases.
8. **What the page shows with no code and no token**, the `kind` field on the device record, and cookie naming by `server_id`.
