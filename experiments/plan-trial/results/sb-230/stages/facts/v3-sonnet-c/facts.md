New fields (cookie, origin, user agent, subprotocol) touch that one site. Evidence: `src/adapters/remote.rs:360-372`.

### Certificates (vendor documentation)
- Apple (iOS 13 / macOS 10.15 onward): a TLS server certificate must carry the DNS name in the SAN (the CN alone is not trusted), and, if issued after 2019-07-01, an EKU with `id-kp-serverAuth` and a validity of 825 days or fewer. A year-4096 certificate fails that rule for a device-trusted certificate. https://support.apple.com/103769 (fetched, quoted). Query: "Apple requirements for trusted certificates in iOS 13 and macOS 10.15 825 days SAN serverAuth".
- Chromium has matched names against the SAN only, ignoring the CN, since Chrome 58 (2017). Two secondary sources agree: https://dev.to/dimastopel/why-subject-alternative-names-sans-matter-for-modern-browsers-30p0, https://cert-depot.com/guides/why-sans-matter. A WebKit comment says Safari would not accept a self-signed certificate without a SAN: https://bugs.webkit.org/show_bug.cgi?id=158345. A reports-disagree note: one forum says no "proceed" option appears without a SAN, another says it does. The plan must add a SAN for the address in the URL either way. Query: "self-signed certificate without subjectAltName IP address Chrome Safari NET::ERR_CERT_COMMON_NAME_INVALID proceed anyway".
- iOS/iPadOS Safari: `wss://` to a self-signed certificate fails even when the certificate is manually trusted. Cockpit documents it (https://cockpit-project.org/running/safari, fetched; names no iOS version) and WebKit bug 41419 is still NEW, modified 2026-01-12 (https://bugs.webkit.org/show_bug.cgi?id=41419, fetched). Reports of OSStatus -9807 until SAN, EKU and validity were fixed: https://bugzilla.cendio.com/show_bug.cgi?id=7401, https://gitlab.nic.cz/turris/reforis/foris-js/-/merge_requests/154. Cockpit's workaround is Settings > Safari > Advanced > Experimental Features > "NSURLSession WebSocket". An open vendor bug with agreeing reports settles that the behaviour exists. So the plan must not rely on `new WebSocket` after a click-through on iOS. Queries: "Safari iOS self-signed certificate accepted click-through WebSocket wss fails fetch works"; "Safari iOS WebSocket self-signed certificate NSURLSession WebSocket experimental feature wss untrusted certificate".

### WebSocket and cookies (standards)
- RFC 6455 §4.1 and §4.2.2 (https://www.rfc-editor.org/rfc/rfc6455.html, fetched; first 100000 of 176684 characters read, both sections inside): the server must pick a subprotocol from the client's offered list. The client must fail the connection if the server names one it did not offer. Without an echo, a client that offered subprotocols is refused by the browser (WHATWG HTML, seen only via search). So a token-as-subprotocol design needs the host to echo it in the 101 (`respond_upgrade`, `src/adapters/remote.rs:519-527`, sends none). Values are tokens, U+0021 to U+007E without separators. Query: "RFC 6455 Sec-WebSocket-Protocol server must echo subprotocol otherwise browser fails connection; token characters".
- RFC 6265 security considerations: cookies are not isolated by port, so a `Secure` cookie from one instance reaches other services on the host. Seen via search summary, RFC page not fetched. Query: "RFC 6265 cookies do not isolate by port; SameSite Strict cookie sent on same-origin WebSocket handshake".

## Unresolved

- **U1. Does the click-through exception cover `fetch` and `wss://` in each browser, and for how long?** iOS Safari `wss://`: settled above as failing. Not found: Safari `fetch`, Chrome and Firefox WebSocket, retention (Paessler says one week for Chrome, HPE says a few days; both are third-party support pages, not Chromium). Query: "Chrome self-signed certificate warning bypass remembered how long proceed exception per host Chromium SSL error allowlist". Build to: a page that works on `fetch` alone, falling back to polling `waiting` and the open session's `last-response` when the socket does not open within 5 s. Favourable: the socket is a faster path on top. Unfavourable: polling is the page and "moves to the top without a reload" still holds. The plan adds the SAN and bounded validity in both cases.
- **U2. Secure context after a click-through.** Query: "secure context page loaded over HTTPS with certificate error click through crypto.randomUUID isSecureContext". Only MDN (randomUUID is secure-context-only) and an old Mozilla bug (https://bugzilla.mozilla.org/show_bug.cgi?id=1162772: Chrome refused a service worker on a self-signed certificate, Firefox allowed it). Build to: ops ids from `crypto.getRandomValues`, which is not gated. Favourable: `randomUUID` may be used. Unfavourable: no change. The cookie carries the same unknown, so decision 2 keeps the subprotocol path as the fallback.
- **U3. `SameSite=Strict` cookie on a same-origin WebSocket handshake; `Secure` on an IP host.** Queries: "WebSocket handshake cookies SameSite Strict same-origin sent Chrome Safari Firefox cookie header upgrade request". Leads only: https://developer.apple.com/forums/thread/104488 and https://bugs.webkit.org/show_bug.cgi?id=232666 (Strict cookies not sent on Safari WebSockets in restored tabs, fix reported around Safari 15.1). Nothing for Chrome or Firefox, nothing on IP hosts. Build to: `authenticate` accepts bearer, cookie and subprotocol in that order. Favourable: the page's script never holds the token. Unfavourable: the page keeps the token and uses the subprotocol.
- **U4. Is the URL with the code kept in history, tab list or iCloud sync before `replaceState` runs, and does `replaceState` clear history?** Query: "history.replaceState replaces current session history entry URL; iOS Safari camera QR code opens link certificate warning history". Only MDN, which says it modifies the current entry. Nothing on the interstitial that shows before any script runs. Build to: the code is single-use and ends in five minutes or three wrong tries (`src/core/remote.rs:46-73`), so a leaked URL is inert after. The plan says the code sits in browser records until the page replaces the URL, and does not claim it never reaches history. This holds either way.
- **U5. Does `.local` resolve from iOS Safari?** Query: "iOS Safari resolves .local mDNS hostname Bonjour local network permission Safari". Vendor articles only: `.local` is multicast-only. Apple's TN3179 not read. Build to: the IP from `local_address()` (bracketed if IPv6). A `.local` second link is an add if favourable.
- **U6. Parallel connections and idle time of iOS Safari per host.** Not searched, so no source. Build to: three static files at most, answered on the connection thread with `Connection: close`, so they free their slot of the four at once. This is right if unfavourable and harmless otherwise.
