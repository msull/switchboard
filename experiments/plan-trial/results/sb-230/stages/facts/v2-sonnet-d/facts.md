# Facts for #230 (browser page on the remote port)

No spike was run. Every open question left needs a real iPhone or an owner decision, and spikes here cannot supply either. The worktree is clean.

## Settled

**About the tree**

- Certificate reissue over the existing key is possible. `tls_config` and `spki_sha256_of_key` load the Keychain key with `rcgen::KeyPair::from_pem` (`src/adapters/remote.rs:137-147`), and `make_identity` calls `params.self_signed(&key)` (`:95-127`). A variant that takes the PEM key, adds SANs and sets a bounded validity leaves `spki_sha256` unchanged. Only the `certificate` field of `identity.json` changes. `make_identity` always generates a new key today.
- `RemoteRequest` is built once, in `read_request` (`src/adapters/remote.rs:506`). No test constructs it (`tests/remote.rs` has zero literals). `RemoteReply` is built literally 28 times in `src/app.rs` and twice in `src/adapters/remote.rs` (`:829`). Adding response headers to it touches all of them unless a constructor or `Default` is added. Both types live in `adapters/`, not `ports/`, so CLAUDE.md's additivity rule for the shared contract does not cover them. Both are still used across `app.rs` and the adapter.
- The card excerpt is not on the wire. `Stopped { last_message }` exists in `src/ports/events.rs:24`, and `switchboard-hook` writes it, capped at 200 chars (`src/bin/switchboard-hook.rs:37,639`). `src/app.rs` and `src/core` have no non-test use of it, and `SessionView` has no such field (`control/src/lib.rs:636-688`, per the notes). An excerpt field on `SessionView` would be a new additive field plus a fixture change. The alternative is a per-session `last-response` fetch, as in `BrowserView.swift:149-163`.
- Swift `PairingInvite` is used in `ConnectionManager.swift:474,482`, `BrowserView.swift:106,883`, `switchboard-remote/main.swift` and 7 test files under `client/Tests`. The `addresses: [Address]` list is read at `main.swift:51,120` and in `KnownServer.swift` and `ServerConnection.swift`. URL parsing in `PairingInvite.parse` must yield a one-element `addresses` list.
- Pool, rate-window, `authenticate`, `read_request` and `respond` behaviour is as described in the investigation notes. I did not re-derive it.

**About browsers and platforms**

- Apple requires a TLS server certificate to carry the DNS name in the SAN. A name only in the CN is not trusted. For certificates issued after 2019-07-01 it must have EKU `serverAuth` and a validity of 825 days or less. https://support.apple.com/103769. The page does not say whether these rules apply to user-trusted certificates. Queries: "Apple support requirements for trusted certificates in iOS 13 and macOS 10.15 validity 825 days SAN serverAuth".
  - Consequence for Decision 1: the year-4096 `not_after` and the missing SAN and EKU would fail Apple's rule for a certificate the owner installs. A bounded validity (under 825 days) and `serverAuth` are needed whichever option is picked.
- Chrome ignores the CN. Since Chrome 58 it checks only the SAN, so a self-signed certificate for an IP needs an IP SAN. Without one it shows `ERR_CERT_COMMON_NAME_INVALID`, with an "Advanced → Proceed (unsafe)" bypass reported (https://community.nethserver.org/t/chrome-58-doesnt-work-with-nethserver/6730, https://kb.metricinsights.com/m/52384/l/745836-ssl-warning-net-err_cert_common_name_invalid). These are community and vendor-KB sources that agree, not Chromium's own docs. Query: "Chrome self-signed certificate IP address no subjectAltName ERR_CERT_COMMON_NAME_INVALID proceed unsafe".
- WebKit bug 41419, "Allow wss:// if user has accepted https:// warning?", is open (status NEW, last modified 2026-01-12), filed 2010-06-30. A WebKit developer's view was that logging was the right direction, and no fix is shown. The only working case reported is a certificate set to "always trust" in the Safari trust settings. https://bugs.webkit.org/show_bug.cgi?id=41419. A web search summary also reports iOS closing `wss://` with error -9807 even with a profile-installed certificate on a Turris project page (https://gitlab.nic.cz/turris/reforis/foris-js/-/merge_requests/154, returned 403 to the fetch tool, so the search summary only). Queries: "Safari iOS self-signed certificate Show Details visit this website proceed, WebSocket wss self-signed exception not applied".
  - Consequence for Decision 2: an open vendor bug with agreeing reports means a click-through exception may not reach `new WebSocket()` in Safari. The page cannot rely on the socket working on iOS.
- The WHATWG WebSocket constructor accepts a subprotocol list, and the connection is established only if the server selects one of them. Each subprotocol must be a non-empty token of characters U+0021–U+007E without separators, with no duplicates (WHATWG commits, https://lists.whatwg.org/pipermail/commit-watchers-whatwg.org/2009/009859.html and `.../2011/013422.html`, plus RFC 6455 §4.1). Base64url is within the token set, but a 32-byte-plus token passes only if the host echoes it in the 101. `respond_upgrade` (`:519-527`) writes no `Sec-WebSocket-Protocol` today. Query: "WebSocket Sec-WebSocket-Protocol server must echo subprotocol otherwise browser fails connection; token characters allowed". The spec text itself was not fetched (secondhand through commit mirrors), so I rate this as two sources that agree, not primary.
- MDN: a secure context is `https`, `wss`, `file`, or a loopback host or `localhost`. A LAN IP over plain HTTP is not secure. MDN does not say how a certificate error or an overridden warning is treated. https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts. The `crypto.randomUUID` secure-context requirement is on MDN (https://developer.mozilla.org/en-US/docs/Web/API/crypto/randomUUID). See Unresolved for the click-through case.

## Unresolved

The plan must build to the unfavourable line for each. The plan never waits on these.

1. **Does a click-through exception cover `fetch` and `wss://` in each browser (iOS Safari especially)?**
   - Tried: queries above, plus "Safari iPhone self-signed certificate IP address ... works fetch XHR after accepting", "Chrome WebSocket wss self-signed certificate works after accepting certificate in same tab https page; Firefox exception wss separate". Only forum posts. They say Chrome works, Firefox needs a separate visit to the wss address, and Safari/iOS is not reliably covered. The one primary source is the open WebKit bug above, which is silent on fetch.
   - Favourable: the page may use `/api/v1/events` as the primary live channel.
   - Unfavourable, and what the plan builds anyway: the page works with REST polling alone. It re-reads the lists on a timer (the envelope carries `revision`, §4.4), uses the socket as an accelerator only, and shows "live updates unavailable" when it fails. Acceptance "moves to the top without a reload" is then met by polling on a browser where the socket fails. The cleanest way out on iOS is the owner installing a proper certificate (see the owner list).
2. **Is a click-through page a secure context, so `crypto.randomUUID` and `Secure` cookies work?**
   - Tried: "secure context self-signed certificate warning accepted isSecureContext crypto.randomUUID https click through"; "Secure cookie set over HTTPS with certificate error self-signed ... IP address host". Nothing relevant came back. MDN is silent.
   - Build to unfavourable: generate the op id without `crypto.randomUUID`. `crypto.getRandomValues` is available in non-secure contexts, so format a UUID v4 from it. Do not make the design depend on a `Secure` cookie being stored. See owner question 2.
3. **Does `SameSite=Strict` send the cookie on a same-origin `wss://` handshake, and does `Secure` work for an IP host?**
   - Tried: "SameSite=Strict cookie sent on same-origin WebSocket handshake; Secure cookie IP address host". One secondhand source (Electron docs: the handshake's Origin is the same-origin https equivalent). WebKit source attaches cookies to the handshake. Nothing on IP hosts. Not enough to settle.
   - Build to unfavourable: if a cookie is chosen, `Authorization: Bearer` stays accepted for REST and the socket authenticates by cookie. If the cookie is unstored or not sent, the page must fall back to polling (as in 1). If the token is stored in `localStorage` instead, the fallback is the `Sec-WebSocket-Protocol` carrier.
4. **Does the browser remember the exception across launches, and for what period?**
   - Tried: only the Cisco forum report that a Chrome override recurs after restart (https://community.cisco.com/t5/audio-and-video-endpoints/net-err-insecure-response-error-when-accessing-https-ip-7335/m-p/3459827/highlight/true). A single forum post, a lead only.
   - Build to unfavourable: assume the warning reappears at each launch and say so in the dialog text. The page must handle a restart by showing the paired state, not requiring a re-pair.
5. **Is the pairing URL, with the code, recorded in history, tab list or iCloud tabs before `replaceState` runs, and does `replaceState` remove it from the history entry?**
   - Tried: "history.replaceState removes URL from browser history entry; page load already recorded in history with query string; Safari iCloud Tabs". Only MDN's description (replaces the current entry's URL) and unrelated WebKit bugs about `replaceState` (https://bugs.webkit.org/show_bug.cgi?id=212839 reports no effect for a fragment on macOS Safari, unresolved). Nothing on iCloud tabs, and nothing on the certificate interstitial.
   - Build to unfavourable: the code is single-use (the pairing window closes on success or after three wrong codes and five minutes). Say plainly in the dialog that the URL is a short-lived credential, and treat the code as spent once used. Do not claim the code never reaches history.
6. **Does a normal page load exhaust the pool of 4 on iOS Safari? How many connections does Safari open and hold?**
   - Tried: no query; I judged it a measurement. It needs a device.
   - Build to unfavourable: serve all static files as one or two paths (inline CSS is out because of the CSP, so use one JS and one CSS file, or a single JS file that injects its stylesheet by a link). Answer them with `Connection: close`, or cap keep-alive on static paths, so a slot is freed at once. Add a test in the style of `stalled_strangers_fill_their_own_pool_and_never_a_paired_clients` (`tests/remote.rs:3226`) for the page load.
7. **Does Bonjour `.local` resolve from iOS Safari?** Not searched for lack of a decision on the URL host. Build to the IP form, which `local_address()` already gives.
8. **Does a page watching many keys evict the headset's watches (cap 128)?** A measurement against the host, not a source question. Build to unfavourable: the page watches only the open session's `last-response` or `screen` key, never one key per listed session.

## For the owner

Each has a branch that works in both cases.

1. **Certificate trust (Decision 1), and whether to reissue.**
   - If the owner wants no warning: the host offers its certificate for download and the owner trusts it on the device. This needs the certificate reissued over the same key with a SAN for the LAN address, EKU `serverAuth` and a validity under 825 days (the Apple rule above). The plan may add a reissue path and a `GET` for the certificate.
   - If the click-through is the trust step: the dialog says so, and the page does not depend on the socket (Unresolved 1).
   - Works either way: add the SAN and EKU to the certificate, bounded validity, same key. It costs nothing at the pin and helps Chrome and Firefox, which reject a name missing from the SAN. Who reissues when the address changes is a decision to record, not a blocker.
2. **Token transport (Decision 2).**
   - Cookie: the page's script never sees the token, but it depends on Unresolved 2 and 3.
   - `localStorage` plus a `Sec-WebSocket-Protocol` token: works wherever the host echoes the subprotocol. The host must read a new request header either way, because `read_request` drops everything except `Authorization` and `Sec-WebSocket-Key`.
   - Works either way: `Authorization: Bearer` stays for native clients and for page REST calls. The page keeps working without the socket.
3. **Origin checks.** Accept `Origin` equal to the request's `Host` on the upgrade and on POSTs, which covers IP, `.local` and loopback with no list. Whichever way the owner picks, the check does not block the native clients, which send no `Origin` header (an absent `Origin` can be allowed).
4. **Revoked vs. never paired.** A distinct additive refusal code, or a non-secret marker kept by the page, or both. Both work with the existing `unauthorized` code kept for older clients.
5. **Scope after pairing.** A new authenticated endpoint, or the `/pair` reply only, accepting a stale header. If the endpoint is declined, the header shows the scope as of pairing and a refused `control` command updates it.
6. **Card excerpt.** An additive `SessionView` field fed from the `Stopped.last_message` the record already holds, or a per-session `last-response` fetch. Works either way: the page shows the fetch as a fallback when the field is absent.
7. **One QR (Decision 3).** The URL, with the JSON still accepted by `PairingInvite.parse` and `switchboard-remote pair`. Parsing both costs one extra branch, and old copies of the text keep working.
8. **Static paths (Decision 4), `kind` on the device (Decision 6), reply to a folder-trust prompt, and a manual phone run.** The plan can specify the set of paths, `Cache-Control: no-store`, CSP and a `device_name` from the user agent without any host-side `kind` field. A `kind` field is additive and optional. Hidden-by-default for the trust-question reply, resume and `prompt_refusal` works either way. Whether the acceptance run on a real phone is recorded is the owner's call. The automated tests cannot cover it.
