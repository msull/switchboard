# Facts for issue #230 (web control surface)

No spike was run: every question the plan turns on is either settled by a source, answerable from the tree, or needs a device (owner). `git status` is clean.

## Settled

**Tree (investigation's [tree] questions)**
- `RemoteReply { .. }` is built by struct literal at ~20 sites in `src/app.rs` (1664, 1679, 2365–2376, 2754, 3570, 3723, 3736, 3767 and others) plus `connection` in `src/adapters/remote.rs`; `RemoteRequest { .. }` literal only at its definition (`remote.rs:360`), none in `tests/`. A new header or cookie field on `RemoteReply` is a many-site change unless it goes through `envelope`/`refuse` (3730, 3754) or has a constructor default. Evidence: `grep -rn "RemoteReply {\|RemoteRequest {" src tests`.
- The QR payload is built inline inside `pairing(cx: &mut DrawCtx, ..)` at `src/ui/remote.rs:160–166`; it needs `cx.core.identity()`, `window` and `local_address()`. A URL form can be tested without egui only if the plan extracts a pure `fn(identity, window, address) -> String`.
- `SessionRecord` (`src/core/model.rs:1053`) is serialized; `SCHEMA_VERSION` is 16 (`model.rs:12`); the header says changes need a bump and a `migrate` step. A stored excerpt on the record is therefore a schema change; a per-list read of the last response is not a record change.
- Every request, including a page load, goes to the frame through the channel (`remote.rs:810–826`), and a connection stays in the 4-connection unauthenticated pool until its first authenticated reply (`remote.rs:701–706`, `835–849`). A static route answered through the frame inherits the pool; one answered on the connection thread would skip the frame and the `DRAIN_PER_PASS` bound. Rate windows key on exact `/api/v1/pair` and `/api/v1/info` only (`remote.rs:631–638`), so `/` and static paths are in no window unless the plan adds one. Tests that touch this: `pair_is_rate_limited_per_listener` and `a_wrong_pin_fails…` (`tests/remote.rs:1395–1411`) count requests to those two paths only, so a page route does not disturb them; `stalled_strangers_fill_their_own_pool…` (`tests/remote.rs:3226`) counts pool occupancy and is the one a page route must be run against.
- Revoked, unknown-token and rotated-key all answer the same 401 `unauthorized` (`app.rs:3142–3149`). Saying "revoked" plainly needs either a new error code (additive) or the page inferring it from `/info`: same `spki_sha256` and `server_id` as stored plus a 401 means revoked-or-unknown; a different key means identity changed.
- The certificate has no SAN, CN `Switchboard <server id>`, validity 1975–4096 (`remote.rs:101–106`; rcgen 0.14.10 defaults). The pin is of the key, so a certificate remade over the same key keeps every pin.

**Fragment and query**
- A URL fragment is not part of the request target and is not sent to the server; the `http`/`https` grammars exclude it. RFC 9110 §4.2.5: the fragment "does not appear in the ABNF definitions for the 'http' and 'https' URI schemes" (https://www.rfc-editor.org/rfc/rfc9110#section-4.2.5); the HTTP messaging thread: "fragments are not part of the request-target and so are never transmitted" (https://lists.w3.org/Archives/Public/ietf-http-wg/2010AprJun/0070.html; Fielding: https://lists.w3.org/Archives/Public/uri/2004Feb/0125.html). Consequence: the query form `/?code=…` puts the code in the first `GET` request line to whoever answers TLS, before any script runs and before the key can be compared; `#code=…&key=…` keeps it out of the request, logs, and `Referer`. The query is in the request line by construction (request-target = path + query). Queries: "URL fragment identifier not sent to server in HTTP request RFC 3986 section 3.5".
- Caveat on the fragment: `history.replaceState` removal of the fragment is a script action after load; the plan builds to it either way.

**WebSocket in browsers (WHATWG WebSockets Standard, https://websockets.spec.whatwg.org/)**
- `new WebSocket(url, protocols)`: no headers parameter; handshake headers are fixed, `Sec-WebSocket-Protocol` comes from `protocols`. So the bearer header cannot be set from a page.
- If `protocols` is non-empty and the 101 does not carry a `Sec-WebSocket-Protocol` acknowledging one, the connection fails. A server using the subprotocol route must echo exactly one of the offered values. (Answers the [run] question for browsers; the `tungstenite` side stays a test detail.)
- A failed handshake fires `error` then `close` with code 1006; the spec forbids exposing failure detail, so script cannot read a 401. The page must therefore check authority with a REST call (e.g. `GET /api/v1/info` or `/projects` with credentials) before and after a socket failure, and say "revoked"/"identity changed" from that, not from the socket.
- The handshake uses credentials mode `include`, so cookies for the origin are sent on it (same source). A fragment in the WebSocket URL throws. Queries: "WebSocket constructor protocols argument no custom headers; onerror no status code…".

**Cookies**
- `HttpOnly` cookies are not readable via `document.cookie`; `Secure` cookies are sent only over https and insecure origins cannot set them (MDN: https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies). Any script on the origin can read `localStorage`; that is the Web Storage definition and the issue's statement stands.
- `SameSite=Strict` sends the cookie only for requests originating from the cookie's own site; `Lax` is the one that adds cross-site top-level navigation (MDN, same page; OWASP https://owasp.org/www-community/SameSite says a Strict cookie is withheld on a followed cross-site link). Consequence: the first load from a camera app is cross-site and carries no Strict cookie, which is fine for the pairing load (it has none yet) but means a bookmark or link tap shows the page before its cookie is sent; the page must make a same-origin `fetch` to learn state, which does carry it. Queries: "SameSite=Strict cookie withheld top-level navigation cross-site link…".

**Certificate trust**
- Chrome ≥ 58 matches names only against the SAN and ignores the CN; a certificate without a matching SAN gives `NET::ERR_CERT_COMMON_NAME_INVALID` (https://textslashplain.com/2017/03/10/chrome-deprecates-subject-cn-matching/, Chromium bug 700595 named there; Squid list https://ml-archives.squid-cache.org/squid-users/2017-May/015309.html agrees). Safari does not accept CN-only either (secondary: https://dev.to/dimastopel/why-subject-alternative-names-sans-matter-for-modern-browsers-30p0). Queries: "Chrome Safari self-signed certificate IP address no subject alternative name ERR_CERT_COMMON_NAME_INVALID proceed unsafe"; "Chrome 58 certificate without subjectAltName…". Plan must build to: the certificate gains an IP SAN for the address in the URL regardless of whether click-through is offered (see Unresolved 1 for what that costs).
- Apple's 398-day limit applies only to certificates from preinstalled roots; user-added roots are exempt (https://support.apple.com/en-qa/102028, page dated 2023-08-21). The 1975–4096 validity therefore does not by itself break a download-and-trust path. Whether a *self-signed leaf with a user exception* is held to it is not stated there (Unresolved 2).
- **Safari (iOS, iPadOS, Apple-silicon macOS) does not support `wss://` to a self-signed or otherwise invalid certificate, even when manually trusted**; the workaround Cockpit documents is a valid certificate, or the "NSURLSession WebSocket" experimental flag in Settings > Safari > Advanced > Experimental Features (https://cockpit-project.org/running/safari, footer 2026; history: WebKit list thread https://lists.webkit.org/pipermail/webkit-dev/2011-June/017335.html "Allow wss:// if user has accepted https:// warning?", and WebKit bug 158345 (open) records the switch to NSURLSession WebSockets as experimental). No source contradicts. Queries: "Safari \"Show Details\" \"visit this website\" certificate exception IP address WebSocket wss self-signed iOS". Consequence the plan must carry: on Safari the events socket may never connect over a click-through certificate. The page needs a polling path on the same REST routes (re-read `/waiting` and the open session on an interval, applying replies by revision per §4.4), used when the socket fails; the "moves to the top without a reload" acceptance step must be met by polling on iOS Safari unless the owner's trust step installs the certificate (Unresolved 2).

## Unresolved

1. **Does Chrome/Safari offer click-through for a SAN-less certificate on an IP-literal address, and does the exception persist and cover the same origin?** Tried: the queries above plus "Chromium net error ERR_CERT_COMMON_NAME_INVALID overridable…"; results were forum posts and said only that HSTS or policy can remove the proceed link, nothing on persistence or scope. Not settled by two qualifying sources. Build to: *favourable* → click-through is the trust step as the issue's option one, said in the paired-devices dialog. *Unfavourable or unknown* → the plan still adds the IP SAN to the certificate (remade over the same key, so pins hold) and ships the certificate download (option two) as the documented path; it must not depend on the click-through working.
2. **Does a downloaded certificate/profile become usable on iOS only after Certificate Trust Settings → full trust, and does it then fix `wss://`?** Tried: "Safari iOS certificate validity period 398 days user exception self-signed trust" (found only the Apple scope note above). Build to: *favourable* → the download path gives the iOS user a working socket; *unfavourable* → polling fallback (above) is the iOS path and the socket is an enhancement. The plan builds the polling path either way.
3. **Do Safari and Chrome store and send a `Secure; HttpOnly; SameSite=Strict` host-only cookie set from a user-accepted certificate on an IP-literal host?** Tried: MDN Cookies page (silent on IP hosts and on exceptions), "SameSite=Strict cookie withheld…" (silent). Build to: *favourable* → cookie transport (decision 2). *Unfavourable* → fall back to the token held by the page (storage) with the `Sec-WebSocket-Protocol` echo for the socket, which the WHATWG source above shows works mechanically; the host keeps accepting the bearer header. Because Safari may not give the socket at all (Settled), the REST path needs the same credential: the plan should make the credential accepted on REST from a cookie *or* header so the polling fallback works under either outcome.
4. **Does `history.replaceState` leave the full URL in an earlier history entry or tab list in Safari?** Tried: not searched past the first round of queries; no source. Build to: if the fragment form is used, the code never reaches the server; the page still calls `replaceState` first and clears the fragment, and the dialog says the code is single-use and the window closes on pairing (`core/remote.rs:65`), which makes a leaked URL inert after pairing either way.
5. **Does the iOS camera pass the `https://` URL unchanged, and does iOS Safari prompt for Local Network permission on a LAN IP?** Tried: not searched; device behaviour. See owner.
6. **How many connections a browser opens per page load, idle keep-alive hold time, and unprompted `/favicon.ico`.** Not searched. Build to: the page route and `/favicon.ico` must answer (or 404 cheaply) through the same unauthenticated pool, and closing a connection after a static reply (`Connection: close`) avoids holding one of the four slots for 30 s (`remote.rs:573`); the plan decides on that basis. A run against the harness with five parallel connections settles the pool count if the plan wants a number.
