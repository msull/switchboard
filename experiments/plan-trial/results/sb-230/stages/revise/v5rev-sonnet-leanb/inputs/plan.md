# Plan: a web control surface on the remote port (#230)

The host serves a small page from the port it already has. A phone opens it from the pairing window's QR, pairs, lists the sessions with the waiting ones first, reads a session's last response or screen, and sends a reply. The page is three embedded files (`web/index.html`, `web/app.js`, `web/app.css`) with no build step and no dependency. It speaks the protocol the headset speaks.

Yardstick for the world outside this tree: `facts.md` for #230. Where a decision rests on a line under Settled, the line is cited. Where it rests on a line under Unresolved or For the owner, the decision says so, and the default is the design that works whichever way the answer goes. Line numbers are from this worktree at `7fe8949`.

## Where this departs from the issue

- **The code travels in the URL fragment, not the query.** The issue's `/?code=…&key=…&id=…` puts the code in the request line of the first `GET`, so a server the owner has not verified receives it before any script runs, and `read_request` hands the query to the frame (`src/adapters/remote.rs:495–503`). A fragment is not part of the request target and is never sent (Settled, "Fragment and query"; RFC 9110 §4.2.5). The URL is `https://<address>:<port>/#code=<code>&key=<spki_sha256>&id=<server_id>`. The page still calls `history.replaceState` before anything else; whether Safari keeps the full URL in an earlier history entry is Unresolved 4, so the code's single use does the rest: `Paired` closes the window (`src/core/remote.rs:65`), and a leaked URL is inert after the first pairing.
- **The key in the URL is not authentication in a browser.** The issue says the comparison lets a genuine page refuse to send the code to a host whose `/info` key differs. A browser cannot see which certificate it is talking to, so a relay that terminates TLS and forwards to the real host shows the page the real key and the comparison passes. The plan keeps the comparison (it catches a QR for another host, and a stale one) and says in the dialog that it is not a defence. A browser pairing is weaker than a native one, which pins the key out of band; the dialog says "pair a browser only on a network you trust".
- **The one-line excerpt is not on the wire, and the spec says it is.** `docs/remote-client.md:207` says the card's excerpt is `last_message` from the `Stop` hook "on the record". `src/core/events.rs:127–135` stores only `last_stop_at` and `pending_at_stop`; `SessionView` (`control/src/lib.rs:637–689`) has no excerpt; the Mac computes it in the UI from the transcript (`src/ui/cards.rs:176–185`, `558–575`). Storing it would change `SessionRecord` (`src/core/model.rs:1053`, `SCHEMA_VERSION` 16) and moving the function would be a change of its own. This cut: a row shows the name, kind, the card word, `waiting_reason`, and the time since `last_activity_ms`; the excerpt is a follow-up. The same commit corrects line 207 to say the excerpt is not on the port yet.
- **"Revoked" cannot be said by the host.** Revoke deletes the `PairedDevice` (`src/core/remote.rs:86–92`), so a revoked token and an unknown one are the same 401 `unauthorized` (`src/app.rs:3142–3149`; Settled, tree bullet on 401). The page infers it from `/info`, which it can read unauthenticated: a 401 with the stored `server_id` and `spki_sha256` unchanged says "this device was removed on the host; pair again"; a different key or id says "identity changed, pair again"; no answer says "can't reach the host". No host change, and no new error code that could not be told the truth.
- **The events socket is an enhancement, not the base.** The issue has the page open `/api/v1/events` directly and meets "moves to the top without a reload" with it. Safari does not support `wss://` to a self-signed certificate even when trusted (Settled, "Certificate trust"), and a failed handshake exposes only close code 1006 (Settled, "WebSocket in browsers"). The base is polling the same REST routes, applying replies by revision as §4.4 says; the socket, when it connects, makes a change arrive at once. Acceptance steps 2 and 3 are met by polling on every browser.
- **The device cannot read its own scope back, so the issue's "hidden when the device lacks `control`" needs one small route.** `scope` in `/info` is the listing parameter, not a device property, and the tree has no `/me` (`src/app.rs:3027–3031`, `3044–3116`). The plan adds `GET /api/v1/me`.
- **The QR names an address the port may not answer on.** `src/ui/remote.rs:157–164` takes `local_address()` whatever `listen.lan` says. The URL uses it only when the port listens on the network, and `127.0.0.1` otherwise, with a line in the window saying the port is Mac-only.
- **Pre-pairing surface.** `docs/remote-client.md:306` and `:319` (and §4.3, line 194) give `/info` and `/pair`. It becomes those two and the three page paths; the plan amends them.

## The record

No record changes. `SCHEMA_VERSION` (16, `src/core/model.rs:12`), `VIEWS_SCHEMA_VERSION` (7, `model.rs:612`) and `IDENTITY_SCHEMA_VERSION` (1, `src/ports/remote.rs:17`) do not move. `devices.json` gains no field: a browser is a `PairedDevice` whose `name` is the body's `device_name` (`src/app.rs:3650–3655`, capped at 64 in `src/core/remote.rs:169`), which the page sets from its user agent ("Safari on iPhone"); its scope is the pairing window's. The page keeps nothing the host needs; the browser keeps the token in an `HttpOnly` cookie and, in `localStorage`, only `{server_id, spki_sha256, server_name}`, which is public and is what lets a later 401 be told from a changed key.

One existing field changes value. **`identity.json`'s `certificate` is reissued over the same key with IP subject alternative names** (the address in the URL and `127.0.0.1`). The certificate has none today (`remote.rs:101–106`), and Chrome matches names only against the SAN (Settled, "Certificate trust"), so the page must not rely on the click-through being offered. The pin is of the key, so every native pin holds. The reissue is persisted rather than made at each launch because a browser's exception is per certificate, and ECDSA signing is randomised, so a certificate remade at each launch would put the warning back at each launch. This is a new value for an existing field, not a new field: no bump. It is reissued once for an installation whose stored certificate has no SAN, and again only when the wanted address set is not covered.

The pairing window stays in memory and unsaved (`src/core/remote.rs:46–54`). The page's rehydration after a restart is a request: `/me` with the cookie.

## The signals

None new. The waiting mark is `SessionView.waiting` and `waiting_reason`; "moves to the top" is the revision in every envelope changing (`src/app.rs:3730–3741`) or a `changed` frame (§4.4). The host emits nothing the headset does not already receive.

## The actions and effects

**Host transport (`src/adapters/remote.rs`, `src/app.rs`).**

- **Cookie.** `/pair` takes an optional `"transport": "cookie"` in its body (additive; a native client omits it). With it, the reply carries `Set-Cookie: __Host-sb=<token>; Max-Age=34560000; Path=/; Secure; HttpOnly; SameSite=Strict` and the body **omits `token`**, so the page's script never holds it. Without it, the reply is unchanged. `read_request` takes `cookie`, `origin` and `host` into new `RemoteRequest` fields; the struct literal is at `remote.rs:506` only (Settled, tree bullet 1). `authenticate` (`app.rs:3127`) uses the bearer if present, else the `__Host-sb` value.
  - Where the credential lives is the security decision, so this is the safer store: a cookie the page's script cannot read, not `localStorage`, and not a `Sec-WebSocket-Protocol` value. Settled gives the mechanics for the socket (cookies ride the handshake, credentials mode `include`); whether Safari and Chrome store and send a `Secure; HttpOnly; SameSite=Strict` cookie set from a user-accepted certificate on an IP-literal host is **Unresolved 3**. It is the first thing the implementer tests (see Order of work). If it fails in a browser, the fallback is a follow-up for the owner (below), not a second transport built now.
  - **Limits, stated.** A cookie is not scoped by port, so another HTTPS service the owner runs on the same address receives it. `__Host-` fixes the host and path, not the port. The cookie name is a prefix the browser enforces (`Secure`, `Path=/`, no `Domain`).
  - **Cross-site writes.** A request authenticated by cookie alone must, if it is not a `GET`, or is an upgrade, carry `Origin: https://<Host header>`; otherwise 403, code `origin`. A bearer request is exempt (native clients send no `Origin`). `SameSite=Strict` already withholds the cookie cross-site; this closes the same-site, other-port case.
- **Reply headers.** `RemoteReply` (`remote.rs:388`) gains `headers: Vec<(&'static str, String)>`, written by `respond` (`remote.rs:530`). There are about twenty literals in `src/app.rs` plus the one in `connection` (Settled, tree bullet 1): add `RemoteReply::new(status, body, authenticated)` and convert them mechanically, so the one site that sets a header says so. `respond` also adds `Cache-Control: no-store` and `X-Content-Type-Options: nosniff` to every JSON reply, which no client reads.
- **`GET /api/v1/me`**, read scope, answers `{device_id, name, scope, server_id, server_name}` from the authenticated device and the identity. It is not in `capabilities`: no Swift client calls it.

**Pages, answered on the connection thread.** `GET /`, `GET /app.js` and `GET /app.css`, matched exactly, are answered in `connection` (`remote.rs:770`) from a new `src/adapters/web.rs` that holds the table of path, `Content-Type` and `include_str!` body. They never reach the frame: the bytes are constant, a page load must not wait on a busy frame, and the `DRAIN_PER_PASS` bound (`remote.rs:580`) is for work the core does. Anything else outside `/api/v1/` still reaches the frame and gets today's JSON 404 (`app.rs:3023`), `/favicon.ico` included; `index.html` declares `<link rel="icon" href="data:,">` so a browser has no reason to ask. A query on a page path is ignored and never logged (the connection thread logs nothing of a request).

- Headers on every page reply: `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and `Connection: close`. No inline script, no inline style, no external resource. If a browser does not admit `wss:` under `connect-src 'self'`, the socket is what is lost and polling carries; that is the enhancement stance, not a gap in the base.
- **Pool and window.** A page request is an unauthenticated connection: it counts in the 4-connection pool from accept (`remote.rs:701–706`), and `Connection: close` frees the slot at once instead of holding it for the 30 s idle timeout (`remote.rs:573`). That choice does not wait on the browser's connection count (Unresolved 6); the implementer measures five parallel connections against the harness and records it in the spike. A new `Limits.page` window allows 120 page requests a minute per listener, 429 past it (a load is three; `/pair` stays at 6 and `/info` at 60, `remote.rs:583–587`). The existing pool and rate tests count `/pair` and `/info` only, so they are undisturbed; `stalled_strangers_fill_their_own_pool…` (`tests/remote.rs:3226`) is the one extended.
- **What the page shows with no fragment and no token:** a "Not paired" screen that says to open the pairing window on the Mac and scan its code, with no host name. Its one request is `/me`, answered 401.

**Certificate.** `remote::issue_certificate(key_pem, server_id, &[IpAddr])` makes a certificate over the stored key with `SanType::IpAddress` entries (rcgen, `remote.rs:101` shows the call it replaces), and `certificate_ip_names(der)` reads the entries back with the module's own `der_element` (`remote.rs:~280`). `bind_remote` (`app.rs:~2940`) already holds the key; before `tls_config` it computes the wanted set (`127.0.0.1`, plus `local_address()` when `listen.lan`), and if the stored certificate does not cover it, issues, saves through `services.remote.save_identity`, and dispatches `AppAction::CertificateReissued(String)`. The core only mirrors the field, as `IdentityLoaded` does after the app has saved, and emits no `SaveIdentity`: an emitted one would reach the rebind test in `run_remote_effect` while `remote_bound` is still `None` and bind twice. Without the mirror, the next `SetServerName` would write the old certificate back over the new one. An address change after launch is picked up at the next relisten or launch, and the dialog says so.

**Certificate file.** For a browser that offers no way past the warning (Unresolved 1: whether Chrome and Safari offer click-through for this certificate, and whether the exception persists, is unconfirmed; the owner's phone settles it), a click-through cannot be the only path, and a download from the same address fails the same way. So the file leaves the Mac by another route. `AppAction::ExportCertificate` becomes `Effect::ExportCertificate(String)` (the stored base64); the app decodes it, writes `switchboard-host.cer` (DER) in the data directory through a new `RemoteStore::save_certificate_file(&self, der: &[u8]) -> Result<PathBuf, String>` (real `RemoteFiles`, atomic; `FakeRemoteStore` records), then dispatches `AppAction::RevealDocument(path)` (`src/core/action.rs:248`, `Effect::Reveal`), or `Failed` on error. The owner sends the file to the device by AirDrop. Whether the device then trusts it, and whether that fixes `wss://` on iOS, is Unresolved 2; the plan promises neither, and the polling base does not need it. The file is public (it is what TLS presents).

**Both new `AppAction` variants** join the group routed to `remote_action` (`src/core/action.rs:1248`).

**Pairing invite.** A pure `invite_url(identity, window, address, port) -> String` in `src/core/remote.rs` builds the fragment URL, so the UI holds no logic and a test can call it. `src/ui/remote.rs:160–166` calls it. The QR and "Copy invite" both carry the URL (decision 3 in the issue: one QR; the headset pairs from Bonjour and a typed code, and the CLI and the paste field parse text, so nothing needs the JSON form on the wire). The Swift side is where the old text was parsed: `PairingInvite.parse` (`client/Sources/SwitchboardProtocol/Info.swift:113–116`) accepts the URL as well as the JSON, and `main.swift:111`, `BrowserView.swift:103–107` and `:883` already go through it. A build that predates this cannot paste the new text; its Bonjour path is unchanged.

## The UI

The page (`web/`), one screen at a time, plain DOM with `textContent` only (no `innerHTML`, which keeps agent output from becoming markup):

- **Boot.** Read `location.hash`; if it holds `code`, `key` and `id`, call `history.replaceState(null, '', location.pathname)` first, hold the values in memory, `GET /api/v1/info`, and compare `spki_sha256` and `server_id` with the URL's. Mismatch: "This address is a different Switchboard than the code was for", nothing sent. Match: `POST /api/v1/pair {code, spki_sha256, device_name, transport: "cookie"}`; on success store `{server_id, spki_sha256, server_name}` and go to the list. Errors by `error.code`: `pairing_closed`, `wrong_code`, `wrong_key`, `rate_limited` each have a sentence.
- **No fragment.** `GET /api/v1/me`. 200: the list. 401: the inference from `/info` described above, or "Not paired" when nothing is stored.
- **Header.** Host name and the device's scope word, from `/me`.
- **List.** `/projects`, then `/projects/{id}/sessions` each, grouped by project, a project with a waiting session first, waiting sessions first within it. A waiting row says "Waiting on you" and `waiting_reason` in words (not colour alone), then name, kind, card word, time since `last_activity_ms`.
- **Session.** A Claude Code session (`kind: claude`) shows `/sessions/{id}/last-response`; any other kind shows `/sessions/{id}/screen`. The reply box shows when `/me` says `control` and `prompt_refusal` is null; with a refusal it shows the refusal's text and no box. Send is `POST /sessions/{id}/send {op, text}` with `op` random hex (made from `getRandomValues`, which exists without a secure context), kept so a retry after a dropped reply repeats the same op and is answered from `operations.log` rather than typed twice. A 403 `scope` re-reads `/me`. "Sent" means accepted; the session's card moving is the progress, per §4.5.
- **Refresh.** Every 3 s while the tab is visible the page reads `/waiting` and compares its `epoch` and `revision` with those of the list it holds; a different one refetches the list and the open session. A reply older than the one applied is dropped (§4.4). When the socket connects (`wss://<host>/api/v1/events`, no subprotocol), a `changed` frame triggers the same refetch at once and the poll slows to 20 s; on `resync_required`, a close or an error, the page refetches, polls at 3 s again, and retries the socket after 5 s doubling to 60 s. The page sends no `watch` frames: reading a content key puts it in the watch set for a minute (§4.4, item 3), and the poll keeps it warm.
- **Every 401** from any call runs the `/info` inference.
- **Device name** from the user agent: browser (`Edg`, `Chrome`, `Firefox`, else `Safari`) "on" device (`iPhone`, `iPad` including a Macintosh UA with touch, `Android`, `Mac`, `Windows`, `Linux`), else "Browser".

The dialog (`src/ui/remote.rs`):

- The pairing section shows the QR from the URL, keeps the code, key and address lines, and adds "Reveal certificate file". When the port is Mac-only it says so in place of the address.
- A sentence beside the existing redaction one (`remote.rs:70–76`): a browser cannot pin this Mac's key; it will warn about the certificate; proceed if the address is this Mac's, or install the certificate file on the device; pair a browser only on a network you trust; the code works once. The sentence promises nothing about which browsers allow the proceed.
- Browsers appear in the devices list like any device, with the user-agent name, scope and Revoke.

## The tests

- **Core (`src/core/tests.rs`).** `invite_url`: fragment form, no `?`, address and port, the loopback case. `CertificateReissued` sets the certificate and returns no effect. `ExportCertificate` returns the effect.
- **Adapters (`src/adapters/remote.rs`).** `issue_certificate` has the SPKI of the key (so pins hold) and the requested IPs; `certificate_ip_names` reads them and returns none for a `make_identity` certificate; coverage is judged by set, so a covered set is not reissued. `RemoteFiles::save_certificate_file` writes the DER it was given.
- **Host (`tests/remote.rs`, a helper beside `http`/`call` at `:245–325` that sends headers and returns the response head).**
  - Each of the three paths answers 200 with its `Content-Type`, the CSP exactly, `no-store`, `nosniff`, `Connection: close`, to an unpaired client; `/favicon.ico`, `POST /` and `/api` still get the JSON 404; a query is not echoed.
  - The embedded page references only paths the host serves: `index.html`'s `src` and `href` values are in the table or `data:`; every `/api/v1/...` string in `app.js` (kept in one table with `{id}` placeholders so a test can read it) answers something other than `not_found` for a paired device. Guards: no `<script>` without `src`, no `on…=` attribute and no `style=` in `index.html`; no `innerHTML`, `eval` or `document.write` in `app.js`.
  - The pairing flow end to end, as the CLI does it: `/info`, then `/pair` with `transport: "cookie"` gives a `Set-Cookie` with `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/` and no `Domain`, and a body with no `token`; the cookie alone reads `/me`; a native pair is unchanged (token in the body, no cookie).
  - `Origin`: a cookie `POST send` with no `Origin` or the wrong one is 403 `origin`; with `https://<host>` it runs; the same with a bearer needs none; a cookie upgrade with a foreign `Origin` is refused and with the right one is 101 (`subscribe_at`, `:1960`, takes extra headers).
  - `/me` shows `read`, then `control` after `SetDeviceScope`. After revoke, the cookie gets 401 `unauthorized` and `/info` returns the same `server_id` and key, which is what the page's inference needs. A rotated identity (`:1423`) returns a different key.
  - Pool and window: `Connection: close` frees the slot (four sequential page loads, then a fifth succeeds); four stalled strangers still make a fifth page request fail at accept; the 121st page request in a minute is 429 while `/info` and `/pair` windows are unaffected.
  - The sessions, waiting and last-response shapes the page reads are already pinned by the shared fixtures; no fixture changes, since no Swift speaker reads `/me`.
- **UI (`tests/ui.rs`, rewrite the assertions at `~:7476–7493`).** "Copy invite" puts the URL on the clipboard with the window's code and the identity's key in its fragment; "Reveal certificate file" dispatches `ExportCertificate`; the Mac-only notice shows when `listen.lan` is off.
- **Swift (`client/Tests/SwitchboardProtocolTests/FixturesTests.swift:157–165`).** The URL parses to the same `PairingInvite`; the JSON still does; a URL without `code` is an error. The URL's shape is repeated inline, as the JSON's is.
- **The page's logic.** `app.js` keeps its pure parts (fragment parse, device name, the `/info` inference, revision ordering) behind a guarded `module.exports`, and `web/app.test.js` covers them with `node --test`. A Rust test runs it and skips cleanly when `node` is absent, like the tmux tests. Nothing drives a real browser: the spike and the owner's phone do.

## Left for the owner

- **If the cookie test fails in a browser:** the fallback is the token held by the page with a `Sec-WebSocket-Protocol` echo (Unresolved 3). It puts the token where script can read it, so it is the owner's call, and a plan of its own.
- **A downloaded certificate is tied to one address.** If the Mac's address changes, the certificate is reissued and the device must trust the new file. A local CA signing the certificate would remove that, at the cost of a second key in the Keychain and a change to the identity model. That is a design decision for the owner.
- **The one-line excerpt** on the wire: move the card's excerpt out of `src/ui/cards.rs` into the core and add an additive `SessionView` field.
- **Owner's phone, branches that do not change this plan:** does the camera scan open the page and does the warning let you proceed (yes: the dialog's sentence is true as written; no: the certificate file is the path); does `changed` arrive without a reload on iOS Safari (the poll already moves the list); does the phone reach the Mac (the dialog states the listen requirement); does the phone show "removed on the host" after Revoke (the inference needs only the two assertions above).
