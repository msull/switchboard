1. **The cookie gives the token to every other service on the Mac, and the page rule cannot stop a replay.** The plan says cookies are scoped by host and not by port, but it only deals with the browser using that cookie on the host's own port (CSRF). The same fact means the browser sends `__Host-switchboard-<id>=<token>` in the `Cookie` header to every HTTPS service on that IP, at any port. That includes a dev server or any other local listener the owner opens in the same browser. With the `127.0.0.1` invite, browsers that treat loopback as a secure context may also send it over plain HTTP to loopback ports. Whatever receives the token can replay it from a non-browser client and set `Origin` and `X-Switchboard-Web: 1` to whatever it likes, so the page rule does nothing against a stolen token, and a `control` token can type into agent sessions. Another service on the same IP can also overwrite the `__Host-` cookie (cookie tossing). Today §5 holds the token only "as a bearer header over the pinned connection". The plan needs one of two things. Either make a leaked cookie useless on its own: for example, split the credential between the `HttpOnly` cookie and a second part held in origin-scoped (port-scoped) storage, sent as a header and required together. Or state this exposure in §5 and in the design.md known gaps, and default a browser pairing to `read`.

2. **An address change silently unpairs the browser and leaves a live token behind.** The cookie, the `localStorage` marker and the certificate exception are all keyed to the IP literal in the URL. After a DHCP change, the page at the new address has no cookie and no marker, so it shows "never paired" instead of anything about the address. The old URL or bookmark no longer works. The old `PairedDevice`, whose token is still valid, stays in the dialog until someone revokes it by hand. The plan picks SAN `localhost` precisely because addresses change, and the spike lists "whether the exception holds across an address change", but the cookie and the marker cannot survive one by construction. Either put a stable name in the invite URL, such as the Mac's `<LocalHostName>.local`, which iOS and macOS resolve over mDNS, or name this as a known gap and say what the page and the dialog show.

3. **The QR texture cache keyed only by code goes stale under the plan's own hint.** The payload now depends on `identity.listen.lan` (the LAN IP vs `127.0.0.1`) and on the port. The new hint tells the owner to turn on "Allow devices on the local network" while the pairing window is open. The cache at `src/ui/remote.rs:166-173` is "unchanged, still keyed by code", so the QR keeps showing the `127.0.0.1` URL after the toggle. "Copy invite" would copy the new payload, so the two would disagree. Key the cache on the payload string. The plan also does not say what is drawn when `lan` is on and `local_address()` returns `None`. Today that case gives an empty `addresses`; with the change it would build a URL with no host. Say that no QR is drawn and give the reason.

4. **Replacing the JSON invite breaks the scan and paste path for every client built before this change.** §5 of `docs/remote-client.md` defines the QR as `{server_id, spki_sha256, code, addresses}`. The current `PairingInvite.parse` (`client/Sources/SwitchboardProtocol/Info.swift:115-117`) only decodes that JSON, so an older `switchboard-remote` or headset build fails on the new URL. The shared contract is meant to change additively. Either keep producing the JSON somewhere (for example a second "Copy invite (JSON)" or a `json=` form), or name the break in the CHANGELOG line and in §5, with the three-argument `pair <host:port> <code> <spki_sha256>` as the workaround.

5. **The certificate is only renewed at startup, while the plan promises renewal "whenever it is within 30 days".** The reissue is placed in `load_identity` (`src/app.rs:2782`), and `tls_config` is built once per bind (`src/app.rs:2957`). An app left running across `not_after` will serve an expired certificate. The browser then warns, and the plan's dialog sentence tells the owner to read that warning as "something else may be answering". The plan also contradicts itself: it says "replaced once, on the first listen" but places the code in the identity load. Run `reissue_if_due` when binding or rebinding and on a daily check from `Tick`, and rebuild the `ServerConfig` when it reissues. A test should cover a certificate that becomes due while the app is running.

6. **The §5 edits leave sentences in place that will be false.** `docs/remote-client.md:312` says the token "is sent only as a bearer header over the pinned connection". The §5 bullet at 304 says "after pairing, every connection verifies the pin before the token is presented". The closing §5 rule says to keep tokens and codes "out of ... URLs", but the invite now puts the code in a URL. The plan's doc list only says "never in a URL stays" and adds a trust paragraph. It needs to rewrite these three statements, and also the "pairing with a pinned host key" summary in design.md's Remote client section (line 3111), for the browser case.

7. **Icon probes the browser makes on its own take slots in the unauthenticated pool and the frame, and the plan does not count them.** iOS Safari requests `/apple-touch-icon*.png` and `/favicon.ico`, and desktop browsers request `/favicon.ico` when no `<link rel=icon>` is present. Under the plan these "stay 404" through the frame: they use an inbox slot and one of the 4 unauthenticated connections during exactly the cold load the spike measures. The named fallback (drop `icon.svg` and its `<link>`) makes `/favicon.ico` certain. Answer these 404s on the connection thread the same way as the static files, and include them in the spike's pool measurement.
