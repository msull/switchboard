## 1. On-disk record and rehydration (before any pane)

The page is a **new client of existing records; it adds almost nothing to disk.**

- Host side, durable, already present:
  - `<data dir>/identity.json` (server id, certificate, `spki_sha256`, listen preference; `src/ports/remote.rs:26`), key in the Keychain.
  - `<data dir>/devices.json`: `PairedDevice { id, name, scope, token_sha256, created, last_seen }` (`src/ports/remote.rs:96`). A browser is one more row. Issue decision 6 needs **no schema change**: `name` is already a free string. The one new input is the device name from the `User-Agent` (parsed to `Safari on iPhone`), which `/pair` currently takes from the body's `device_name` (`src/app.rs:3650`). Simplest: the page computes the name and posts it as `device_name` (no host change). A header parse on the host is not needed. Cap/sanitize the length anyway.
  - If cookies are chosen (decision 2), the host still stores only the token's SHA-256. **Do not add a session table.** The cookie value is the bearer token itself, so `authenticate` (`src/app.rs:3127`) looks it up by `token_sha256` exactly as now. Revocation (`AppAction::RevokeDevice`, `src/core/remote.rs:86`) therefore already kills it on the next request, with no new record.
- Page side, durable: one thing, the token. Under the cookie option it is in an `HttpOnly` cookie the script never reads, so the page keeps **no durable state of its own**. Everything else (sessions, last responses, screens) is in memory and refetched, which is the rule the spec gives clients (§7: bodies in memory only). Scope/host name come from `/info` and an authenticated read.
- Rehydration on page load, no pairing query present:
  1. `GET /api/v1/info` → `server_id`, `spki_sha256`, `server_name`, `epoch`, `revision`.
  2. Authenticated `GET /api/v1/projects`, per project `GET .../sessions` (or `waiting`), carrying the cookie.
  3. 401 → "pair again" state. A key differing from the one remembered → "identity changed". Revoked → 401 with `unauthorized` ("the token is not known; pair again", `src/app.rs:3142`), which the page must show as "revoked", not as a generic error.
  4. Open `/api/v1/events` (subscribe first), then snapshot, then reconcile by revision (§4.4), and `watch` the open session's `conversation` or `screen`.
- Bearer-header clients (visionOS, CLI) keep working untouched. Nothing here changes `SCHEMA_VERSION` or `model.rs`.
- What the page remembers across a reload besides the cookie: at most the host's `server_id` + `spki_sha256` in `localStorage` (per-viewer convenience, tolerated empty), so "identity changed" can be said. The spec says the client keeps the pin; a browser cannot enforce it at the TLS layer (see §3), so this is advisory only.

## 3. Findings that change the plan

1. **The certificate has no subject alternative name.** `CertificateParams::new(Vec::new())` (`src/adapters/remote.rs:99`). Native clients pin the SPKI and ignore names. Browsers validate the name against the host in the URL (an IP such as `192.168.x.y`, or `localhost`). With no SAN every browser reports a *name mismatch* as well as "self-signed", and iOS Safari's click-through for it is flakier. This needs fixing for the feature (and it is additive, because the SPKI is unchanged): add IP and DNS SANs, which means the cert must be **reissued from the same key** on address change. The spec already says (§5) a reissue from the same key keeps pins valid, but `identity.json` currently stores one certificate made once. Settle: SANs for the current LAN addresses + `localhost` + `<hostname>.local`, reissued from the stored key when the address set changes (key is in the Keychain; `make_identity` generates both together today, so a "reissue cert from key" function is new). Also rcgen's default validity is very long; iOS only honours "trust this certificate" profiles for ≤398 days, so if decision 1 picks certificate download, validity and `serverAuth` EKU must be set explicitly. This is the main hidden cost of the issue.
2. **There is no clean way to pin in a browser. State it plainly (decision 1).** Recommendation: **the click-through is the trust step, said in the paired-devices dialog; do not offer a certificate download in this cut.**
   - Why: a download means a configuration profile on iOS and a Keychain import on macOS: it makes the owner install a root-trust-adjacent artifact on a phone, which is more dangerous than the problem, needs the 398-day/EKU/SAN work above, and has to be served by the same unauthenticated port.
   - What the click-through buys: the browser remembers the exception for that origin and the channel is encrypted to whoever answered. What it does not buy: authenticity of the first page. The `key` in the URL protects against an impostor `/info`, but an impostor serving the page can omit the check and read the code. Say this in the dialog sentence. The QR is out of band, so the real protection is that the code is 40 bits, single-use, three attempts globally (§5), and only the owner's screen shows it.
   - A compensating step worth the plan's attention: show the key's short form (`short_hash`, `src/ui/remote.rs:303`) **on the page** after pairing and in the paired-devices row, so the owner can compare by eye as the headset flow does.
3. **Token transport (decision 2): recommend the cookie.** Reasons: `fetch` and `new WebSocket` both send it without script access; `localStorage` is readable by any script on the origin; the `Sec-WebSocket-Protocol` route needs the token in script memory and in a header that proxies/log lines see, and the host would have to echo the subprotocol. Costs the plan must include:
   - `RemoteRequest` gains `cookie` (take only the `sb_token`-named cookie out of the headers, as the bearer is taken out so it is "never logged with them", `src/adapters/remote.rs:355-358`); `authenticate` reads bearer, else cookie. Additive.
   - `RemoteReply` needs a way to add a `Set-Cookie` header on the `/pair` reply and to set a content type/headers for static files. `respond` (`:530`) hard-codes the head; change `RemoteReply` additively (a `headers: Vec<(&'static str,String)>` or a `content_type` plus extras) with `Default`-style helpers so the ~40 constructors in `app.rs` keep compiling. Check how many sites build `RemoteReply { .. }` literally (many: `app.rs:1675`, `:1684`, `:3570` and others) before choosing. A constructor-based or `..Default` change is cheaper.
   - **Cookie auth opens CSRF and cross-site WebSocket hijack that bearer headers never had.** `SameSite=Strict` covers most, but a LAN page on another origin at the *same host different port* is same-site. Require on every cookie-authenticated request that mutates, and on the WebSocket upgrade: `Origin` equals `https://<Host header>`. That means parsing `origin` and `host` too. Bearer-header requests skip the check. `Secure` works on an untrusted self-signed origin once the exception is accepted. Add the `Path=/`, and `Max-Age` long (the token does not expire; revocation is the control).
   - Cookies are per host, not per port (browsers ignore the port for cookie scoping): two Switchboard hosts on one machine/IP with different ports would **overwrite each other's cookie**. Name the cookie with the port or the first 8 chars of the `server_id` (`sb_<id8>`), or accept one-host-per-address and say so. Recommend the id-suffixed name; it also makes "identity changed" detectable.
   - The pairing reply must keep returning the token in the JSON body for native clients (do not change the body), and *also* set the cookie, only when the request carries a marker (e.g. an `X-Switchboard-Web: 1` header or `"web": true` in the body) so the CLI does not receive cookies.
4. **The "one-line excerpt the card shows" is not on the wire.** `last_message` lives on the record from the Stop hook (`src/adapters/hooks.rs:71`, `src/bin/switchboard-hook.rs:37`); `SessionView` (`control/src/lib.rs:637`) has no such field and `docs/remote-client.md` §4.3 says the card excerpt is the record's `last_message`, "a field of the session's metadata". Either add an additive, redacted, 4 KiB-bounded `last_message` (or `excerpt`) to `SessionView`, which then flows through the fingerprint (`src/core/revision.rs`) and the Swift fixtures (decoding must stay tolerant: the Swift side decodes with defaults for new fields, check `client/Sources/SwitchboardProtocol/Views.swift`), or the page shows state + `waiting_reason` only and fetches `last-response` on open. The issue says "no new read model unless the page cannot do without one"; I'd say the card excerpt is that case, and the plan should do it through the redaction path (§4.3: card excerpt "masked from the turn's full text, then cut"). Confirm with `rg last_message src/app.rs` — it is not served today.
5. **Pool accounting for a browser page load (decision 4).** A browser opens up to 6 parallel connections per origin, each is an unauthenticated connection until its first reply with `authenticated: true`. The static files return `authenticated: false` forever, so a connection that only serves page files stays in the pool of 4 and a 5th simultaneous connection is closed at accept. With HTTP/1.1 keep-alive the page, CSS and JS share connections, but Chrome speculatively opens extra ones. Plan: (a) serve the page from a small number of files (`/`, `/app.js`, `/app.css`, maybe one favicon response) and put CSS+JS inline-free but few; (b) the page's own `fetch` carrying the cookie will make a connection move to the paired pool on its first authenticated reply, which already works; (c) the static route needs its own rate window (it is not covered by `Limits::limited`, `:631`): e.g. 120/minute per listener, counted in the connection thread, answered 429 before the frame. Static bytes should be answered **on the connection thread, not the frame**: they are `&'static str`, need no core state, and would otherwise occupy the 64-slot inbox and the 8-per-pass drain. The one wrinkle is that `serve_remote` is where the allowlist lives today; the new allowlist for static paths would live in the adapter (`connection`), which §4.1 says must be "thin"; keep it to an exact-match table, fixed at compile time. This also keeps §5's "nothing before pairing but `/info`, `/pair` and now the page itself" true by construction: the static table is closed and contains no host data.
6. **Allowlist change in the spec.** "Any path outside `/api/v1/` is refused" (`src/app.rs:3023`, spec §4.3 "refused before translation") becomes: exact `GET` of `/`, `/app.js`, `/app.css` (and optional `/favicon.ico` → 204/404) served; every other non-`/api/v1/` path remains 404. Methods other than GET/HEAD on those → 405 (`405` already in the reason table). `GET /` with the pairing query is the same document.
7. **Headers for the static answers (decision 4).** Proposed set, all tested in `tests/remote.rs`:
   - `/`: `text/html; charset=utf-8`; `/app.js`: `text/javascript; charset=utf-8`; `/app.css`: `text/css; charset=utf-8`.
   - `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. `connect-src 'self'` covers `wss:` same-origin in current browsers; Safari older than 15.4 did not match `'self'` for WebSocket, so add `wss:` explicitly if testing shows it (cannot be tested without a browser: note as a known risk).
   - `Cache-Control: no-store` (the page carries no secrets, but "no caching across versions" in the issue; an `ETag` of the build version is the alternative and also fine, but `no-store` is simplest and the files are small). `Referrer-Policy: no-referrer` (the URL briefly carries the code), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`.
   - The pairing URL query reaches the server in the request line; it is parsed into `RemoteRequest.query` and the code must **not** be logged: `refuse`/log lines print `request.path` only (no query) already (`src/app.rs:3760`), keep it so. The page script strips it with `history.replaceState` first. `Referrer-Policy: no-referrer` stops it leaking via referrer; the history entry is replaced before any navigation.
   - Also make the code in the URL harmless after the fact: it is single-use and closes the window on success, which is already true.
8. **Version skew between page and host:** page is `include_str!`ed so it always matches the binary; the page should read `protocol` from `/info` (`REMOTE_PROTOCOL`) and refuse a higher major, as the Swift client does.
9. **URL form for the QR (decision 3): one URL, keep the JSON as parse-only compatibility.** `https://<address>:<port>/?code=<code>&key=<spki_sha256>&id=<server_id>`. Everything is URL-safe (Crockford code, hex key, UUID). Changes: `src/ui/remote.rs:160` builds the URL (needs a non-empty address; when `local_address()` is `None` fall back to the JSON/no QR, since the URL needs a host); "Copy invite" copies the URL; the multiple `addresses` in the JSON collapse to one, so choose the address a phone can reach (`remote::local_address()`, `src/adapters/remote.rs:962`). `PairingInvite.parse` (Swift) and the CLI must accept both: if the text starts with `https://`, parse host:port and the three query items, else JSON. Keep JSON decoding for old hosts ↔ new clients (a new client against an old host's pasted JSON; an old CLI cannot read the new URL, which is the one forward-compat break to say in the changelog). Add a Swift fixture and a parse test, and a Rust test that the UI payload parses. The headset's typed-code path and Bonjour path need no change. There is no reason to keep two QRs.
10. **Revocation visibility.** Revoke drops the subscriber queue so the socket closes (`src/app.rs:486`); the page then re-requests, gets 401 `unauthorized`, and shows "revoked". The page cannot tell "revoked" from "token never valid" except by having been paired earlier in this origin (cookie present at load, 401 on first call). Say "This device was revoked or the host forgot it. Pair again." Key rotation → new `spki_sha256` from `/info` ≠ remembered → "identity changed, pair again", and the page sends nothing.
11. **`/info` rate limit** (60/min per listener, `INFO_PER_MINUTE` `:584`) is shared by every browser load and by the page's reconnect loop. The page must call `/info` once per load, not per poll, and back off on 429.
12. **Reply by revision and the events socket from a browser.** Page needs: `hello` first; buffer events; snapshot; reconcile (§4.4). Browser `WebSocket` cannot set headers, so with the cookie it just connects to `wss://<host>/api/v1/events`. The frame sends `watch`/`unwatch` text frames the same as native. Subscriber `all` (scope=all) is not wanted: workers hidden.
13. **Waiting-first grouping needs only existing data:** `GET waiting` and `SessionView.waiting`, `card`, `kind`, `waiting_reason`. "A session that starts waiting moves to the top without a reload" = a `changed {waiting}` / `changed {session}` event, then refetch.
14. **Reply box:** posts `POST /api/v1/sessions/{id}/send` with an `op` (UUID via `crypto.randomUUID()`, which needs a secure context: fine under HTTPS even self-signed once excepted) and handles the three op statuses from `/ops/{op}` (§4.5): never resubmit on `interrupted`. Hidden unless the device's scope is `control`: scope is **not returned by any authenticated read today**. `/pair` returns it once; on a later load the page has only the cookie. Need a source: add an additive `scope` (and `device_name`) to an authenticated reply. Cheapest: a new `GET /api/v1/me` -> `{name, scope, server_name}` or extend `/info` with a `device` object when authenticated (`remote_info` is reached before `authenticate`, `src/app.rs:3028`, so `/info` would need to peek at the cookie/bearer). Prefer a new `GET /api/v1/device`, behind auth, read scope: one new arm in `serve_remote` plus the doc row. A scope lowered in the dialog (`SetDeviceScope`) then shows on the next call; the page should re-read it on a 403.
15. **Dispatch tickets / draft / dictation endpoints stay unused** (out of cut).

## 4. Proposed shape (for the plan)

Order, each a working app, smallest first (CLAUDE.md "Adding a feature" and one-commit milestones):

1. **Cert SANs.** `make_identity`/reissue from the stored key; tests: SPKI unchanged across reissue; native pin still verifies; the cert lists the LAN IP and `localhost`. (`src/adapters/remote.rs`, `tests/remote.rs` `a_change_of_address_rebinds_the_port` `:1493` is the neighbor.)
2. **Adapter plumbing:** `RemoteRequest { cookie, origin, host }`, `RemoteReply` headers/content type, a closed static table answered in `connection` with its own rate window and pool behavior; `respond` takes headers. Unit tests in the adapter.
3. **Host API additions:** cookie auth in `authenticate`, `Set-Cookie` on a web `/pair`, Origin check for cookie-authenticated POST/upgrade, `GET /api/v1/device`, excerpt on `SessionView` (control crate additive) with fingerprint and fixtures. Core test where state moves (none expected: no new core state).
4. **`web/` (index.html, app.js, app.css)** embedded with `include_str!`; no build step. `web/` row in README Layout. Plain JS, no inline script (CSP).
5. **QR becomes the URL**; Swift `PairingInvite.parse` and CLI accept URL or JSON; script/dev-aid unchanged except README note on "Copy invite".
6. **Docs:** remote-client.md §4.1 (static pool), §4.3 (static paths table and `device`), §5 (cookie, Origin, click-through, key on page, URL form, dialog sentence), §11 tests, §13 decisions; design.md remote status; CHANGELOG Unreleased line; the paired-devices dialog sentence in `src/ui/remote.rs`.

## 6. Risks and open questions for the owner

- Certificate SANs and browser acceptance on iOS Safari cannot be verified from CI. The plan should list a manual acceptance on a real phone (the issue's acceptance paragraph).
- Cookie `Secure` over a self-signed exception works in Safari/Chrome; Firefox is stricter about exceptions per origin with a changed SAN set. Reissuing the cert when the address changes invalidates the browser's saved exception: the owner clicks through again (not a pairing loss, since the key is the same and the cookie stays).
- The URL puts the code in the request line the host receives (and in the QR image). The host logs path only. Browser history: removed by `replaceState`, but the initial navigation entry is already recorded by some browsers before script runs; mitigate with the single-use code and 5-minute window, and say so.
- Mixed content: the page is `https`, so the QR must be `https://`. Phones that scan and offer "open in browser" may preview the URL (some scanners fetch it server-side; here it is a LAN address so they cannot).
- Multi-host on one IP and cookie scoping (finding 3).
- Is the Bonjour-name (`<hostname>.local`) wanted as a second address in the SANs? Not required for the first cut.
- Whether to extend `SessionView` with the excerpt (finding 4) or drop the excerpt for the first cut. Recommendation: add it (additive, redacted).
