1. Stale line reference. The plan says `PairingInvite.parse` is at `client/Sources/SwitchboardProtocol/Info.swift:90`. In the worktree, `struct PairingInvite` is at `:94` and `parse` is at `:114`. The plan states that all references were checked against the current worktree, so this one should be corrected. The other references I spot-checked do match: the schema versions (16, 7, 1, protocol 1), the `RemoteReply` literal sites in `src/app.rs` and the one at `adapters/remote.rs:829`, `serve_remote`, `authenticate`, `remote_pair`, `Limits`, `connection`, `short_hash`, `agent_excerpt`, `core/events.rs:132` and `write_fixtures`.

2. The `pairing_invite` and `local_address` split is not stated. `local_address()` lives in `src/adapters/remote.rs:962`, not in the core. The plan puts a pure `pairing_invite(identity, code, address)` in `core/remote.rs` and says the UI stops building the payload. It should say explicitly that the UI still calls `local_address()` and passes the result in as an argument. Otherwise an implementer may import an adapter function into `src/core/`, which the layering rule forbids. The plan should also say that the port is `cx.remote_port.unwrap_or(identity.listen.port)`, as in `src/ui/remote.rs:157`, and that `pairing_invite` takes a `SocketAddr`. As written, the IPv6 bracketing test cannot be written against the stated three-argument signature.

3. The "an expired cookie is a re-pair" claim is wrong against the stated decision. The token never expires, but the cookie lasts 400 days, so after that the device record in `devices.json` is orphaned. The page has no way to tell the owner, and the dialog keeps listing a device that will never authenticate. Either say that this is accepted and show `last_seen` in the dialog, or have `authenticate` re-issue `Set-Cookie` on use. The plan chooses neither, yet the spec says tokens "do not expire".

4. Spec §5 line 312 says the token is "sent only as a bearer header ... never in a URL". The plan updates the token line in §5. It does not mention that the pairing code now appears in a URL: the QR, "Copy invite" text, the browser history entry for the first load, and the clipboard. `replaceState` only helps once the script runs. Add a stated limit: the code is single-use, 40-bit and valid for five minutes. Say that the first navigation lands in history, and that `Referrer-Policy: no-referrer` is sent only on the static answer. A 404 or 429 on `GET /?code=…` is built by `connection` and would not carry that header unless the plan says so. Please state that every response on the static path carries the header set, including the 405 and 429 answers.

5. The 429 and 405 answers for static paths are specified only in prose. The test list asserts the headers on 200 only. Add them to the test, since the CSP and `no-store` must also be on the error answers or the plan's own claim "every static answer carries" is untested.

6. Unauthenticated static serving is a new kind of exposure and the plan under-argues it. `docs/remote-client.md` §5 says that before pairing a non-loopback bind serves only `/info` and `/pair`. The plan keeps that rule by adding the three page files. It does not say whether the pages are served after pairing, or when the pairing window is closed. If they are always served on a LAN bind, any host on the network can fetch the page and fingerprint the app with no pairing window open. Say whether the table is gated on the window being open, or state that it is deliberately always on.

7. The shared 120-a-minute static window is per listener, not per peer. Any stranger on the LAN can exhaust it and block the owner's page load. The plan notes this for `/info` only in passing. Say that it is accepted, or key the window by peer address.

8. The `/device` endpoint lacks a scope row detail. The plan adds `("GET", ["device"])` to `serve_remote` and "the endpoint table with scope read", but does not say the existing allowlist test or the doc table at `docs/remote-client.md` §4.3 is updated in the same commit. Name the allowlist test that must change, since `serve_remote`'s "unknown endpoint is 404" assertions will otherwise fail.
