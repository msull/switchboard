The plan changed at the path `review/1/repo/plan.md`. I re-read the file after editing and confirmed each change below is in it. I checked every code claim in the feedback against worktree `7fe8949` before editing; points 3, 4, 5 and 6 turned out to be right, and I found my own errors in 5 and in the §5 reasoning behind point 2.

1. **Decisions 3 to 6 were cited and not written. Fixed.** The plan now has a "The decisions" section with all six. Decision 4 gives the static path table, the full CSP string, the headers, the pool bound, the `page` rate window and the page's states. Decision 6 gives the scope rule for a browser device and the name rule. Decision 3 gives the one-URL invite. The "Tests" section quotes the CSP string from decision 4.

Decision 1 now says so. Decision 4 now justifies the page exception to §5's "require pairing before anything but `/info` and `/pair`": the bytes hold no session data, they are the same for every host of this version, and they reveal only what the documented protocol already reveals. The spec amendments name §5 line 306 (the four static paths added) and §4.1 line 123 (the frame rule: the static set is answered by the adapter). Both are in "Docs and status".

3. **The lan guard breaks the fixtures. Fixed by putting the guard in the UI only.** "Actions and effects" now says why core does not refuse: the default identity has `lan: false`, so `tests/remote.rs` at 407, 584 and 1627 and `src/core/tests.rs` at 11878–11936 would all break. The UI test at `tests/ui.rs` 7424 now seeds lan on, and two new UI tests cover lan off and lan on. The `pair()` helper count is written as 35 "by grep", since my grep and the feedback's 36 differ by one.

4. **The `RemoteReply` count was wrong. Fixed.** "Actions and effects" now lists the ten literal constructions in `src/app.rs` (1664, 1679, 2365, 2371, 2376, 2754, 3570, 3723, 3736, 3767), the one in the adapter (829), and says the other 18 matches are return types. Order step 2 says eleven sites.

7. **The QR change is not additive. Recorded as breaking, with the handling.** I did not keep the JSON in the QR. Two codes on one window would be harder to use than one, and the only consumer of the JSON that cannot be rebuilt is an installed `switchboard-remote` binary, which the plan now says must be rebuilt. The parsers keep reading JSON, so text copied from the previous build still pairs with a rebuilt client. The visionOS and iPadOS clients pair by Bonjour and a typed code and never read the QR. Decision 3 gives this reasoning; "Contract additions" lists the invite change as breaking; the CHANGELOG line says the CLI must be rebuilt; §5 line 309 is in "Docs and status".

Fixed.** "Order" now starts with steps 1 to 3, which run now: the UI guard and `invite_url`, the adapter header and close changes, and the static table with placeholder pages at pool 4. 9. **The Origin check passes requests with no Origin. Fixed.** Decision 2's "Origin rule" now says: a cookie request that is not `GET` must carry an `Origin` equal to `https://<Host>`, or it gets 403 `origin`. A `GET` with an `Origin` must match it; a `GET` without one passes. It also says what a non-browser client holding the cookie gets: reads that the cookie allows, and writes only with the bearer. The test "a_cookie_is_checked_against_its_origin" in "Tests" covers each case.
