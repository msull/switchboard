# Feedback on plan.md (issue #230), against worktree HEAD 7fe8949

1. **Decisions 3 to 6 are cited and never written.** The plan cites decision 4 for the static file set, the CSP, the page rate window and the pool bound (lines 46, 47, 77, 84), and decision 6 for a browser device's scope (line 21). Only decisions 1 and 2 exist. Line 84 asserts "the exact CSP string", and no string is given anywhere; line 76 names only `connect-src 'self'`. The plan needs the full CSP value, the scope rule for a browser device, and the static-path table written out before anyone can implement or test them.

2. **The plan says docs/remote-client.md §5 holds, and it does not.** Decision 1 (line 26) says §5 forbids a route outside `/api/v1/` before pairing, which is why the certificate is not offered for download, and then says "The rule in `docs/remote-client.md` §5 holds: before pairing, a non-loopback bind answers only `/info`, `/pair` and the page's own files." The spec's bullet (§5, "Require pairing **before** anything but `/info` and `/pair`") has no page exception. The plan adds four unauthenticated paths outside `/api/v1/` (`/`, `/app.css`, `/app.js`, `/favicon.ico`), and the certificate-download argument rejects a route of the same kind. The spec amendment list (line 32) does not name this bullet. The static serve in `connection()` also bypasses the §4.1 pipeline ("HTTP request → auth and scope check → allowlist → …"), which the amendment list does not mention. Either amend those lines and justify the exception, or drop the pre-pairing page.

3. **The lan guard breaks existing tests, and the plan lists only one of them.** `OpenPairing` with lan off is refused (line 42). The test fixtures run with lan off: `port_built` never sets lan, the app's first-run identity is `Listen::default()` (`src/app.rs` 2836), and `Listen::default()` is `lan: false` (`src/ports/remote.rs` 66). Affected:
   - the `pair()` helper in `tests/remote.rs` (406–424), called 36 times, so every pairing test in that file;
   - direct `OpenPairing` dispatches at `tests/remote.rs` 584 and 1627 (the fixture writer);
   - the core pairing tests at `src/core/tests.rs` 11878, 11899, 11922, 11936, whose `identity()` helper uses `Listen::default()` (11776);
   - the dev aid `pairing <code>` (`src/script.rs` 730), which now needs `remote-listen lan` first. Line 106 says no script change is needed, and the README (lines 277–278) documents the order.
   Only `tests/ui.rs` 7424 is named (line 95). The plan must say where the guard lives. If it stays in core, name the fixture change and what turning lan on does to the address the tests connect to. If it moves to the UI only, say so, and drop the core test at line 93.

4. **The `RemoteReply` count is wrong.** The plan says there are "28 literal `RemoteReply { … }` sites in `src/app.rs`" (line 44). `grep` matches 28 lines, but 18 are return types (`-> RemoteReply {`). There are 10 literal constructions, at `src/app.rs` 1664, 1679, 2365, 2371, 2376, 2754, 3570, 3723, 3736 and 3767. Correct the count; the mechanical change is smaller than the plan implies.

5. **"Connection: close" does not cover the direct writes.** Line 48 says every reply with `authenticated: false` closes, so a stranger holds an unauthenticated slot for one request. But `connection()` writes the rate-limit 429 (`src/adapters/remote.rs` 789) and the `busy` 503 (819) straight to the socket and `continue`s the loop. Those keep the slot for up to `IDLE_TIMEOUT` (30 s), and a stranger who is rate-limited on `/pair` holds it. Either those writes close too, or the claim that a slot is held for one request is false.

6. **The design reference does not exist.** Line 102 says `docs/design.md` trust boundary (219–265) "gains 'a browser is a paired device' in the device-kind sentence." That section has no device-kind sentence. The nearest text is the paragraph about the redacted screen read by a paired device (around lines 250–256). Name the sentence that changes, or say a new bullet is added.

7. **The QR change is not additive and is not listed as a contract change.** CLAUDE.md requires the contract to be extended additively. `docs/remote-client.md` §5 (line 309) specifies the QR as `{server_id, spki_sha256, code, addresses}` with the same JSON as text. Line 53 replaces both with a URL ("The QR encodes `invite_url`, as does the text beside it"), and the "Contract additions" section (lines 122–128) does not record the removal. Any client that parses the QR's JSON breaks on a new code, including the `switchboard-remote pair "$(pbpaste)"` path that `README.md` 276–278 documents and any installed Swift client that scans. The `addresses` array also shrinks to one IPv4 address. Either keep the JSON payload for native clients and add the URL alongside it, or list the change as breaking and say how old clients are handled.

8. **The gate blocks work that does not depend on it.** Step 1 (line 112), the iPhone and second-Mac spike, gates every later step. Steps 2 and 3 (the lan guard, `invite_url`, the adapter headers and the `Connection: close` change) do not depend on any spike outcome; only the pool bound in step 4 does. The plan also names nobody to run the spike and has no fallback if it cannot run before the commit. Start the independent steps now, and say which later steps wait on which outcome and who records the results.

9. **The Origin check passes requests that send no Origin.** Line 30 refuses a cookie-authenticated request only when it carries an `Origin` that is not `https://<Host>`. A cookie request with no `Origin` passes. Browsers send `Origin` on cross-site writes, but a state-changing cookie request should not depend on that. Refuse any cookie-authenticated non-`GET` without a matching `Origin` (or a `Sec-Fetch-Site` of `same-origin`), and say what a non-browser client holding the cookie gets.

10. **One test checks a Rust copy of the Swift parser.** Line 88 parses the URL "the way `PairingInvite.parse` does" in Rust. That checks a re-implementation, not the Swift code, which is the code that matters. The only check of the real parser is the Swift case at `client/Tests/SwitchboardProtocolTests/FixturesTests.swift` 157, and the plan does not say how it stays in step with `invite_url`. Put the expected URL in a shared fixture that both the Rust and Swift tests read, or drop the Rust test.
