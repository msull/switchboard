1. **Decision 1's trust step proves nothing, and contradicts the plan's own first departure.** The plan has the owner "check the key on the page against" the key in the pairing window. But the page's key comes from `/info`, which is served by whatever host terminates TLS. An impostor that the owner clicks through can relay the real host's `/info` and show the genuine 16 digits. The plan concedes this in its first bullet ("a host that terminates TLS can serve a page and an `/info` that agree"), then relies on the same comparison in Decision 1 and in the user-facing sentence ("Check the key on the page against this one"). A browser's certificate viewer shows the certificate fingerprint, not the SPKI hash, so the owner cannot compare against it either. docs/remote-client.md §5 and design.md's "Trust boundary" are binding: "Pairing verifies the key before the code is sent." This design sends the code (in the GET URL, then in `/pair`) to an unverified peer, and the token comes back to that peer as a `Set-Cookie`. The plan needs one of these:
   - a real owner-checkable binding, such as the SPKI hash shown in a form the browser exposes, or an IP SAN plus a fingerprint the owner can read in the certificate dialog;
   - an explicit amendment to the "key verified before the code is sent" rule, written into design.md and §5 as a deliberate weakening, with the owner's sign-off;
   - removing the "check the key on the page" instruction, since it gives false assurance.

2. **Dropping the JSON invite breaks the additive-contract rule and shipped clients.** CLAUDE.md says to extend the contract additively and never remove. The plan replaces the QR and "Copy invite" payload (`src/ui/remote.rs:160-166`) with a URL and drops the JSON "from the host". Already-installed native clients decode only the JSON. Swift's `parse` already falls back to a URL, but only in the plan's new version. The JSON also carries `addresses`, which can hold several entries, while the URL carries one. Keep the JSON available, for example behind a separate "Copy invite for headset" or as a field of the URL, or state the break and justify it. As written, "one invite, not two" is a removal.

3. **Reachability is not addressed.** `bind_remote` (`src/app.rs:2924`) binds loopback until the owner allows the local network. A phone cannot load the page or `/pair` at all until then. The plan says nothing about the pairing window or its QR when the bind is loopback-only. The URL uses `local_address()`, which may not be the bound interface. State what the pairing window shows in that case (a prompt to enable LAN, or the QR suppressed) and test it.

4. **The origin rule is incomplete.** The plan checks `Origin` against the `Host` header, and both are attacker-influenced in the DNS-rebinding and shared-cookie scenarios it names. It also exempts every cookie `GET`. `GET …/screen`, `last-response` and `events` are the redacted content. With a shared cookie jar across ports, a hostile page on the same IP can issue credentialed cross-origin `GET`s, and the response is not readable but timing is. Also, `SameSite=Strict` does not cover other ports on the same site. Decide whether cookie `GET`s should require `Sec-Fetch-Site: same-origin` or `Origin` too. Also say what happens when a browser sends no `Origin` on a same-origin `GET`: the plan says "missing" is refused for `POST` only, and the upgrade rule is inconsistent with that for old browsers.

5. **Two hosts on one IP share one cookie.** The cookie is `__Host-sb`, `Path=/`, and cookies ignore ports. A second Switchboard instance on another port (the plan itself notes `SWITCHBOARD_REMOTE_PORT`) overwrites the first host's token, and each sees the other's token as unknown. The plan only notes this as a forgery surface. It needs a per-`server_id` cookie name, which `__Host-` allows, or it must state the limitation and the revoke-on-401 behavior it causes. As written, the page would show "revoked" and clear the `localStorage` entry on a mere collision.

6. **`/me` is not in the "no new endpoint" accounting.** `GET /api/v1/me` is an additive contract change. It is listed in the commit body, but the plan says "fixtures: none added" because only the page reads it. CLAUDE.md puts the wire in `docs/remote-client.md` §4.3 as the shared contract, and the Swift side has a fixtures test pattern (`write_fixtures`, `tests/remote.rs:1587`). Say whether `/me` needs a fixture so a native client can decode it, or why not.

7. **Rate-limit accounting is under-specified.** `Limits::limited` (`src/adapters/remote.rs:630`) matches an exact path against `PAIR_PATH` and `INFO_PATH`. `PAGE_PER_MINUTE` needs three paths sharing one window, and the plan does not say how `limited` is changed. With a single shared window, a normal reload (3 requests) plus a reconnect storm could lock out the owner's own page. The 429 for a static path also needs the same CSP and headers or none, and the plan is silent on that. Say which.

8. **The page's JS has no automated test, yet the plan makes security claims about it.** The plan relies on "`textContent` never `innerHTML`" and the Origin and cookie behaviors working in a browser, and covers them by grep-style tests and a manual acceptance run on a phone. The plan commits to a "Spike first" that needs a phone. If the spike's Safari row fails (no `Secure` cookie from a click-through origin, as the plan itself anticipates), Decision 2 collapses and the plan stops. The order lists the spike as step 1 of a single commit, so the whole design is unresolved at plan time. Mark Decision 2 as conditional in the plan's contract and commit message, or split the spike into its own commit that gates the rest, consistent with CLAUDE.md ("add a new spike directory for any new risky mechanism before building on it").

9. **Process and docs.**
   - The plan commits the spike README in the same commit as the feature. CLAUDE.md's milestone rule is one commit per milestone with status updated, and the plan does not say which design.md "Milestone N status" it updates. The cited design.md section is "Remote client (2026-10-12)", and the plan does not name the status block it edits besides "known gaps (`:3573`)". Verify that line number against the worktree before relying on it.
   - The "30 literals (28 in `src/app.rs`, 2 in the adapter)" count is a `grep -c` of lines, not literals. Recount before sizing the mechanical edit.
   - The README.md Layout row for `web/` is listed, but the plan does not say how `web/*` is embedded (`include_str!`), which affects `scripts/bundle.sh` and the Linux CI build. Say it.
