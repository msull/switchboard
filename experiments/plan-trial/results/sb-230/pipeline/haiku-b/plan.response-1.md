# Response to feedback 1

Each point names the plan section that changed, or says why it did not. All edits are in `plan.md` in this folder; the earlier plan is untouched. I re-read the file after editing and confirmed each change is present.

I also checked the feedback's line references against the worktree. Point 9 is right about `src/app.rs:3024`. The `RemoteRequest` derive is at `:359`, not `:358`; the plan now cites it that way.

1. **`Connection: close` not honoured.** Accepted. `connection` loops on `read_request` (`src/adapters/remote.rs:783`) and `respond` writes keep-alive (`:545`). The plan now says the static arm writes its reply and returns `Ok(())` without reading another request. Changed sections: *Actions and effects*, "Static files" paragraph (adds the return and the `close` flag); *Tests*, Integration bullet 1 (the socket must read EOF within a second after `GET /`).

2. **Other unauthenticated replies also hold slots.** Accepted, and the fix covers more than the feedback asked for. The rule is now that any reply on a connection that has not paired closes it. That covers `/api/v1/info`, `/api/v1/pair`, refusals, the 429 and 503 replies, and favicon. The page also declares `<link rel="icon" href="data:,">`. Changed sections: *Where this departs* bullet on the unauthenticated pool; *Actions and effects*, "Static files" paragraph; *Tests*, Integration bullet 1 (`GET /favicon.ico` gets EOF) and the browser-pairing test; *Tests*, Spike item 4 (counts every request, including favicon).

3. **Cookie token in a `Debug`-derived struct.** Accepted. The plan introduces a `Secret` newtype whose `Debug` prints `<redacted>`. Both the cookie and the existing bearer are held as `Secret`, and `as_str` is the only way out. Changed sections: *Actions and effects*, "The cookie" paragraph; *Tests*, Unit bullet (a `{:?}` of a request prints neither token).

4. **Browser `control` pairing left open to a relay.** Accepted as a recorded decision, not a cap. A cap at `read` would fail the acceptance walk, which needs a reply sent from the phone. So the owner chooses `control` in the window, and the plan records that the relay risk reaches it. The window shows a line whenever its scope is `control`. §5 of the spec gets the same wording, and the browser's pairing rule is stated there: the code goes after the page's own key compare, which stops stale or wrong hosts but not a relay. Changed sections: *Actions and effects*, "Trust" paragraph; *UI*, "Pairing window"; *Tests*, UI bullet; *Tests*, Documents (§5 browser rule).

5. **Dropping the JSON invite breaks mixed versions.** Accepted. The JSON branch is kept. `PairingInvite.parse` will read the URL as a second form, so an old host's JSON QR still pairs. Changed sections: *Where this departs*, JSON bullet (rewritten); *UI*, "Pairing window" (the JSON payload is no longer written, but the parser still reads it); *Tests*, Swift bullet (keeps `testInviteParsesTheQRText` and adds `testInviteParsesTheURL`); *Tests*, Documents (CHANGELOG line says the QR is a URL and the native path still takes JSON); *Contract additions* (the URL form is listed as an addition). The README example at `README.md:277` is still valid, so it is not changed.

6. **Cookie requests with no `Origin` pass.** Accepted in part. Every cookie request that is not a `GET`, and every upgrade, must carry a matching `Origin`. A missing one is `403 forbidden_origin`. A cookie `GET` without `Origin` is still accepted, because `SameSite=Strict` already stops a cross-site navigation from sending the cookie, and a same-origin `GET` may omit the header. The plan says so, so the rule is not stricter than it needs to be. Changed sections: *Actions and effects*, "The cookie" rule bullet; *Tests*, the Origin integration test (adds a cookie `POST` with no `Origin` gets 403, and a cookie `GET` with no `Origin` gets 200).

7. **Certificate contingency has no write path.** Accepted. The plan names the path: `save_identity` (`src/adapters/remote.rs:77`) writes through `JsonStore::write_atomic`, which does the temp file, fsync and rename. Remote files pass `false` for `.bak` today (`:68`). The plan passes `true` for `identity.json`, because CLAUDE.md requires `.bak`, and the commit will say so. The key is read from `remote-key:<server_id>` at launch, as now. Changed sections: *Tests*, Spike gate, fallback for item 5.

8. **The spike gate names no operator.** Accepted. The owner runs the browser rows (1 to 3, 5 and 6) on a Mac, because they need a person to accept a warning and a browser to send the headers. Row 4 is counted from the same browser session. Results go in `spikes/23-browser-client/README.md`, one line per row, with the browser version and date. No code is written until rows 1 to 6 are recorded for macOS Chrome and Safari. Changed sections: *Tests*, Spike gate paragraph.

9. **One line reference is off.** Accepted. The 404 is now cited as `src/app.rs:3024`, in the *Actions and effects* static-files paragraph. The `RemoteRequest` derive is cited as `:359`, in the *Actions and effects* cookie paragraph.

Not changed beyond the above: the *Record* section, *Signals*, the *Device endpoint* and the *Commit* line are unchanged, because no feedback point touched them.
