## Where this departs from the issue

- **The routes are `/api/v1/info` and `/api/v1/pair`, not `/info` and `/pair`.** The issue, and spec §5, use the short names. The arms are in `serve_remote` (`src/app.rs:3028-3029`), and the rate windows key on `PAIR_PATH` and `INFO_PATH` (`src/adapters/remote.rs:631`). The plan uses the full paths throughout, and the amended §5 names them.
- **The QR URL carries the code in the fragment, not the query.** `?code=` would put the code in the request line of the first `GET /`: `read_request` keeps the query on every request (`src/adapters/remote.rs:444`). A fragment is never sent to the server. The page still calls `history.replaceState` before its first fetch.
- **The key in the URL is a wrong-host check, not a defence against an on-path attacker.** The issue says a genuine page refuses to send the code to a host whose `/api/v1/info` key differs. That holds for a stale QR, a QR from another Mac, or an address reassigned after a DHCP change. It does not hold against a relay: an attacker that forwards the host's real `/api/v1/info` passes the check, then receives the code and the token. A browser cannot pin the TLS key, so the click-through is the only trust step (see Actions and effects, Trust).
- **"The browser then trusts that certificate for that address" is unverified.** Neither the code nor this review can show it. The spike measures it. The certificate has no SAN and rcgen's default validity (`src/adapters/remote.rs:102`). The plan leaves both alone unless the spike shows a browser refusing the click-through, because a self-signed certificate is untrusted whatever it names.
- **The page cannot show the device's scope as things stand.** The issue's header and reply box assume it is available. `scope` is returned only in the `/api/v1/pair` reply (`src/app.rs:3662`); no read endpoint returns it. The plan adds `GET /api/v1/device`. The issue asks for a new read model only if the page cannot do without one, and it cannot.
- **"Revoked" and "never paired" give the same answer.** Revoking deletes the record, so the host answers the same 401 `unauthorized` for a revoked token as for one it never issued (`authenticate`, `src/app.rs:3127`; `RevokeDevice`, `src/core/remote.rs:86`). The page says both: "This device is not paired any more. It was revoked on the Mac, or the host forgot it. Scan a new code on the Mac to pair it again." A tombstone record to say "revoked" alone is not worth a schema change for one sentence.
- **The pairing reply carries the token in its body.** `remote_pair` returns `"token": token` (`src/app.rs:3661`). A cookie does not keep the token from the script if the body still has it. The browser variant omits it.
- **The unauthenticated pool is held by connections, not by requests.** The four slots (`MAX_UNAUTHENTICATED`, `src/adapters/remote.rs:567`) are taken per connection and released when it closes. A keep-alive connection that goes idle holds its slot for `IDLE_TIMEOUT`, 30 s (`:573`), and `respond` always writes `Connection: keep-alive` (`:545`). A page loaded over keep-alive would keep a second device from pairing for that long. The plan therefore closes every reply on a connection that has not paired, not only the static files. `/api/v1/info`, `/api/v1/pair`, the refusals and a favicon request all hold a slot otherwise.
- **The QR's JSON form is an existing contract.** `PairingInvite.parse` decodes it (`client/Sources/SwitchboardProtocol/Info.swift:114`). The README documents `switchboard-remote pair "$(pbpaste)"` on that text (`README.md:277`), and a host still on the old build shows it. The plan adds the URL as a second form the parser accepts, and keeps the JSON branch, so both forms pair and mixed versions still work. The window's "Copy invite" copies the URL.

## Record

No serialized type changes, so no schema bump. `PairedDevice` (`src/ports/remote.rs:96`) holds a browser exactly as it holds a headset: name, scope, token hash, created, last seen. The page builds the name from `navigator.userAgent` ("Safari on iPhone", with "Browser" as the fallback). `new_device` already truncates a name to 64 characters (`src/core/remote.rs:169`), so the host needs no new cap. No `kind` field: the dialog does not need to tell devices apart. `devices.json` is unversioned. `IDENTITY_SCHEMA_VERSION` stays 1 (`src/ports/remote.rs:17`). `SCHEMA_VERSION` stays 16 (`src/core/model.rs:12`), and `VIEWS_SCHEMA_VERSION` stays 7 (`:612`). If a parallel ticket bumps either first, nothing here changes. The identity record is unchanged unless the spike forces the certificate contingency under Tests.

## Signals

No new signal. The page uses the events socket's existing `hello`, `changed`, `removed` and `resync_required` frames (spec §4.4).

## Actions and effects

No `AppAction` or `Effect` variant. Pairing reuses `AppAction::Paired` and `PairingFailed`, and the device lookup reuses `DeviceSeen`. What is new is at the port: the connection thread, the frame's handlers and the headers.

**Static files on the connection thread.** `connection` (`src/adapters/remote.rs:770`) asks a new table in `src/adapters/remote_page.rs` for a `GET` before the rate check. The table has three exact entries, embedded with `include_str!`:

- `/` → `index.html`, `text/html; charset=utf-8`
- `/app.js` → `text/javascript; charset=utf-8`
- `/app.css` → `text/css; charset=utf-8`

Each reply carries `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`. Anything else falls through to `serve_remote`, which refuses it as it does today (`404 not_found`, `src/app.rs:3024`). The lookup is an exact match against the table, so traversal and `//` paths match nothing.

The unauthenticated slot is taken at accept, before the path is known (`src/adapters/remote.rs:701-707`), so static files have no pool or rate window of their own. The slot is released when the connection closes, so the close is what matters. `connection` (`:770`) changes at its request loop (`:783`): `respond` takes a `close` flag, and when the connection is not paired (its `paired` flag is false) every reply is written with `Connection: close` and the function returns `Ok(())` straight after the write, without reading another request. That covers the static files, `/api/v1/info`, `/api/v1/pair`, every refusal, and the 429 and 503 replies the connection thread writes itself. A paired connection keeps its keep-alive. The page declares `<link rel="icon" href="data:,">`, so browsers do not request `/favicon.ico`. The cost is one TLS handshake for each unpaired request, which a native client that used to reuse a connection for `/api/v1/info` and `/api/v1/pair` now pays. `respond` also takes the content type and extra headers; the new `RemoteReply.headers` field (`src/adapters/remote.rs:389`) is empty at every existing literal.

**Trust.** The click-through is the trust step, and the amended §5 says so. What it buys: a QR scan puts the host's key in the URL, and the page posts the code only after `/api/v1/info` reports the same key. That stops a stale QR, another Mac, or a reassigned address before the code leaves the phone. What it does not buy: a relay on the network during the five-minute window. The pairing window's text says that a browser cannot check the host's key and that the owner should pair only on a network they trust. A browser pairing is capped at `read` whatever scope the window holds, so a relay that gets past the browser's check reads what a read-scope headset reads: sessions, last responses, screens, runs and pinned files, redacted as §4.3 says. The cap limits what a relay can do, not what it can see (`docs/remote-client.md:304` names the transcripts as the exposure). The read scope is therefore a decision in its own right, separate from `control`. Whether a browser may hold `control` is an open decision (see Open decisions): the owner has not made it, and this plan does not make it for them. The cap is applied in `remote_pair` before the device is made. `new_device` (`src/core/remote.rs:166`) takes its scope from the window today, so it gains a scope argument for the browser grant. The window shows this line whenever its scope is `control`: "A browser paired here gets read scope. Control from a browser is not yet allowed." A host-served certificate download is rejected: it arrives over the same unauthenticated first connection, and on iOS it adds a profile-install step for no more trust.

**Browser pairing.** The page posts `POST /api/v1/pair` with `client: "browser"` in the body. It must not be a new path: a new path would escape the `/api/v1/pair` window at `src/adapters/remote.rs:631` and miss the failure count. `remote_pair` (`src/app.rs:3606`) then answers with `Set-Cookie` and the same body without `token`, and the connection closes after the reply (see Actions and effects, Static files). The browser's next request is on a new connection with the cookie. The code match, the key match, the failure counter and the window are unchanged.

**The cookie.** `__Host-sb_session=<token>; Path=/; Secure; HttpOnly; SameSite=Strict; Max-Age=34560000` (400 days, Chrome's cap; Safari's is to be measured). `read_request` (`src/adapters/remote.rs:444`) reads `Cookie`, `Origin` and `Host` into three new `RemoteRequest` fields (struct at `:360`; it derives `Debug` at `:359`). The cookie's value and the bearer are both held as `Secret`, a new newtype in `src/adapters/remote.rs` whose `Debug` prints `<redacted>`, so a `{:?}` of a request prints no token. `as_str` is the only way out. `authenticate` (`src/app.rs:3127`) tries the bearer first, as now, and the cookie second. For cookie requests only:

- An `Origin` header must equal `https://` followed by the `Host` header. A cookie request that is not a `GET`, and every WebSocket upgrade, must carry one; a missing or foreign `Origin` on those is `403 forbidden_origin`. A cookie `GET` without `Origin` is accepted: a cross-site navigation does not carry the cookie under `SameSite=Strict`, and a same-origin `GET` may omit the header.
- A `401` from a cookie request sets the same cookie with `Max-Age=0`, so the browser drops it.

Why `Origin`: `SameSite=Strict` stops other sites, but sites ignore ports and cookies are not port-scoped, so another local server on the same host could ride the cookie. Native clients send no `Origin` and no cookie, so the bearer path is unchanged. A cookie is never sent to another host name, so a page that rebinds a name to the LAN address cannot carry it. The `__Host-` prefix stops a cookie set without `Secure` or with a `Domain` from replacing this one. It does not isolate ports, which is why the `Origin` rule is needed.

**Device endpoint.** `GET /api/v1/device` is a `serve_remote` arm after `authenticate`. It replies in the envelope with `authenticated: true` and `{device_id, name, scope}`, built like `remote_info` (`src/app.rs:3568`). Read scope is enough. A send refused for scope hides the page's reply box.

## UI

**Pairing window** (`src/ui/remote.rs:160-172`). The payload becomes `pairing_url(addr, identity, code)`, a pure function in `src/adapters/remote.rs` next to `local_address` (`:962`). It returns `https://<ip>:<port>/#code=<code>&key=<spki_sha256>&id=<server_id>`, with brackets around an IPv6 address. With no LAN address there is no QR, as now. The JSON payload is no longer written; the parser still reads it. "Copy invite" (`:201-207`) copies the URL. The window's text drops the address line and adds: "A browser shows a certificate warning. Accept it on the device. A browser cannot check the host's key, so pair only on a network you trust." While the scope is `control`, a second line says: "A browser paired here gets read scope. Control from a browser is not yet allowed."

**Devices dialog** (`src/ui/remote.rs:267-271`). No change. A browser is listed by its name, with Revoke.

**The page** (`web/index.html`, `web/app.js`, `web/app.css`):

- **Load.** If the fragment holds `code`, `key` and `id`, copy them and call `history.replaceState(null, '', '/')` before any fetch. Then read `/api/v1/info`. If its key differs from `key`, show "This is not the host whose code was scanned" and post nothing. Otherwise post `/api/v1/pair` with `{code, spki_sha256, device_name, client: "browser"}`. On success, store `{server_id, spki_sha256}` in `localStorage` inside try/catch, so a later load can say "identity changed, pair again". Storing a non-secret per-viewer value is the only use of it.
- **No code and no cookie.** Show the host name and "Scan the code on the Mac to pair this browser", or "Pairing is closed on the Mac" when `pairing_open` is false. No typed-code form: a typed code has no key to check.
- **Sessions.** Grouped by project, waiting ones first, marked with the word "Waiting" (not colour alone). Each card shows kind, state and the one-line excerpt.
- **Session view.** The last response (`/last-response`, with a note when `truncated`) for a Claude Code session, else the screen (`/screen?lines=`). Session text is set with `textContent` only. Transcript and screen text is untrusted, so nothing is set with `innerHTML`.
- **Reply box.** Visible only with `control` scope. It posts `send` with an `op` from `crypto.randomUUID()`, or `crypto.getRandomValues` when that is absent.
- **Live.** A WebSocket to `/api/v1/events` on the same origin. Apply events and replies by revision per resource key, as §4.4 says: drop anything older than the held revision, refetch on `changed`, refetch everything on `resync_required`, reconnect with backoff. A 401 on reconnect shows the not-paired text.
- **States.** Not paired, identity changed, wrong host, pairing closed, read-only scope.
- **Layout.** One column at phone width, a 16 px gutter, no horizontal scroll, dark mode through `prefers-color-scheme`.

## Open decisions

- **Browser `control`.** Whether a browser paired through the URL may hold `control` scope. Control lets the browser send replies, resume sessions and trust them, and a relay that gets past the browser's key check would then do the same. The owner decides this before the §5 text and the reply step are written. Until then every browser pairing is `read`, and nothing in this plan assumes the answer. It is moot if browser `read` is refused.
- **Browser `read`.** Whether a browser paired through the URL may hold `read` scope at all. A relay that gets past the browser's key check reads the transcripts, last responses, screens, runs and pinned files that a read-scope headset reads (§4.3, `docs/remote-client.md:304`). The owner decides whether that exposure is acceptable on the network the browser will use. The cap at `read` in `remote_pair` stays until then.
  - If the owner refuses it, this plan is not built as written: the browser pieces (the static arm, the cookie, `client: "browser"`, `GET /api/v1/device`) come out, and a new plan is written for whatever trust step the owner accepts. The native URL QR and the parser change do not depend on this decision and stay.
  - If the owner grants it, `control` is decided second, because `control` means nothing to a browser that cannot hold `read`.
