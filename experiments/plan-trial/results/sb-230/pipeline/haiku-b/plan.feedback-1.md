1. **`Connection: close` is not honoured, so static replies keep their slot.** `connection()` (`src/adapters/remote.rs:770`) is a `while let Some(request) = read_request(...)` loop, and `respond` (`:530`) always writes `Connection: keep-alive`. The plan says static replies close and that the slot returns "as its response is written", but it never says the static arm must `return Ok(())` after writing, and the Tests list has no check that the socket reaches EOF. Without that return the thread waits out `IDLE_TIMEOUT` (30 s) and holds one of the four unauthenticated slots. Add the return to the plan, and a test that reads EOF after `GET /`.

2. **Other unauthenticated replies also hold slots.** The page's own `/api/v1/info` and `/api/v1/pair` replies go through `respond` with keep-alive, and the browser's automatic `/favicon.ico` request is answered by `serve_remote`'s 404 (`src/app.rs:3024`) on a keep-alive connection. Each holds one of the four slots for 30 s, so a second phone can be closed at accept during the first one's pairing. The plan's fix covers only the three static files. Either close every unauthenticated reply, or have the page declare `<link rel="icon" href="data:,">` and say so. Spike item 4 should count the favicon request too.

3. **The cookie token would sit in a `Debug`-derived struct with no rule against logging it.** `RemoteRequest` (`src/adapters/remote.rs:358`) derives `Debug`, and its doc says the bearer is "taken out of the headers so it is never logged with them". The plan adds `Cookie` as a `RemoteRequest` field and says nothing about extracting the `__Host-sb_session` value the same way. The plan should say the cookie's token is extracted to the same protected form as `bearer` (or a redacting type) and add a test that `{:?}` of a request carrying the cookie does not print the token.

4. **Browser pairing leaves `control` scope open to a relay, and the plan does not decide that.** `remote-client.md` §5 (line 309) says the code is not sent until the key is checked, "the code alone would let an intermediary ... take the token". The plan's own Trust paragraph concedes that a relay passes the browser's `/api/v1/info` check, so the click-through is the only step. The plan then keeps "the window's chosen scope", and `control` scope lets a device `send`, `resume` and `trust` (`tests/remote.rs`, `the_control_scope_sends_with_the_op_as_the_key...`). "`read` stays the default" is not a cap, since the owner can pick `control` in the window. The plan must either cap browser pairings at `read`, or record an explicit owner decision in §5 that browser `control` pairings carry this risk. The §5 rule "Pairing verifies the key before the code is sent" also needs browser-specific wording, not only the "Before pairing" list.

5. **Dropping the JSON invite is a removal from a shared contract, and the plan does not account for mixed versions.** §5 (line 309) names the QR content as the contract. `PairingInvite.parse` decodes JSON (`client/Sources/SwitchboardProtocol/Info.swift:114`), and the README (line 277) documents `switchboard-remote pair "$(pbpaste)"` on that text. The plan removes the JSON branch "since nothing writes it after this change", but a host still on the old build can still show the JSON QR, and a client built from this repo can meet it. The shared-contract rule in CLAUDE.md is additive-only. Keep the JSON branch as a fallback, or state the break and add the CHANGELOG line that says so.

6. **Cookie requests with no `Origin` pass.** The plan's rule is "an `Origin` header, if present, must equal ..." for cookie requests. Browsers send `Origin` on every cross-origin POST, but the plan's own argument is that native clients send neither `Origin` nor a cookie, so a cookie request without `Origin` has no legitimate sender. For any cookie-authenticated non-GET and for every upgrade, a missing `Origin` should be refused as `403 forbidden_origin`. The test list covers only a missing `Origin` on an upgrade. Add the POST case.

7. **The certificate contingency has no write path.** Under Tests, the fallback "re-issuing the certificate over the stored key at launch" changes `identity.json`'s `certificate` field. CLAUDE.md requires every record write to go through the store's atomic path (temp file, fsync, `.bak`, rename). The plan says neither that the write uses that path nor that the key comes from the Keychain account `remote-key:<server_id>`.

8. **The spike gate names no operator.** Spike 23 is "before any code", and its items 1 to 6 need macOS Chrome and Safari with a real click-through. Nothing in the plan says who runs them or where the results go before code starts. Only the iOS rows have a "not run" rule, so an unrun macOS row leaves the gate undefined. Say that the code waits for the macOS rows, or that the owner records them.

The 404 "not_found" reply the plan cites as `src/app.rs:3023` is on line 3024. Line 3023 is the `let Some(rest) ... else {` guard.
