1. The pool test under "Browser pairing end to end" cannot pass as written: "fill the unauthenticated pool, then load". The accept loop (`src/adapters/remote.rs:697-707`) closes a new connection when `unauthenticated >= MAX_UNAUTHENTICATED`, before TLS and before any request is read. Every connection starts in the unauthenticated pool, and only a reply with `authenticated: true` moves it (`remote.rs:834-848`). So a cookie request on a fifth connection never reaches `serve_remote`. The test should fill three slots, load with the cookie on the fourth, and then show that a fifth connection is accepted.

2. The "Pool" claim in decision 4 ("a cold, unpaired load is three requests plus the favicon, on keep-alive connections, inside the four-slot unauthenticated pool") assumes the browser uses one connection. HTTP/1.1 browsers open parallel connections to fetch `app.js`, `app.css` and the favicon (Chrome allows up to six per host and also preconnects). The WebSocket needs its own connection too. A connection that never authenticates keeps its slot until `IDLE_TIMEOUT` (30 s, `remote.rs:573`). Past four, the accept loop drops the connection silently, so the page sees a network error on a subresource, not a 503. This matters most on a reload, or with a second tab or a native client pairing at the same time. The plan should either say how the page and server stay inside four (for example, the page loads nothing in parallel before `/pair` and the static replies send `Connection: close` while unauthenticated), or add the open-connection count to the spike's measured rows and to the `remote-client.md` §4.1 text. It should not assert that the load fits.

3. A stale cookie on a static request is described as "not an error", but the plan routes it through `authenticate`. Every miss there returns `self.refuse(..)` (`src/app.rs:3127-3148`), which logs a refusal line. With the plan's change it would also attach the clearing `Set-Cookie`. A revoked browser that reloads would therefore log three or four 401 refusals per load, the same kind of noise the favicon 204 is there to avoid, and its cookie would be cleared before the page can tell "revoked" from "unpaired". The plan says rehydrate tells these apart with `GET /device` returning 401 "with the same key" stored, so that still works from `localStorage`. Still, the static path should look the cookie up with `device_by_token` directly: no refusal, no log line, no `DeviceSeen`, no clearing header. Only API routes should clear the cookie.

4. "On `trust_question` it says the session is at the folder trust question" treats `trust_question` as a reply from `send`. It is not. It is a `bool` on `SessionView` (`control/src/lib.rs:662`). `remote-client.md:279` says a send to a pane at the trust question "is accepted but goes nowhere". If the page waits for an error, the owner's reply is silently lost. The page has to read `trust_question` from the session view and say so, or hide the reply box, before sending. The core and UI tests should use the field.

5. The count of `RemoteReply` literals is wrong for this worktree. `src/app.rs` has 28, but `src/adapters/remote.rs` has one (the 504 at `remote.rs:829`), not two. The other match is the struct definition at 389. The connection thread also writes the 429, 503 `busy` and 503 `full` replies by calling `respond` directly with no `RemoteReply` (`remote.rs:788-793, 821-826, 839-844`). When `respond` gains a content-type parameter and the every-reply headers, those three call sites need them too. The plan does not list them.

6. `src/adapters/bonjour.rs:41` is cited as where `hostname -s` is published. That line calls `super::remote::default_server_name()`, and `hostname -s` is at `src/adapters/remote.rs:304-312`. The reference should point there.
