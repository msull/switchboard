1. **Departure 1 (fragment, not query) states as fact that a fragment is "never sent, never in a `Referer`, and not fetched by a link previewer".** Nothing the plan cites supports this. Facts has no line for it (lines 37 and 43 are the nearest, and both are Unresolved). The tree says nothing either (`read_request` `src/adapters/remote.rs:444` only shows the query is split off). The decision is probably right, but it is resting on nothing. Cite the primary source in the plan: RFC 3986 §3.5 and RFC 9110 §7.1 (a fragment is not part of the request target) and RFC 9110 §10.1.3 (`Referer` carries no fragment). The previewer half stays Unresolved and the plan should say so. I did not fetch these. This is a request to cite them, not a claim that they disagree.

2. **Decision 1 has a fallback for "the owner wants a download" but none for "click-through hard-fails even with the SAN".** Facts line 34 and line 35 are both Unresolved: whether Safari offers "Visit this website", and whether `fetch` and `wss://` keep working after a click-through. The only written fallback (`GET /cert.der`) rests on Facts line 36, the iOS profile install, which is also Unresolved. If both fail, the plan has no path and the acceptance run cannot pass. The plan should say what it does then. For example: leave the page unusable on that browser and document that, or serve the page over plain `http:` on a second listener. Also say explicitly that Facts line 9, where an IP SAN is needed for a bare-IP URL, is an inference. The plan builds on it with only a "if webpki will not take a leaf as its own root" test fallback.

3. **The reissue only covers the existing-identity path.** The plan puts the SAN reissue "in `load_identity` (`src/app.rs:2781`), after the key check succeeds". The key-lost arm (`src/app.rs:~2811`, which calls `make_identity`) and the first-run `None` arm (`~2836`) also mint certificates. They go through `make_identity(server_id, name, listen)` (`src/adapters/remote.rs:~95`), which takes no addresses. A fresh install or a rotated key therefore shows a QR whose certificate has no SAN until the next launch. That is the exact failure the section exists to prevent. State whether `make_identity` gains an address parameter (it changes every call site and test), or whether those arms call `reissue_certificate` straight after. List the call sites.

4. **`IDENTITY_SCHEMA_VERSION` is left as "the value at implementation time, plus one".** It is 1 in the worktree (`src/ports/remote.rs:17`) and nothing in the plan or facts says a parallel ticket exists. CLAUDE.md wants a concrete bump for a serialized change. Write 2. Say that `RemoteFiles::load` accepts 1, and what a build that is still on 1 does with a v2 file. The plan claims "no migration step is needed" without checking whether the loader or store refuses a newer version.

5. **The plan adds a new risky mechanism with no spike.** CLAUDE.md says "add a new spike directory for any new risky mechanism before building on it". Three are new: a browser-trusted certificate with an IP SAN, WebSocket auth through `Sec-WebSocket-Protocol`, and a page served from the connection thread against the 4-slot pool. Facts line 3 says no spike was run because nothing could settle the questions without a device. The plan neither adds a `spikes/` entry nor explains why the rule does not apply. At minimum the `rustls` verifier check on a SAN certificate and the 101 echo are checkable locally, so a spike README should record them.

7. **The `RemoteRequest.subprotocol` plumbing misses a clone.** `connection` clones only `upgrade_key` before `request` is moved into `RemoteIncoming` (`src/adapters/remote.rs:~795–815`), and `respond_upgrade` is called with the key alone at `~858`. The echo value has to be carried out of the frame path too, either cloned before the move or computed on the connection thread. The plan says only that the 101 "echoes `switchboard.v1` only", which is a constant. State that, and drop the `subprotocol` field if it is not needed. It is a needless contract addition.
