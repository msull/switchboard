## 1. What is on disk, and how it rehydrates (before any pane)

A browser control surface adds no new durable record by itself; the existing remote records carry it.

- `identity.json` (`src/ports/remote.rs:26` `Identity`): server id, display name, certificate DER (public), `spki_sha256`, `listen {lan, port}`. Private key in the Keychain under `remote-key:<server_id>`. The page needs nothing new here. A browser pins nothing, so the certificate and key hash are the only host-identity facts the page can use.
- `devices.json` (`src/ports/remote.rs:96` `PairedDevice`): `id, name, scope, token_sha256, created, last_seen`. A browser is one more row. The issue's decision 6 ("name from the user agent") needs **no schema change**: `/pair` already takes `device_name` (`src/app.rs:3650`), so the page can send the name it derives. If the host should derive it from the `User-Agent` header, `read_request` (`src/adapters/remote.rs:444`) keeps no such header today, so `RemoteRequest` (`:360`) would need an additive field. That is not a `model.rs` type, so no `SCHEMA_VERSION` bump. Adding a "kind" field to `PairedDevice` is serde-default-able but is a contract extension to decide on.
- The pairing window is in core state only, never saved (`src/core/action.rs:978` `PairingWindow {until, code, scope, failures}`; `PAIRING_WINDOW` 5 min, `PAIRING_ATTEMPTS` 3). Restart loses it, as the spec intends.
- **Rehydration of the browser's session is the browser's, not the host's.** The host rehydrates a device purely from `token_sha256` → `PairedDevice` (`core.device_by_token`, used in `authenticate`, `src/app.rs:3114`). So whichever way the token reaches requests (header, cookie, subprotocol), the host-side check is the same hash lookup, and revoking the row (`AppAction::RevokeDevice`, `src/core/remote.rs:86`) kills it on the next request. `dispatch_inner` (`src/app.rs:486`) already drops that device's subscribers, which closes its WebSocket. The page does not need to learn the old state to recover: it needs a stable way to tell "401, revoked or unknown token" from "key changed" from "host unreachable".
- What the page keeps on the device (token, or a cookie, plus the server's key hash and id) is the one new storage decision. It lives outside the tree; see Open questions.
- Live state is a cache, as the repo's idea says: the page's view is rebuilt from `GET /api/v1/projects`, `/projects/{id}/sessions`, `/waiting`, then the `/events` `hello {epoch, revision}`, with snapshot-after-subscribe and revision-held-per-key (§4.2, §4.4). A changed `epoch` means refetch everything.

## 2. The code the issue touches (files and lines in this tree)

Host listener, `src/adapters/remote.rs` (1088 lines)
- `read_request` `:444`. Parses method, target, lowercased headers; keeps only `content-length`, `authorization: Bearer`, and `upgrade`+`sec-websocket-key`. It does not keep `Cookie`, `Origin`, `Host`, `User-Agent`, `Sec-WebSocket-Protocol` or `If-None-Match`. MAX_HEAD / MAX_BODY bound it. The query is kept undecoded as pairs (`:495`), documented as "ids and numbers only".
- `respond` `:530`. Always `Content-Type: application/json`, `Connection: keep-alive`, no other header. There is no way today to set `Content-Type: text/html`, `Content-Security-Policy`, `Cache-Control`, `Set-Cookie`, or `Sec-WebSocket-Protocol` on the 101 (`respond_upgrade` `:519`). Statuses with reasons are a fixed list (`200 400 401 403 404 405 413 429 503 504`); a 304 or 301 would print "Error".
- `respond_upgrade` `:519` does not echo a subprotocol and does not check `Origin`.
- Pools and rate windows `:570–640`: `MAX_UNAUTHENTICATED = 4`, `MAX_PAIRED = 12`, `PAIR_PER_MINUTE = 6`, `INFO_PER_MINUTE = 60`. `Limits::limited(path)` (`:631`) matches only the exact `PAIR_PATH`/`INFO_PATH`, so any other path, including `/`, is unlimited by rate. A connection is "unauthenticated" until the frame answers one request with `authenticated: true` (`connection`, `:770`, moves it to the paired pool then). A browser's first page load, `/info`, `/pair`, each on a keep-alive connection, sits in the 4-slot pool; browsers also open several parallel connections for a page with a few files (not measured).
- `connection` `:770`: TLS handshake, then one request at a time to the frame via `shared.requests.try_send`; a full channel answers 503.
- `local_address` `:962`: the one routed address, as the QR's `addresses`. `make_identity` `:95`: the certificate is built with `CertificateParams::new(Vec::new())`, so **no Subject Alternative Name** and CN `Switchboard <server_id>`; the key is P-256 ECDSA, validity "year 4096". Native clients never look at name or validity (the `Pin` verifier `:183`); a browser does.

Frame, `src/app.rs` (4482 lines)
- `serve_pending` `:1572` drains the port (`DRAIN_PER_PASS` 8) and calls `serve_remote`.
- `serve_remote` `:3017`. First line: `request.path.strip_prefix("/api/v1/")`; anything else → `refuse(..., 404, "not_found", ..., false)`. `GET /` therefore answers a JSON 404 today. `("GET", ["info"])` and `("POST", ["pair"])` are served before `authenticate`. Everything else goes through `authenticate` (`:3103`), which reads **only `request.bearer`**. Then `("GET", ["events"])` → `remote_subscribe` (`:2723`), and the allowlist `match` of reads/commands. Commands need `Scope::Control` (`remote_command`, `:~3170`, a read device gets 403 `scope`).
- `remote_info` `:3567`: server id and name, protocol, capabilities, `spki_sha256`, version, limits, `pairing_open`. Served to anyone, so the page's "compare the URL's `key` with what `/info` presents" works with an existing endpoint. Note, though: the page script cannot read the certificate or its key from `fetch`, only `/info`'s JSON claim of the key. If the host is an impostor, it will say whatever it likes (this is the issue's own caveat; see Open questions).
- `remote_pair` `:3606`. Requires an open window; requires `spki_sha256` in the body to equal the identity's, else `PairingFailed` (counts toward the three) and 403 `wrong_key`; code compared uppercased; token 32 random bytes base64url; reply `{token, scope, server_id, device_id}` in an envelope, `authenticated: false`. The token is in the JSON body, so the reply cannot be the cookie-setting one without `respond` gaining headers.
- `remote_subscribe` `:2723`; `subscriber_frame` `:1704` handles `watch`/`unwatch` text frames, so the page gets `screen` and `conversation` `changed` events only by sending `watch` for those keys, as §4.4 says.
- Content routes: `last-response`, `screen`, `conversation` at `:1967` (`ContentView::LastResponse`), `remote_content_route`; dispatched through the content worker.
- `serve_remote` match, and the existing test of the allowlist, `tests/remote.rs:682`, both treat any non-`/api/v1/` path as "not available". The issue's "any path outside `/api/v1/` is refused" is a code fact at `:3023`.

## 3. How the surfaces would sit (shape, then pane)

1. Adapter: serve static files before the frame. Two options in the tree's idiom: (a) answer them on the connection thread from `&'static str`s (no frame, no `RemoteIncoming`), which keeps them off the 8-per-pass drain and out of the frame, but then they need their own rate/pool rule because `Limits::limited` and the unauthenticated pool apply by path; or (b) hand them to `serve_remote` as a `Served::Now` like `/info`, with `respond` taking a content type and extra headers. CLAUDE.md puts "what the frame decides" in `app.rs`, "moves bytes and enforces bounds that need no state" in the adapter, which points at (a) for constant files, but a decision about `Set-Cookie` after `/pair` is frame state, so `RemoteReply` would need additive header fields in either case.
2. Auth carrier: `authenticate` reads `request.bearer` only. A cookie or a `Sec-WebSocket-Protocol` carrier means `read_request` keeps another header and `RemoteRequest` gains a field (additive; the file's types are adapter-local, not `model.rs`/`action.rs`). The 101 reply would have to echo the chosen subprotocol if that route is picked, or a conforming browser closes the socket.
3. Page: `web/` with `index.html`, a script, a stylesheet, embedded by `include_str!` (new in the tree), constants in the adapter or a small `src/web.rs`. The first cut's views map to endpoints already in the allowlist: `/projects`, `/projects/{id}/sessions`, `/waiting`, `/sessions/{id}/last-response`, `/sessions/{id}/screen`, `POST /sessions/{id}/send`, `/events`, `/info`, `/pair`.
4. Pairing window: the URL instead of (or beside) the JSON; the CLI and headset text paths must accept both.

## 4. Things found that bear on the decisions

- Decision 4's "which pool and rate window": today there is none for static paths; `Limits::limited` ignores them and the connection counts as unauthenticated until a paired request. A page load does not reach the frame under (a), so the 4-slot unauthenticated pool is the only bound, and a phone page loading three files over three connections can occupy most of it while the owner's other devices are unaffected (they have the paired pool). Not measured.
- `GET /` is currently a JSON 404 through `refuse`, which logs by path and code (`src/app.rs:3754`). A stranger probing `/` with a browser thus gets a JSON error today.
- The WebSocket handshake checks neither `Origin` nor `Host`, and `authenticate` is a pure bearer check. Today that is safe because a bearer header cannot be sent by a cross-site page. A cookie carrier changes that: a cookie rides on any request the browser makes to that origin, so the cross-site-request and cross-site-WebSocket cases need an `Origin` check on `POST` and on the upgrade in addition to `SameSite=Strict`. The page is same-origin, but a hostile page on another host-name for the same IP is a different origin that a browser would still send `SameSite=Strict` cookies to only when same-site; `SameSite` is by registrable domain and ignores port, so another service on the same IP and another port is same-site. That is a claim about browsers, not settled here.
- The token in a `Sec-WebSocket-Protocol` value is visible to the script (it must put it there), so it lives in script-readable storage; the cookie route keeps it away from script but ties the carrier to the browser's cookie rules for a self-signed origin (see Open questions).
- The pairing `/pair` reply is `authenticated: false`, so after pairing, the first authenticated request moves the connection to the paired pool; the page's keep-alive connection does the same. No change needed.
- `query` is stored undecoded and documented "ids and numbers only". The page's own `?code=&key=&id=` is read client-side and never sent to the host except in the initial `GET /?code=...` request itself: the **request line carries the code to the host and into whatever logs it**. `refuse` logs "by method, path and code only", `read_request` splits the query off, and the connection thread does not log. Still, the code is in the browser's history and any proxy or `Referer` until `replaceState` runs, and in the QR. The issue's `history.replaceState` handles the address bar; a page-load request to `/?code=...` has already been made, so the code has been sent to the host in the clear of nothing but TLS. That is acceptable only because the host is the one that issued it. It is not hidden from an impostor host; this is the issue's own trust-step caveat.
- The code is single-use and closes the window on success (§5), and three wrong codes close it. A QR URL opened twice (a link preview, a camera app prefetching, a messaging app unfurling a pasted URL) is a `GET` only, not a `/pair`, so it does not consume the code. A **link previewer's own GET** hits the host with no cookies; it would be served the page. Not a code use, but see the open question on prefetch.
- Existing text path for the CLI: `switchboard-remote pair '<invite json>'` via `PairingInvite.parse`. A URL would need a parser that accepts `https://host:port/?code&key&id`. `addresses` is a `[String]` of `host:port`; a URL has one authority. The `id` param is `server_id`, so the field names map: `key`↔`spki_sha256`, `id`↔`server_id`, `code`↔`code`, authority↔`addresses[0]`.
