# Issue #230: a web control surface on the remote port — investigation notes

Read: `CLAUDE.md`, `docs/remote-client.md` (all 553 lines), `docs/lessons.md`, the "Remote client" status section of `docs/design.md` (3107–3583; the file is 3678 lines, I did not read the rest), and the code named below. Line numbers are from this worktree (HEAD 7fe8949, Release 0.4.1). Nothing was run, built or tested.

## 1. The on-disk record and its rehydration (before the pane)

The issue adds **no new durable record**. The page is a view over records that exist; the one durable thing it touches is the device record.

- **Device record.** `PairedDevice` (`src/ports/remote.rs:96`): `id`, `name`, `scope`, `token_sha256`, `created`, `last_seen`. Stored in `<data dir>/devices.json` through `RemoteFiles::save_devices` (`src/adapters/remote.rs:83`). Only the SHA-256 of the token is kept. A browser is one more row. Issue decision 6 (name from the user agent, listed and revocable) needs no schema change: the name is the `device_name` string `/pair` already takes (`src/app.rs:3650`, truncated to 64 chars in `new_device`, `src/core/remote.rs:~150`). Nothing records that a device is a browser, or which credential kind it holds. If the plan wants "browser" shown in the dialog, that is a new field on `PairedDevice` (`#[serde(default)]` keeps old files readable; `IDENTITY_SCHEMA_VERSION` is a different file). Whether devices.json needs a version bump is open.
- **Rehydration at start.** `load_identity` (`src/app.rs`, near 2975) reads `identity.json` and `devices.json`, fetches the key from the secret store, and dispatches `AppAction::IdentityLoaded`. A device and its scope survive a restart; a token stays valid because its hash is on disk. So a browser paired yesterday is authenticated today by whatever credential it kept. A missing key remakes the identity and clears `devices.json` (`remote-client.md` §3.1, §5; test `a_missing_key_at_start_remakes_the_identity_and_clears_the_devices`, `tests/remote.rs:1422`). The page must then show "identity changed, pair again" for a browser whose stored key hash no longer matches `/info`.
- **Credential on the browser's side** (not the host's record): a bearer token held by the page, or an `HttpOnly` cookie holding it. Either way the host rehydrates by hashing it and calling `device_by_token` (`src/core/remote.rs:~118`). The pairing window itself (`PairingWindow`, code, scope, failures) is in memory only and never saved; that stays.
- **Live state the page shows** is rebuilt by the protocol's own subscribe-then-snapshot (`remote-client.md` §4.4): `hello`, then the snapshots, then the buffered events reconciled by revision. The page keeps everything in memory (the spec's "client keeps content in memory only", §7). A reload refetches. The page's only persisted bit is its credential (see Q on cookie vs `localStorage`) and possibly the host key it was paired with.
- **Static assets** are compiled in (`include_str!`/`include_bytes!`). No file on disk to rehydrate. The tree has `include_bytes!` only for fonts and an icon (`src/ui/theme.rs:203`, `src/main.rs:167`), so no `web/` directory or embedded-page precedent exists yet. Release notes need a `CHANGELOG.md` line under Unreleased.

## 2. Where the code is

### The listener and request parsing — `src/adapters/remote.rs`
- `RemoteRequest` (`:360`): `method`, `path`, `query`, `body`, `bearer`, `upgrade`. No `User-Agent`, `Cookie`, `Origin`, `Host`, `Sec-WebSocket-Protocol`, `If-None-Match` fields.
- `read_request` (`:444`): lowercases header names, but **keeps only** `content-length`, `authorization` (must start `Bearer `), `upgrade` and `sec-websocket-key`. Everything else is parsed and discarded. Query values are undecoded (`:495`–`503`), documented as "ids and numbers only": a pairing URL's `key`/`id`/`code` are not read here (they go to the page), but a percent-encoded query would not be decoded by this parser.
- `respond` (`:530`): **hard-codes `Content-Type: application/json`**, `Connection: keep-alive`, no other header, and a fixed status-reason table (200, 400, 401, 403, 404, 405, 413, 429, 503, 504). A page, a `Set-Cookie`, a CSP, `Cache-Control`, a 304 or a 101 with a subprotocol header cannot be sent without changing this. `RemoteReply` (`:389`) is `{status, body, authenticated}`: it has no content type or header slot.
- `respond_upgrade` (`:519`): writes the 101 with `Sec-WebSocket-Accept` only, no `Sec-WebSocket-Protocol`. A browser that offered a subprotocol requires the server to echo one or it fails the socket.
- Pools and limits: `MAX_UNAUTHENTICATED = 4`, `MAX_PAIRED = 12` (`:567`); `HANDSHAKE_TIMEOUT` 5 s, `IDLE_TIMEOUT` 30 s, `WRITE_TIMEOUT` 10 s (`:570`–`574`); `PAIR_PER_MINUTE = 6`, `INFO_PER_MINUTE = 60` (`:583`); `Limits::limited` (`:631`) rate-limits **only** `/api/v1/pair` and `/api/v1/info` by exact path match. The accept loop (`:694`–`721`) closes a connection at once when 4 unauthenticated ones exist, **before** any request is read, so there is no way yet to tell a page load from a probe at accept time. A connection leaves the unauthenticated pool only when the frame's reply has `authenticated: true` (`:835`–`849`).
- `connection` (`:770`): every request, whatever the path, is `try_send` to the frame (`:810`). A static file would cost a frame pass (one frame interval, per `remote-client.md` §10 results) and take one of 64 inbox slots and one of the 8 per-pass drains (`DRAIN_PER_PASS`, `:580`) unless the connection thread answers it directly.
- `subscriber` (`:878`): the events socket; non-blocking, queue 256; text frames from the device (`watch`/`unwatch`) go to the frame as `SubscriberFrame`.
- `local_address` (`:962`): the one routed outward; `None` with no network.
- Certificate: `make_identity` (`:95`) builds `CertificateParams::new(Vec::<String>::new())`, i.e. **no subjectAltName**, CN `Switchboard <server id>`, `rcgen` default validity. The native clients pin SPKI so never needed names; a browser does (see Q).

### The frame side — `src/app.rs`
- `serve_pending` drain (`:1575`–`1600`): polls 8 requests per pass and calls `serve_remote`.
- `serve_remote` (`:3017`): **the allowlist.** `strip_prefix("/api/v1/")` or `404 not_found` via `refuse` (`:3023`). Unauthenticated: `GET info`, `POST pair` only (`:3029`–`3032`). Then `authenticate` (`:3128`): **bearer header only**; no cookie path; no bearer is a 401 `unauthorized` "pair this device first"; an unknown token is 401 "the token is not known; pair again". Revocation therefore shows to the page as a 401 with that message and the same code as "never paired"; there is no distinct `revoked` code. (`authenticate` also dispatches `DeviceSeen` on every request.)
- The routes the page needs already exist: `GET projects`, `GET projects/{id}/sessions`, `GET sessions/{id}`, `GET waiting`, `GET sessions/{id}/last-response`, `GET sessions/{id}/screen`, `POST sessions/{id}/send`, `GET events` (`:3040`–`3105`; content routes via `remote_content_route`, `:1947`). `send` and the others go through `remote_command` (`:3159`), body `{op, ...}` with the op the idempotency key; control scope is checked there.
- `remote_subscribe` (`:2723`): requires `request.upgrade`; `Subscriber{id, queue, device, all}` (`:242`); `RevokeDevice` handling in `dispatch_inner` (`:486`) drops the device's subscribers, which closes their sockets. A revoked browser's open WebSocket closes; the browser's close event carries no reason text from this path.
- `remote_info` (`:3568`): `server_id`, `server_name`, `protocol`, `capabilities`, `spki_sha256`, `version`, `limits`, `pairing_open`. It does **not** say whether the caller is paired or its scope/host name beyond `server_name`. The issue's "the device's scope in the header" needs the page to learn its own scope: the `/pair` reply has `scope` (`:3660`) but a returning browser (no `/pair`) has no call that returns its own scope or device name. Candidates are an extra field on an authenticated reply or a new endpoint; neither exists today.
- `remote_pair` (`:3606`): requires an open window, then JSON body `{spki_sha256, code, device_name}`; wrong key or wrong code each call `PairingFailed` (3 closes the window, `src/core/remote.rs:~44`); the reply is `{token, scope, server_id, device_id}` in the usual envelope. The token is in the JSON body. No `Set-Cookie`.
- `refuse` (`:3754`): logs method, path, code only (no query, so a `?code=` would not be logged by this line; the other log lines were not audited).
- Subscribers receive events as JSON text; the envelope fields in `event_json`; `hello` first.

### The pairing window — `src/ui/remote.rs`, `src/core/remote.rs`
- `src/ui/remote.rs:155`–`215`: builds the JSON payload `{server_id, spki_sha256, code, addresses}` (`:161`–`166`), `addresses` = `["<ip>:<port>"]` or empty, from `remote::local_address()` and `cx.remote_port.unwrap_or(identity.listen.port)`; `qr_texture` (`:280`) with `qrcode::QrCode::new`; "Copy invite" (`:204`) puts the same JSON on the clipboard. The key is also shown as `short_hash` (first 16 hex digits in groups of four).
- The dialog text says "Scan, or type the key and the code." A URL QR changes what a camera app does with it (it opens the browser), which is the point, but then a native client scanning it gets a URL.
- Only one address is put in the payload; the dialog also shows `Address ip:port`. With the port on loopback (`listen.lan == false`) the address is still the LAN IP, which then refuses connections. Not a new issue but the page URL inherits it.
- `core/remote.rs`: `OpenPairing{code, scope}`, `PairingFailed`, `Paired`, `RevokeDevice`, `SetDeviceScope`, `new_device` (takes the scope from the window). Pairing logic is core-side and deterministic; nothing in it knows what kind of client paired.
- The existing UI test `remote_devices_dialog_opens_pairing_and_revokes_a_device` is at `tests/ui.rs:7424`. It asserts on the dialog, not on the QR payload (I did not read its body, so whether it asserts the payload text is unchecked).

### The text pairing path that must keep working — Swift
- `client/Sources/SwitchboardProtocol/Info.swift` (`PairingInvite`, ~`:90`–`117`): `Decodable` with `server_id`, `spki_sha256`, `code`, `addresses`; `parse(_:)` is `Wire.decode(PairingInvite.self, from: Data(text.utf8))`, i.e. **JSON only**; a URL string would throw.
- `client/Sources/switchboard-remote/main.swift`: usage lines 12–13; `pair` (`:107`–`125`) takes either `'<invite json>'` (as one argument, `PairingInvite.parse(rest[0])`) or `<host:port> <code> <spki_sha256>`. - The Swift tests are not in CI or the pre-commit hook (design.md A2 status). A change to `PairingInvite.parse` is not exercised by `cargo test`.

### What the headset/CLI does that the page would copy
- The "last response" the Swift browser shows comes from `GET sessions/{id}/last-response` (`BrowserView.swift:35`, `:153`, via `manager.lastResponse`).
- **The "one-line excerpt the card shows" is not a wire field.** The Mac computes it in the UI: `agent_excerpt` (`src/ui/cards.rs:558`): first non-empty line of the last turn's `final_text`, else the last activity line, else `You: <prompt>`, clipped to 160 chars; non-agent kinds use `state.captions` (screen text). `SessionView` (`control/src/lib.rs:637`) has no excerpt, no `last_message`. (`last_message` exists only in the hook log and core tests.) `remote-client.md` §4.3 says the card's excerpt is "`last_message` from the `Stop` hook … a field of the session's metadata"; the code does not match that sentence. So the issue's "each with its kind, state and the one-line excerpt the card shows" implies either one `last-response` fetch per session (N requests per list view, each through the content worker and watch set, cap 128 keys) or a new additive field on `SessionView`, which the issue says to avoid ("No new read model unless the page cannot do without one"). The hash for the fingerprint diff is derived on `SessionView`, so adding a field moves `changed` frames.

## 3. Shape of the change, as the tree allows it (not a plan)

- Adapter: a second kind of reply (non-JSON body, content type, extra headers) and a way to answer a static path either on the connection thread (before the frame, outside `RemoteIncoming`) or on the frame. The allowlist comment in `serve_remote` (`:3014`–`3016`) and `remote-client.md` §4.1/§5 ("Any path outside `/api/v1/` is refused", "nothing but `/info` and `/pair` before pairing") are the sentences that change.
- Auth: whichever credential carrier is chosen must be accepted in `authenticate` (`:3128`), and `RemoteRequest` must carry it, since `read_request` drops cookies today. The native bearer path must stay.
- Pairing URL: `src/ui/remote.rs:161` payload and the Swift `PairingInvite.parse` (`Info.swift`) and the CLI's `pair` argument (`main.swift:107`). A URL form is parseable on both sides without JSON, but the Swift side would be a new parser and an `addresses` list does not fit a URL with one authority (only one address fits).
- Docs: `remote-client.md` §4.1, §4.3, §5 and the Milestone list; `docs/design.md` "Remote client" status section (ends at ~`:3583`); README Layout (`web/`, new files), `CHANGELOG.md` Unreleased; possibly a spike (`spikes/*/README.md`) for browser behaviour per CLAUDE.md ("add a new spike directory for any new risky mechanism before building on it"). The WebSocket-credential mechanism and the certificate trust on iOS/Safari are such mechanisms.
- Hard-rule interactions to carry: no keystroke injection/osascript for testing a browser; tmux only on the test socket; the page and any fixture must not name a client; commit/PR text carries no tool attribution (CLAUDE.md overrides the harness reminder to add trailers); secrets never in URL or logs.

## 4. Things the issue says that this tree contradicts or does not support

- "The pairing window's QR … a QR carrying `{server_id, spki_sha256, code, addresses}`": true (`src/ui/remote.rs:161`).
- "Any path outside `/api/v1/` is refused": true (`:3023`, 404).
- "the one-line excerpt the card shows": not on the wire (above).
- "the device's scope and host name in the header": host name is in `/info` (`server_name`); the scope is only in the `/pair` reply; nothing answers a returning device.
- "revoked states said plainly": the host answers a revoked token with the same 401 / `unauthorized` as an unknown one (`:3128`–`3156`); the message text differs only for no-token vs unknown-token. A revoked token is indistinguishable from a never-valid token because only hashes of live tokens are kept.
- "§5's rule that no non-loopback bind serves anything but `/info`, `/pair`": the spec text is `remote-client.md:306` ("Require pairing before anything but `/info` and `/pair`") and `:319`; and the UI checkbox hover text (`src/ui/remote.rs:~126`) says "only paired devices get past /info". Both say what the issue says to keep, with the page added.
- "§4.1 allows four unauthenticated connections": true, `MAX_UNAUTHENTICATED` (`:567`). Nothing counts a keep-alive connection that finished loading the page and sits idle for up to `IDLE_TIMEOUT` (30 s).
- "`/api/v1/events` WebSocket with the revision counter and `changed` events": true. Note the events URL accepts `?scope=all` as a query parameter, so query handling exists for the WebSocket path.
- Issue says the page may "post `send`"; the body shape is `{op, ...}` (control port `Body::Send`), op required (`serve`, `:3772`+). The page must make a UUID op per send and use `/ops/{op}` on timeout per §4.5. A page that is reloaded mid-send loses its op unless it keeps one.
