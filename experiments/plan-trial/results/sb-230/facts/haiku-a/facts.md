### Browser protocol

- Cookies do not isolate by port: "Cookies do not provide isolation by port." A cookie one port writes, another port on the same host can read and overwrite (https://www.rfc-editor.org/rfc/rfc6265#section-8.5). So a cookie name must include `server_id`.
- Site comparison ignores port, and a host with no registrable domain (an IP address) has site `(scheme, host)`: "the port and domain components are ignored"; "If origin's host's registrable domain is null, then return (origin's scheme, origin's host)" (https://html.spec.whatwg.org/multipage/browsers.html#same-site). Reading of that algorithm: an `https:` page on another port of the host's IP is same-site with the host, so a `SameSite=Strict` cookie reaches it. An `http:` page on that IP is not same-site (scheme differs). `localhost` is a different host.
- So `SameSite=Strict` does not stop a same-site page on another port; the host must check `Origin` on state changes too. MDN: `Strict` sends the cookie "only in response to requests originating from the cookie's origin site" (https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies).
- Browser clients always send `Origin` on the WebSocket opening handshake: "The request MUST include a header field with the name Origin if the request is coming from a browser client" (https://www.rfc-editor.org/rfc/rfc6455#section-4.1). The host can check it on the `/api/v1/events` upgrade.
- Subprotocol omission is valid: "if the server does not agree to any of the client's requested subprotocols, the only acceptable value is null" and the server "MUST NOT send back a Sec-WebSocket-Protocol header" in that case (https://www.rfc-editor.org/rfc/rfc6455#section-4.2.2). The client fails only when the server names a value it did not offer (§4.1). So a token offered in `Sec-WebSocket-Protocol` needs no echo; a server that echoes must echo one offered value. Tree: `respond_upgrade` writes the 101 by hand with no subprotocol (`src/adapters/remote.rs:519-526`), so it can omit the header as is.
- Preflight: a request is "simple" only with GET/HEAD/POST and a `Content-Type` of `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`, plus CORS-safelisted headers. `Content-Type: application/json` or a custom header such as `X-Switchboard` is preflighted, and "Once the preflight request is complete, the real request is sent" (https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS). So a `text/plain` POST with a JSON body needs no preflight; the host cannot rely on a refused OPTIONS alone. Check `Origin` and the body's `Content-Type`.
- CSP Level 3: "'self' now matches 'https:' and 'wss:' variants of the page's origin, even on pages whose scheme is 'http'" (https://www.w3.org/TR/CSP3/ §1.3). MDN: "`connect-src 'self'` does not resolve to websocket schemes in all browsers" (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/connect-src). So name `wss:` explicitly, or the same origin, and test each target browser.
- Browsers cannot pin a site's own key in Chrome: HPKP was removed, "For these reasons, this feature is being removed," and the page names no replacement for pinning one's own pages (https://developer.chrome.com/blog/chrome-72-deps-rems). Safari and Firefox not checked. The URL `key` can only be compared by the page's script, which the answering server supplies.
- `HttpOnly` cookies are not readable by `document.cookie`; `Secure` cookies are sent only over HTTPS; a `__Host-` cookie must be `Secure`, have no `Domain`, and `Path=/`; `SameSite` defaults to `Lax` when unset (https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies).
- `Referrer-Policy: no-referrer` omits `Referer`. The default `strict-origin-when-cross-origin` sends origin, path and query on same-origin requests, so the code in `?code=` would be sent unless the page sets the policy. The policy is set by the response's `Referrer-Policy` header (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy).

### Certificate

- Chrome's 398-day limit applies to "TLS server certificates from CAs that are trusted in a default installation of Google Chrome," not to locally operated CAs (https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/certificate_lifetimes.md). So Chrome's rule does not reach the self-signed leaf. The rcgen default expiry (year 4096, `src/adapters/remote.rs:91-93`) is therefore not a Chrome validity error.
- Apple's 825-day rule is stated for "TLS server certificates issued after" July 2019 (https://support.apple.com/en-us/HT210176). The page does not say whether it covers a user-accepted self-signed leaf. Unresolved for Safari; a validity of 398 days or less avoids the question.
- The certificate has no SAN: `CertificateParams::new(Vec::<String>::new())` and only a CN (`src/adapters/remote.rs:102-107`). Chrome 58 stopped using the subject CN for hostname matching and takes hostnames from SAN only (Chrome engineer's post, 2017: https://textslashplain.com/2017/03/10/chrome-deprecates-subject-cn-matching/, announcing "Chrome 58 will require"). Consequence: a warning for an IP host. The shape of that warning is unresolved (below).
- Reissuing from the same key verifies: `docs/remote-client.md:308` ("a certificate reissued from the same key (a new expiry) still verifies"). The tree has no reissue path: `identity.json` is made once (`docs/remote-client.md:99`).
- TLS has no ALPN (`grep alpn src/adapters/remote.rs` is empty), and the port answers one request per connection over HTTP/1.1 (`docs/remote-client.md:128`). A browser therefore speaks HTTP/1.1 to it.

### Tree

- `respond()` hard-codes `Content-Type: application/json` and `Connection: keep-alive` (`src/adapters/remote.rs:530-546`). `RemoteReply` is `status`, `body`, `authenticated` only (`:389-393`). Writing a static response needs a header-capable writer. `RemoteReply {` occurs 30 times in `src` and `tests`, counting the definition.
- `read_request` keeps the bearer only from `Authorization` (`src/adapters/remote.rs:444-514`, investigation §1). It keeps no `Cookie`, `Origin`, `Host`, `User-Agent` or `Sec-WebSocket-Protocol`; the test request at `:1046` shows only `Host` and `Authorization` in use.
- `GET /` is refused 404 today: `serve_remote` returns `not_found` for any path without `/api/v1/` (`src/app.rs:3023-3025`).
- `/info` and `/pair` are served before authentication (`src/app.rs:3028-3029`). `/info` returns `server_id`, `server_name`, `protocol`, `capabilities`, `spki_sha256`, `version`, `limits`, `pairing_open`, and no caller fields (`src/app.rs:3568-3600`). A device cannot learn its own scope or name after pairing; only the `/pair` reply carries scope (`docs/remote-client.md:313`, "`/pair` answers with the token and the granted scope").
- The `/pair` body's `device_name` is trusted as sent (`src/app.rs:3650`). The User-Agent is not kept (`read_request`, above).
- Authentication: no bearer gives 401 "pair this device first"; an unknown token gives 401 "the token is not known; pair again" (`src/app.rs:3131-3148`). A revoked device's record is removed (`docs/remote-client.md:316`, "Revocation removes the record"), so revoked and never-paired look the same. Key rotation deletes every record (`src/app.rs:2816`, `devices.clear()`), so "identity changed" also looks the same on the wire. A "revoked" state the issue asks for needs a distinct code or a page-side rule.
- Limits: only `/pair` (six a minute) and `/info` (sixty a minute) are rate-limited (`src/adapters/remote.rs:622-638`). Static GETs would be unlimited unless added.
- Pools: 4 unauthenticated, 12 paired (`src/adapters/remote.rs:566-568`). A socket beyond the unauthenticated pool is closed at accept (`:701-707`). It moves to the paired pool only on an authenticated reply (investigation §1, `:835-849`). Idle timeout 30 s (`:573`). Spike 22 measured a full pool refusing a connection in 0.6 ms (`spikes/22-remote-port/README.md:79`).
- Native clients send only a bearer: `client/Sources/SwitchboardTransport/HostClient.swift:177` and `:384`. No `Cookie` or `Set-Cookie` appears in `client/Sources`. A cookie branch in `authenticate` does not change them.
- `SessionView` has no excerpt field (`grep excerpt control/src/lib.rs` is empty). ### QR

- The tree encodes with `QrCode::new` (`src/ui/remote.rs:281`), which is `EcLevel::M` (`qrcode-0.14.1/src/lib.rs:75-76`, the crate pinned at `Cargo.toml:65`).
- Byte-mode capacity at level M: version 8 = 152, version 9 = 180, version 10 = 213 (https://www.thonky.com/qr-code-tutorial/character-capacities). Version 10 is 57 modules (https://koloqr.com/guides/qr-code-capacity); version 9 is 53 by the 4-module step.
- Payload lengths, computed from the field widths (UUID 36, key 64 hex, code 8, address 21 max): JSON form 189 bytes, so version 10 (57 modules). URL with the 64-hex key 153 bytes, so version 9 (53 modules). URL with a 43-character key 132 bytes, so version 8 (49 modules).
- The Rust probe did not run: `cargo` is `/opt/homebrew/opt/rustup/bin/cargo` with no toolchain installed (`rustc` not found), so the byte counts are arithmetic, not measured through the crate.

## Unresolved

- Certificate exception scope: whether Safari, Chrome, Firefox keep a proceed-through exception per host, per host and port, or per session. Tried: WebSearch. Found a Firefox bug saying trust is tied to a URL including port (https://bugzilla.mozilla.org/show_bug.cgi?id=700837), a lead, not a spec, and no WebKit or Chromium primary. Needs a click on a device.
- Whether a cookie set over a click-through self-signed HTTPS origin is stored as `Secure` and sent on `fetch` and `wss://`. Tried: MDN says `Secure` needs HTTPS, not what a certificate error does to it. Needs a browser.
- Whether a cross-site WebSocket handshake carries `SameSite=Strict` cookies. Tried: WHATWG WebSockets (https://websockets.spec.whatwg.org/) says cookies go through Fetch with credentials mode "include"; the SameSite rule was not found. Moot if `Origin` is checked.
- Whether the page's `Referrer-Policy: no-referrer` covers its own script and stylesheet fetches. Tried: MDN is ambiguous ("unless it's overwritten by a Referrer-Policy HTTP header on the CSS stylesheet's response"; script not stated). Mitigation for the plan: set the header on every static response, and consider inlining assets under a CSP hash so there are no subresource fetches; both need a browser check.
- Whether `history.replaceState` removes the code from the browser's visited-URL record (address-bar suggestions, history database). Tried: MDN covers only session entries. Needs a browser check.
- Browser socket count per origin during a page load, and whether a refused socket is retried. The only number found: Chrome's maximum of 6 per host (https://support.google.com/chrome/a/answer/3339263, "Maximum per Host: 6 connections"). Safari and Firefox not found. With 6 possible sockets and 4 unauthenticated slots, a page load can exhaust the pool. Needs a run.
- Whether an idle keep-alive browser socket holds an unauthenticated slot and so blocks `/pair` for up to 30 s. The tree says the slot is held (`src/adapters/remote.rs:701-707`, `:573`); the browser's idle behaviour needs a run.
- What a browser shows for a certificate with no SAN for an IP host: an interstitial the owner can proceed past, or a hard failure. Tried: SSL Dragon and community posts (leads only, e.g. https://www.ssldragon.com/how-to/fix-ssl-errors/net-err-cert-common-name-invalid/). Needs a device.
- Whether Safari's 825-day rule applies to a user-accepted self-signed leaf (see Certificate).
- iOS Camera behaviour on a URL with an IP and a self-signed certificate: whether a banner needs a tap before Safari opens, and where the warning appears. Tried: Apple's Camera guide says tap the link at the bottom; third-party sources say a banner; no source covers self-signed certificates. Needs a phone.
- Whether iPadOS reports a Mac User-Agent, and whether `navigator.maxTouchPoints > 0` identifies it. Tried: developer forum and blog leads only, no WebKit primary. The plan should not rely on the User-Agent for the device name anyway.
- Whether the 53- and 57-module QR codes scan at a phone's distance and on a dark display. Needs a phone (see Spike decision).
- Whether a browser sends its `Origin` as `https://<ip>:<port>` for the page (the scheme and port form). Assumed from RFC 6455 §4.1; the browser form was not checked.
