Read: CLAUDE.md, docs/lessons.md (general architecture lessons only; nothing remote-specific), docs/remote-client.md §4.1-4.5 and §5, the remote status section of docs/design.md (`## Remote client (2026-10-12)`, line 3107), and the code named below. ## 1. On-disk record and rehydration (before the pane)

Nothing new has to be stored for the first cut, and it should stay that way.

- **Device record.** A browser is a `PairedDevice` (`src/ports/remote.rs:96`: id, name, scope, `token_sha256`, created, last_seen) in `<data dir>/devices.json`, written by `RemoteFiles::save_devices` (`src/adapters/remote.rs:83`). `/pair` already makes it (`remote_pair`, `src/app.rs:3606`). The token is only ever stored as a hash. A browser needs no new field. A "browser" marker would be an additive field on `PairedDevice` and might need a schema bump, per CLAUDE.md "Extending the contract". The issue does not ask for one.
- **Revoke.** `AppAction::RevokeDevice` deletes the record, and the next `authenticate` (`src/app.rs:3125`) answers 401 `unauthorized` ("the token is not known; pair again"). The existing code also closes that device's subscriber. The page's "revoked" state is therefore "a 401 after having a credential". Nothing needs persisting host-side.
- **Identity.** The identity (`identity.json`, key in the Keychain under `remote-key:<server_id>`) is already durable. The page's "identity changed" test compares the SPKI in `/info` with the one it paired against. A key rotation clears `devices.json`, so the old browser token 401s too. The page has two different states to word: key differs (identity changed) and key same but token refused (revoked).
- **Pairing window.** `PairingWindow` is in-memory only (`src/core/remote.rs:43`, `AppAction::OpenPairing`). It is never saved, and it stays that way.
- **Browser-side rehydration.** The only client state is the credential. Options (see Decision 2): an `HttpOnly` cookie (the browser keeps it; the script holds nothing) or `localStorage`. On a reload the page rehydrates from the REST snapshots (`/projects`, `/projects/{id}/sessions` or `/waiting`, `/sessions/{id}`), which are whole collections at a revision (§4.2). It then opens `/api/v1/events` and follows §4.4 "Subscribe first, then snapshot". There is no replay; `resync_required` means refetch everything. The epoch changes on host restart, so everything refetches. That matches "workspaces are data, processes are a cache": the page is a pure cache of the host.
- **Which `/info` key a browser holds across visits.** Per-origin, so a rotated key shows as "identity changed". A browser that already has a cookie/token for that origin hits `/info` first and compares.

## 2. Code the issue touches

### Host HTTP layer: `src/adapters/remote.rs` (1088 lines)
- `read_request` (`:444-517`) parses the request. It takes only `Authorization: Bearer` from headers (`:490`), lowercases header names, ignores `Cookie`, `Origin`, `Host` and `User-Agent` (it keeps no other headers). Cookie auth, an Origin check and a user-agent device name all need a change here: either add fields to `RemoteRequest` (`:360`, additive) or carry the extra headers some other way. The WebSocket upgrade key is already extracted (`:494`). `Sec-WebSocket-Protocol` is not read.
- `respond` (`:530-551`) writes every response as `Content-Type: application/json` with `Connection: keep-alive` and no other headers. Static files need a response writer with a caller-chosen content type, `Content-Security-Policy`, `Cache-Control`, `X-Content-Type-Options`, `Referrer-Policy`, and for `/pair` a `Set-Cookie` (if cookies are chosen). The reason table (`:532`) lacks 301/302/304/etc.
- `respond_upgrade` (`:519`) writes the 101 by hand. It would need to echo a chosen `Sec-WebSocket-Protocol` if that route is taken, or the browser fails the connection.
- `connection` (`:770-875`): the single path every request takes. The rate window check is `shared.limits.limited(&request.path)` (`:786`); `Limits::limited` (`:631`) only knows `PAIR_PATH` and `INFO_PATH` (`:586-587`), so any other path, a page file included, is unlimited. A rate window for `GET /` and the static files is a new line there. Every connection starts in the unauthenticated pool (`MAX_UNAUTHENTICATED = 4`, `:578`; accept loop `:696-716`). A reply with `authenticated: true` moves it to the paired pool (`:826-841`), and the move is made on the first authenticated reply. A page load on a phone is several requests, but over keep-alive they ride one connection. Browsers open up to six parallel connections per host though, so a page load plus `/info` may hold several of the four unauthenticated slots at once (see Open questions). Static-file replies are unauthenticated, so the connection stays in the 4-pool until the browser authenticates.
- `error_body` (`:556`) and the 404 for non-`/api/v1/` paths are JSON.
- TLS identity: `make_identity` (`:95-127`) builds `CertificateParams::new(Vec::<String>::new())`: **no subject alternative names**, a CN of `Switchboard <server_id>`, rcgen's default validity (year 4096, per the comment at `:91`), a P-256 key. `pinned_client` (`:168`) and the `Pin` verifier (`:183`) ignore the name and check the SPKI, which is why this works natively. A browser does name matching against SANs. The consequences are open questions below (this is the largest unknown under Decision 1).
- `local_address` (`:962`): the UDP-connect trick to find the Mac's outbound LAN IP. The QR URL uses it.

### Routing and the allowlist: `src/app.rs`
- `serve_remote` (`:3017-3135`): `strip_prefix("/api/v1/")` first; anything else returns 404 `not_found` through `refuse` (`:3023-3025`). `GET /` and the page files would be a branch before this one, answered with no authentication. The comment at `:3014` says "everything else refused before it is translated to the wire". The allowlist is the `match` at `:3028-3105`.
- `("GET", ["info"])` and `("POST", ["pair"])` are answered before `authenticate` (`:3028-3032`).
- `authenticate` (`:3125-3153`) reads `request.bearer`. Cookie auth would add a second source here, and it makes CSRF a new concern (see Open questions).
- `remote_pair` (`:3606-3660`): requires `spki_sha256` equal to the host's (`:3631`), then the code. Failures call `AppAction::PairingFailed` (three close the window). It returns `{token, scope, server_id, device_id}` through `envelope(..., false)`; `device_name` is taken from the body (`:3644`) with fallback `"Device"`. A Set-Cookie would need `RemoteReply` (`:389`: status, body, authenticated) to gain a header field.
- `remote_info` (`:3568`): returns `server_id`, `server_name`, `spki_sha256`, `capabilities`, `pairing_open`, `limits`. The page's key comparison reads this. It has `scope` listed in capabilities but no per-device scope; the device's scope is only returned by `/pair`. For the header ("the device's scope and host name") the page needs the scope after a reload: with a cookie the script never sees the pair reply, so the scope has to come from somewhere. No endpoint today says "who am I" (see Open questions).
- `remote_subscribe` (`:2723`): the WebSocket accept. It needs `request.upgrade` and a bearer-authenticated device.
- `remote_command` (`:3156`): `send` needs `{op, text}`; `op` 1-64 chars is the idempotency key; text 1 byte to 16 KiB; a `read` device gets 403 `scope`. The page's reply box posts exactly this, with a UUID per send, and follows with `/ops/{op}` on a timeout (§4.5).
- `remote_content_route` (`:3099-3103`): serves `screen`, `conversation`, `last-response` through the content worker.
- Where `serve_remote` is called: `:1595` (`serve_pending`).
- `Served::Now` / other variants: the static branch would be `Served::Now` with a body reply, or better handled on the connection thread (see Open questions on whether the frame should be involved at all for static files; today every request goes to the frame, which is why the frame's 8-per-pass drain bound and the 64-deep inbox apply to page loads too).

## 3. Findings per decision named in the issue

(Observations from the tree only. The decisions are the plan's.)

1. **Browser trust.** Today's certificate has no SANs and a CN of `Switchboard <uuid>`, a year-4096 expiry, and is made once per installation. Whether a browser will let the owner click through such a certificate, per browser, is not a tree question. The host-side options in the tree: (a) leave as is; (b) reissue the certificate over the same key with SANs for the current LAN IP(s)/hostname. `spki_sha256` is key-based, so reissue is already allowed by §5 ("a certificate reissued from the same key (a new expiry) still verifies"), but the LAN IP changes with DHCP and the cert is stored in `identity.json`, so it would be generated per listen rather than once; (c) serve the cert for download. §5's "no non-loopback bind serves anything but `/info`, `/pair`" is a sentence in the spec and also a doc comment at `src/app.rs:3014`, plus the test `the_allowlist_refuses_everything_else_with_no_side_effect`; all three need amending together.
2. **Token to the WebSocket.** Today only `Authorization: Bearer` is read (`:490`). Every route above needs a decision on whether the cookie is accepted on every `/api/v1/` route or only some. `fetch` with `credentials: 'same-origin'` and a WebSocket to the same origin both send cookies. A cookie adds CSRF surface that the bearer header never had (a cross-site form post or a cross-site WebSocket cannot set the header, but the browser would attach a cookie). `SameSite=Strict` addresses the site-level case; a different port on the same host counts as same-site (site = scheme + registrable domain, port ignored), which is a matter for [source]. The host has no Origin check today. The rule at §5, "never in a URL", is spec text to be amended or kept.
3. **One QR or two.** In the tree: the JSON is built once at `src/ui/remote.rs:147` and used for both QR and clipboard. The three native consumers all go through `PairingInvite.parse` (CLI, headset sheet, `SWITCHBOARD_INVITE`), so the change point is one function plus the CLI's three-argument form (which already has no JSON). Fixtures: `FixturesTests.swift:157-165` holds the only JSON example of an invite.
4. **Static paths.** Known constraints in the tree: 8 KiB head limit (`MAX_HEAD`, `:437`), 64 KiB body, one request at a time per connection, the frame drains 8 per pass, 4 unauthenticated connections, inbox 64. `/info` is limited to 60/min and `/pair` to 6/min per listener (not per client address). A page load of N files from one phone makes N requests; with per-listener windows, a page window must be sized so one phone's load does not starve `/info`, and a second visitor can still be locked out by a stranger's flood (existing property for `/info`). The existing responses are always JSON; there is no `Content-Length`-only 304 path or `HEAD` handling (the method is passed through as a string; `HEAD` currently 404s).
5. **Where the page lives, tests.** `Cargo.toml` has no `include` list or `exclude` that would drop `web/` from the crate (only `vendor/egui_term` excluded, line 91), and no `build.rs` was looked for. README Layout table needs a line per new file (CLAUDE.md). `scripts/bundle.sh` needs no change for `include_str!`.
6. **Device record.** Name comes from the body's `device_name` (`:3644`); a UA-derived name would be computed in the page (from `navigator.userAgent`) and sent, or on the host from a `User-Agent` header that `read_request` does not keep. Either way it is a string the device chose, like the CLI's `<hostname> (cli)`.
