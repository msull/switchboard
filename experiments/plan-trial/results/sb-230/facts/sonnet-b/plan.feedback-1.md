1. **The paired pool is not part of the plan, and a page breaks it.** Decision 4 reasons only about the 4-slot unauthenticated pool (facts line 33; `src/adapters/remote.rs:567`). The plan leaves the paired pool untouched. A connection moves to that pool on its first authenticated request (`:835-848`), and `MAX_PAIRED` is 12 (`:568`). The page fetches `/me`, `/projects`, one `/projects/{id}/sessions` per project and the session content, all with `Authorization`, and holds a WebSocket as well. A browser opens up to about 6 parallel connections per host, and a phone plus a second tab can pass 12. Past 12, the host answers 503 `full` (`:838-842`), and the page would then read that as an error or as "revoked". No facts line supports "the page's connections fit". Either say how many connections the page uses (for example, serialise the fetches) or add a fallback. Nothing is written.

2. **The plan contradicts itself on rate limiting.** Line 39 says the static files are answered "before the rate check". Line 42 adds a `page` window to `Limits`. In the tree the rate check is the first thing in the request loop (`:788`) and is keyed on the path (`:631-635`). The `page` window therefore has to run before the static branch, or it never fires. Say which comes first. The 429 test on the page flood depends on it.

Add a ban on `setAttribute('style'` and `cssText` in `app.js`, or the page can break silently in a browser. This rests on nothing in the facts. It is a premise the plan did not state.

Both should say the behaviour is untested in a browser. At the very least, put this in the changelog and the `docs/design.md` gap bullet as an explicit known gap.
