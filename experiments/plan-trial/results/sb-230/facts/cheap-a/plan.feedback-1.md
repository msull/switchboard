1. **`wire::Body::Device { id, name, scope }` rests on nothing.** The plan (Routes, Contract additions) adds a variant to `wire::Body`. In the tree, `Body` in `src/app.rs` (e.g. `Body::Status`, `Body::Decide`, line 1279 onward) is the control port's reply type, from the separate `wire` crate (Cargo.toml:86). The remote REST replies are built as `serde_json::json!` (`remote_info` at `src/app.rs:3568`; the `/pair` reply at about 3655–3668). No facts line proposes a `Body` variant. Facts "For the owner" 7 suggests only "a new read route (for example `GET /api/v1/me`)". Adding a variant changes another crate's contract and would need a rationale. Build the reply with `json!` like `remote_info` and drop `wire::Body::Device` from the plan and the contract list.

2. **Page files on the connection thread, with `Connection: close`: the plan never says how the connection ends.** Facts (Settled, unauthenticated slots) say a static-only connection holds its slot until close or idle timeout. The plan's fix is `Connection: close` on the reply. The loop in `src/adapters/remote.rs:~785–865` is `while let Some(request) = read_request(..)` and continues after a reply. A header alone ends nothing. The plan must say that the page arm returns from the loop after writing, and that the unauthenticated count is released on return. The test `page_connections_free_their_slots` only covers this if it checks the socket reaches EOF. The same problem applies to the rate-limit path, which `continue`s.

3. **The `Host` value goes into the CSP unvalidated.** The plan builds `connect-src 'self' wss://{host}` from the request's `Host` (Settled, facts 28 proposes this). Nothing says to validate it. `;` and spaces in a `Host` would add or alter CSP directives in the reply. Only the requester sees the reply, so the risk is low, but the plan should either restrict `Host` to `[A-Za-z0-9.:\[\]-]` and 400 otherwise, or use `'self'` plus a fixed `wss://`-free fallback. The 400 test covers only a missing `Host`.

4. **The "revoked vs. identity changed" inference is contradicted by the tree in one case.** The plan says "on this host a record goes only by revoke or by key rotation (`src/app.rs:2809–2817`)". `devices.clear()` is at about line 2815, so the cite holds. But `AppAction::RevokeDevice` (`src/core/remote.rs:86`) is the only other removal, and a read-only core path (`Ok(_) if self.core.read_only()`, line 2807) skips the save. The plan should state that the key-missing path (`make_identity`, with the same `server_id`) also regenerates the cert and SPKI. That is what makes "different `/info` key" the rotation signal. It is probably right, but it is asserted from the tree without that cite. The facts file marks the question as an owner choice (item 6) with the same fallback, so this one is minor.

5. **Decision 1 (click-through) and the spike gate rest on Unresolved lines, with a fallback only for one of them.** The facts list as Unresolved: iOS Safari per-address exception retention, whether `wss://` works under the exception, and whether `localStorage` survives. The plan writes fallbacks for the exception (re-accept or download), for `wss://` (polling every 3 s) and for storage (`sessionStorage`, but only "if the owner rejects", not "if storage fails"). The page behaviour when `localStorage` throws is covered at the end of "The page", so this is acceptable. But the fallback for "iOS camera will not open an `https://<ip>:<port>/` link" (facts Unresolved) is missing. If it fails, the single URL QR (decision 3) does not work on the phone at all. The plan puts it in the spike's list but names no fallback beside decision 3. Add one: keep the JSON QR plus a typed-URL path.

6. **`Sec-WebSocket-Protocol` fallback extraction.** The plan says "the first offered protocol that is not `switchboard.v1` becomes `bearer`". The tree's token alphabet is URL-safe base64 without padding (`src/core/remote.rs:337–341`), which is valid as a subprotocol token, so this holds. Add a one-line cite so the choice is shown to rest on that, not on assumption. The same plan says the host "echoes `switchboard.v1` only when the client offered it". Add what happens when an unauthenticated upgrade is refused: the 401 goes out as a normal HTTP reply with no `Sec-WebSocket-Protocol` header, and the browser reports a failed handshake, so the page cannot read the 401 status from a WebSocket. The plan's "a socket that closes with the device gone" triggers the `/info` check, but a failed handshake gives no close code. Say so; the page must treat any failed open as "run the `/info` check".
