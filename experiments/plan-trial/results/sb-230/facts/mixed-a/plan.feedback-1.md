1. **The Origin rule's exemption for `GET` rests on a premise the tree contradicts.** The plan (decision 2, second bullet) leaves cookie-authenticated `GET`s unchecked because "no `GET` route changes a record (the route table, `src/app.rs:3027-3110`)". The route table does not support that. Every authenticated request, `GET` included, runs `self.dispatch_inner(AppAction::DeviceSeen(device.id))` in `authenticate` (`src/app.rs:3150`). That updates `last_seen` and, once `LAST_SEEN_SAVE_INTERVAL_SECS` has passed, emits `save_devices` (`src/core/remote.rs:72-84`), which rewrites `devices.json`. So an https page on another port of the same IP is same-site (facts:25) and sends no `Origin` on a `GET` (facts:32). It can still make the paired device show as "seen" in the dialog, put connections in the 12-slot paired pool (a cookie `GET` sets `authenticated: true`, which moves the connection there, `src/adapters/remote.rs:835-848`), and fill the frame's 64-deep inbox. None of this leaks data, but the plan's sentence is wrong as written. Either state these side effects as accepted, in the plan and in §5, or skip `DeviceSeen` for a cookie-authenticated `GET` that has no `Origin`. Then add a test pinning whichever is chosen.

2. **The cookie's exposure to other listeners on the same address is not stated.** Decision 2 cites facts:24 ("Cookies do not provide isolation by port") only to explain why the name carries `server_id`. The same line has a second consequence. Over https, the browser sends `sb-<server_id>` with `Path=/api/v1` to any other https server on that IP whose path falls under `/api/v1`, for example a development server on the Mac. That server receives the token in clear. Such a server can also set a cookie under the same name, because `server_id` is public in `/info` (`src/app.rs:3575`), and replace the device's credential with one of its own. The plan offers "keeps the token out of script" as the cookie's benefit and never weighs this cost. Spec §5 (`docs/remote-client.md:312`) says the token is sent "only as a bearer header over the pinned connection". The plan amends that line, so the amendment must say where the cookie can go. The dialog's trust sentence should say it too. If the owner considers this unacceptable, the plan already names the fallback (the token in script, `localStorage`), so this needs words, not new code.

3. **`Max-Age=34560000` rests on nothing, and when it runs out the page gives a false message.** No fact or tree line supports the 400-day lifetime. The cookie is set once at `/pair` and never refreshed. After 400 days, or once the browser has evicted the cookie (facts:65 is unresolved on how browsers keep cookies over a click-through), `GET /device` returns 401. `sb.host` is still set, so step 4 tells the owner "this device was revoked on the Mac". The device still has its row in `devices.json`, so that is wrong. Either re-send `Set-Cookie` on an authenticated cookie request (on `/device` is enough) so the lifetime slides, or add "or this browser dropped the pairing" to the revoked wording. Note the stale row in the docs either way.

4. **The `web` field changes type between this commit and its own fallback, which is not additive.** `remote_pair` reads every body field as a string: `body.get(name).and_then(|v| v.as_str())` (`src/app.rs:3637-3643`). `web: true` would read as `""`, so the plan needs a separate bool read, which it does not mention. The fallback in decision 2's fourth bullet then has "the `web` field take `"token"`", a string value for a field that shipped as a bool. Under "Extending the contract" in CLAUDE.md, that is a type change to a wire field. Choose a string-valued field now, for example `"credential": "cookie"` with `"token"` reserved for later, so the fallback adds only a value. Correct the contract-additions list to match.

5. **Step 3 of the page's protocol does not say what happens when `sb.host` is absent.** Facts:58 says ITP clears `localStorage` after seven days without use, and the plan wraps `localStorage` in `try`/`catch` (from "The record"). After that, a page opened without a link has no `sb.host`, but the cookie may still be valid. The plan does not say whether the page skips the identity check and goes on to `/device`, or stops and says "not paired". Say which, and say that the identity-changed check is lost after a week idle. It protects only against a wrong genuine host (from decision 1), so losing it may be acceptable, but the plan should state it.

6. **The commit message does not carry the contract additions.** CLAUDE.md says an additive contract change must "say what you added in the commit message". The plan's "Commit message" section has only the subject line, and "Contract additions" is a separate heading. State that the commit body lists the contract additions: the `RemoteRequest` and `RemoteReply` fields, `GET /api/v1/device`, the new `/pair` field, the cookie credential, and the Origin rule. Also state that it ends without any attribution trailer.
