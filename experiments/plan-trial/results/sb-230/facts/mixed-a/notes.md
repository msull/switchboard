# Notes for issue #230: a web control surface on the remote port

Read: CLAUDE.md, docs/design.md (Trust boundary, Remote client 2026-10-12 and its status entries), docs/lessons.md, docs/remote-client.md in full. Line numbers below are from this worktree (branch `dispatch/230-...`, at "Release 0.4.1"). Nothing was run: no build, no test, no browser.

## 1. On-disk record and rehydration (before any pane)

Workspaces are data, processes are a cache. The web surface adds almost no new durable data, and the notes say where the tree currently has none.

- **Already durable, and enough for a browser device.** `devices.json` (`PairedDevice` in `src/ports/remote.rs`: id, name, scope, `token_sha256`, created, last_seen) and `identity.json` (`Identity`: server_id, name, certificate, `spki_sha256`, listen). A browser is one more `PairedDevice`. Revocation is `AppAction::RevokeDevice` (`src/core/remote.rs:86`) deleting the row. That is the whole server-side record. No schema bump is needed unless a field is added to `PairedDevice` (e.g. a device "kind" or user-agent string). `#[serde(default)]` would make that additive, but `identity.json`/`devices.json` have their own versioning (`IDENTITY_SCHEMA_VERSION`), not `SCHEMA_VERSION`. [tree] to confirm whether a `devices.json` change needs a migration step.
- **No tombstone for a revoked device.** A revoked token and a never-known token are the same thing to the host: `authenticate` (`src/app.rs:3127`) answers 401 `unauthorized`, "the token is not known; pair again". The acceptance line "revoke the phone and the page says so on its next request" cannot be met from the current reply. It would need either a tombstone (hash of revoked tokens, a new durable record) or the page saying "not paired or revoked" for both. The issue asks for "revoked" and "identity changed" to be said plainly, so this is a decision.
- **The page's own state (client side), rehydrated per load:** the token (a cookie or `localStorage`, decision 2), the pinned `spki_sha256` and `server_id` from the pairing URL, the last revision. Everything else (sessions, conversation, screen) is in memory and refetched, as the Swift client does (§7 "What the client keeps": nothing from a host on disk). Rehydration of a page = load HTML, read the stored credential, `GET /api/v1/info`, open `/api/v1/events`, wait for `hello`, fetch snapshots, apply buffered events by revision (§4.4 "Subscribe first, then snapshot"). The existing protocol already gives that; the page re-implements the Swift client's reconcile (per-key held revision, epoch change refetches everything, `resync_required` reconnects).
- **The pairing window** is not saved (`PairingWindow` in core, `OpenPairing` at `src/core/remote.rs:46`; code made by `remote::pairing_code()`, 40 bits, single use, three failures close it). A URL carrying the code is therefore valid only while that in-memory window is open.
- **Host-side secrets:** key in Keychain as `remote-key:<server_id>`; token never stored, only its SHA-256. A web token in a cookie does not change this, but "keep tokens out of logs, URLs" (§5 line 318) now meets a request line that contains the code (see 3.4).

## 2. What exists, with files and lines

### The port (adapter): `src/adapters/remote.rs`
- `RemoteRequest` `:360` carries method, path (query stripped), query pairs, body, `bearer`, `upgrade`. There is **no cookie, no Origin, no Host, no `Sec-WebSocket-Protocol`, no User-Agent field**. Only `authorization`, `upgrade`, `sec-websocket-key`, `content-length` are read in `read_request` (`:444`, bearer at `:487`, upgrade at `:491`); every other header is dropped. The user-agent for a device name (issue item 6) would be a new field.
- `RemoteReply` `:389` is `{status, body, authenticated}`: **no content type, no extra headers**. `respond` (`:530`) hardcodes `Content-Type: application/json` and `Connection: keep-alive`, with a status table that has no 304 and no 308. There is no `Set-Cookie`, `Content-Security-Policy`, `Cache-Control` or `X-Content-Type-Options` anywhere (grep found none). `RemoteReply { .. }` is built by struct literal in about 28 places in `src/app.rs` (count from grep) plus the adapter, so adding a field is a mechanical but wide edit, unless a constructor or `Default` is added first.
- `respond_upgrade` (`:519`) writes a 101 with no `Sec-WebSocket-Protocol`. A browser that offered a subprotocol and gets none back fails the connection (see Open questions), so the subprotocol candidate needs a change here as well as in `read_request`.
- `connection` (`:770`): TLS handshake with 5 s (`HANDSHAKE_TIMEOUT :570`), then a request/reply loop; first request within 5 s then `IDLE_TIMEOUT` 30 s (`:573`). `Limits::limited` (`:631`) rate-limits **only** `/api/v1/pair` (6/min) and `/api/v1/info` (60/min), per listener, not per client address. Every request, including any new static path, goes through `shared.requests.try_send` to the frame (inbox 64, drain 8 per pass) unless the adapter is changed to answer static files itself before that hand-off, as it already answers 429 and 503.
- Pools: a connection starts in the unauthenticated pool (`MAX_UNAUTHENTICATED = 4`, `:567`) and moves to the paired pool (12) only on a reply with `authenticated: true` (`:835`). The accept loop closes a fifth stranger at once (accept thread in `bind`, `:660`-ish). A static page reply would be `authenticated: false` (nothing paired about it), so a browser's page, CSS and JS loads, each possibly on parallel TLS connections, all sit in the 4-slot pool.
- Subscriber (`:878`): WebSocket fed from a queue of 256; a revoked device's queue is dropped (`dispatch_inner`, `src/app.rs:486`) and the socket closes.
- `make_identity` (`:95`): `CertificateParams::new(Vec::<String>::new())` means **no subject alternative names**, CN `Switchboard <server_id>`, key P-256, not_after year 4096. A browser sees a no-SAN, self-signed certificate on an IP-literal host.
- `local_address()` `:962` returns one IPv4 the system routes outward on, or `None`. No hostname, no `.local` name, no IPv6.

### The frame: `src/app.rs`
- `serve_remote` `:3017`. The first line is the allowlist's front door: `request.path.strip_prefix("/api/v1/")`, else a 404 `not_found` (`:3023`). `GET /` today is a 404. `info` and `pair` are served before `authenticate`; everything else needs the bearer.
- `authenticate` `:3127` reads `request.bearer` only. A cookie path means a second source of the token here, and the same function runs `DeviceSeen`.
- `remote_info` `:3568` (what `/info` says: server_id, server_name, protocol, capabilities, `spki_sha256`, version, limits, `pairing_open`). `remote_pair` `:3606` (checks window, then `spki_sha256` equals the host's own key, then code; makes the token; reply `{token, scope, server_id, device_id}`; `device_name` from body, default "Device"). The token travels in the JSON body, so a cookie needs a `Set-Cookie` on this one reply (decision 2).
- `remote_subscribe` `:2723` (requires `request.upgrade`, sends `hello`, registers `Subscriber{device}`); `?scope=all` includes Dispatch workers, plain does not (`hide_workers` `:2687`).
- `bind_remote` `:2936`: `0.0.0.0` when `identity.listen.lan`, else `127.0.0.1` (`:2963`). Bonjour advertises only on LAN.
- The 401 path: `refuse` `:3754` logs method, path and code only; the query is not logged (the path has the query stripped). So the code in `?code=` does not reach the log through `refuse`. [tree] a read of every `log::` that prints a request (none found for the query) would confirm.

## 3. Findings that bear on the decisions

1. **What a self-signed click-through buys is narrower than the issue's framing, and the `key` check has nothing to compare against in the browser.** Page JS cannot read the TLS certificate or its SPKI. The only "key presented by `/info`" available to the page is the `spki_sha256` field of the `/info` JSON, which is whatever the answering server writes. A page served by the impostor serves its own page and its own `/info`. So the URL's `key` guards against reaching the wrong genuine Switchboard by address (a reused DHCP address, two Macs), not against an attacker. On the host side, `remote_pair` (`:3606`) already refuses a `/pair` whose body key is not the host's own, and the page would put the URL's key in that body: against a genuine host that is the only meaningful check; against an impostor the impostor decides. That is the same as the issue's own statement; the notes add that the comparison is page-side and unenforceable from the host's point of view.
2. **Cookies are not port-scoped.** A cookie set by `https://192.168.1.5:43187` is sent to every other port on that host, and a `__Host-` prefix constrains Domain/Path/Secure but not port. Two Switchboard instances on one machine (the dev aid `SWITCHBOARD_REMOTE_PORT`, and tests use it) would share a cookie name unless it carries the server id. `SameSite=Strict` is about site, not origin, so another page on a different port of the same IP is same-site: CSRF on `POST /send` and cross-site-WebSocket-hijack protections need an explicit check (Origin or Host, or a custom request header), none of which exists, because the port has only ever had bearer headers, which a cross-origin page cannot attach. Moving to ambient credentials (a cookie) removes that property for the whole `/api/v1` surface, including the native clients' routes: the cookie is accepted at the same endpoints. This is the largest security consequence of decision 2 and should be named in the plan.
3. **The unauthenticated pool is 4 and a browser's page load is bursty.** HTML, CSS, JS, favicon, `/info`, each possibly on its own TLS connection (browsers open up to ~6 per host), all unauthenticated until a reply with `authenticated: true`. A page load by a stranger-or-owner can occupy the pool, and the pool does not distinguish a browser from a flood. Static replies are also not rate-limited. If the page is served on the frame, it competes with the 8-per-pass drain and the 64 inbox; if served on the connection thread, that skips the frame (and the rule "handlers are thin; no logic in the adapter") but needs a pool decision. A paired browser also holds a paired slot per WebSocket for as long as the tab lives, out of 12 shared with the headset and the CLI.
4. **The pairing code lands in the host's request line.** A URL `GET /?code=...` is read by `read_request` into `RemoteRequest.query` (`:496-505`), so the code crosses the TLS connection and sits in the frame's memory like any query. It is not logged by `refuse` (path only). Also: the browser's history entry exists until `replaceState` runs, a `Referer` carries the URL to any subresource that is not same-origin (there should be none under the CSP the issue asks for), and some browsers sync history or open links from a camera app in a different process before the page script runs. A fragment (`#code=`) never reaches the host or a Referer and `replaceState` still works on it; the issue chose the query string. Whether that is deliberate is a question, not a finding.
5. **The code is single use, the URL is a bearer of it.** Anyone who can see the QR for the five-minute window (a screen share, a photo of the dialog) has the code; the key in the QR does not authenticate the person, as today with the JSON QR. No change from the native flow, but the URL is now also in the phone's camera/Messages/clipboard apps. Equivalent to "Copy invite".
6. **Cert has no SAN.** Even with the click-through, some browsers apply extra rules to certificates they treat as untrusted (HSTS-like blocks, no "Proceed" on some versions for no-SAN, ATS-like policies on iOS WebKit for `WebSocket`/`fetch`). Whether a no-SAN, IP-literal, self-signed P-256 certificate can be click-through-accepted on iOS Safari and Android Chrome, and whether that acceptance extends to `wss://` and to `fetch` is what decides option A (click-through) versus option B (host offers its certificate). Not checked.
7. **The spec's sentences to amend** (the plan is told to amend the spec and the status section): `docs/remote-client.md` §4.1 (bounds: "a TLS handshake..."; the pools; add the page's place in them), §4.3 (add the static paths, which are outside the `/api/v1` allowlist and not in the table; "Everything else on the wire is refused before translation" holds for `/api/v1` only), §5 (line 306 "Require pairing before anything but /info and /pair"; line 309 the QR payload JSON, "scans or types both"; line 312 "It is sent only as a bearer header ... never in a URL", which a cookie contradicts; line 313 "The client stores the token and the pinned key hash in its Keychain"; line 317 "The client verifies the pin on every connection" which a browser cannot), and the design.md sections "Remote client (2026-10-12)" (A1 sentence on "everything else is refused by name", "the QR carrying the server id, key hash, code and address") and "Known gaps". README (Layout row for `web/`, `src/adapters/remote.rs`, `src/ui/remote.rs`, `tests/remote.rs`; dev aids; the `pbpaste` pairing line at ~276), CHANGELOG Unreleased line, and the dialog's text.
8. **Static assets and the layering rule.** The page files are data embedded with `include_str!` (no precedent for text assets in `src`, only `include_bytes!` for fonts and the icon in `src/main.rs:167`, `src/ui/theme.rs:203`). A `web/` directory at the repo root would also need `Cargo.toml` `include`/`exclude` and the bundle script checks (`scripts/bundle.sh`) [tree] not read. CLAUDE.md: `src/core` is deterministic and `src/ui` only draws; the page is neither, it is adapter data. Where the path table lives (adapter or `app.rs`) is a design call; `serve_remote` is where the allowlist lives today.
9. **Hard rules touched.** No keystroke injection: not relevant to the page's own JS. Never write into a project's `.claude/`/`.switchboard/`: not touched. Secret values: the page shows redacted text only; the page's CSP and storage choice are what keep a token out of script reach. No client names anywhere that reaches GitHub: nothing in this issue needs one. Attribution: CLAUDE.md forbids a `Co-Authored-By` or "generated with" line in commits and PR bodies, overriding the harness reminder; the plan's commit and PR steps should say so.
