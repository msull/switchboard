# Issue #230 facts: a web control surface on the remote port

There was no spike. The tree and primary sources settle everything that
can be checked here. What is left needs a real browser on a device and
a person's tap through the certificate warning. Safari is the only
browser on this Mac, and driving it needs `safaridriver --enable`, an
admin step, so none of it runs here. Line numbers are at 7fe8949.

## Settled

### The tree

- `RemoteRequest` is built in one place, `read_request` (`src/adapters/remote.rs:506`). Nothing in `tests/`, `control/` or `client/` names `RemoteRequest` or `RemoteReply` (grep), because `tests/remote.rs` speaks raw HTTP. A new request field (cookie, origin, user agent, subprotocol) touches one constructor. Evidence: `grep -rn "RemoteRequest {"` gives only `src/adapters/remote.rs:506`.
- `RemoteReply { status, body, authenticated }` (`src/adapters/remote.rs:389-393`) is built literally 28 times in `src/app.rs` and twice in `src/adapters/remote.rs`. A headers field needs a `Default` or a constructor, or all 30 sites change. Evidence: `grep -c "RemoteReply {"`.
- `RemoteRequest` and `RemoteReply` are in `src/adapters/`, not in `ports/`, `model.rs` or `action.rs`, so CLAUDE.md's additive-contract rule ("`src/core/model.rs`, `src/core/action.rs` … and `src/ports/` are the shared contract") does not cover them. Evidence: CLAUDE.md "Extending the contract"; `src/adapters/remote.rs:360,389`.
- The certificate can be reissued over the existing key without changing `spki_sha256`. The SPKI hash is computed from the key alone (`spki_sha256_of_key`, `src/adapters/remote.rs:138-141`), and rcgen signs any params with a loaded key (`KeyPair::from_pem`, `:139,146`; `CertificateParams::self_signed(&self, signing_key)`, rcgen-0.14.10 `src/certificate.rs:154`). `make_identity` always generates a new key (`src/adapters/remote.rs:105`), so a reissue is a new function.
- rcgen 0.14 can carry what a browser or an installed trust needs: `subject_alt_names` with `SanType::IpAddress` and DNS names, `extended_key_usages` with `ServerAuth`, `not_before`/`not_after` and `is_ca`. Evidence: rcgen-0.14.10 `src/certificate.rs:57-64,755,812`; `src/lib.rs:313`.
- rcgen's default validity is notBefore 1975-01-01 to notAfter 4096-01-01, and the current certificate takes both. Evidence: rcgen-0.14.10 `src/certificate.rs:83-84`; `src/adapters/remote.rs:106` (`CertificateParams::new` with no override).
- The current certificate has no subjectAltName, only a CN, and no EKU. Evidence: `src/adapters/remote.rs:106-111`.
- `local_address()` always returns IPv4. It binds `0.0.0.0` and connects to `192.0.2.1`, so a URL built from it never needs IPv6 brackets. Evidence: `src/adapters/remote.rs:962-970`.
- The Bonjour host name is `<hostname -s>.local.` as registered by `mdns-sd` (`src/adapters/bonjour.rs:41-48`, `default_server_name` `src/adapters/remote.rs:304-313`). Whether that matches macOS's own LocalHostName is not checked here (Unresolved).
- A code is single use: the first pairing closes the window. The window also closes after three failures or five minutes. A code left in browser history is dead once used or expired. Evidence: `src/core/remote.rs:46-69` (`Paired` sets `self.pairing = None`).
- The record carries no `last_message`. It exists only on the hook event (`src/ports/events.rs:24`, `src/adapters/hooks.rs:71,196`) and is not on `SessionView` (`control/src/lib.rs:636-688`). The card's excerpt is computed in the UI from the transcript for agents (`agent_excerpt`, `src/ui/cards.rs:176-178,558`) and from the pane caption or host title for the other kinds (`src/ui/cards.rs:179-184`). An excerpt on the wire is therefore new work, not a field to expose.
- The watch set is global across the port, capped at 128, least recently read evicted silently. A page that watches one key per listed session can push a headset's keys out. The headset loses only the `changed` events until its next read. Evidence: `docs/remote-client.md:131,254,543`.
- The spec forbids the token in a URL: "sent only as a bearer header … never in a URL" (`docs/remote-client.md:312`) and "keep tokens out of logs, URLs" (`:318`). Both lines name the bearer header, so either cookie or subprotocol transport amends `:312`.
- §5's claim that "a relayed request through a substituted certificate fails" (`docs/remote-client.md:309`) rests on the client sending the `spki_sha256` it saw on the wire. The host checks only what the body says (`remote_pair`, `src/app.rs:3639-3647`), so the claim holds only for a client that can read its own connection's certificate (whether any browser API exposes it: Unresolved).
- The pairing token is base64url with no padding, 43 characters (`src/adapters/remote.rs:340`; `docs/remote-client.md:312`). Its characters `A-Z a-z 0-9 - _` are all RFC 7230 `tchar`, so it is a valid `Sec-WebSocket-Protocol` token. Evidence: https://www.rfc-editor.org/rfc/rfc7230#section-3.2.6 (tchar includes `-` and `_`).
- Swift: `PairingInvite.parse` decodes JSON only (`client/Sources/SwitchboardProtocol/Info.swift:114-116`). It is called by `switchboard-remote` (`main.swift:111`) and `BrowserView` (`:106` for a pasted line, `:883`). `ConnectionManager` builds one (`:474`) and uses `invite.addresses.compactMap(Address.init).first` (`:483`), so only the first address is used and a one-element list from a URL is enough. Eight test files under `client/Tests` name `PairingInvite`.

### Browsers and platforms

- `new WebSocket(url, protocols)` takes no headers. The handshake is a Fetch with credentials mode `"include"`, so the browser's cookies for the URL go with it. Evidence: https://websockets.spec.whatwg.org/ ("credentials mode … include"; constructor signature).
- If the page passes a subprotocol and the 101 response does not echo one of them, the browser fails the connection. The host must therefore write `Sec-WebSocket-Protocol` in `respond_upgrade` (`src/adapters/remote.rs:519-527`) if the token travels that way. Evidence: https://websockets.spec.whatwg.org/ (opening handshake: "covers a subprotocol requested by the client, but not acknowledged by the server").
- Secure contexts are decided by scheme alone: an `https`/`wss` origin is "potentially trustworthy" whatever the certificate's state. Evidence: https://w3c.github.io/webappsec-secure-contexts/ ("Is origin potentially trustworthy?", step 3). Whether each browser follows this after a click-through was not checked (see Unresolved).
- `crypto.randomUUID()` and `crypto.subtle` require a secure context; `crypto.getRandomValues()` does not, so the page can make op ids without depending on secure-context status. Evidence: https://w3c.github.io/webcrypto/ (Crypto interface WebIDL).
- Cookies are not isolated by port: a host's cookies go to every port on that host. A `__Host-` prefix needs `Secure`, `Path=/` and no `Domain`, and still ignores the port. Evidence: https://httpwg.org/http-extensions/draft-ietf-httpbis-rfc6265bis.html (Introduction; `__Host-` prefix section).
- `localStorage` is per origin ("the `Storage` object associated with window's origin's local storage area"), and an origin is scheme, host and port, so two instances on different ports do not share it. Evidence: https://html.spec.whatwg.org/multipage/webstorage.html#dom-localstorage; https://html.spec.whatwg.org/multipage/browsers.html#concept-origin-tuple.
- Chrome: a certificate-error bypass is remembered for one week (604800 s), keyed by host (not port), the certificate chain's SHA-256 fingerprint and the error code. Evidence: https://chromium.googlesource.com/chromium/src/+/main/components/security_interstitials/content/stateful_ssl_host_state_delegate.cc (`kCertErrorBypassExpirationInSeconds`).
- Chrome: an allowed decision is applied to any later request to that host carrying that certificate, not only to top-level navigation. `OnCertError` queries the policy by request host and certificate and continues on `ALLOWED`, with no frame-type check. Evidence: https://chromium.googlesource.com/chromium/src/+/main/content/browser/ssl/ssl_manager.cc. WebSocket certificate errors reach the same browser-side handler through the network-service client (`services/network/websocket_factory.cc`, https://chromium.googlesource.com/chromium/src.git/+/b95c2d2c8a7ea8efcec38e091c19bfbeac6af8d1/services/network/websocket_factory.cc). That is an older snapshot, read but not run.
- Chrome lets the user proceed past a missing SAN (COMMON_NAME_INVALID), an untrusted authority, a date error, "validity too long" and "self-signed local network". Only the fatal set (contains errors, revoked, invalid, pinned key) or strict enforcement (HSTS-style) blocks it. Evidence: https://chromium.googlesource.com/chromium/src/+/main/components/security_interstitials/core/ssl_error_options_mask.cc.
- Chrome's Local Network Access prompt applies to requests from a public-network page to local or loopback addresses. A page loaded from the LAN address calling its own origin is local-to-local and outside it. Evidence: https://developer.chrome.com/blog/local-network-access.
- Firefox: a certificate exception pins the presented certificate to host and port, and Firefox shows no prompt for a failed subresource such as `wss`. The page must therefore be loaded (and the exception made) on the same host:port as the socket, which same-origin guarantees. Evidence: https://bugzilla.mozilla.org/show_bug.cgi?id=1109773 (comment on exceptions pinning to host/port); https://bugzilla.mozilla.org/show_bug.cgi?id=1187666 (WONTFIX: no dialog for subresources).
- Apple (iOS 13 / macOS 10.15 and later): a TLS server certificate must carry the server's name in subjectAltName, and a CN is not trusted. EKU `serverAuth` and validity ≤ 825 days are required only of certificates whose NotBefore is after 2019-07-01. Evidence: https://support.apple.com/en-us/103769. The current certificate's NotBefore is 1975 (above), so as issued only the SAN rule bites. A reissue with today's NotBefore must also carry `serverAuth` and ≤ 825 days, or a manually trusted install is refused.
- iOS: a certificate profile installed by hand (downloaded or emailed) needs Settings > General > About > Certificate Trust Settings > "Enable full trust for root certificates" before it is trusted for TLS. Evidence: https://support.apple.com/en-us/102390.

## Unresolved

- Whether any browser API lets a page read the certificate of its own connection. If none does, the page's key check proves only what `/info` claims, and §5's relay sentence must be amended for browsers. Not looked up; no source found either way.
- Whether Safari (iOS and macOS) applies a click-through exception to `wss://` from the page. WebKit bug 41419 ("allow wss:// if user has accepted https:// warning") is still NEW, last modified 2026-01-12, with no fix noted. Its reports date from the CFStream era. Tried: https://bugs.webkit.org/show_bug.cgi?id=41419 and https://bugs.webkit.org/show_bug.cgi?id=158345 (which says WebKit moved to an NSURLSession WebSocket, behind a flag at the time). Nothing says whether the current implementation honours the exception, and it needs a person's tap in Safari. **This is the question the plan turns on most.** See For the owner.
- Whether `fetch` from the page honours the Safari exception. It is expected, since the page itself loaded, but no WebKit source or document was found. Tried: the WebKit bugs above and a web search.
- How long Safari (macOS and iOS) remembers a click-through, and whether it survives a relaunch. Tried: web search; no Apple or WebKit source found.
- Whether each browser treats a clicked-through page as a secure context in practice (`isSecureContext`, `Secure` cookies). The spec says yes by scheme. No vendor statement was found, and Chrome is known to refuse service-worker registration on certificate errors (https://bugzilla.mozilla.org/show_bug.cgi?id=1162772 and a search; a lead only), which shows certificate state can gate features. Not run.
- Whether `SameSite=Strict` cookies go on a same-origin `wss` handshake in each browser. The specs imply yes: a same-origin Fetch with credentials included, and schemeful same-site treats `wss` and `https` as the same scheme (https://groups.google.com/a/chromium.org/g/blink-dev/c/qB7DKqxkiaA/m/w0XzGvEyBAAJ, a proposal, not a spec). The rfc6265bis text read did not cover WebSockets, and no browser was run.
- Whether a `Secure` cookie can be set from an IP-literal https host with a clicked-through certificate. rfc6265bis leaves "secure connection" to the user agent. Not run.
- Whether the URL with `?code=` lands in Safari's global history, tab list or iCloud Tabs before `replaceState` runs, and whether `replaceState` rewrites those. The HTML spec covers only the session-history entry; global history is user-agent behaviour. Mitigated by the single-use code (Settled). Tried: search; no source.
- How many parallel HTTP/1.1 connections per host iOS Safari opens, and whether the certificate-warning handshake holds a slot in the pool of 4 until timeout or frees it at once. A lead only: Apple's `URLSessionConfiguration.httpMaximumConnectionsPerHost` is documented as 4 on iOS and 6 on macOS, but that is the app API, not Safari. Not run.
- Whether the `<hostname -s>.local` name `mdns-sd` registers matches the Mac's own LocalHostName, which mDNSResponder advertises separately, and so which `.local` name a URL should carry. Not checked.
- Whether iOS Safari resolves `<name>.local` and whether Android browsers do. Not searched to a primary source; needs a device.
- Whether iOS offers the "full trust" toggle for a self-signed leaf with no `basicConstraints CA:true` (the current certificate is `IsCa::NoCa`). The Apple page speaks of "root certificates" only. Not checked.

## For the owner

- **Run on a real iPhone (and once in macOS Safari):** open `https://<lan ip>:<port>/` from the current certificate, accept the warning, then in the page check `fetch('/api/v1/info')`, `new WebSocket('wss://…/api/v1/events')`, `isSecureContext`, and whether a `Secure; HttpOnly; SameSite=Strict` cookie set by a `fetch` POST is sent on the socket. If all work: the plan takes the click-through as the trust step (decision 1) and may use the cookie (decision 2). If the socket fails: the plan either makes certificate install the trust step (reissue with an IP SAN, `serverAuth`, ≤ 825 days and possibly CA:true, plus the iOS full-trust toggle), or replaces the socket for the page with polling or a `fetch`-streamed event feed on the same path the exception already covers. If `isSecureContext` is false: the page avoids `randomUUID` (use `getRandomValues`) and the cookie cannot be `Secure`, which favours the subprotocol token.
- **Decision 1, click-through or install:** if click-through, the paired-devices dialog says the warning is the trust step and that the page's key check catches only a wrong host, not an impostor page; the certificate stays as it is. If install, the host serves the certificate before pairing (a fourth pre-pairing path), the identity is reissued over the same key with SANs, `serverAuth` and a bounded validity, and someone owns reissuing when the IP changes.
- **Decision 2, cookie or subprotocol:** if cookie, `read_request` reads `Cookie`, `/pair` sets it, the name carries `server_id` to keep two instances apart, and the owner accepts that other HTTPS services on that host receive it (ports are not isolated). If subprotocol, the token lives in page storage readable by any script on the origin, and `respond_upgrade` must echo the value.
- **Check `Origin` on the upgrade and on POSTs?** If yes, decide the accepted set (LAN IP, `.local` name, loopback, each with the port). If no, a cookie transport is open to cross-site WebSocket hijacking from another LAN page, and the plan should prefer the subprotocol.
- **"Revoked" versus "never paired":** if a new refusal code, it is an additive code from `authenticate` (`src/app.rs:3125-3153`). If not, the page keeps a non-secret "paired with server X" marker and infers revocation.
- **Scope in the header after pairing:** if a new authenticated endpoint, it is additive and the Swift client can use it too. If not, the header shows the `/pair` reply's scope and may go stale.
- **Card excerpt:** if on the wire, it is a new computed field on `SessionView` with a fixture change on both sides, since the record has no `last_message`. If not, the page fetches `last-response` per session as the headset does and spends watch-set slots.
- **One QR or two:** if one URL, `PairingInvite.parse` learns URLs (only the first address is used), the README's "Copy invite" text changes, and the JSON stays as a parse fallback. If two, nothing in Swift changes.
- **URL host: IP or `.local`:** if `.local`, a certificate exception or SAN binds to that name and survives IP changes. If IP, a new address means a new warning in Chrome; in Firefox a new address is a new host:port.
- **Static paths:** if answered on the connection thread, they cost no frame time and no inbox slot. If on the frame, they go through `serve_remote`. Either way, decide whether they get a rate window and whether a page load may hold the unauthenticated pool of 4 (the device run above shows how many connections Safari opens).
- **Page logic untested by CI** (no JS harness allowed): if accepted, the host-side tests cover paths, headers and the pairing flow, and the page is checked by hand. If not, the issue's no-dependency rule needs relaxing.
