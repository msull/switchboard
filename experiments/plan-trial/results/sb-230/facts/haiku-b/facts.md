# Issue #230 facts: a web control surface on the remote port

Worktree: `/Users/sbgragent/.dispatch/worktrees/340ccb28`, base `7fe8949`. Investigation read: `notes.md`. Nothing was built, run or committed; `git status` is empty. No spike was run (see Unresolved, last item). Browser behaviour could not be tested here: no Chrome or Chromium is installed, and Safari needs a person's hands and a device.

## Settled

- The remote port answers only `/info` and `/pair` before authentication; every other path is refused unless it is under `/api/v1/`. Evidence: `src/app.rs:3026-3029` (`strip_prefix` and the `("GET", ["info"])` / `("POST", ["pair"])` arms before `authenticate`); notes §0 for the 404.
- The host certificate has no subjectAltName. Evidence: `src/adapters/remote.rs:97` (`CertificateParams::new(Vec::<String>::new())`).
- The host certificate's validity is rcgen's default, `not_after` = year 4096. Evidence: `rcgen-0.14.10/src/certificate.rs:83-85` (registry copy, version pinned in `Cargo.lock`); the tree's own comment at `src/adapters/remote.rs:91-92` says the same.
- The host key is P-256 and `spki_sha256` is the hash of the key's SubjectPublicKeyInfo, not of the certificate. Evidence: `src/adapters/remote.rs:91` (doc), `:107-108` (`sha256_hex(&key.subject_public_key_info())`). Consequence: re-issuing the certificate over the same key (new SAN, shorter validity) leaves `spki_sha256` and the QR's `key` unchanged. The key lives in the Keychain and the certificate in `identity.json`; re-issue would need new code to write the new certificate.
- Apple's stated requirements for TLS server certificates: validity of 825 days or fewer, a DNS name in the Subject Alternative Name extension, RSA keys of at least 2048 bits, and the rules apply to certificates issued after 1 July 2019. Evidence: https://support.apple.com/103769 (fetched). The same page does not say whether they apply to a certificate the user has accepted as an exception. See Unresolved.
- Chrome's 398-day rule is named in the Chromium commit "Enforce 398-day validity for certificates issued on-or-after 2020-09-01" (https://chromium.googlesource.com/chromium/src/+/ae4d6809912f8171b23f6aa43c6a4e8e627de784). I read only the commit title from a search result, so it is a lead; see Unresolved.
- RFC 6455 §4.1, client rule: if the server's response includes `Sec-WebSocket-Protocol` naming a subprotocol the client did not request, the client MUST fail the connection. The rule is triggered only when the header is present; the RFC says nothing about a response that omits it. Evidence: https://www.rfc-editor.org/rfc/rfc6455#section-4.1 (fetched).
- RFC 6455 §4.1, client request: a browser client MUST send an `Origin` header. Evidence: same section (fetched). The adapter does not read `Origin` (`src/adapters/remote.rs`, `read_request`, per notes F2; keys read are `authorization`, `upgrade`, `sec-websocket-key`, `content-length`).
- A token carried in `Sec-WebSocket-Protocol` would be visible to the page's script. `new WebSocket(url, protocols)` takes the protocol list from script, and the negotiated value is readable from `WebSocket.protocol`. Evidence: https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket (fetched). This rules the subprotocol option out for the "script never sees the token" claim.
- Fragments are not sent to the server: the fragment is not part of the `http`/`https` scheme syntax and does not appear in their ABNF. Evidence: https://www.rfc-editor.org/rfc/rfc9110#section-4.2.5 (fetched). Consequence: a code carried after `#` never reaches the host; a code after `?` is in the request line of `GET /`.
- The default `Referrer-Policy` is `strict-origin-when-cross-origin`, which sends the path and query string in `Referer` on same-origin requests; `no-referrer` sends no `Referer`. Evidence: https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Referrer-Policy (fetched). Consequence: the page's script and stylesheet requests, made while the HTML is parsed (before any `replaceState`), carry `?code=` in `Referer` unless the page sends `Referrer-Policy: no-referrer`.
- `history.replaceState` changes the URL shown and replaces the current history entry; it does not add an entry. Evidence: https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState (fetched). It does not remove the request that already carried the code (the `GET /?code=` and the subresource requests made before the script ran).
- The site used for SameSite cookies is the scheme plus the registrable domain; the port is ignored; `http` and `https` are different sites. Evidence: https://developer.mozilla.org/en-US/docs/Glossary/site (search snippet, not fetched in full; treat as settled for host names, see Unresolved for IP addresses).
- `maxTouchPoints` is 0 on Mac and typically 5 on phones. Evidence: https://developer.mozilla.org/en-US/docs/Web/API/Navigator/maxTouchPoints (fetched). The same page does not cover iPad.
- `RemoteRequest` is constructed in one place: `src/adapters/remote.rs:506` (`Ok(Some(RemoteRequest {`), defined at `:360`. A grep of `src/` and `tests/` for `RemoteRequest {` finds no other literal. Adding fields is therefore not a breaking change for code in the tree.
- `PAIRING_WINDOW` is five minutes and `PAIRING_ATTEMPTS` is 3. Evidence: `src/core/action.rs:972-973`.
- `SessionView.card` is a label word, not an excerpt. Evidence: `control/src/lib.rs:645-646` ("The card's word: `CARD_WORKING`, `CARD_IDLE`, 'waiting on you', ..."). The issue's "one-line excerpt the card shows" has no field behind it in the wire view. `control/src/` contains no `last_message`.
- `last_message` exists only on the hook event (`src/ports/events.rs:24`, `src/adapters/hooks.rs:71`), not on `SessionView`. Evidence: the grep above.
- The schema-version rule in `src/core/model.rs:1-3` is stated for "workspace records" serialized through the model. `devices.json` (`Vec<PairedDevice>`, `src/adapters/remote.rs:80-85`) is not in `model.rs`, so the text does not reach it. Whether to bump anyway is a plan call.
- `ServerInfo.capabilities` is `[String]`. Evidence: `client/Sources/SwitchboardProtocol/Info.swift:8`. A new capability string does not change the decoded type.
- The `/info` answer is not an authentication of the server. `/info` is answered before authentication (`src/app.rs:3028`), and its `spki_sha256` comes from whichever process holds the socket. A page that compares the URL's `key` with `/info` therefore detects a mismatch of address, not an impostor who answers both. The only binding of the key to the server is TLS, which a browser does not pin to the SPKI. Settled from the tree; the issue's §1 claim should say so.
- The QR is built with `qrcode::QrCode::new` (`src/ui/remote.rs:281`), which picks the version and uses error-correction level M by default (`qrcode-0.14.1/src/types.rs:102`). Its doc says it fails only when the data is too long (`qrcode-0.14.1/src/lib.rs:71-74`). A URL of about 150 to 200 bytes is far below the limit; the size was not measured.
- The pool of unauthenticated connections is 4, and a fifth is dropped at accept. Spike 22 measured this against its own pinned client: "the pool of 4 was full" and "connection was refused in 0.6 ms" (`spikes/22-remote-port/README.md:79-83`). The spike did not use a browser.

## Unresolved

- Safari and a self-signed certificate with no SAN and a 4096 `notAfter`: whether Safari offers a click-through at all, and whether an exception persists. Tried: Apple's requirements page (above). It states the rules but not their scope for user-accepted exceptions. A search turned up a Syncthing report and a forum post, both anecdotal. Needs a device.
- Whether the 825-day and DNS-SAN rules bind the user's exception, and whether they apply to an IP-address host (Apple says "DNS name"). Same tried; no primary source settles it.
- Chrome and the 398-day rule: whether `ERR_CERT_VALIDITY_TOO_LONG` is bypassable for a self-signed private certificate. Tried: a search. The Chromium commit title is the only primary lead; a squid-users thread says private roots are exempt, unresolved in that thread. A Chrome test is not possible here (no Chrome installed).
- Chrome and missing SAN: whether a CN-only certificate for an IP is bypassable. Tried: a search. Only TrueNAS and vendor forum posts say it is refused, and they are not evidence. Chrome 58 claim not fetched from a primary source.
- Protocol negotiation when the client requested a subprotocol and the server returns none: WHATWG (as quoted in WebKit bug 271122, `https://bugs.webkit.org/show_bug.cgi?id=271122`) says fail; RFC 6455 does not. Not needed if the subprotocol option is dropped; the lead is recorded.
- Whether a browser sends its cookies on the WebSocket handshake. Tried: a search. Only 2011 WHATWG commit logs (`https://lists.whatwg.org/pipermail/commit-watchers-whatwg.org/2011/013056.html`) and a security write-up. Lead only. The current Fetch and WebSockets text was not fetched.
- `SameSite=Strict` with an IP-address host: whether two pages on different host names on the same network are "same-site" for the cookie. The MDN site glossary says nothing about IP addresses. Open. Consequence if different host names are cross-site: a page on another name cannot send the cookie under `Strict`. Still needs the WHATWG URL/site definition for IP hosts.
- Whether `Secure; HttpOnly; SameSite=Strict` cookies set after a click-through are stored and sent in Safari and Chrome. Not found in any source read. Needs a device or a fetched browser source.
- Whether iOS Safari keeps a `Max-Age` server-set cookie across relaunches and for how long. WebKit ITP 2.1 (`https://webkit.org/blog/8613/intelligent-tracking-prevention-2-1/`, search snippet only) caps persistent `document.cookie` cookies at seven days; a later blog says the JS cap was removed in 2022. The two conflict and neither was verified. Needs WebKit release notes or a device.
- Whether Safari's `'self'` in `connect-src` allows `wss:` to the same host and port. MDN says `'self'` does not cover WebSocket schemes in every browser. WebKit bug 201591 (`https://bugs.webkit.org/show_bug.cgi?id=201591`) reports Safari still blocking same-host `wss` as of a February 2021 comment. Current status not checked. A plan that lists `wss://<host>:<port>` explicitly in `connect-src` does not depend on the answer; that recommendation is the plan's to make.
- Whether browsers request `/favicon.ico` by themselves and what they do with a 404. Tried: a search. Mozilla bug 1745680 (search snippet) says Firefox, Chrome and Safari request the root path. Current Safari behaviour not checked. A `<link rel="icon">` with a data URI would avoid the request but needs `img-src data:` in the CSP; not tested.
- The iPad's user agent in desktop-site mode, and whether `maxTouchPoints > 1` tells an iPad from a Mac. The MDN value is documented for Mac (0) and phones (typically 5); iPad not stated. Needs a device.
- Browser limit on concurrent connections to one host. Tried: a search. Secondary sources say 6 for Chrome on HTTP/1.1; RFC 9112 §9.4 (not fetched) says a client SHOULD NOT keep more than 2. The number that matters is how many unauthenticated connections Safari opens for `/`, a script, a stylesheet, a favicon, and the WebSocket on a cold load. Needs a device or a network trace.
- Whether a browser allows the host's certificate exception to cover `wss://` on the same host and port in Safari and Chrome for Android. Not found. Needs a device.
- Whether `Host`-header rebinding from another origin reaches the host under a certificate exception. Not searched; the cookie argument above depends on the SameSite answer.
- Whether the Keychain-stored key and the certificate in `identity.json` can be re-issued with a SAN and a 825-day validity without changing `spki_sha256` (see Settled). The arithmetic holds; no code in the tree does it.
- No spike was run. The only browser-behaviour questions are the ones above, and none can be answered on this machine without a browser window driven by hand. A non-browser spike (for example an `openssl` check of the certificate's extensions) would repeat what `src/adapters/remote.rs:97` and `rcgen` already show, so it was not run.

## For the owner

1. Certificate trust step (issue §1). If Safari and Chrome show a click-through for the current certificate, the plan can keep the click-through as the trust step and say so in the paired-devices dialog. If either browser refuses with no exception (no SAN, 4096-year validity), the plan must re-issue the certificate with an IP SAN and a validity within 825 days (the key and `spki_sha256` stay the same, see Settled), or the browser path does not work at all. Both answers need one phone test with the current build.
2. Token transport (issue §2). If cookies are stored and sent on `fetch` and the WebSocket handshake after a click-through (Unresolved), use an `HttpOnly; Secure; SameSite=Strict` cookie and a `/pair` reply with no token in the body for browsers, and add `Origin` checking, since a cookie makes `control` POSTs ambient. If cookies are not sent on the WebSocket, the plan must pick another carrier; the subprotocol option is out because script sees it (Settled).
3. Code in the URL. The issue puts the code in `?code=`. If the owner accepts that the code reaches the host in the request line, keep it; the plan then needs `Referrer-Policy: no-referrer` on the page (Settled). If not, the code can go after `#`, which never reaches the host or any `Referer` (Settled), and the page reads `location.hash` before `replaceState`.
4. One QR or two (issue §3). The URL replaces the JSON for the headset's paste and `PairingInvite.parse`, which need a Swift URL parser and tests (notes F14). The CLI's three-argument form already needs no JSON. If the owner wants the JSON kept, it stays for the headset and CLI only.
5. Identity-change detection (issue §1, notes F19). The page's stored key is readable by any script on the origin if it sits in `localStorage`; a cookie is not. The `/info` key check is an address check, not a server check (Settled), so the owner should decide whether it is worth storing at all.
6. Revoked versus never paired (notes F8, acceptance criterion). Today the host cannot tell them apart. A tombstone for revoked token hashes is new state in `devices.json`; the alternative is a page that says "not paired or revoked" for any 401, which does not meet the acceptance wording.
7. Caller's scope (notes F9). No endpoint returns it. Owner: a new read endpoint amends §4.3's "nothing more" rule, or the page learns scope by attempting a send.
8. Frame or connection thread for the page (notes F7). The page's bytes are constant; serving them on the connection thread avoids a frame pass but is unlimited by rate window, and the pool is the only bound (notes F7). Owner's choice.
9. Connections for a cold page load (Unresolved). If a phone's Safari opens more than four unauthenticated connections, the fifth is dropped at accept (spike 22). Needs one device run with the pool counted; the plan may need a larger unauthenticated pool for static paths.
10. Acceptance run. Needs a phone on the same network, a real Safari, and a bundle signed with the stable identity (CLAUDE.md, "Platform-specific code"). This is the owner's, not runnable here.
11. Shipping items (CLAUDE.md "Adding a feature" steps 4–5): a CHANGELOG line under Unreleased, a README Layout row for `web/`, the design.md remote status section, and the amendment to `docs/remote-client.md` §4.1, §4.3 and §5.
