# Feedback 1 on plan.md (issue #230): premises

Checked against the worktree at `7fe8949` (`git status` clean). "facts.md:NN" is a line of the facts file. Browser behaviour was not run; the two web-platform questions I could settle by fetch are noted where they bear.

1. **The re-issue fallback rotates the key, so it breaks the pins it claims to keep (Decision 1, "For the owner"; facts.md:48, facts.md:10).** The plan says the fallback is "a re-issue over the same key (`make_identity` plus the identity write, `src/adapters/remote.rs:95-118`)" and that `spki_sha256` stays the same. The tree says otherwise: `make_identity` calls `rcgen::KeyPair::generate()` at `src/adapters/remote.rs:101` and never takes an existing key, so `spki_sha256` (`:112`) changes. facts.md:48 is right that no code in the tree re-issues over the same key. The fallback needs new code: load the PEM from the Keychain item `remote-key:<server id>`, build params with a DNS SAN and an 825-day `not_after`, and sign with `KeyPair::from_pem`. The range is `95-127`, not `95-118`. The fallback also has three gaps the plan does not write down: (a) the URL carries a host name, but `pairing_link(addr: SocketAddr, …)` takes an address, so its signature must change; (b) an 825-day certificate expires about two years out, and the plan says nothing renews it; (c) the `.local` name changes when the Mac is renamed, and the certificate then no longer matches the URL.

2. **Decision 2 rests on an unresolved line, and its only fallback covers the wrong case (facts.md:40, facts.md:38).** The cookie carrier needs Safari to store and send a `Secure; HttpOnly; SameSite=Lax` cookie set after a click-through. facts.md:40 says that was not found in any source. The fallback written (Owner call 2, "poll") covers only whether the WebSocket carries the cookie. If the cookie is not stored at all, the page has no carrier: the plan rules out the subprotocol (facts.md:15) and `localStorage` (Decision 2). Name a second carrier, or make the device run a gate before the cookie code merges, and say which. Fetched evidence on the WebSocket question: the WHATWG WebSockets spec sets the handshake's credentials mode to `"include"` (https://websockets.spec.whatwg.org/, §2.2 step 2), so cookies are eligible on the handshake, subject to SameSite. That makes the poll a fallback, not the likely path, and the plan should say so.

3. **Browser pairing gives up the pinned-key guarantee the spec and design state, and the plan does not amend that guarantee (Decision 1, pairing sequence, Docs).** `docs/remote-client.md:309` says pairing verifies the key "before the code is sent. The code alone would let an intermediary terminate the first connection, forward the code to the real host, and take the token." `docs/design.md:3111-3112` says the client does "pairing with a pinned host key". Under the plan, a browser pairs after a click-through and checks only the address, which facts.md:27 settles: an intermediary that copies the key passes. The plan records this in "Where this departs" item 11 and in the dialog text, but the docs list (plan lines 128-133) amends §4.1, §4.3, §5 (QR, carrier, tombstone, `/info` and `/pair`) and §11. It does not amend `remote-client.md:309` or `design.md:3111-3112`, and it adds no owner call for the trade. Add an owner call that names the weaker browser threat model, and amend both lines.

4. **No spike for the new browser mechanisms, which CLAUDE.md requires first (plan "Order inside the commit"; CLAUDE.md "Architecture": "add a new spike directory for any new risky mechanism before building on it").** The plan builds on the cookie carrier with `HttpOnly; Secure; SameSite=Lax` across a click-through, the Origin rule, the CSP and `no-referrer` on a static page, the certificate exception on a SAN-less certificate, and the four-slot pool for a cold load. facts.md:49 says no spike was run and none can be run here. Add `spikes/23-…` (a page and cookie on the real TLS listener, a phone run recorded in its README) before the commit steps that build on it: the Origin rule and `authenticate`, the UI, and the page.

5. **Tests the plan says keep passing, or omits, will fail (plan lines 108–121).**
   - `tests/remote.rs:674` asserts `devices.is_empty()` after `RevokeDevice`. The plan keeps the tombstone in `devices()` (plan line 108), so this fails.
   - `tests/remote.rs:676` asserts `(401, "unauthorized")` for a revoked token. The plan answers `401 revoked` (plan line 52). Plan line 115 says `revoke_and_a_scope_change_take_effect_on_the_next_request` (`:657`) "keep[s] passing"; it does not.
   - `tests/ui.rs:7487–7492` parses the copied invite as JSON and checks `code`, `spki_sha256` and `addresses`. "Copy invite" becomes a URL (plan line 93), so this fails. It is not in the UI test list (plan line 119).
   - `tests/ui.rs:7500` asserts `devices().is_empty()` after Revoke. Same cause as `:674`.
   Name each in the test section and say what it asserts after the change.

6. **The poll fallback does not leave "nothing else" unchanged (plan line 60).** The session view "watches the open session's key (the `watch` frame of §4.4) and refetches on `changed`" (plan line 100). Both ride the events WebSocket. A poll that drops the WebSocket removes `watch` and `changed` from the page. Write the fallback as a change to the page's session view.

7. **`pairing_link(SocketAddr, …)` cannot express a missing LAN address (plan lines 41, 93).** `remote::local_address()` returns `Option<IpAddr>` (`src/adapters/remote.rs:962`). The UI maps `None` to an empty string (`src/ui/remote.rs:157–159`). The new builder takes a `SocketAddr`, so the plan does not say what the QR shows when there is no LAN route. Write the case: no QR and a message, or a loopback address with the warning from plan line 94.

8. **Rebinding is waved off, but the Origin rule does not stop it (plan line 63, facts.md:47).** A rebound name sends `Origin: https://<name>:<port>` and `Host: <name>:<port>`, so "`Origin` equals `https://` plus `Host`" passes. What stops the attack is that the cookie is scoped to the IP address, so a request to another name does not carry `switchboard_token`. That argument does not depend on the SameSite answer facts.md:47 says it does. Write the argument, or compare `Host` with the address the URL carried.

9. **The Lax argument omits what cross-site GETs can do (plan line 62).** The plan is right that Lax withholds the cookie from cross-site POST and subresource requests. Fetched RFC 6265bis §5.6.7.1 (https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis) says Lax still sends it with cross-site top-level navigations that use a safe method. So a link on another site can make a GET carrying the cookie. The GETs with a side effect are: `authenticate` dispatches `DeviceSeen` (`src/app.rs:3150`), and `GET sessions/{id}/draft` calls `ensure_editor` (`src/app.rs:3361`, `:3381–3382`), which changes UI state only. Both are harmless, but the CSRF argument covers only POST, so say so.

10. **The commit message does not name the contract additions (plan line 151; CLAUDE.md "Extending the contract").** The rule is to say what was added in the commit message. `PairedDevice.revoked` (`src/ports/remote.rs:96–107`) is an addition to a port type, and `RevokeDevice`'s effect changing from removal to tombstone is a behaviour change to an existing variant. The message needs a body that names both.

11. **No schema bump, and a downgrade re-admits revoked tokens, with no owner call on it (plan lines 21–23).** The no-bump decision rests on facts.md:25 and `src/core/model.rs:1–3`, so it is allowed. The consequence is not. `devices.json` is a bare array with no version (`src/adapters/remote.rs:80–85`), and `PairedDevice` does not deny unknown fields (`src/ports/remote.rs:95`). So an older build reads a revoked row as live, and revocation can be undone by downgrading. The plan records this only as a hazard in spec §11. Add an owner call, with the fallback as a versioned wrapper `{schema_version, devices}` that refuses to write a newer version, which is the store rule in `docs/design.md:125–128`.

12. **The pairing sequence overstates the key check (plan line 87).** "A mismatch stops with 'This is not the Mac the code came from.'" facts.md:27 says the `/info` comparison detects an address mismatch, not an impostor. The message claims more than the check does. Reword it to say that the address answers with a different key.

13. **The CSP text contradicts the header (plan lines 73–74).** The text says "`connect-src` names `wss:` rather than `'self'`". The header is `connect-src 'self' wss:`. Pick one, and say why. facts.md:42 is the reason `wss:` is needed, and `'self'` is needed for `fetch`.

14. **Decisions 2 and 4 contradict settled lines, and the plan cites the tree only for the one it defends (facts.md:7; `docs/remote-client.md:312`).** facts.md:7 says the port answers only `/info` and `/pair` before authentication (tree: `src/app.rs:3028–3029`). Decision 4 changes that. Decision 2 puts the token in a cookie, where spec §5 (`docs/remote-client.md:312`) says "sent only as a bearer header". The plan amends the spec for both (plan lines 128–131), which is allowed, but it should cite the tree line against facts.md:7 and list both as owner calls.

15. **Stale line citations in the facts the plan carries (facts.md:8, facts.md:10).** facts.md:8 cites `src/adapters/remote.rs:97` for the SAN-less certificate; it is `:102`. facts.md:10 cites `:107–108` for the SPKI hash; it is `:112`. The plan's own `make_identity` range is wrong (objection 1). Correct these before the plan's line references are reused.

16. **The iPad mislabel is left with no written fallback (Decision 6; facts.md:44).** The plan says the mislabel is "cosmetic, so no fallback is built." Write the consequence as the fallback: an iPad in desktop-site mode is labelled Mac, and nothing else depends on the name.
