# SB-187 facts

The issue makes no claim about a browser, platform, crate, protocol or tool outside this tree. Every investigation open question tagged `[tree]` or `[source]` is answered from this worktree, and Switchboard's own `workflow.start` is in-tree. So no web search was run and there is nothing to cite from a vendor. No spike was written. The `[run]` questions are repeatable with the fake-based `Env` in `dispatch/tests/first_slice.rs` and are plan work, not facts. Paths below are relative to the worktree.

## Settled

- The cause is `review_subject`, `dispatch/src/scheduler.rs:10534-10548`: it keeps only `AttemptState::Complete` attempts, so a `Failed` `review/1` is skipped and the walk reaches `plan/1`. It also returns that attempt's `session`.
- `start_workflow` calls it at `dispatch/src/scheduler.rs:7465`. The rerun arm is `dispatch/src/scheduler.rs:7401-7418`: `may_rerun` then `start_workflow(.., next_n(..))`, else `asks_again` then `ask_rerun`.
- `review_subject` takes no context or lane argument (`dispatch/src/scheduler.rs:10534`), while `lane_files_by` does (`dispatch/src/scheduler.rs:10908-10950`). They disagree for a stage with `runs_per_lane` (`dispatch/src/pipeline.rs:730`). The plan must say whether per-lane plan review is in scope. `lane_files_by`'s non-lane path is the only one the issue exercises (context `joined`).
- The failed attempt's copy is not removed by anything on the failure path. Removals in `dispatch/src/scheduler.rs` are `remove_dir_all` of evidence directories (10081, code-review evidence), `remove_file` of secret artifacts (10154, the `forgotten` map, see `dispatch/src/events.rs:916-925`) and the round-file remove at 7642. None targets a workflow attempt's `plan.md`. So the copy exists when the rerun starts, unless the owner deleted it by hand. Plan: check the file exists before using it and fall back to today's behaviour if not.
- Switchboard's `workflow.start` requires `source` to be a Claude Code session with a resume handle (transcript), and `plan` to be an absolute path (`src/core/workflow.rs:303-321`). It clones the source's transcript for the planner. `source` and `plan` are independent arguments, so a revised file can be passed with the original session (`src/core/control.rs:1384-1394`).
- The `revise` answer reaches the planner only as a prompt: `object_workflow` pushes an objection round with the owner's text and calls `prompt_planner` (`src/core/workflow.rs:969-1006`). The owner's note therefore lives in attempt 1's planner clone conversation and in `plan.feedback-N.md` on disk. The original plan session (what attempt 2 clones today) has never seen the note. Cloning it with the revised file gives a planner that does not know the note, though the file already reflects it.
- `rerun_note` returns `None` for any stage kind other than `Agent | Review` (`dispatch/src/scheduler.rs:8988-8996`), so a plan review (workflow) stage carries no note across a rerun. The code review path does (`carry_source`, `unspent_note`: `dispatch/src/review.rs:3608-3636`), but both are keyed on `AttemptKind::Review` attempts and `rounds` fields, so neither applies to a `Workflow` attempt without new code.
- `shown_where` accepts `Complete` or an open workflow attempt only (`dispatch/src/ticket.rs:1476-1491`). The test at `dispatch/src/ticket.rs:~1862-1869` pins "a parked review's copy is not the plan going forward" for `Cancelled` and `Failed`. A fix that makes a failed copy count for `show` has to narrow that test. A fix scoped to `review_subject` alone does not touch it.
- `input_where` is `Complete` only and is what agents are handed (`dispatch/src/ticket.rs:1452-1463`). The plan stage's downstream agents must keep ignoring a failed review's copy, so change `review_subject` rather than `input_where`.
- `show`'s `files:` block comes from `ticket_paths` (`dispatch/src/serve.rs:536-593`) via `shown_lane_files`, so once attempt 2 runs it names only attempt 2's copy. `plan_rounds` and `review` pick the latest workflow attempt with artifacts (`dispatch/src/serve.rs:513-530`, `561-565`), so attempt 1's `plan round N (owner)` line is dropped after the rerun. `PathsView` is in the control crate (`dispatch-control`, `lib.rs:548-578`) and is shared with the app's ticket page, so an additive field there reaches both.
- `Attempt` has no field naming the copy an attempt reviewed. Adding one is a serialized-record change: `RECORD_VERSION` is 28 (`dispatch/src/store.rs:26`) with migrations at `store.rs:450-460`. `#[serde(default)]` fields exist (`dispatch/src/ticket.rs:31-76`) but the project rule (CLAUDE.md "Extending the contract") is a version bump plus a migrate step. Alternative with no schema change: derive the source from the previous attempt of the same stage and context whose `plan` file exists, and show that derived fact in `show`.
- Existing test `a_failed_review_run_fails_the_attempt_and_a_rerun_starts_a_new_run` (`dispatch/tests/first_slice.rs:3257`) asserts only `runs.len() == 2`, so it passes before and after a fix. A new test must assert on the `WorkflowStart` `plan` copy's contents and `source`. A note surviving a failure is modelled by `a_note_survives_a_review_that_fails_before_its_fix_pass` (`dispatch/tests/first_slice.rs:8386`).

## Unresolved

Not settled: whether the planner clone is still a valid, cloneable record after the run vanished (`no such run` implies Switchboard lost the run), which needs a live app or the fakes. If not, the plan must use the original plan session with the revised file, and must put the owner's note text (from `plan.feedback-N.md`) in front of the attempt 2 reviewer, so the plan never waits on this line.
- Whether a `Cancelled` review (parked, restarted) should count like a `Failed` one. Not a fact the tree can answer, see For the owner. Build to: handle `Failed` only, which is the issue's case, and leave `Cancelled` as today.
- Whether `restart` (`dispatch/src/restart.rs:802-835`) clears attempts in a way that leaves `review_subject` with a stale failed copy. Tried: headers only. Build to: filter candidate attempts by the same "not forgotten, not cleared by restart" checks that `input_where` uses, and add a test with a plan restart after a failed review (so a rerun of the plan after a finished or failed review never uses an older review's copy; rule: the failed review's copy counts only if its attempt is newer than the latest Complete plan attempt).
- Whether `show --json` still lists attempt 1's owner note after attempt 2 starts. Reading says no (`dispatch/src/serve.rs:513-530`). Build to: the plan adds the line regardless and asserts it in a test.

## For the owner

- Should the rerun silently use the failed attempt's revised copy, or also say in the rerun question which copy it will review? Favourable (silent plus say): the plan adds a `(reviewing review/1's revised copy)` clause to `rerun_ask` (`dispatch/src/scheduler.rs:9335-9377`) and a `show` line. Unfavourable (silent only): the plan still fixes `review_subject` and adds the `show` line, because the issue's minimum is a correct source. Both cases work with the fix in `review_subject` plus the `show` annotation.
- Should the `revise` note be shown to attempt 2's reviewer as well as the revised plan? Favourable: carry the note text via the round file into attempt 2. Unfavourable: send only the revised plan. In both cases the plan starts attempt 2 from the revised file.
- Is a revised copy in a `Cancelled` review meant to count like a `Failed` one? Favourable: also accept `Cancelled`, narrowing the test at `dispatch/src/ticket.rs:~1862`. Unfavourable: `Failed` only. Build `Failed` only first; it works in both cases.
- Is the issue's symptom (two of three round-1 points already fixed, a contradicted owner answer) accepted without the owner's ticket? Both cases: the plan reproduces with a fake run (`revise`, then fail, then `rerun`) and asserts the `plan` copy differs from `plan/1`'s.
- What wording and where in `show`? Plan default: one line `plan (reviewed copy of review/1, revised)` in the `files:` block and the same in the app's ticket page via the shared `PathsView`. If the owner wants other wording, only the string changes.
