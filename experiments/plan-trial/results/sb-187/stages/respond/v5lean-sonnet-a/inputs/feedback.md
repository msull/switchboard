1. **`rerun_copy` assumes the newest failed review attempt holds the newest plan, and nothing supports that.** The helper (plan, "The actions and effects" item 1) takes `latest_attempt(t, "review", ctx)` (`dispatch/src/scheduler.rs:9444`), which looks only at the review stage. It never compares that attempt with the plan stage. `review_subject` (`scheduler.rs:10534-10548`) takes the latest `Complete` attempt that has the subject artifact, across all stages. A `Failed` `review/1` that is older than a `Complete` `plan/2` (the plan was re-run, or restarted over a range per `docs/design.md:1972`, after the failure) would win over `plan/2`. The rerun would then review a stale copy and discard the newer plan. Facts cites no line on attempt ordering across stages. The plan's own wording, "newest attempt of the same stage and context", is the premise, and it is unsupported.
   Fix: have `rerun_copy` return the failed copy only if no `Complete` attempt that has the subject artifact is newer than that failed attempt. Compare their position in `t.attempts`, since `n` is per stage. Add a test: failed `review/1`, then `plan/2` complete, then a review rerun copies from `plan/2`. I did not run a restart to see whether `plan/2` can follow a failed review in a real ticket. I read the code only.

2. **The `serve.rs` rule for `revised_from` and `rerun_copy` are not the same rule as the plan says.** "Contract additions" says `rerun_copy(t, stage, ctx, subject)` is "used by `start_workflow`, `rerun_carries` and `ticket_paths`". The UI section says `ticket_paths` uses "one `pub(crate)` function taking the attempt", with a rule of "newest earlier attempt … Failed". The two signatures differ. `ticket_paths` runs after the new attempt exists, so `latest_attempt` would return the new attempt itself and give `None`. State one function and one signature (the earlier-attempt lookup, `n` below the open one), and say which `rerun_copy` is. The "cannot drift" claim in "The record" rests on this being one function.
