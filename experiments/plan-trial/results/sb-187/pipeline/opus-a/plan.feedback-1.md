1. The carry rule ignores restarts. `restart::discard` (`dispatch/src/restart.rs:839-857`) turns a completed review attempt in the range into `Cancelled { reason: "discarded by restart at …" }`. A Failed one stays Failed. Under the plan's rule, after `restart` at the review stage the next review attempt finds that discarded or failed attempt before `plan/N`, sees non-empty `revisions`, and reviews the discarded revised copy. A restart promises the opposite: "the later work is discarded" (`restart.rs:1-9`). The rule needs the same cutoff `ask_rerun` already uses: skip attempts that ended before `t.restarts.last().at_ms` (`scheduler.rs:7230-7241`), or skip any whose reason starts with `DISCARDED_BY`. It also needs a test: a restart at the review stage after a revised attempt starts from the plan stage's copy.

2. The plan says nothing about a send-back to the review stage. `send_back` (`scheduler.rs:4962` and `4995`) cancels the target stage's completed attempt with `SENT_BACK_FROM…`. When that target is the review stage, the finalized and revised `review/k` becomes a Cancelled Workflow attempt with `revisions`, so the new rule silently changes which copy the sent-back review starts from: today it is `plan/N`, after the change it is the revised copy. That may be the right call, but the plan has to choose it, state it in design.md, and pin it with a test. It should not arrive as a side effect.

3. The rule can stop at another lane's attempt. "Stopping at the newest Complete attempt that wrote `subject`" is today's `review_subject` walk, and that walk does not filter by context (`scheduler.rs:10534-10547`). Per-lane plan reviews exist (`serve.rs:1521-1568` tests `review-plan` in lanes `repo` and `docs`). In that case another lane's Complete review that started after this lane's failed one ends the walk before the failed attempt is reached, and the revision is dropped again. `review_source` takes `ctx`, so it should apply `ctx` to the stopping attempt too, or the plan should say why per-lane reviews are out of scope.

4. The `revise` note can still be lost. The plan says the note "was never lost" and relies on the revised file alone. But `revisions` is pushed when `workflow.object` is sent (`ticket.rs:346-350`), before the planner has written anything. When the run dies between the send and the planner's write, which is exactly the "runner restart mid-run" in the issue's repro, the copy that carries is unrevised or half-written. `review/2` is then cloned from the plan stage's session and never sees the note, so the owner's objection disappears without a word, and the issue asks for the opposite. Either hand the carried attempt's owner rounds to the rerun (as `rework` or as the planner's opening objection), or at minimum put the note's file in the log line and in the rerun question, so the owner can tell whether it was applied. Add a test where the run fails before the copy changes.

5. The plan has no tests for `Cancelled`. Its rule covers `Cancelled` as well as `Failed`, and its Docs bullet says "failed or cancelled". All five tests fail the attempt through `runs.clear()`. Add one where the review attempt is cancelled by a park (`scheduler.rs:2872`) with a revision and then resumed. `rerun_ask`'s `Cancelled` arm (`scheduler.rs:9363`) is a different question path from `ask_rerun`, and it needs the new `rerun_carries` text checked too.
