# Feedback on plan.md (issue #187)

Checked against the worktree at `/Users/sbgragent/.dispatch/worktrees/b0b9af6f` (branch `dispatch/187-...`, `Cargo.toml` 0.4.1), CLAUDE.md and docs/design.md. Version constant, `RECORD_VERSION` = 28 at `dispatch/src/store.rs:26`, and the no-schema-bump reasoning check out. Most line references check out too. The objections are below.

1. **Copying `revisions` onto the rerun attempt makes the new run's own reviewer rounds read as the owner's objection.** Round files are named by round number alone (`dispatch/src/report.rs:156`, `round_file`), and a fresh run's rounds start at 1 (`revise` computes `view.round + 1`, `scheduler.rs:7614`). After the rerun, `review/2/plan.feedback-1.md` is the reviewer's own round 1, but `review/2` carries a copied `Revision { round: 1 }`. Consumers that match round number against `revisions` then go wrong:
   - `report.rs:361` (`plan_review`) skips any round whose number is in `a.revisions` and records it as the owner's objection with `new: None, open: 0`. The reviewer's round-1 points are dropped from `plan_points` and the open count.
   - `serve.rs:515` (`plan_rounds`) sets `by` from the same match, so the Plan tab labels the reviewer's round as "owner".
   - `serve.rs:531` (`review_round`) returns at least 1 for the new attempt before any round exists, so the shown copy is labelled "round 1" in `show` and the Plan tab.
   - Round-level `Revised` events (`events.rs:878`) would also match by round.

   The plan says "the copied entries are the copy's history, not the new run's rounds", but it does not change any of these consumers, and its test list does not cover them. Either the copied history needs its own marker that these readers ignore (which needs a serialized field and so a `RECORD_VERSION` bump plus a `store::migrate` step, and the plan says there is none), or the gate has to be expressed without reusing round numbers. The plan has to pick one and add tests for `plan_review`, `plan_rounds` and `review_round` on a rerun attempt with a reviewer round 1.

2. **The design text the plan says to match is not in its Docs list, so it would stay wrong.** The "Spec text to match" paragraph names `docs/design.md:1785-1787`, `docs/design.md:2160-2163` and `docs/dispatch.md:1046`. The Docs paragraph only adds a new dated section. Left alone, `design.md:2160-2163` still says the Plan tab shows "the newest complete plan" when a failed revised copy will now be shown. The plan should list the exact sentence edits to each of the three passages, or say that `dispatch.md:1046` needs no edit because `input_where` is unchanged.

3. **A citation does not support its claim.** The plan says the owner's revision is "removed on a refusal (`docs/design.md:2975`)". Line 2975 is in "Held stops (2026-10-08)", and nothing in `design.md` describes a refused objection's revision being removed. The behaviour lives in code: `dispatch/src/scheduler.rs:11313` (`attempt.revisions.pop()` in the refused-`REVISE` arm). Cite that, or add the design text the plan relies on.

4. **The rerun label asserts a future the owner may not choose.** The label `(revised copy, round N, review failed: the rerun reviews it)` and the Plan tab text "review failed; the rerun reviews it" are wrong when the owner answers `park` to the rerun question. The rerun question is only asked, not guaranteed. `asks_again` and `may_rerun` (`scheduler.rs:10608`, `:10665`) show that the rerun may never happen. Use the state the code actually has (for example, whether a `rerun` decision is pending or acted, via `rerun_in_flight` / `may_rerun`), or word the label as a fact about the copy, such as "review failed; not reviewed again yet".

5. **`plan_files` gets prior copies, but the plan does not say which lane each one belongs to, or whether `plan_files` may change meaning.** For a plan stage that runs per lane, `lane_files_by` (`scheduler.rs:10900`) picks one copy per lane through `shown_where`. The plan says `ticket_paths` lists "each other failed or cancelled plan review that has a revisions entry, marked `prior`", with no lane filter. That gives `LaneFile.lane` the wrong value for a per-lane run, and `print_lane_files` (`main.rs:896`) would print another lane's copy under this lane. The doc comment on `PathsView.plan_files` (`dispatch-control/src/lib.rs:574-577`) says "the plan as it stands", and prior copies are not that. Say whether `prior` entries go in `plan_files` or a new field, and how their lane is taken from `Attempt.context`.

6. **`review_source` ignores `forgotten`.** `input_where` and `shown_where` both skip an attempt whose `forgotten` map holds the artifact name (`ticket.rs:1452`, `:1476`). The plan's `review_source` does not, and it is the first path to copy from a failed attempt. If the owner has forgotten that copy's file, `start_workflow` (`scheduler.rs:7469`, the `std::fs::copy`) fails and the ticket parks with an I/O error. Add the same `forgotten` filter to `review_source`, and add a test that a forgotten failed copy is not chosen.

Nothing else in the plan needs an objection. The no-keystroke, no-project-dot-directory and no-new-action constraints hold, and the serde-default additions to `PathsView` and `LaneFile` are additive. The `CHANGELOG.md` `## [Unreleased]` heading exists.
