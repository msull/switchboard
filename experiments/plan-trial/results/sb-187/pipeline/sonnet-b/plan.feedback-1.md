1. `show` misses the window that matters. `prior_lane_files` attaches prior rows only "for each shown row whose attempt is a Workflow", and `shown_where` (ticket.rs:1476) skips Failed attempts. After `review/1` fails and while the `rerun` question is pending (or the answer is unacted), the shown row is `plan/1`, which is a Complete non-review attempt. No prior row appears, so the owner sees nothing about the revised copy at the moment they are asked "Run it again?". The prior rows only show up once `review/2` is open or complete. The plan has to anchor the rows on the pending `rerun` decision or the latest failed attempt, not only on a shown Workflow row. It also needs a test for this window.

2. The `show` rule disagrees with the scheduler's rule. The scheduler takes only failed or cancelled attempts that are newer than the chosen Complete attempt and whose file exists. `prior_lane_files` takes any earlier same-stage attempt with a revision and does no existence check. It can list a revised copy from before a later Complete attempt, or one whose file is gone, as "prior revision" even though no rerun would start from it. The plan says it is "the same rule" (the plan section on `print_lane_files`), but it is not. Share one helper, or pass `exists` and the same ordering condition.

3. `rerun_ask(t, a)` has no pipeline, so it cannot know the subject name. `workflow_source` needs `subject`. `rerun_ask` and `rerun_carries` receive only the ticket and the attempt, and the resume call at 8294 may not have a pipeline either. The plan adds `exists` to their signatures but never says where the subject name comes from. Deriving it from the single key of `a.artifacts` is possible, but the plan must say so. `review_subject` also errors on a missing session, while `rerun_carries` cannot return an error. The plan does not say what the sentence says in that case.

4. The question text can be wrong when it is read. It is fixed when asked (`ensure_decision` dedupes on stage, name and attempt, not on text). The source is chosen later, in `start_workflow`. If the revised file is deleted in between, the question says "revised copy" and the run uses the original. The plan should say the sentence states what the rerun will do if the file is still there, or have `start_workflow` log or event the fallback. Today the fallback is silent.

5. Starting from the failed copy leaves a known gap that the plan does not fix. The owner's note lives in `round_file`, and only the planner applies it to the copy. If the runner died first, the revised copy has no revision, the new attempt starts from a file that lacks the note, and the sentence still says "owner revised". The plan accepts this in one bullet. But then the "rerun carries the note" claim is only conditionally true, and the changelog line ("starts from the owner's revised plan") overstates it. Either name the gap in the changelog and docs, or have the new attempt pass the unapplied round file along.

6. The rule uses `!revisions.is_empty()` as the sign of owner input. A revision is pushed before `workflow.object` is sent and popped only if Switchboard refuses it. A lost send (the "lost-send" case in docs/dispatch.md:2975) keeps the revision while the planner never saw the round. That is the gap in item 5 again, and the plan should test it. The tests list has no case for a failed attempt whose revision was lost-send.

7. The plan adds `LaneFile.prior` to `dispatch-control` without checking the wire contract. It does not say whether `dispatch-control` has a protocol or version constant to bump for `show --json`. It also does not say that the struct-literal test constructors in serve.rs (about 1399-1570) need `..LaneFile::default()` or an explicit `prior`. Say which.
