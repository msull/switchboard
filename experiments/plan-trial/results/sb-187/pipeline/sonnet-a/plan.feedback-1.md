1. The plan's central claim is unverified and probably false in the failure it targets: "the revised copy already holds the revision." `revise` (`scheduler.rs:7565`) only writes the owner's note to the round file (`plan.feedback-<round>.md`), pushes a `Revision` onto `review.revisions`, and sends the note to the run (`Body::WorkflowObject`). The planner has to apply the note to `plan.md` inside a run. The `revisions` entry is pushed before the send, and a `Reply::Failed` from the send is only logged with a warning. In the motivating case the run is gone (`no such run`), so the planner may never have applied the note. Then `revisions` being non-empty does not show that the copy holds the revision, and the new question text "which holds your revise note's changes" can be false. The plan must say how it knows the round was applied (for example, the run reached a later round or the round completed). Otherwise it must carry the note forward, for example by seeding the new attempt with the round file or saying the note is unapplied. Plan item 8 names the half-written-copy problem for copies with no revise, but never applies it to this case.

2. `review_source` ignores `forgotten`. `Ticket::shown_where` (`ticket.rs:1460`, `:1484`) and the existing artifact logic honor `a.forgotten.contains_key(name)`. The selector as specified (Complete, or Failed/Cancelled with `revisions`, the subject artifact and `exists`) could pick a forgotten attempt's copy. It must skip attempts whose subject artifact is forgotten. The plan also lists no test for this.

3. The session rule changes behavior for the existing case. Today the session comes from the same Complete attempt that supplied the path, and `review_subject` errors "was not written by a session" when that attempt has none. The plan says the session comes from "the first Complete attempt with a session at or before that point in the walk". That would silently skip a session-less Complete plan attempt and clone an older author's conversation, which is a different author from the one who wrote the plan text. Say which attempt's session is used. Say what happens when the nearest Complete subject-writing attempt has no session. Add a test.

4. The plan never states what happens with a failed attempt whose revised copy is older than the owner's later edits or a newer failed review. In the newest-first walk, the first revised Failed/Cancelled attempt wins. A second failed review/2 that began from review/1's revised copy and then got its own revise would win next time, which is correct. A review/2 that failed without a revise would be skipped, and review/1's copy would still be used. Say this is intended, and test the two-failure chain. The listed unit tests cover only one failed attempt.

5. `LaneFile.others` and `OtherCopy` are a wire change on `dispatch-control`, which is shared by the CLI and the server. The plan calls the change additive but does not say how an older client or server treats the new field. `#[serde(default)]` covers reading an older reply. It does not cover an older reader that rejects unknown fields (`deny_unknown_fields`). Confirm the struct does not use it, and add a round-trip test in `dispatch-control` for old JSON without `others`. The listed tests only cover `serve.rs` and `main.rs`.

6. Several signatures change but the plan lists no check of all callers. `rerun_carries` goes from `&'static str` to `String` and the callers format it into `format!` at `:7266` and `:9373`. `review_subject` is replaced, and `start_workflow` is not the only place that may depend on it, so the plan should grep for all uses. It also drops the "park with 'nothing wrote {subject}'" path unless `review_source` keeps returning `Result`. The plan's return type for `ReviewSource` is not a `Result`, yet `start_workflow` must still park on a missing subject or session. Specify the error path.

7. `rerun_ask` and `ask_rerun` text is stored on the `Decision` question when it is created (`ensure_decision`). If the revised copy file disappears later, or a different attempt becomes the source, the stored question goes stale. The plan says the question and the start are "consistent" but they are computed at different times. Say whether the question is recomputed on read, or accept and document the gap.
