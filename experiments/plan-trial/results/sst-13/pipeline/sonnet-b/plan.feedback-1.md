1. Docs are not updated. `AGENT_KNOWLEDGE.md` section 6 (Singleton Pattern, ~l.926) documents `saved_updated_singleton` for `SingletonVersionedResource`. The plan only touches the docstring and CHANGELOG. Add a line there saying a stale save raises `VersionConflictError` (a `ConflictError` / `ValueError`), so the guide matches the new behaviour.

2. Test coverage is thinner than the stated rule for behaviour changes. `LocalStorageMemory` has its own `ensure_exists` and `update_existing`, but singletons are DynamoDB-only (`BaseSingleton.ensure_exists` is typed against `DynamoDbMemory`). The plan should say so explicitly, so nobody wonders about the missing local-storage case. Test 1 should also cover the stale-save-then-reread case with `consistent_read`, as `ensure_exists` defaults to it. Without that, the "stored value is still dark" assertion could read an eventually-consistent item.

3. Test 1 asserts `exc.resource_id == "VersionedSettings"` and the plan then adds a fallback ("if this fails, assert against `existing.resource_id`"). This is hedging in a plan. `ensure_exists` visibly uses `override_id=cls.__name__` (singleton.py:12), so state the literal and drop the fallback.

4. Table state between tests is not addressed. The singleton id is fixed (the class name), so the three tests share one item if the `dynamodb_memory` / `local_dynamodb_test_table` fixtures are not per-test. Confirm in `conftest.py` that the table is recreated per test, or have the tests tolerate pre-existing state (derive versions from `a.version`, which the plan mostly does). Note this in the plan.

5. Minor: `expected_version` and `actual_version` are the same values `update_existing` would raise with anyway (it re-reads the latest). The plan should note that the pre-check stays, because it fails before any write and gives the singleton-specific context, rather than being replaced by relying on `update_existing`. A reviewer may otherwise ask why there are two checks.
