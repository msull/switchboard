# Review of plan.md (issue #13 singleton gap)

1. **AGENT_KNOWLEDGE.md is not updated, and the plan does not mention it.** Section 6 ("Singleton Pattern", AGENT_KNOWLEDGE.md:966-967) says only "Versioned singletons check that you're updating from the latest version". After this change a stale `saved_updated_singleton` raises `VersionConflictError`, which callers need to know to catch it. Add a bullet to that "Key behavior" list naming the type, and add the doc change to the acceptance checklist (section 6). The "Exception hierarchy" block (AGENT_KNOWLEDGE.md:1770-1781) covers only the transaction types; extending it to `ConflictError` is optional but should be decided in the plan.

2. **"Type-only, so not breaking" is only half true, and the CHANGELOG should say so.** `VersionConflictError` inherits `TransactionConditionFailedError` and therefore `TransactionError` (`exceptions.py:127`, `:96`). A caller with `except TransactionError:` retry logic will now also catch stale-singleton failures, which previously escaped it as a bare `ValueError`. `ValueError` handlers are unaffected, and no `src/` code catches `TransactionError` (grep), so the library itself is fine. The plan should either state this broadening in the CHANGELOG bullet or justify it explicitly (for example: it matches what `update_existing` already raises at `dynamodb_memory.py:576`).

3. **The `LocalStorageMemory` test is left optional on a condition the plan's own investigation already resolves.** `LocalStorageMemory.get_existing` accepts `consistent_read` (`local_storage_memory.py:221`), and `create_new` accepts `override_id` (`local_storage_memory.py:339-343`), so `ensure_exists` works on the local backend. The check in `singleton.py` runs before any memory call, so the change applies to both backends. The test file already declares backend parity a goal (`test_local_storage_raises_the_same_types_as_dynamodb`, `tests/test_typed_conflicts_and_save.py:209`). Make the local variant a required test in section 3, not an "optional" one with a skip condition.

4. **Sequencing of the close-out contradicts the code change.** Section 5 says to close #13 "as delivered in 21.0.0", while section 1 and section 5's last paragraph put a new singleton fix on this branch, with a CHANGELOG bullet that references #13. Either close #13 after this branch merges, or make the close-out comment say explicitly that the singleton stale-version gap is fixed in the next release. As written, the comment and the branch disagree about what #13 delivered.

5. **New tests do not follow the file's convention.** Every test in `tests/test_typed_conflicts_and_save.py` has a one-line docstring that states why the test matters (for example lines 86-88, 95-96, 149-150, 168-174). The plan's `TestSingletonVersionConflict` tests have none. Add a docstring to each, in the same style, so the back-compat intent of test 2 (catchable as both `ConflictError` and `ValueError`) is recorded in the file.
